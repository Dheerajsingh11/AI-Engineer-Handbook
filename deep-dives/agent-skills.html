Agent Skills

Packaged, loadable capabilities. This page explains what an agent "skill" is (and how it differs from a tool), why progressive disclosure lets one agent hold hundreds of capabilities without drowning its context, walks the anatomy of a skill, builds one, and covers discovery, versioning and the security of loading skills on demand.

Section 01 BeginnerStart from zero

Assumed knowledge

Tool types (Topic 8.4) and context engineering (Topic 5.3). A skill is a level above a tool, so know what a tool is first.

A tool is a single function the agent can call. A skill is bigger: a packaged, reusable capability — instructions, plus optional tools, scripts and reference files — that an agent loads when it becomes relevant and ignores the rest of the time.

The problem skills solve: you want an agent that can do a hundred specialised things — format a legal contract, reconcile a spreadsheet, run your deployment runbook — but you cannot cram a hundred detailed procedures into every prompt. That would blow the context window and bury the model in irrelevant instructions.

The core idea: progressive disclosure

A skill is loaded in layers. At rest, the agent sees only a one-line name and description — cheap. When a task matches, it loads the skill's full instructions. Only if it needs them does it open the skill's bundled files and scripts. So an agent can know about hundreds of capabilities while only paying context for the one it is using right now. This is the same coarse-to-fine idea as retrieval (Topic 4.6) and Matryoshka embeddings (Topic 4.2), applied to capabilities.

Tool vs skill, in plain English
Tool
One callable function. "Send an email." Atomic.
Skill
A packaged capability: how-to instructions + any tools, scripts and references it needs. "Handle the full month-end close." Composite.
Progressive disclosure
Loading a skill's detail only when it becomes relevant, to save context.
Skill manifest
The metadata (name, description, when-to-use) the agent reads to decide whether to load the skill.
Skill library
The collection of skills an agent can draw on.

Section 02 BeginnerTool or skill?

When to make something a tool vs a skill
Make it a TOOL when…Make it a SKILL when…
It is one atomic actionIt is a multi-step procedure
The model just needs to call itThe model needs instructions on how to do it
It has no reusable knowledge attachedIt bundles domain knowledge, templates, or reference files
Example: query_database(sql)Example: "our incident-response runbook"

They compose. A skill usually contains tools. The "process a return" skill might bundle the check_order and issue_refund tools plus the step-by-step policy for using them. The skill is the packaging; the tools are the moving parts inside it.

Section 03 IntermediateThe anatomy of a skill

Concretely, a skill is a folder with a manifest and content. The manifest is what the agent reads first; everything else loads on demand.

StructureA skill on disk
skills/
  invoice-processing/
    SKILL.md              # manifest + instructions (loaded when relevant)
    reference/
      tax-rules.md        # loaded only if the task needs it
      field-mappings.csv
    scripts/
      validate_totals.py  # a script the agent can run in a sandbox
MarkdownSKILL.md — manifest first, then instructions
---
name: invoice-processing
description: >                                # THIS is the always-loaded part.
  Extract and validate structured data from  # Write it like a tool description --
  invoices. Use when the user uploads an      # it is how the agent decides to
  invoice or asks to process billing docs.    # load the rest.
---

# Processing an invoice                       # Loaded only when the skill is invoked.

1. Extract vendor, line items, subtotal, tax, total.
2. Validate: line items must sum to the subtotal;
   subtotal + tax must equal total. If not, flag it.
3. For tax rules by region, read reference/tax-rules.md.
4. Run scripts/validate_totals.py to double-check the arithmetic.
5. Return the structured record; list any low-confidence fields.
The description carries all the routing weight

At rest, the agent sees only the name and description from the manifest — a few dozen tokens per skill. That description is doing the same job as a tool description (Topic 5.1): it is the only information the model uses to decide whether this skill is relevant. Say plainly what the skill does and when to use it. A vague description means the skill never gets loaded when it should — the capability exists but is invisible.

Section 04 AdvancedHow loading works — the three levels

Progressive disclosure in practice is three tiers of context cost:

The three levels of skill loading
LevelLoadedContext costWhen
1. ManifestName + description of every skillTiny (always)At all times
2. InstructionsThe skill's full SKILL.md bodyModerateWhen the task matches
3. ResourcesReference files, scriptsOnly what is openedWhen the instructions call for them
PythonA minimal skill loader
import yaml, pathlib

class Skill:
    def __init__(self, folder):
        self.folder = pathlib.Path(folder)
        text = (self.folder / "SKILL.md").read_text()
        front = text.split("---")[1]
        meta = yaml.safe_load(front)
        self.name = meta["name"]
        self.description = meta["description"]       # Level 1: always shown
        self._body = text.split("---", 2)[2]         # Level 2: on demand

    def manifest(self):
        return {"name": self.name, "description": self.description}

    def load(self):                                  # called when the agent selects it
        return self._body

    def read_resource(self, rel):                    # Level 3: explicit open
        return (self.folder / rel).read_text()

# The agent's system prompt lists only manifests -- cheap even for
# hundreds of skills. A "load_skill(name)" tool pulls in level 2.
library = [Skill(p) for p in pathlib.Path("skills").iterdir() if p.is_dir()]
manifests = [s.manifest() for s in library]          # the always-loaded index
This is how agent platforms scale capability

Anthropic's Agent Skills, and the plugin/skill systems in agent platforms generally, work on exactly this manifest-then-load model. It is why an assistant can advertise dozens of specialised behaviours without every conversation paying for all of them. If you are building an internal agent that must do many distinct company procedures, skills are the pattern that keeps it from collapsing under its own instructions — encode each procedure as a skill, not as another paragraph in one giant prompt.

Section 05 ProfessionalDiscovery, versioning and security

Operating a skill library
ConcernPractice
DiscoveryIf the library is large, retrieve relevant skill manifests (RAG over skills) rather than listing all of them
VersioningVersion each skill; a bad edit to a widely-used skill is a wide-blast-radius change (Topic 5.5)
TestingEach skill gets its own eval cases — a skill is a unit of behaviour to regression-test (Topic 8.10)
ConflictsOverlapping skills confuse selection; keep descriptions distinct, as with tools
OwnershipSkills are how you let non-engineers contribute agent behaviour — but review them like code
A skill is executable content — treat it as untrusted

Skills bundle instructions and often scripts. A skill from a third party, or one a user can add, is a channel for both prompt injection (malicious instructions in SKILL.md) and code execution (a hostile script). Apply Topic 5.6 and Topic 8.4: review skills before enabling them, run any bundled scripts only in a sandbox, scope what a loaded skill's tools can touch, and never auto-load skills from an untrusted source. The convenience of "anyone can add a skill" is also its risk.

Section 06 ProfessionalExercises

Do these — roughly an evening
  1. Write a SKILL.md for a real multi-step procedure you know (a runbook, a formatting standard). Get the description right.
  2. Build the loader from Section 04. Confirm that only manifests occupy context until a skill is selected.
  3. Give an agent five skills and a task that matches one. Verify it loads only that skill's body, not the others'.
  4. Add a bundled script to a skill and have the agent run it in a sandbox (Topic 8.4). Confirm it cannot escape.
  5. Take one thing you built as a giant system prompt and refactor it into three skills. Compare context usage per task.
  6. Plant an injected instruction inside a SKILL.md and load it. Observe the effect, then add the Section 05 controls.
