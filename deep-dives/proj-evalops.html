Project 5 — Eval & Guardrails

The layer that makes Projects 2 and 3 shippable: a regression suite that runs on every prompt change and blocks the merge when quality drops, a judge calibrated against your own labels, guardrails on both sides of the model, and production traces that feed failures back into the golden set.

Build order · two weeks
  1. Stage 1The runnerDatasets, assertions, an LLM judge.
  2. Stage 2CalibrationLabel 100 outputs by hand. Non-negotiable.
  3. Stage 3The CI gatePrompts as versioned artifacts; regressions fail the build.
  4. Stage 4Guardrails & tracesInput and output filters; production feeds the golden set.
Why this is the highest-leverage project in the set

Most candidates cannot answer “how do you know a prompt change did not break production?” It is the most under-supplied skill in the market and the clearest possible signal that you have operated an LLM system rather than demonstrated one. Build it against Projects 2 and 3 — never in the abstract.

Step 02The eval runner

Three grader types cover almost everything. Use the cheapest one that can answer the question — a deterministic assertion is faster, free, and more reliable than any judge.

Pythonevals/runner.py
from dataclasses import dataclass
import asyncio, statistics

@dataclass
class Case:
    id: str
    input: dict
    # Cheap and exact. Reach for these first.
    must_contain: list[str] | None = None
    must_not_contain: list[str] | None = None
    expect_refusal: bool = False
    # Expensive and fuzzy. Only where correctness is genuinely a judgement.
    rubric: str | None = None

async def run_case(system_under_test, case: Case, judge, runs: int = 3) -> dict:
    # Run each case several times. A single sample of a stochastic system
    # is not a measurement -- you need the mean AND the spread, or you will
    # chase noise as if it were a regression.
    outputs = await asyncio.gather(*(system_under_test(case.input) for _ in range(runs)))

    scores = []
    for out in outputs:
        if case.must_contain and not all(s in out.text for s in case.must_contain):
            scores.append(0.0); continue
        if case.must_not_contain and any(s in out.text for s in case.must_not_contain):
            scores.append(0.0); continue
        if case.expect_refusal:
            scores.append(1.0 if out.refused else 0.0); continue
        scores.append(await judge.score(case, out) if case.rubric else 1.0)

    return {"id": case.id,
            "mean": statistics.mean(scores),
            "stdev": statistics.pstdev(scores),   # high stdev = an unstable case,
            "runs": runs}                          # worth fixing before trusting it
Pythonevals/judge.py — a rubric, not a vibe
JUDGE_SYSTEM = """You grade one answer against a rubric. You are strict
and consistent. Grade only what the rubric asks about.

Return JSON: {"score": 0|1|2|3, "reason": "one sentence"}

3 - fully correct, complete, and grounded in the sources
2 - correct but incomplete, or one minor unsupported detail
1 - partially correct with a material error
0 - incorrect, or unsupported by the sources"""

class Judge:
    def __init__(self, model="claude-opus-5", version="judge-v3"):
        # PIN the model and version the rubric. An unpinned judge means a
        # silent provider-side change reads as a quality regression in your
        # system, and you will spend two days looking in the wrong place.
        self.model, self.version = model, version

    async def score(self, case, output) -> float:
        r = await gateway.complete_json(
            model=self.model, system=JUDGE_SYSTEM,
            messages=[{"role": "user", "content":
                f"Rubric:\n{case.rubric}\n\nQuestion:\n{case.input['question']}"
                f"\n\nSources:\n{output.context}\n\nAnswer:\n{output.text}"}],
            # Grading must be reproducible: no sampling variance.
            temperature=0,
        )
        return r["score"] / 3.0

Step 03Calibrating the judge

This is the step that separates this project from every eval tutorial. An uncalibrated judge is a random number generator with good manners. Label 100 outputs yourself, measure agreement, and fix the rubric until it correlates.

Pythonevals/calibrate.py
def cohens_kappa(human: list[int], model: list[int], k: int = 4) -> float:
    """Agreement corrected for chance. Raw agreement flatters a judge that
    always says 3 on a set that is mostly 3s -- kappa does not.

    < 0.20 useless   0.21-0.40 poor   0.41-0.60 moderate
    0.61-0.80 substantial (ship it)   > 0.80 excellent"""
    n = len(human)
    observed = sum(h == m for h, m in zip(human, model)) / n

    # Expected agreement if both raters guessed with their own marginals.
    expected = sum((human.count(c) / n) * (model.count(c) / n) for c in range(k))
    return (observed - expected) / (1 - expected) if expected < 1 else 1.0


async def calibrate(judge, labelled: list[dict]) -> dict:
    model_scores = [round(await judge.score(r["case"], r["output"]) * 3)
                    for r in labelled]
    human_scores = [r["human_score"] for r in labelled]

    # The disagreements are the product. Read every one: they tell you
    # exactly which rubric clause is ambiguous, and fixing the rubric is
    # almost always more effective than changing the judge model.
    disagreements = [
        {"id": r["case"].id, "human": h, "model": m, "text": r["output"].text}
        for r, h, m in zip(labelled, human_scores, model_scores) if abs(h - m) >= 2
    ]
    return {"kappa": cohens_kappa(human_scores, model_scores),
            "disagreements": disagreements}
Judge failure modes to check for — and to name in an interview
  • Position bias in pairwise comparison: the first answer wins more often. Fix by running both orderings and averaging.
  • Length bias: longer answers score higher regardless of correctness. Detect by correlating score with token count.
  • Self-preference: a judge favours output from its own model family. Relevant the moment you compare providers.
  • Rubric drift: you edit the rubric mid-project and old scores become incomparable. Version it, and re-run the baseline when it changes.

Step 04Prompts as versioned artifacts

Pythonprompts/registry.py
import hashlib, yaml
from pathlib import Path

class Prompt:
    """A prompt is code: it has a version, a hash, an owner, and a test
    result attached. Loading it from a string literal in the middle of a
    service is how prompt changes ship unreviewed and unmeasured."""

    def __init__(self, path: Path):
        spec = yaml.safe_load(path.read_text())
        self.name, self.version = spec["name"], spec["version"]
        self.template = spec["template"]
        self.model = spec["model"]
        # The hash goes into every trace, so any production output can be
        # traced back to the exact prompt text that produced it.
        self.hash = hashlib.sha256(self.template.encode()).hexdigest()[:12]

    def render(self, **kw) -> str:
        return self.template.format(**kw)

Step 05The CI gate

YAML.github/workflows/eval.yml
name: eval
on:
  pull_request:
    paths: ["prompts/**", "app/retrieve/**", "app/generate/**"]

jobs:
  regression:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0 }        # need the base ref to compare against

      - name: Run the suite on both versions
        env: { ANTHROPIC_API_KEY: "${{ secrets.ANTHROPIC_API_KEY }}" }
        run: |
          # Evaluate the PR and the base branch on the SAME cases in the
          # SAME run. Comparing against a stored historical number invites
          # drift from every other variable that changed in between.
          python -m evals.cli --ref "${{ github.base_ref }}" --out base.json
          python -m evals.cli --ref HEAD --out head.json
          python -m evals.compare base.json head.json --out delta.md

      - name: Comment the delta on the PR
        uses: actions/github-script@v7
        with:
          script: |
            const body = require('fs').readFileSync('delta.md', 'utf8');
            github.rest.issues.createComment({
              issue_number: context.issue.number,
              owner: context.repo.owner, repo: context.repo.repo, body });

      - name: Gate
        run: python -m evals.gate delta.json    # non-zero exit fails the build
Pythonevals/gate.py — do not fail the build on noise
import math

def significant_regression(base, head, tolerance=0.02, z=1.96) -> bool:
    """A drop only counts if it exceeds BOTH the business tolerance and the
    run-to-run noise. Gating on the raw mean makes the suite flaky, the
    team disables it, and you are back to shipping prompts unmeasured --
    which is the actual failure mode this project exists to prevent."""
    delta = base["mean"] - head["mean"]
    if delta <= tolerance:
        return False

    # Pooled standard error across both runs.
    se = math.sqrt(base["stdev"] ** 2 / base["n"] + head["stdev"] ** 2 / head["n"])
    return se == 0 or delta / se > z
The sentence this project earns you

“A prompt change is a pull request. CI runs the suite against both versions, posts the per-metric delta as a comment, and blocks the merge if faithfulness drops more than two points beyond run-to-run noise.” Very few mid-level candidates can say that and mean it. It answers the CI question, the evaluation question and the rollout question at once.

Step 06Guardrails, both directions

Pythonguardrails/chain.py
from dataclasses import dataclass

@dataclass
class Verdict:
    allow: bool
    reason: str = ""
    redacted: str | None = None

class GuardrailChain:
    """Ordered, cheapest-first. Each stage can allow, redact or block.
    Order matters for cost: a regex that catches 80% of cases should never
    sit behind a model call that costs a thousand times more."""

    async def check_input(self, text: str) -> Verdict:
        if v := self.pii.scan(text):            # regex -- microseconds
            return Verdict(True, "pii redacted", redacted=v.redacted)
        if self.length.exceeds(text):           # arithmetic -- free
            return Verdict(False, "input too long")
        if await self.injection.classify(text): # model -- expensive, last
            return Verdict(False, "possible injection")
        return Verdict(True)

    async def check_output(self, text: str, context: str) -> Verdict:
        if leaked := self.secrets.scan(text):   # keys, tokens, internal hosts
            return Verdict(False, f"secret leak: {leaked}")
        if not self.schema.valid(text):
            return Verdict(False, "schema violation")
        # Groundedness LAST: it is the most expensive check, and the cheap
        # ones will already have rejected most of what would fail here.
        if await self.grounding.score(text, context) < 0.8:
            return Verdict(False, "ungrounded claim")
        return Verdict(True)
Measure the false-positive rate, always

A guardrail that blocks 100 % of attacks and 8 % of legitimate requests is an outage with good intentions. Track precision and recall for every filter separately, and treat over-blocking as a production incident. When an interviewer asks “what happens when the filter is wrong?”, the answer they want is that you measured it, chose a threshold deliberately, and have a path for a user to appeal a block.

Step 07Closing the loop from production

Pythonobserve/loop.py
async def sample_and_score(trace_store, rate: float = 0.02):
    """Score a small sample of live traffic with the same judge the CI gate
    uses. Offline evals answer 'did we break it'; this answers 'is it still
    working on traffic we never anticipated' -- and only the second one
    catches drift in what users actually ask."""
    for trace in await trace_store.sample(rate=rate):
        score = await judge.score_from_trace(trace)
        await trace_store.attach_score(trace.id, score, judge_version=judge.version)

        if score < 0.5:
            # A production failure becomes a permanent regression test.
            # This is the loop that makes the suite get better over time
            # instead of slowly going stale -- and it is the part of the
            # answer that shows you have run something, not just built it.
            await golden_set.propose(
                Case(id=f"prod-{trace.id}", input=trace.input,
                     rubric=DEFAULT_RUBRIC),
                needs_human_review=True)

Alert on the things that move slowly and silently: weekly mean score by route, refusal rate (a sudden rise usually means retrieval broke, not that users changed), p95 latency, and the embedding-distribution shift that signals users are asking about something your corpus does not cover.

Exercises
  1. Deliberately regress a prompt — remove the citation instruction — and confirm CI catches it. Screenshot the PR comment for your README; it is the single most persuasive artifact in the portfolio.
  2. Run the same suite with three different judge models. Where they disagree is where your rubric is ambiguous.
  3. Cut suite cost by 70 % without losing sensitivity: cheaper judge for easy cases, batch API for the offline run, cache identical calls. Report the before and after.
  4. Take the injection suite from Project 3 and wire it into this gate so a prompt change cannot weaken injection resistance.
  5. Run the suite against a second provider and quantify the behaviour change — this is what makes the failover in Project 1 safe rather than hopeful.
