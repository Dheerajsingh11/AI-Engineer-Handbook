Structured Generation & Decoding

Making an LLM return exactly the shape you asked for. This page covers structured generation and constrained decoding — getting reliable JSON, valid tool calls and schema-conforming output — why prompting alone is not enough, how constraining the decoder guarantees valid structure, and the math of masking the token choice.

Section 01 BeginnerStart from zero

Assumed knowledge

Tool & function calling (Topic 5.1) and how an LLM predicts the next token (Topic 1.3). This page is about making that output machine-parseable and reliable.

The moment you put an LLM inside a program, you stop wanting prose and start wanting structure — a JSON object, a specific field, a valid function call your code can act on. But a language model generates free text, and "mostly valid JSON" breaks a parser just as badly as no JSON. Structured generation is the set of techniques that make the output conform to a schema every time.

Why "please return JSON" is not enough

You can ask a model for JSON in the prompt, and most of the time you will get it. But most of the time is a production nightmare: one response in fifty adds a chatty preamble, forgets a closing brace, or invents a field — and your pipeline crashes on the input you did not test. Prompting makes valid output likely; it cannot make it guaranteed. For anything downstream that must parse the output — agents calling tools (Topic 8.4), data extraction, API responses — "likely" is not good enough, and the fix is to constrain the generation itself rather than hope.

The words, in plain English
Structured output
Output that conforms to a defined shape (a JSON schema, a type).
Constrained decoding
Forcing the model to only pick tokens that keep the output valid.
Schema
A formal description of the allowed structure (e.g. JSON Schema, a Pydantic model).
Grammar
A set of rules defining every valid string in a format.
Logit mask
Blocking disallowed next-tokens by setting their score to −∞.

Section 02 IntermediateThe spectrum of reliability

There are several ways to get structured output, trading simplicity for guarantee.

From hopeful to guaranteed
ApproachHowGuarantee
Prompt & hope"Return JSON like…" plus a retry on parse failureNone — probabilistic
Few-shot examplesShow the exact format several timesHigher, still not certain
Provider JSON modeAn API flag that biases toward valid JSONValid JSON, not your schema
Provider structured outputsPass a schema; the API enforces itStrong — schema-valid
Constrained decodingMask tokens against a grammar (Section 03)Guaranteed valid by construction
PythonDefine the shape once, get it back typed
from pydantic import BaseModel

# Describe the structure as a type -- this becomes the schema.
class Ticket(BaseModel):
    category: str
    urgency: int          # 1-5
    summary: str

# Modern APIs and libraries accept the schema and RETURN a valid object.
# The library handles schema -> constraint -> parsed result.
ticket = extract(model, prompt, schema=Ticket)   # -> Ticket(...) or raises
route(ticket.category, ticket.urgency)            # safe: fields guaranteed present

The practical advice: reach for the strongest option your stack supports. If your provider offers schema-based structured outputs, use them — they are close to free and remove a whole class of bugs. If you self-host or need formats beyond JSON, a constrained-decoding library (Outlines, guidance, llama.cpp grammars) gives you the hard guarantee. Keep "prompt and retry" only as a last resort, and always validate the parsed result against your schema even when you think it is guaranteed — defence in depth.

Section 03 AdvancedHow constrained decoding works

The guarantee comes from the one place it can: the model's token-by-token generation. At each step the model produces scores (logits) over every possible next token; constrained decoding simply forbids the ones that would break the structure.

Constrained next-token distribution — mask, then softmax P(token | context) = softmax( logits + mask ) where maskt = 0 if token t is allowed, −∞ if it is not Adding −∞ to a disallowed token's logit drives its probability to exactly 0 after the softmax (Topic 1.2). The model still chooses — but only among tokens that keep the output valid. Structure becomes impossible to violate, not merely unlikely.
A state machine walks alongside the model

The engine tracks a grammar as a state machine. After the model has emitted {"urgency":, the grammar knows the next token must be a digit — so at that step every non-digit token is masked to −∞, and the model can only produce a number. After {"category": " it allows string characters until a closing quote. Because the mask is computed from the grammar's current state at every step, the output cannot leave the valid set — a malformed brace or a missing field is literally unreachable. The cost is a little bookkeeping per token; the payoff is a categorical guarantee that prompting can never give.

The subtle costs

Constraining is powerful but not free. Over-constraining can hurt quality: if you force a rigid schema on a task the model wants to reason through, you can cut off the "thinking" tokens that would have produced a better answer — which is why letting the model reason first and emit structure last (or using a two-step call) often wins. The schema must match reality: forcing a field the model has no basis to fill just yields a confident fabrication in the right shape. And a valid shape is not a correct value — constrained decoding guarantees the JSON parses, never that its contents are true. Structure and correctness are different problems; this page solves only the first.

Section 04 ProfessionalIn production

In a real system, structured generation is the glue that makes LLMs safe to program against. It underpins tool calling (the model must emit a valid function name and arguments, Topic 5.1), agents (each step's action must parse, Topic 8.4), and data extraction (turning documents into rows). The professional pattern: define the schema as a typed object once (Pydantic), let the strongest available mechanism enforce it, validate the result anyway, and design the schema to permit reasoning where the task needs it — a "reasoning" string field before the answer, or a separate reasoning call. Do this and an entire category of "the model returned garbage" incidents simply disappears. It is one of the highest-reliability-per-effort techniques in applied LLM work.

Section 05 ProfessionalExercises

Do these — an afternoon
  1. Ask a model for JSON by prompt alone across 100 varied inputs. Count the parse failures — feel why "likely" is not enough.
  2. Switch to your provider's structured-outputs / schema mode. Re-run and confirm the failures vanish.
  3. Use a constrained-decoding library (Outlines or llama.cpp grammars) to force a schema on a local model. Try to make it emit invalid output — you cannot.
  4. Over-constrain a reasoning task (force a bare answer with no room to think). Measure the quality drop, then add a reasoning field and re-measure.
  5. Build an extraction pipeline: documents in, validated typed objects out. Add schema validation even though generation is constrained.
  6. Explain the logit mask to a colleague using the −∞ formula. If they get why the output cannot be invalid, you understand Section 03.
