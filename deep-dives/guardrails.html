16.6

Guardrails & Content Moderation

The safety layer around the model. This page covers programmatic guardrails and content moderation — the input and output checks that sit between your users and the LLM — the frameworks that implement them (Llama Guard, NeMo Guardrails, validators), and how to defend against prompt injection and jailbreaks at the proxy layer.

Section 01 BeginnerStart from zero

Assumed knowledge

LLM security (Topic 5.6), AI safety (Topic 16.2) and structured generation (Topic 5.7). This page is the applied layer: the code you put around the model in production.

Alignment (Topic 9.7, 16.2) makes the model itself safer, but it is never a hard boundary — a determined user can still coax it, and it can still hallucinate or emit something it shouldn't. Guardrails are the programmatic checks you build around the model — validating what goes in and what comes out — so safety does not depend on the model alone. They are to an LLM what input validation and a WAF are to a web app.

The model is not the security boundary

The core mindset: never trust the model to police itself. A prompt can be adversarial; retrieved documents can carry hidden instructions; the output can leak data or say something harmful. So you wrap the model in a guardrail loop — check the input, run the model, check the output, and only then return it (or block/retry). This is defence in depth: alignment reduces how often the model misbehaves; guardrails catch it when it does. Both matter, and in production the guardrails are the part you own.

The words, in plain English
Input guardrail
A check on the user's request before it reaches the model (injection, off-topic, PII).
Output guardrail
A check on the model's answer before it reaches the user (moderation, grounding, format).
Moderation model
A classifier (e.g. Llama Guard) that labels text as safe/unsafe by category.
Semantic routing
Deciding what to do by how close a request is (in embedding space) to known cases.
Validation loop
Generate → check → if it fails, block or regenerate.

Section 02 IntermediateInput & output guardrails

Guardrails come in two positions — before the model and after — and each catches a different class of problem.

What to check, and where
PositionChecks
Input (before the model)Prompt-injection detection; off-topic / out-of-scope; disallowed topics; PII in the request; rate/abuse limits
Output (after the model)Toxicity / unsafe content moderation; hallucination & grounding checks (is it supported by the context?); PII leakage; format/schema validity (Topic 5.7); competitor/brand rules

Each check can be implemented three ways, in rising cost and capability: rules/regex (fast, cheap, brittle — good for PII patterns and banned terms), a small classifier or moderation model (a purpose-built model that labels the text), or an LLM-as-judge (ask a model “is this answer grounded / safe?”, Topic 19.1 — flexible but slower and costlier). Real systems layer them: cheap rules first, a moderation model next, an LLM judge only for the hard calls.

Section 03 IntermediateThe frameworks

Tools that implement guardrails
ToolWhat it is
Llama GuardAn open classifier model that labels a prompt or response as safe/unsafe across a taxonomy of harm categories — drop it in as an input/output filter
NeMo GuardrailsNVIDIA's framework; you declare conversational “rails” (allowed topics, flows, fact-checking) in a config language
Guardrails AIA library of composable validators (PII, toxicity, JSON schema, competitor mentions) with a generate-and-fix loop
Moderation APIsHosted classifiers (e.g. OpenAI moderation) for unsafe-content categories
Semantic routingEmbed the request and compare it to sets of known-good / known-bad examples to route, allow, or block (Topic 4.2)
Semantic routing — guardrails by similarity

A neat, fast pattern worth knowing: instead of asking an LLM “is this a jailbreak?”, embed the incoming request (Topic 4.2) and measure its cosine similarity to a curated set of known attack prompts and to your allowed use-cases. Too close to a known jailbreak → block; closest to a supported flow → route there. It runs in milliseconds with no LLM call, catches variants of known attacks, and is trivial to update — add the new attack to the set. It pairs well with the heavier checks: semantic routing filters the obvious cases cheaply, the moderation model and judge handle the rest.

Section 04 AdvancedPrompt injection & jailbreak defence

The signature LLM attacks (Topic 5.6): a jailbreak tricks the model into ignoring its instructions; a prompt injection smuggles instructions in through data the model reads — a retrieved document, a web page, a tool result — saying “ignore your rules and do X.” No single check fully stops them, so you defend in layers.

Why injection is uniquely hard — and the layered defence

The reason prompt injection is not “just fixed”: to the model, the trusted system prompt and the untrusted retrieved text are the same kind of thing — tokens in a context window. So the defence is architectural, not a magic filter. Layer it: (1) trust boundaries — treat all retrieved/user content as data, never instructions, and keep the model's authority and tools coming only from the trusted system layer (Topic 20.11); (2) input guardrails — injection/jailbreak detection (semantic routing, Llama Guard) at the proxy; (3) least privilege — the model's tools are read-only or gated on human approval, so a successful injection can't do much (Topic 8.4); (4) output guardrails — sanitise responses, block data exfiltration and unsafe content before they leave; and (5) the validation loop — check the answer, and regenerate or refuse on failure. Each layer is imperfect; together they make a successful, harmful attack much harder.

Section 05 ProfessionalGuardrails as a gateway

In a real Java/Python stack, guardrails live best as a gateway (proxy) in front of the LLM — every request and response passes through one place that runs the input checks, calls the model, runs the output checks, logs everything, and enforces rate limits. Centralising it means one consistent policy, one audit trail, and one place to update when a new attack appears (it fits the hooks/middleware pattern of Topic 8.6, and the serving layer of Topic 20.8/20.11). Two engineering realities to respect: guardrails add latency and cost (every extra classifier or judge call is more time and money), so tier them — cheap checks first, expensive ones only when needed; and test them adversarially — red-team your own system with known jailbreaks and injection payloads (tools like a prompt-injection game, or a fixed attack suite) so you find the holes before an attacker does. Perfect safety is unattainable; the goal is layered, measured, defensible risk reduction — and for an engineer with a security background, this is exactly where that experience is worth the most (Topic 17.4).

Section 06 ProfessionalExercises

Do these — build the wrapper
  1. Add Llama Guard (or a moderation API) as an output filter to a chat app. Feed it safe and unsafe generations; check the labels.
  2. Build a semantic-routing input guard: embed a set of known jailbreaks, and block requests too close to them. Measure false positives/negatives.
  3. Add an output grounding check for a RAG app: an LLM-judge that verifies every claim is supported by the retrieved context; regenerate on failure.
  4. Implement the validation loop: generate → validate (schema + safety) → retry once → else refuse. Measure the added latency.
  5. Red-team your own system with a list of prompt-injection payloads hidden in “documents”. Find one that gets through, then add a layer that stops it.
  6. Put all the checks behind one gateway function. Confirm a single policy now covers every endpoint.
