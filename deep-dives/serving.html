Inference, Serving & Quantisation

Running models yourself, cheaply and fast. Section 02 IntermediateWhere latency comes from

Generation has two phases with opposite performance characteristics. Confusing them is why serving capacity plans so often miss.

Prefill versus decode, revisited for serving
PrefillDecode
ProcessesThe whole prompt at onceOne output token per pass
Bound byCompute (GPU FLOPs)Memory bandwidth — every weight is read per token
SetsTime to first tokenTokens per second, and total latency
Scales withPrompt lengthOutput length
The counterintuitive fact that shapes serving

Decode is memory-bandwidth-bound, not compute-bound. To generate one token, the GPU reads every weight of the model from memory, then does a relatively small amount of arithmetic with it. The bottleneck is moving the weights, not multiplying them.

Two consequences follow. First, the GPU is mostly idle during single-request decode — which is why batching is free throughput: process eight requests together and you read the weights once for all eight. Second, quantisation speeds up decode directly, because there are fewer bytes to move per token, not just less memory used.

Section 03 AdvancedWill it fit? The arithmetic

Before serving anything you need to know whether the model, its KV cache and your batch fit in the GPU's memory. The formula is short and worth carrying.

GPU memory budget weights  =  params × bytes_per_param KV cache  =  2 × layers × kv_heads × head_dim × seq_len × batch × bytes total  ≈  weights + KV cache + activations + overhead The KV cache is the term people forget, and at long context it can exceed the weights. Grouped-query attention shrinks it by sharing keys and values across heads — which is why kv_heads, not the full head count, appears in the formula.
PythonSizing a deployment
def gpu_memory_gb(params_b, bytes_per_param,
                  layers, kv_heads, head_dim,
                  seq_len, batch, dtype_bytes=2):
    weights = params_b * 1e9 * bytes_per_param
    kv = 2 * layers * kv_heads * head_dim * seq_len * batch * dtype_bytes
    overhead = weights * 0.10        # activations, fragmentation, CUDA context
    return (weights + kv + overhead) / 1e9

# An 8B model (32 layers, 8 KV heads, head_dim 128) on a 24 GB card
for bytes_pp, label in [(2, "fp16"), (1, "int8"), (0.5, "int4")]:
    total = gpu_memory_gb(8, bytes_pp, 32, 8, 128,
                          seq_len=8192, batch=1)
    fits = "fits" if total < 24 else "TOO BIG"
    print(f"{label:5s}: {total:5.1f} GB on 24 GB -> {fits}")

# fp16 : 18.7 GB on 24 GB -> fits
# int8 :  9.9 GB on 24 GB -> fits (room for a bigger batch)
# int4 :  5.5 GB on 24 GB -> fits (or run a much larger model)

# The same 8B at 128k context, batch 1, fp16:
print(f"{gpu_memory_gb(8, 2, 32, 8, 128, 131072, 1):.0f} GB")
# 35 GB -- the KV cache alone is 17 GB, already matching the 16 GB
# of weights. At a serving batch of 8 the cache exceeds 130 GB.
# THIS is why long context is expensive to serve, not just to buy.

Section 04 AdvancedContinuous batching and other engine tricks

Naive batching waits for a fixed group of requests, runs them together, and returns when the slowest finishes. Requests that finish early leave their GPU slots idle until the batch completes. Continuous batching — vLLM's headline feature — fixes this by scheduling at the token level: a finished request's slot is immediately given to a waiting one.

What a modern serving engine does for you
TechniqueMechanismBenefit
Continuous batchingToken-level scheduling; slots freed immediately2–4× throughput over static batching
PagedAttentionKV cache in non-contiguous pages, like OS virtual memoryNear-zero cache waste; higher batch sizes
Prefix cachingReuse the KV cache of a shared prompt prefixLarge win when a long system prompt is common
Speculative decodingSmall model drafts n tokens; big model verifies in one pass2–3× faster decode, identical output
Tensor parallelismSplit one model across several GPUsServe models larger than one card
Multi-LoRAOne base model, many adapters swapped per requestPer-tenant fine-tunes cheaply (Topic 3.5)
Python / ShellvLLM behind an OpenAI-compatible endpoint
# One command exposes an OpenAI-compatible server. The compatibility
# is the point: Spring AI already speaks this protocol, so your Java
# service points at it with a one-line config change.
python -m vllm.entrypoints.openai.api_server \
    --model meta-llama/Llama-3.1-8B-Instruct \
    --quantization awq \
    --max-model-len 8192 \
    --gpu-memory-utilization 0.90 \
    --enable-prefix-caching \
    --enable-lora \
    --lora-modules support=/adapters/support billing=/adapters/billing

# Call it exactly like any OpenAI-compatible API:
curl http://localhost:8000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model": "support",
       "messages": [{"role": "user", "content": "Where is my order?"}]}'
# "model": "support" selects the LoRA adapter for that tenant.

JavaAn embedding model in-process with ONNX Runtime
// For an embedding or re-ranker model in a latency-sensitive RAG
// path, in-process ONNX beats an HTTP call: no network hop, no
// second deployment, no serialization overhead per request.
@Component
class OnnxEmbeddingModel implements EmbeddingModel {

    private final OrtEnvironment env = OrtEnvironment.getEnvironment();
    private final OrtSession session;
    private final HuggingFaceTokenizer tokenizer;

    OnnxEmbeddingModel(@Value("${embedding.model.path}") String path) throws Exception {
        var opts = new OrtSession.SessionOptions();
        opts.addCUDA(0);                             // GPU if present; CPU is fine for small models
        this.session = env.createSession(path + "/model.onnx", opts);
        this.tokenizer = HuggingFaceTokenizer.newInstance(Path.of(path));
    }

    @Override
    public float[] embed(String text) throws OrtException {
        var encoding = tokenizer.encode(text);
        try (var ids  = OnnxTensor.createTensor(env, wrap(encoding.getIds()));
             var mask = OnnxTensor.createTensor(env, wrap(encoding.getAttentionMask()));
             var out  = session.run(Map.of("input_ids", ids, "attention_mask", mask))) {

            float[][] tokenVectors = ((float[][][]) out.get(0).getValue())[0];
            // Mean pool with the mask -- averaging over padding is a
            // real bug that quietly degrades every embedding (Topic 4.2).
            return normalize(meanPool(tokenVectors, encoding.getAttentionMask()));
        }
    }
}
A sensible split for a Java shop

Serve generation from vLLM as a separate service — it needs GPUs and a Python container your platform team operates like any other. Point Spring AI at its OpenAI-compatible endpoint. Serve embeddings and re-rankers in-process with ONNX Runtime, because they are small, latency-critical, and called on every retrieval. This keeps Python confined to the model-serving tier while the hot path stays entirely on the JVM.

Section 07 ProfessionalExercises

Do these — roughly a weekend, plus GPU rental for some
  1. Compute the memory budget for a model and GPU you care about, at 8k and 128k context. Confirm which quantisation you need.
  2. Run a model in Ollama locally and call it from Spring AI by changing only configuration.
  3. Stand up vLLM on a rented GPU. Measure throughput at batch sizes 1, 8 and 32 and watch it climb.
  4. Enable prefix caching and send 100 requests sharing a long system prompt. Measure the time-to-first-token improvement.
  5. Compare fp16 against AWQ int4 on the same model: memory, throughput, and quality on your golden set.
  6. Export an embedding model to ONNX and serve it in-process from Java. Compare latency against an HTTP call to a Python service.
  7. Load two LoRA adapters into one vLLM instance and select between them per request by tenant.
  8. Drive the server past its KV cache limit and observe preemption. Then cap max context and confirm the behaviour changes.
