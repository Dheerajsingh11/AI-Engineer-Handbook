Section 01 BeginnerStart from zero

Assumed knowledge

Sections 01–02 need nothing. From Section 04 you will want the dot product and matrix multiplication from Topic 1.1, and softmax from Topic 1.2. Both are one page each and worth doing first.

A Large Language Model does exactly one thing: given some text, it guesses what comes next. Everything else — chat, summarising, writing code, reasoning — is that single ability applied repeatedly.

It is worth sitting with how strange that is. There is no plan. When a model writes a 500-word essay, it does not know what the last sentence will be when it writes the first. It writes one fragment, looks at everything so far including what it just wrote, and guesses the next fragment. Coherence is emergent, not designed.

The loop, in full

  1. Split the text into tokens. Not words — chunks. "unhappiness" might become un + happi + ness. Each chunk has an ID number.
  2. Look up a vector for each token. Token 4919 becomes a list of 4096 numbers. This is the embedding table — a plain lookup.
  3. Push the vectors through the stack. Dozens of identical layers, each letting tokens look at each other and refine their meaning in context.
  4. Score every possible next token. The final vector is multiplied out to one score per vocabulary entry — perhaps 100,000 numbers.
  5. Pick one using softmax and a sampling rule. Append it to the text.
  6. Go back to step 1. Repeat until a stop token appears or the limit is hit.
The words, in plain English
Token
A chunk of text the model treats as one unit. Roughly 4 characters or ¾ of an English word. You are billed per token and limited per token, so this is a commercial unit as well as a technical one.
Vocabulary
The complete fixed list of tokens a model knows, decided before training and never changed. Typically 32,000–200,000 entries.
Context window
The maximum number of tokens the model can look at in one go — your prompt plus its answer. Exceeding it is a hard error, not a gradual degradation.
Parameters ("7B", "70B")
The count of learned numbers in the model. More usually means more capable and always means more memory and more cost.
Attention
The mechanism that lets each token look at other tokens and pull in what is relevant. It is what made transformers work.
Inference
Running a trained model to get an answer. As opposed to training, which is creating the model in the first place. You will almost only do inference.
Weights
The actual numbers inside the model, fixed after training. "Open weights" means you can download them and run the model yourself.
Three consequences you can predict from the loop alone
  • Output length dominates latency. Step 6 means generating 500 tokens requires 500 full passes through the model. Reading a long prompt happens once, in parallel. This is why "be concise" measurably speeds up your application.
  • The model cannot revise. Once a token is emitted it is part of the input forever. There is no backspace. This is why chain-of-thought helps — it gives the model room to reach the right answer before committing to it.
  • It has no memory between calls. Every request resends the entire conversation. "Memory" is something your application implements, which is why §5.3 exists.

Section 02 IntermediateTokenisation, and building BPE from scratch

Why not just use words? Because a word vocabulary has no good size. English has hundreds of thousands of words plus names, typos, code identifiers and inflections; any fixed list will miss most of them, and every miss becomes <UNK>, destroying information. Why not characters? Because sequences become 5× longer, and attention cost grows quadratically with length.

Byte Pair Encoding resolves this by learning the vocabulary from data. Start with individual characters, then repeatedly merge whichever adjacent pair occurs most often. Common words end up as single tokens; rare words decompose into meaningful pieces; nothing is ever unknown.

PythonA working BPE tokeniser, trained and applied
from collections import Counter

def get_pair_counts(word_freqs):
    """Count adjacent symbol pairs, weighted by word frequency."""
    pairs = Counter()
    for symbols, freq in word_freqs.items():
        for i in range(len(symbols) - 1):
            pairs[(symbols[i], symbols[i + 1])] += freq
    return pairs

def merge_pair(pair, word_freqs):
    """Replace every occurrence of `pair` with the joined symbol."""
    a, b = pair
    merged = a + b
    out = {}
    for symbols, freq in word_freqs.items():
        new, i = [], 0
        while i < len(symbols):
            if i < len(symbols) - 1 and symbols[i] == a and symbols[i + 1] == b:
                new.append(merged)
                i += 2
            else:
                new.append(symbols[i])
                i += 1
        out[tuple(new)] = freq
    return out

def train_bpe(corpus, num_merges=50):
    # '_' marks a word boundary so the model can tell
    # " the" (mid-sentence) from "the" (start of line).
    words = corpus.lower().split()
    word_freqs = Counter(tuple(w) + ("_",) for w in words)

    merges = []
    for _ in range(num_merges):
        pairs = get_pair_counts(word_freqs)
        if not pairs:
            break
        best, count = pairs.most_common(1)[0]
        if count < 2:                       # nothing worth merging left
            break
        word_freqs = merge_pair(best, word_freqs)
        merges.append(best)
    return merges

def encode(word, merges):
    """Apply learned merges in the order they were learned."""
    symbols = list(word.lower()) + ["_"]
    for a, b in merges:
        i = 0
        while i < len(symbols) - 1:
            if symbols[i] == a and symbols[i + 1] == b:
                symbols[i:i + 2] = [a + b]
            else:
                i += 1
    return symbols

corpus = ("the cat sat on the mat the cat ate the rat "
          "the rat ran the cat ran the mat sat") * 20

merges = train_bpe(corpus, num_merges=20)
print(merges[:6])
# [('t','h'), ('th','e'), ('the','_'), ('a','t'), ('at','_'), ('c','at_')]
# It discovered "the" as one token, and "at" as a reusable suffix.

print(encode("cat", merges))      # ['cat_']        one token
print(encode("category", merges)) # ['cat','e','g','o','r','y','_']  decomposed
Everything odd about LLMs that traces back to this code
  • Counting letters is hard. The model sees ['straw','berry'], not s-t-r-a-w-b-e-r-r-y. Asking how many r's there are is asking about information it was never given.
  • Arithmetic is shaky. 1234 may tokenise as 12+34 while 1235 becomes 123+5. Digits have no consistent representation, so the model must learn arithmetic over an unstable encoding. Use a calculator tool instead.
  • Non-English costs more. Merges are learned from a mostly-English corpus, so Hindi or Thai text fragments into far more tokens for the same meaning — often 2–4× the price and 2–4× the context consumed.
  • Trailing whitespace changes output. "Answer:" and "Answer: " tokenise differently, putting the model in a different state. Never leave a trailing space before expecting a completion.

Section 03 IntermediateAttention, derived

Consider "The animal didn't cross the street because it was too tired." What does "it" refer to? To represent "it" properly, the model must pull in information from "animal". Attention is the mechanism that does this, for every token, in parallel.

The idea: a soft dictionary lookup

Think of a hash map. You have a query, you compare it against every key, and you retrieve the matching value. A hash map is all-or-nothing: one key matches, you get one value.

Attention is the same operation made continuous. Every key gets a match score rather than a yes/no, and you retrieve a weighted blend of all values in proportion to those scores. Because it is a smooth blend rather than a hard selection, it is differentiable, and therefore learnable by gradient descent. That single change is what made transformers possible.

  1. Project each token three ways. Multiply its vector by three learned matrices to get a query (what I am looking for), a key (what I offer) and a value (what I will hand over if chosen). Same input, three different learned views.
  2. Score every pair. Dot every query with every key: QKT. For n tokens this is an n×n grid where entry (i,j) says how much token i cares about token j.
  3. Scale by √dk. Explained below — this is the step everyone glosses over.
  4. Mask the future (for generation). Set scores for later positions to −∞ so softmax drives them to exactly zero. Without this the model could cheat during training by reading ahead.
  5. Softmax each row. Each token's scores become weights summing to 1 — a distribution over what to pay attention to.
  6. Blend the values. Multiply the weights by V. Each token's output is a weighted mixture of every token's value, dominated by the ones it scored highly.
Scaled dot-product attention Attention(Q,K,V)  =  softmax(QKT√dk)V Six steps, one line. Note that this is precisely the cosine-similarity retrieval of Topic 1.1, executed inside the model rather than inside a database — which is why RAG feels like such a natural extension of what the model already does.

Where the square root comes from

This is the detail that separates people who have read the formula from people who understand it.

Why divide by √dk and not dk
  1. Assume the components of q and k are independent with mean 0 and variance 1. A reasonable approximation after layer normalisation.
  2. q · k = Σi=1dk qiki, and each term has mean 0, variance 1. Variance of a product of independent zero-mean unit-variance variables is 1.
  3. Var(q · k) = dk, so the standard deviation is √dk. Variances of independent terms add. This is the crux: the spread of the scores grows as √dk, not as dk.
  4. Dividing by √dk returns the scores to unit variance, independent of dimension. Dividing by dk would over-correct and squash the scores toward zero, making attention uniformly flat.

Why it matters. At dk=128, unscaled scores would have a standard deviation around 11. Softmax over values spread that widely is effectively a hard argmax — one token gets weight ~1, everything else ~0. In that regime the gradient is almost exactly zero everywhere, so the model cannot learn. The scaling keeps softmax in the responsive part of its range. This is not a cosmetic detail; without it, training does not converge.

Section 04 AdvancedBuild a transformer block from scratch

PythonMulti-head causal attention and a full block, NumPy only
import numpy as np

def softmax(x, axis=-1):
    x = x - x.max(axis=axis, keepdims=True)
    e = np.exp(x)
    return e / e.sum(axis=axis, keepdims=True)

def causal_mask(n):
    """True where position i must NOT see position j (j > i)."""
    return np.triu(np.ones((n, n), dtype=bool), k=1)

def attention(Q, K, V, mask=None):
    d_k = Q.shape[-1]
    scores = Q @ K.swapaxes(-2, -1) / np.sqrt(d_k)   # (..., n, n)
    if mask is not None:
        scores = np.where(mask, -np.inf, scores)
    weights = softmax(scores, axis=-1)
    return weights @ V, weights

def multi_head_attention(X, Wq, Wk, Wv, Wo, n_heads):
    """X: (n_tokens, d_model). Returns (n_tokens, d_model)."""
    n, d_model = X.shape
    d_head = d_model // n_heads

    # One projection, then SPLIT into heads. Cheaper than
    # n_heads separate small projections, mathematically identical.
    Q = (X @ Wq).reshape(n, n_heads, d_head).transpose(1, 0, 2)  # (h, n, d)
    K = (X @ Wk).reshape(n, n_heads, d_head).transpose(1, 0, 2)
    V = (X @ Wv).reshape(n, n_heads, d_head).transpose(1, 0, 2)

    out, weights = attention(Q, K, V, mask=causal_mask(n))       # (h, n, d)

    # Concatenate heads back together, then mix them with Wo.
    out = out.transpose(1, 0, 2).reshape(n, d_model)
    return out @ Wo, weights

def layer_norm(x, gamma, beta, eps=1e-5):
    """Normalise each token's vector independently. Note: across
    features, NOT across the batch -- that is BatchNorm, and it
    behaves badly with variable-length sequences."""
    mu  = x.mean(axis=-1, keepdims=True)
    var = x.var(axis=-1, keepdims=True)
    return gamma * (x - mu) / np.sqrt(var + eps) + beta

def gelu(x):
    """Smooth alternative to ReLU used throughout transformers."""
    return 0.5 * x * (1 + np.tanh(np.sqrt(2 / np.pi) * (x + 0.044715 * x**3)))

def transformer_block(X, params, n_heads):
    # PRE-norm: normalise before the sublayer, add the residual after.
    # Post-norm (the original paper) needs careful warmup to train;
    # pre-norm is what every modern model uses.
    h = layer_norm(X, params["g1"], params["b1"])
    attn, _ = multi_head_attention(h, params["Wq"], params["Wk"],
                                   params["Wv"], params["Wo"], n_heads)
    X = X + attn                                   # residual connection

    h = layer_norm(X, params["g2"], params["b2"])
    ff = gelu(h @ params["W1"] + params["b_1"]) @ params["W2"] + params["b_2"]
    X = X + ff                                     # residual connection
    return X

# --- run it ------------------------------------------------------
rng = np.random.default_rng(0)
n, d_model, n_heads, d_ff = 8, 64, 4, 256
s = 0.02                                            # small init

params = {
    "Wq": rng.normal(0, s, (d_model, d_model)), "Wk": rng.normal(0, s, (d_model, d_model)),
    "Wv": rng.normal(0, s, (d_model, d_model)), "Wo": rng.normal(0, s, (d_model, d_model)),
    "W1": rng.normal(0, s, (d_model, d_ff)),    "b_1": np.zeros(d_ff),
    "W2": rng.normal(0, s, (d_ff, d_model)),    "b_2": np.zeros(d_model),
    "g1": np.ones(d_model), "b1": np.zeros(d_model),
    "g2": np.ones(d_model), "b2": np.zeros(d_model),
}

X = rng.normal(size=(n, d_model))
out = transformer_block(X, params, n_heads)
print(out.shape)                                    # (8, 64)

# Confirm the causal mask works: row i must have zero weight past i.
_, w = multi_head_attention(X, params["Wq"], params["Wk"],
                            params["Wv"], params["Wo"], n_heads)
print(np.allclose(np.triu(w[0], k=1), 0))           # True
That is genuinely the whole architecture

Stack that block 32 to 120 times, add token embeddings at the bottom and a projection to vocabulary size at the top, and you have GPT. There is no additional mechanism hiding elsewhere. The difference between this and a frontier model is scale, data, and enormous engineering effort on training and inference — not a fundamentally different idea.

Positional encoding, concretely

Attention computes QKT, which is a sum over pairs — and addition is commutative, so reordering the tokens produces the identical result. "Dog bites man" and "man bites dog" would be indistinguishable. Position must therefore be injected explicitly. RoPE does it elegantly: rotate each query and key vector by an angle proportional to its position. The dot product between two rotated vectors then depends only on their relative offset, which is what actually matters linguistically — and it is why RoPE models can be stretched to longer contexts than they were trained on.

A practical note that trips people up: in a RAG system, your embedding model is usually encoder-only and your generator is decoder-only. They are different architectures with incompatible vector spaces. You cannot embed with one and search a store built by the other.

The training pipeline

  1. Pre-training. Next-token prediction over trillions of tokens of internet text, books and code. Costs millions of dollars and months of GPU time. This is where knowledge and fluency come from. The result is a model that continues text but does not follow instructions.
  2. Supervised fine-tuning (SFT). Training on curated instruction–response pairs. Cheap by comparison. Turns a text continuer into an assistant.
  3. Preference alignment. Humans compare pairs of responses. RLHF trains a reward model on those comparisons and optimises the policy against it with PPO, with a KL penalty to stop it drifting from the base model. DPO reaches a similar result by optimising the preference objective directly, with no separate reward model — simpler and now widely preferred. This stage produces tone, helpfulness and refusal behaviour.

Your adaptation ladder, cheapest first: prompt engineering → few-shot examples → RAG → LoRA fine-tuning → full fine-tuning → continued pre-training. Each step up costs roughly an order of magnitude more in effort and money. Move down the list only when the level above has demonstrably failed against a measured baseline. In enterprise work you will rarely need to pass RAG.

Section 06 ProfessionalWhere latency and cost actually come from

Generation has two phases with completely different performance characteristics. Confusing them is why capacity planning for LLM services so often goes wrong.

Prefill versus decode
PrefillDecode
What happensThe entire prompt is processed at onceOne token generated per pass
ParallelismAll tokens simultaneouslyStrictly sequential — token n needs token n−1
BottleneckCompute (GPU FLOPs)Memory bandwidth — every weight is read for every token
DeterminesTime to first tokenTokens per second, and total latency
Scales withPrompt length (quadratically for attention)Output length (linearly)
Optimise viaPrompt caching, shorter promptsQuantisation, GQA, speculative decoding, shorter outputs
The KV cache, and why it dominates your memory bill

Without caching, generating token 500 would recompute keys and values for all 499 previous tokens — making generation quadratic and hopeless. The KV cache stores them, so each new token only computes its own K and V. Generation becomes linear.

The cost is memory, and it is larger than people expect: 2 × layers × heads × head_dim × seq_len × batch × bytes. For a 70B model at 32k context, that is tens of gigabytes for a single request — frequently more than the weights themselves. This is the entire motivation for Multi-Query and Grouped-Query Attention, which let heads share K and V to shrink the cache by 8× or more. It is also why your provider charges differently for long contexts.

Practical levers, in order of impact

  1. Structure prompts for caching. Providers cache the prefill of a stable prefix. Put the long system prompt and retrieved documents first, variable user input last. Reordering alone can cut cost and time-to-first-token substantially, and requires no other change.
  2. Cap output length. Decode dominates latency. max_tokens plus an instruction to be concise is the highest-leverage latency fix available.
  3. Stream. Server-sent events do not reduce total time but transform perceived speed. Time-to-first-token becomes the number the user feels.
  4. Right-size the model. Routing simple requests to a small model and hard ones to a large one typically saves far more than any prompt micro-optimisation.
  5. Batch offline work. Throughput per GPU rises steeply with batch size. Anything not user-facing should go through a queue and be batched — which is exactly the §5.4 architecture.

Section 07 ProfessionalHallucination, mechanically

By now the cause should be obvious rather than mysterious. The model samples from a distribution over plausible continuations. Nothing in that process consults a source of truth. When the distribution places its mass on something false, the model says something false — confidently, because confidence is just a high probability, and high probability is not the same as correctness.

Section 08 ProfessionalExercises

Do these — roughly a weekend
  1. Run the BPE trainer on a real book. Print the first 100 merges in order and watch a vocabulary form: letters, then affixes, then whole common words.
  2. Compare token counts for the same paragraph in English and in a non-Latin-script language using a public tokeniser playground. The ratio is your multilingual cost multiplier.
  3. Implement attention and verify the causal mask by asserting the upper triangle of the weight matrix is exactly zero.
  4. Remove the /sqrt(d_k) scaling and print the attention weights at d_k=128. Watch them collapse to one-hot. That is a dead gradient.
  5. Extract attention weights from a small open model with output_attentions=True and plot the matrix for a sentence containing an ambiguous pronoun. Find the head that resolves it.
  6. Measure time-to-first-token and total time for a 100-token prompt with a 500-token answer, then a 5,000-token prompt with a 20-token answer. Explain the difference using the prefill/decode table.
  7. Restructure one of your prompts to put static content first. Measure the cost difference over 100 calls with prompt caching enabled.
