Project 4 — Fine-Tune & Self-Host

Take one narrow task out of the agent — classifying a raw finding into a CWE category with a severity rating — and find out whether a fine-tuned 8B model can replace the frontier API call. The deliverable is not the model. It is the decision document, with numbers, and it is allowed to conclude that the API won.

Build order · three weeks, under $50 of GPU time
  1. Stage 0Attention from scratchOne weekend. Makes the fundamentals round free.
  2. Stage 1Data & baselineBuild the set, then measure what you must beat.
  3. Stage 2LoRA & quantiseTrain, sweep, compress, measure the loss at each step.
  4. Stage 3Serve & decidevLLM throughput, then the cost model.
The result you are actually after

Most fine-tuning projects never establish what they had to beat, so they cannot tell whether they beat it. Yours will. If the honest conclusion is “few-shot on the frontier model was more accurate and cheaper at our volume, so we did not ship the fine-tune”, that is a strong interview answer — it demonstrates measurement, cost reasoning and the willingness to kill your own work. Say it plainly.

Step 02Stage 0 — attention from scratch

One weekend, no framework. After this the entire fundamentals round costs you nothing, because you will be describing something you have debugged rather than something you have read about.

Pythonscratch/attention.py — multi-head attention in numpy
import numpy as np

def softmax(x, axis=-1):
    # Subtract the max before exponentiating. Without this, a logit of
    # 800 overflows to inf and the whole row becomes NaN -- the single
    # most common bug when writing this by hand.
    x = x - x.max(axis=axis, keepdims=True)
    e = np.exp(x)
    return e / e.sum(axis=axis, keepdims=True)


def attention(Q, K, V, mask=None):
    """Q,K,V: (heads, seq, d_head). Returns (heads, seq, d_head)."""
    d_head = Q.shape[-1]

    # The n x n score matrix -- this is the O(n^2) everyone asks about.
    scores = Q @ K.transpose(0, 2, 1)

    # Scale by sqrt(d_head). Dot products of d-dimensional vectors have
    # variance proportional to d; unscaled, softmax saturates and the
    # gradients vanish. This is why the sqrt is in the paper.
    scores = scores / np.sqrt(d_head)

    if mask is not None:
        # Causal mask: -inf BEFORE softmax, so those positions get exactly
        # zero weight. Zeroing after softmax would leave rows unnormalised.
        scores = np.where(mask, scores, -np.inf)

    return softmax(scores) @ V


def multi_head(x, Wq, Wk, Wv, Wo, n_heads):
    """x: (seq, d_model). Heads split the SAME d_model, they do not add
    width -- each head gets d_model/n_heads dimensions to specialise in."""
    seq, d_model = x.shape
    d_head = d_model // n_heads

    def split(W):
        return (x @ W).reshape(seq, n_heads, d_head).transpose(1, 0, 2)

    mask = np.tril(np.ones((seq, seq), dtype=bool))
    out = attention(split(Wq), split(Wk), split(Wv), mask)

    # Concatenate the heads back and mix them with the output projection.
    # Without Wo the heads never interact -- that projection is what makes
    # multi-head attention more than n independent attentions.
    return out.transpose(1, 0, 2).reshape(seq, d_model) @ Wo
Stage 0 exercises
  1. Stack two of these with a feed-forward block, residuals and layer norm. Train it on a few thousand characters of text until it produces something word-shaped.
  2. Remove the sqrt(d_head) scaling and watch training fail. Now you can explain the term rather than recite it.
  3. Add a KV-cache to the generation loop and measure the speed-up. This is the concrete version of the most common mechanics question.

Pythondata/split.py — where fine-tuning projects quietly break
import hashlib, re

def normalise(text: str) -> str:
    # Near-duplicates are the leak. Two reports of the same bug differing
    # only in a hostname will land in train AND test, and your accuracy
    # will look wonderful and mean nothing.
    t = text.lower()
    t = re.sub(r"https?://\S+", "<url>", t)
    t = re.sub(r"\b\d+\.\d+\.\d+\.\d+\b", "<ip>", t)
    t = re.sub(r"\s+", " ", t)
    return t

def split(examples, test_frac=0.15, val_frac=0.10):
    seen, unique = set(), []
    for ex in examples:
        h = hashlib.sha256(normalise(ex["text"]).encode()).hexdigest()
        if h not in seen:
            seen.add(h); unique.append(ex)

    # Hash-based assignment, not random.shuffle: the split is then stable
    # across runs and machines, so a later accuracy comparison is real.
    def bucket(ex):
        v = int(hashlib.sha256(ex["id"].encode()).hexdigest()[:8], 16) / 0xFFFFFFFF
        return "test" if v < test_frac else "val" if v < test_frac + val_frac else "train"

    out = {"train": [], "val": [], "test": []}
    for ex in unique:
        out[bucket(ex)].append(ex)
    return out
Hold the test set back, genuinely

Look at the test set once, at the end. Every time you tune a hyperparameter against it you leak information, and after a dozen sweeps your reported accuracy is optimistic by several points. Sweep against validation; touch test once. Interviewers ask about this specifically because it is the discipline that separates people who have trained models from people who have run training scripts.

Step 04The honest baseline

Pythoneval/baseline.py — run this BEFORE any training
async def baseline(test_set, model="claude-sonnet-5", shots=8):
    """Few-shot on a frontier model. This is the number the fine-tune must
    beat -- on accuracy, on cost, or on latency. If it beats none of the
    three, the fine-tune should not ship, and saying so is the result."""
    examples = format_shots(train_set[:shots])
    correct = 0
    for row in test_set:
        pred = await gateway.complete(
            model=model,
            system=f"{TASK_INSTRUCTIONS}\n\nExamples:\n{examples}",
            messages=[{"role": "user", "content": row["text"]}],
            # Constrain the output so parsing cannot be the failure mode --
            # you are measuring classification, not JSON compliance.
            output_config={"format": CWE_SCHEMA},
        )
        correct += (pred["cwe"] == row["cwe"])
    return {"accuracy": correct / len(test_set), "model": model, "shots": shots}

Step 05The LoRA fine-tune

Pythontrain/sft.py
from transformers import AutoModelForCausalLM, AutoTokenizer, BitsAndBytesConfig
from peft import LoraConfig, get_peft_model
from trl import SFTTrainer, SFTConfig
import torch

# QLoRA: load the base in 4-bit, train adapters in higher precision.
# This is what puts an 8B fine-tune on a single 24 GB card.
bnb = BitsAndBytesConfig(
    load_in_4bit=True,
    bnb_4bit_quant_type="nf4",              # normal-float 4, better than plain int4
    bnb_4bit_compute_dtype=torch.bfloat16,  # compute in bf16, store in 4-bit
    bnb_4bit_use_double_quant=True,
)

model = AutoModelForCausalLM.from_pretrained(
    BASE_MODEL, quantization_config=bnb, device_map="auto")

lora = LoraConfig(
    r=16,                 # rank: capacity of the update. 8-16 for narrow tasks,
                          # 32-64 when the task is further from the base's training.
    lora_alpha=32,        # scaling; the update is multiplied by alpha/r, so alpha=2r
                          # is the common convention -- change r and alpha together.
    lora_dropout=0.05,
    target_modules=["q_proj", "k_proj", "v_proj", "o_proj",
                    "gate_proj", "up_proj", "down_proj"],
                          # Attention projections alone are cheaper; adding the MLP
                          # projections usually helps. Ablate it and record both.
    task_type="CAUSAL_LM",
)

model = get_peft_model(model, lora)
model.print_trainable_parameters()   # expect roughly 0.1-1% of total

trainer = SFTTrainer(
    model=model,
    train_dataset=train_ds,
    eval_dataset=val_ds,
    args=SFTConfig(
        num_train_epochs=3,          # small sets overfit fast -- watch eval loss
        per_device_train_batch_size=4,
        gradient_accumulation_steps=4,   # effective batch 16 without the VRAM
        learning_rate=2e-4,          # ~10x a full fine-tune: only adapters move
        lr_scheduler_type="cosine",
        warmup_ratio=0.03,
        bf16=True,
        eval_strategy="steps", eval_steps=50,
        logging_steps=10,
        # Keep the checkpoint with the best VALIDATION loss, not the last.
        # The last one is usually already overfitting.
        load_best_model_at_end=True,
        metric_for_best_model="eval_loss",
    ),
)
trainer.train()
model.save_pretrained("adapters/cwe-classifier-r16")   # tens of MB, not GB
Read the curves, do not just read the final number

Training loss falling while validation loss rises is overfitting, and on a 3000-example set it usually begins in epoch 2. Both losses flat and high means the learning rate is too low or the rank is too small. Loss spiking to NaN means the learning rate is too high — or you are training in fp16 without loss scaling. Being able to describe these three shapes from your own runs is worth more in an interview than any hyperparameter you chose.

Step 06Quantisation, and what it costs

BashMerge, convert, quantise
# 1. Merge the adapter into the base -- llama.cpp needs one set of weights.
python -c "
from peft import AutoPeftModelForCausalLM

# 2. Convert to GGUF at full precision first (this is the reference point).
python llama.cpp/convert_hf_to_gguf.py merged/ --outfile model-f16.gguf --outtype f16

# 3. Walk down the ladder. Measure accuracy at EVERY rung -- the quality
#    cliff is model-specific and cannot be predicted from the bit width.
for q in Q8_0 Q5_K_M Q4_K_M Q3_K_M; do
  ./llama.cpp/llama-quantize model-f16.gguf "model-$q.gguf" "$q"
done

Measure on your task, not on perplexity

Published quantisation comparisons report perplexity, which is a poor proxy for whether a classifier still picks the right CWE. Run your test set at every rung. The interview answer you want is specific: “Q4_K_M cost us 1.2 points of accuracy for a 3.3× size reduction, so we shipped it; Q3 cost nine points and we did not.”

Step 08The decision document

Pythonanalysis/tco.py — the arithmetic the interview wants
def api_cost(n_calls, in_tok, out_tok, in_price, out_price):
    """Prices are per million tokens. claude-haiku-4-5 is 1.00 / 5.00;
    claude-sonnet-5 is 2.00 / 10.00; claude-opus-5 is 5.00 / 25.00."""
    return n_calls * (in_tok * in_price + out_tok * out_price) / 1_000_000

def self_host_cost(n_calls, req_per_sec, gpu_hourly, utilisation=0.35):
    # The line everyone forgets: you pay for the GPU while it idles.
    # At 35% utilisation your effective cost is ~3x the busy-hour cost.
    gpu_seconds = n_calls / req_per_sec / utilisation
    return gpu_seconds / 3600 * gpu_hourly

# The break-even volume is the whole answer. Below it, the API wins on
# cost as well as accuracy; above it, self-hosting starts to pay -- and
# you still owe the engineering time, which belongs in the write-up.

Close the project with a one-page document covering: accuracy for baseline / fine-tuned / quantised; cost per million classifications each way, with the break-even volume; p95 latency each way; and the non-cost factors — data residency, provider dependency, the ongoing operational burden of running your own inference. Then state a recommendation and commit to it.

Exercises
  1. Sweep LoRA rank across 4 / 8 / 16 / 32 / 64 at fixed alpha/r ratio. Plot validation accuracy against trainable-parameter count and find where it plateaus.
  2. Train on 500, 1000, 2000 and 4000 examples. The resulting curve tells you whether more labelling would pay — a genuinely useful thing to be able to answer.
  3. Ablate target_modules: attention-only versus attention plus MLP. Report accuracy and adapter size for both.
  4. Take the fine-tuned model and give it the RAG context from Project 2. Does fine-tuning plus retrieval beat either alone?
  5. Register the vLLM endpoint as a second Provider in Project 1 and fail over to it. Run the Project 5 eval suite against both and quantify the behaviour change.
