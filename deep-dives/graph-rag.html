Knowledge Graphs & GraphRAG

The questions vector search structurally cannot answer. This page explains why "how are these two people connected?" defeats similarity search, builds an entity-and-relation extraction pipeline, implements community detection for global summarisation, and is honest about GraphRAG's substantial ingestion cost.

Section 01 BeginnerStart from zero

Assumed knowledge

Standard RAG from Topics 4.1–4.6. Graph terminology is introduced here; no prior graph-database experience is assumed.

Vector search finds passages that resemble your query. That is a genuinely powerful capability and it covers most questions. But an entire class of questions is invisible to it.

Where similarity search structurally fails
QuestionWhy vector search cannot answer it
"How is Dr. Okonkwo connected to the Meridian project?"The connection may run through three documents that never mention both
"Which suppliers are affected if Vendor X fails?"Requires traversing a dependency chain, not matching text
"What are the main themes across all 500 reports?"A global question — no single passage contains the answer
"Who reported to someone who worked on Project Atlas?"Two-hop relational query
"What changed between v2 and v5 of this policy?"Requires knowing the version relationship
The structural limitation

Standard RAG retrieves k chunks that each individually resemble the query. If the answer requires combining information from chunks that do not resemble each other, it will never assemble them — each is individually a poor match, so none makes the top k.

GraphRAG solves this by extracting entities and relationships at ingestion time, building an explicit graph, and then traversing that graph at query time. Connections become first-class data rather than something the model must infer from co-occurrence.

The words, in plain English
Entity
A thing: a person, company, product, system, concept. Becomes a node.
Relationship
A connection between two entities: "works for", "depends on", "supersedes". Becomes an edge.
Knowledge graph
The whole network of entities and relationships.
Triple
The atomic unit: (subject, predicate, object). "Okonkwo — leads — Meridian".
Hop
One step along an edge. Multi-hop questions need several.
Entity resolution
Deciding that "Dr. Okonkwo", "A. Okonkwo" and "Amara Okonkwo" are one person. The hard part.
Community
A densely connected cluster of entities, found algorithmically.
Cypher
Neo4j's query language. Reads like ASCII art of the pattern you want.

Section 02 IntermediateBuilding the graph

Ingestion gains three stages beyond standard RAG: extract, resolve, and detect communities.

PythonEntity and relationship extraction
import json
from collections import defaultdict

EXTRACT_PROMPT = """Extract entities and relationships from the text.

Allowed entity types: PERSON, ORGANISATION, PRODUCT, PROJECT, SYSTEM,
CONCEPT, LOCATION, EVENT.

For each entity give: name (as written), type, and a one-sentence
description drawn ONLY from this text.

For each relationship give: source, target, a short relationship type
in UPPER_SNAKE_CASE, a description, and strength 1-10.

Return JSON:
{{"entities": [{{"name":..., "type":..., "description":...}}],
  "relationships": [{{"source":..., "target":..., "type":...,
                      "description":..., "strength":...}}]}}

Text:
{chunk}"""

def extract_graph(chunks, chat_fn):
    entities = defaultdict(lambda: {"descriptions": [], "chunks": [], "type": None})
    relationships = []

    for chunk_id, text in enumerate(chunks):
        result = json.loads(chat_fn(EXTRACT_PROMPT.format(chunk=text)))

        for e in result["entities"]:
            key = e["name"].strip().lower()          # crude first-pass resolution
            entities[key]["type"] = e["type"]
            entities[key]["descriptions"].append(e["description"])
            entities[key]["chunks"].append(chunk_id)

        for r in result["relationships"]:
            relationships.append({
                "source": r["source"].strip().lower(),
                "target": r["target"].strip().lower(),
                "type": r["type"],
                "description": r["description"],
                "strength": r.get("strength", 5),
                "chunk_id": chunk_id,        # provenance: enables citation
            })
    return entities, relationships


def summarise_entities(entities, chat_fn):
    """One entity mentioned in 40 chunks accumulates 40 descriptions.
    Collapse them into one coherent description, or the node text is
    a repetitive mess that embeds badly."""
    for name, data in entities.items():
        if len(data["descriptions"]) == 1:
            data["summary"] = data["descriptions"][0]
        else:
            joined = "\n- ".join(data["descriptions"][:30])
            data["summary"] = chat_fn(
                f"Combine these descriptions of '{name}' into one "
                f"coherent paragraph. Resolve contradictions by noting "
                f"both.\n\n- {joined}")
    return entities
Entity resolution is the part that decides whether this works

Lowercasing names gets you perhaps 60% of the way. The remainder is genuinely hard: "IBM" / "International Business Machines" / "Big Blue"; "Dr. Okonkwo" / "Amara Okonkwo" / "A. Okonkwo"; and the reverse problem, two different people who share a name.

Fail to merge and your graph fragments into disconnected duplicates, so traversal finds nothing. Over-merge and you fabricate connections that do not exist — which is worse, because the system then confidently asserts relationships between unrelated people.

A workable approach layers three signals: exact and normalised string matching, embedding similarity between entity descriptions above a threshold, and an LLM adjudicating the remaining ambiguous pairs. Keep an alias table, and make it reviewable by a human — for any high-stakes corpus, entity resolution needs an audit trail.

Section 03 AdvancedCommunities and global questions

"What are the main themes across all 500 documents?" cannot be answered by retrieving 5 chunks, and the corpus does not fit in a context window. Microsoft's GraphRAG answers it with a hierarchy of pre-computed summaries.

  1. Detect communities in the graph using the Leiden algorithm — it finds groups of nodes more densely connected to each other than to the rest, producing a hierarchy from fine-grained clusters up to broad themes.
  2. Summarise each community with an LLM at ingestion time, bottom-up: summarise small communities, then summarise those summaries for their parent community.
  3. Answer global questions by map-reduce over community summaries at an appropriate level, rather than over raw chunks.
  4. Answer local questions by finding the relevant entities and traversing outward from them.
PythonCommunity detection and hierarchical summarisation
import networkx as nx

def build_networkx_graph(entities, relationships):
    G = nx.Graph()
    for name, data in entities.items():
        G.add_node(name, type=data["type"], summary=data.get("summary", ""))
    for r in relationships:
        if G.has_edge(r["source"], r["target"]):
            # Repeated relationships strengthen the edge
            G[r["source"]][r["target"]]["weight"] += r["strength"]
        else:
            G.add_edge(r["source"], r["target"],
                       weight=r["strength"], type=r["type"],
                       description=r["description"])
    return G

def detect_communities(G, resolution=1.0):
    """Louvain/Leiden maximise modularity: how much more densely
    connected each group is than chance would predict."""
    communities = nx.community.louvain_communities(
        G, weight="weight", resolution=resolution, seed=42)
    return [sorted(c) for c in communities]

COMMUNITY_PROMPT = """These entities and relationships form a cluster
in a knowledge graph. Write a report covering: the main theme, the key
entities and their roles, and the most significant relationships.

Entities:
{entities}

Relationships:
{relationships}"""

def summarise_communities(G, communities, chat_fn):
    reports = []
    for i, members in enumerate(communities):
        subgraph = G.subgraph(members)
        entity_text = "\n".join(
            f"- {n} ({G.nodes[n]['type']}): {G.nodes[n]['summary'][:200]}"
            for n in members[:50])
        rel_text = "\n".join(
            f"- {u} --[{d.get('type','RELATED')}]--> {v}: {d.get('description','')}"
            for u, v, d in subgraph.edges(data=True))
        reports.append({
            "id": i, "members": members,
            "size": len(members),
            "report": chat_fn(COMMUNITY_PROMPT.format(
                entities=entity_text, relationships=rel_text)),
        })
    return reports

def global_query(question, reports, chat_fn, top_n=15):
    """Map-reduce over community reports. Each report answers
    partially; a final pass combines them."""
    partials = []
    for r in sorted(reports, key=lambda x: -x["size"])[:top_n]:
        answer = chat_fn(f"""Using only this report, answer the question.
If the report is not relevant, reply exactly NOT_RELEVANT.

Report:
{r['report']}

Question: {question}""")
        if "NOT_RELEVANT" not in answer:
            partials.append(answer)

    return chat_fn(f"""Combine these partial answers into one coherent
response. Note any disagreements.

{chr(10).join(f'---{chr(10)}{p}' for p in partials)}

Question: {question}""")

Section 04 AdvancedQuerying the graph

CypherNeo4j queries for questions vector search cannot answer
// Multi-hop: how are two entities connected, and by what path?
MATCH path = shortestPath(
  (a:Entity {name: 'amara okonkwo'})-[*..4]-(b:Entity {name: 'meridian'}))
RETURN [n IN nodes(path) | n.name]         AS chain,
       [r IN relationships(path) | r.type] AS how,
       length(path)                        AS hops;

// Impact analysis: what transitively depends on a failing vendor?
MATCH (v:Entity {name: 'vendor x'})<-[:DEPENDS_ON*1..3]-(affected)
RETURN DISTINCT affected.name, affected.type,
       length(shortestPath((v)<-[:DEPENDS_ON*]-(affected))) AS distance
ORDER  BY distance;

// Local neighbourhood: everything around an entity, for context
MATCH (e:Entity {name: 'meridian'})-[r]-(neighbour)
RETURN e.name, type(r), r.description, neighbour.name, neighbour.type
ORDER  BY r.strength DESC
LIMIT  25;

// HYBRID: vector search to find entry points, then traverse.
// This is the pattern that works best in practice -- semantic
// search locates the starting nodes, the graph supplies structure.
CALL db.index.vector.queryNodes('entity_embedding', 5, $queryVector)
YIELD node AS seed, score
MATCH (seed)-[r]-(neighbour)
RETURN seed.name, score, collect(DISTINCT {
         relation: type(r), to: neighbour.name, desc: r.description
       })[..10] AS context
ORDER BY score DESC;
JavaNeo4j from Spring, with a vector index
@Repository
class KnowledgeGraphRepository {

    private final Neo4jClient client;

    List<PathResult> findConnection(String from, String to, int maxHops) {
        return client.query("""
                MATCH path = shortestPath(
                  (a:Entity {name: $from})-[*..%d]-(b:Entity {name: $to}))
                RETURN [n IN nodes(path) | n.name] AS chain,
                       [r IN relationships(path) | r.type] AS relations
                """.formatted(maxHops))
            .bind(from).to("from").bind(to).to("to")
            .fetchAs(PathResult.class)
            .mappedBy((ts, record) -> new PathResult(
                    record.get("chain").asList(Value::asString),
                    record.get("relations").asList(Value::asString)))
            .all().stream().toList();
    }

    // Hybrid: semantic entry, structural expansion
    List<EntityContext> seedAndExpand(float[] queryVector, int seeds) {
        return client.query("""
                CALL db.index.vector.queryNodes('entity_embedding', $seeds, $vec)
                YIELD node, score
                MATCH (node)-[r]-(n)
                RETURN node.name AS entity, node.summary AS summary, score,
                       collect(DISTINCT {rel: type(r), to: n.name})[..10] AS edges
                ORDER BY score DESC
                """)
            .bind(queryVector).to("vec").bind(seeds).to("seeds")
            .fetchAs(EntityContext.class).mappedBy(this::toContext)
            .all().stream().toList();
    }
}

Section 05 ProfessionalThe cost, stated honestly

GraphRAG is powerful and it is not free. The costs are concentrated in ingestion, which makes them easy to underestimate during a prototype on 50 documents.

Standard RAG versus GraphRAG, 10,000 documents
Standard RAGGraphRAG
Ingestion LLM calls01–3 per chunk, plus summarisation
Ingestion costEmbeddings onlyOften 10–100× higher
Ingestion timeMinutes to hoursHours to days
Incremental updatesTrivial — re-chunk one documentHard — a new entity can alter community structure
Query latency50–300 ms200 ms–several seconds
InfrastructureOne vector storeVector store + graph database
Answers relationship questionsPoorlyWell
Answers global questionsNoYes
When GraphRAG is the wrong choice
  • Your questions are mostly lookups. "What is the refund policy?" needs no graph. Measure what proportion of real questions are relational before committing — it is usually smaller than expected.
  • Your corpus changes constantly. Rebuilding communities is expensive, and incremental graph updates are a genuinely unsolved engineering problem.
  • Your documents have few named entities. Extraction on abstract prose produces a sparse, low-value graph.
  • You have not yet done hybrid search and re-ranking. Those are cheaper, faster to implement, and fix more problems. Do §4.6 first.
The pragmatic middle path

Full GraphRAG is not the only option. Three lighter-weight approaches capture much of the value:

  • Entity-linked chunks. Extract entities and store them as chunk metadata. Now you can filter retrieval by entity, and answer "everything about Vendor X" without any graph traversal. Cheap, and often enough.
  • A graph over an existing schema. If your relational database already models the relationships — orders, customers, suppliers — expose that as a tool (§5.1). You already have a knowledge graph; it is called your database.
  • Hybrid entry. Vector search to find seed entities, then one or two hops of traversal. Most of the benefit for a fraction of the ingestion cost.

Section 06 ProfessionalExercises

Do these — roughly a weekend
  1. Take 20 real user questions and classify each as lookup, relational, or global. The proportions tell you whether this page is relevant to your project.
  2. Run entity extraction over 100 chunks. Count the duplicate entities that crude lowercasing failed to merge.
  3. Implement three-stage entity resolution (string, embedding, LLM adjudication). Measure how many duplicates each stage catches.
  4. Build the graph in NetworkX and run community detection. Inspect the largest communities by hand — do they correspond to themes you recognise?
  5. Write a multi-hop question your standard RAG cannot answer. Confirm it fails, then answer it with a Cypher traversal.
  6. Implement the hybrid pattern: vector search for seeds, then one hop of expansion. Compare against pure vector search on relational questions.
  7. Measure the full ingestion cost for 1,000 documents both ways. Decide whether the relational questions justify it.
  8. Implement the cheap alternative — entities as chunk metadata — and see how many of your relational questions it already handles.
