Phase 013–4 weeksFundamentals & Mathematical Primitives

The math that actually shows up

You do not need a mathematics degree to build AI systems. You need a small, specific set of ideas — roughly one chapter of linear algebra, one of probability, and a clear mechanical picture of what a transformer does. Everything below is chosen because it appears in code you will write or in a decision you will have to defend.

1.1  Linear Algebra

Basic Deep dive →

Every piece of meaning inside an LLM is a list of numbers. A word, a sentence, a whole PDF page — all of them become a point in a space with hundreds or thousands of dimensions. Linear algebra is the vocabulary for talking about those points: how far apart they are, how to combine them, and how to transform them.

The four objects

  • Scalar — a single number. 0.42. In code, a Python float.
  • Vector — an ordered list of numbers, written v ∈ ℝn. An embedding is exactly this. [0.12, -0.88, ...] with n = 1536.
  • Matrix — a rectangle of numbers, A ∈ ℝm×n. A batch of 32 embeddings is a 32 × 1536 matrix. Every learned weight in a model is a matrix.
  • Tensor — the general case, any number of axes. A batch of sequences of embeddings is 3-D: [batch, tokens, dim]. This shape triple is the single most common thing you will debug.
Java bridge

A vector is a double[]. A matrix is a double[][]. The difference is that NumPy operates on the whole array at once in optimised C, so you write a @ b instead of three nested for loops — and it runs a hundred times faster. Getting comfortable with that shift, from loops to whole-array operations, is most of the learning curve.

Vector operations you will actually use

Addition and scalar multiplication are element-wise and unremarkable, but they carry meaning: adding embeddings roughly blends concepts, and averaging the token embeddings of a sentence is a real (if crude) way to embed a whole sentence — this is called mean pooling.

The dot product is the workhorse. It multiplies two vectors element-wise and sums the result, collapsing two lists into one number that measures alignment.

Dot product a · b  =  Σi=1n ai bi  =  ‖a‖ ‖b‖ cos θ Positive means the vectors point broadly the same way, zero means they are perpendicular (unrelated), negative means opposed. The second form is the one to remember — it says the dot product is length times length times agreement of direction.

Norms measure a vector's length. There are several, and the choice matters more than beginners expect.

Types of norm
NormFormulaBehaviourWhere it appears
L1 (Manhattan)Σ |ai|Sums absolute values; robust to outliersLasso regularisation, sparse feature selection

Normalising a vector means dividing by its L2 norm so its length becomes exactly 1. This is done to nearly every embedding before it is stored, and it has a consequence worth internalising.

Cosine similarity cos θ  =  a · b‖a‖ ‖b‖ Ranges from −1 (opposite) through 0 (unrelated) to 1 (identical direction). It ignores magnitude entirely, which is what you want: a long document and a short query about the same subject should score high, and cosine makes that possible.

The identity every RAG engineer should know. If both vectors are L2-normalised then ‖a‖ = ‖b‖ = 1, so cosine similarity is the dot product — the division disappears. That is why vector databases tell you to normalise on write and then use the cheaper inner-product metric. Same ranking, fewer operations.

Types of similarity and distance Core

Picking the wrong metric is a silent bug: retrieval still returns results, they are just subtly worse. Match the metric to how the embedding model was trained — the model card always says.

Matrices and matrix multiplication

Matrix multiplication is a batch of dot products. If A is m×n and B is n×p, then C = AB is m×p, and each entry Cij is the dot product of row i of A with column j of B. The inner dimensions must match — and when a model throws a shape error, this is almost always why.

Matrix product Cij  =  Σk=1n Aik Bkj Not commutative: AB ≠ BA. Reading a matrix as a function that transforms vectors is the key intuition — a neural network layer is a matrix that rotates, stretches and projects its input into a more useful space.

Projection, rank and dimensionality reduction Advanced

Embeddings are big, and much of that size is redundant. Three ideas let you shrink them:

  • Projection — multiplying by a matrix that has fewer output than input dimensions. Everything in a transformer that changes width is a projection.
  • Rank — the number of genuinely independent directions in a matrix. Low rank means redundancy, which is exactly what LoRA exploits: instead of fine-tuning a huge weight matrix W, you learn a small correction BA where B and A are thin. Millions of trainable parameters instead of billions.
  • SVD and PCA — decompositions that find the directions of greatest variance, letting you keep 95% of the information in a fraction of the dimensions. This is also the theory behind Matryoshka embeddings, where a model is trained so that the first 256 of its 1536 dimensions are already a usable embedding.
The curse of dimensionality

In high dimensions, random vectors are almost always nearly perpendicular, and the distance between the nearest and furthest neighbour of a point shrinks toward zero. Distances become less discriminating the more dimensions you add. This is why a good 768-dimension embedding often beats a mediocre 3072-dimension one, and why exact nearest-neighbour search stops being useful at scale — the ANN indexes in Phase 4 exist because of this.

1.2  Probability & Statistics

Basic Deep dive →

An LLM is a probability distribution over the next token. Not a lookup table, not a database — a distribution. Once that lands, temperature, hallucination and evaluation all stop being mysterious.

The primitives

A random variable takes values with certain probabilities. Conditional probability P(A|B) is the probability of A given that B happened — and next-token prediction is literally P(token | all previous tokens). Bayes' theorem tells you how to update a belief when evidence arrives:

Bayes' theorem P(A|B)  =  P(B|A) · P(A)P(B) Posterior = likelihood × prior, normalised. It underpins Naive Bayes classifiers, A/B test analysis, and the general habit of asking "how much should this new evidence actually move me?"

Softmax, temperature and sampling Core

A model's final layer produces logits — raw, unbounded scores, one per vocabulary token. Softmax turns them into a probability distribution: all positive, summing to 1.

Softmax with temperature P(tokeni)  =  exp(zi / T)Σj exp(zj / T) The exponential exaggerates differences: a logit slightly ahead becomes a probability far ahead. Temperature T divides the logits before exponentiating. Low T spreads the logits apart and sharpens the distribution; high T squashes them together and flattens it. As T→0 you get pure greedy selection; as T→∞ you approach uniform noise.

Common misconception

temperature=0 does not guarantee identical output across calls. Floating-point non-determinism in batched GPU kernels, mixture-of-experts routing that depends on which other requests share your batch, and silent model updates all break reproducibility. Pin the model version, set a seed if the provider offers one, and still write tolerant tests.

PythonSoftmax, temperature and top-p from scratch
import numpy as np

def softmax(logits, temperature=1.0):
    z = np.asarray(logits, dtype=float) / temperature
    z = z - z.max()              # subtract max for numerical stability
    e = np.exp(z)
    return e / e.sum()

logits = [3.2, 2.9, 1.1, 0.4, -0.7]

softmax(logits, 0.2)   # [0.817, 0.182, 0.000, 0.000, 0.000]  near-deterministic
softmax(logits, 1.0)   # [0.457, 0.339, 0.056, 0.028, 0.009]  balanced
softmax(logits, 2.0)   # [0.322, 0.277, 0.113, 0.079, 0.047]  flat, adventurous

def top_p(probs, p=0.9):
    # Keep the smallest set of tokens whose mass reaches p.
    order = np.argsort(-probs)
    cumulative = np.cumsum(probs[order])
    cutoff = np.searchsorted(cumulative, p) + 1
    keep = order[:cutoff]
    renormalised = probs[keep] / probs[keep].sum()
    return keep, renormalised

top_p(softmax(logits, 1.0), 0.9)   # keeps only the first 3 tokens

Measuring surprise: entropy, cross-entropy, perplexity Advanced

These three are the same idea at different angles, and they are how language models are trained and compared.

  • Entropy H(p) = −Σ pi log pi — the average surprise of a distribution. A confident model has low entropy. Measuring per-token entropy at inference is a cheap, useful hallucination signal.
  • Cross-entropy −Σ yi log pi — the surprise of the true answer under your predicted distribution. This is the training loss for language models and for classification.
  • KL divergence DKL(p‖q) — how far distribution q is from p. Used in RLHF/PPO to stop a fine-tuned model drifting too far from the base model.
  • Perplexity = exp(cross-entropy) — cross-entropy made readable. Perplexity 10 means the model is about as uncertain as if it were choosing uniformly among 10 options. Lower is better.

Evaluation metrics Core

1.3  LLM Mechanics

Core Deep dive →

This section is the one that pays off fastest. Almost every production problem — latency, cost, truncation, hallucination, weird behaviour with long inputs — traces back to a mechanical detail of how transformers work.

Tokenisation

Models do not see characters or words. Text is split into tokens, each mapped to an integer, each integer mapped to a learned vector. As a rule of thumb, one token is about four characters or three-quarters of a word in English.

Consequences you will hit in production

Cost and limits are per token, not per character. Non-English text often costs two to three times more for the same meaning because tokenisers are trained mostly on English. Numbers split unpredictably (1234 may become 12+34), which is a large part of why models are shaky at arithmetic. Whitespace matters — a trailing space changes tokenisation and can measurably change output. And the classic party trick, "how many r's in strawberry", is hard precisely because the model never sees the letters.

The transformer, one block at a time

Input tokens become embeddings, position information is added, and then the same block repeats N times (32, 80, 120…). Each block does two things: attention, where tokens exchange information, and a feed-forward network, where each token is processed independently. Residual connections and normalisation wrap both.

Scaled dot-product attention Attention(Q, K, V)  =  softmax (QKT√dk) V Each token emits a query ("what am I looking for?"), a key ("what do I offer?") and a value ("what I will actually pass on"). QKT is every query dotted with every key — a full grid of relevance scores. Softmax turns each row into weights, and the output is a weighted blend of the values. The √dk divisor keeps the dot products from growing with dimension and pushing softmax into a region where gradients vanish.

Notice that this is the cosine-similarity machinery from §1.1, applied inside the model rather than inside a database. Attention is retrieval — which is why RAG feels like such a natural extension.

Why context windows cost what they do. The QKT grid is n×n for n tokens, so attention is quadratic in sequence length. Doubling the input roughly quadruples that work. Sliding-window attention, FlashAttention and their relatives all exist to soften this curve — and it is why a 200k-token prompt is not simply "100× a 2k prompt" in either cost or latency.

Positions, normalisation, and the rest of the block

Attention is order-blind — shuffle the tokens and the maths is unchanged — so position must be injected. Sinusoidal encodings (original paper) use fixed sine waves; learned encodings train a vector per position; RoPE rotates Q and K by an angle proportional to position, which generalises past the training length and is now dominant; ALiBi adds a distance penalty directly to attention scores. RoPE is the reason "context window extension" tricks work at all.

The rest of the block: LayerNorm or RMSNorm stabilises activations (modern models put it before the sublayer — pre-norm — because it trains more stably); the feed-forward network expands to roughly 4× width and back, with a GELU or SwiGLU activation, and holds most of the model's parameters; residual connections add each sublayer's input to its output so gradients survive hundreds of layers.

PythonSingle-head causal attention in 20 lines
import numpy as np

def softmax(x, axis=-1):
    x = x - x.max(axis=axis, keepdims=True)
    e = np.exp(x)
    return e / e.sum(axis=axis, keepdims=True)

def causal_attention(X, Wq, Wk, Wv):
    # X: (n_tokens, d_model) -- the embedded sequence
    Q, K, V = X @ Wq, X @ Wk, X @ Wv       # each (n, d_k)
    d_k = Q.shape[-1]

    scores = (Q @ K.T) / np.sqrt(d_k)      # (n, n) relevance grid

    # Mask the future: position i may not look at j > i.
    n = scores.shape[0]
    mask = np.triu(np.ones((n, n)), k=1).astype(bool)
    scores = np.where(mask, -np.inf, scores)

    weights = softmax(scores, axis=-1)     # each row sums to 1
    return weights @ V                     # (n, d_k) context-aware output

n, d_model, d_k = 6, 32, 32
X = np.random.randn(n, d_model)
Wq, Wk, Wv = (np.random.randn(d_model, d_k) * 0.1 for _ in range(3))

out = causal_attention(X, Wq, Wk, Wv)
print(out.shape)   # (6, 32) -- one enriched vector per token

How a model gets made Advanced

  1. Pre-training — next-token prediction over trillions of tokens. This is where knowledge and language ability come from, and where nearly all the compute goes.
  2. Supervised fine-tuning (SFT) — training on curated instruction/response pairs so the model answers rather than merely continues text.
  3. Preference alignment — RLHF trains a reward model from human comparisons and optimises against it with PPO; DPO skips the reward model and optimises preferences directly; Constitutional AI uses a written set of principles and model-generated critique. This stage produces helpfulness, tone and refusal behaviour.

Adaptation options for you, cheapest first: prompt engineering → few-shot examples → RAG → PEFT/LoRA fine-tuning → full fine-tuning → continued pre-training. Move down this list only when the level above has genuinely failed. In enterprise work you will rarely need to go past RAG.

Inference mechanics — where your latency comes from

  • Prefill — the whole prompt is processed in parallel. Compute-bound. This determines time to first token, and it grows with prompt length.
  • Decode — tokens are generated one at a time, each pass reading the entire model. Memory-bandwidth-bound. This sets tokens per second, and it is why output length dominates total latency.
  • KV cache — keys and values for previous tokens are stored so they need not be recomputed. It makes generation feasible, and it is the main consumer of GPU memory. GQA/MQA exist to shrink it.
  • Prompt caching — providers can cache the prefill of a stable prefix. Put your long, unchanging system prompt and documents first and the variable user input last, and you can cut cost and TTFT substantially.
  • Quantisation — storing weights in fewer bits. fp32 → bf16/fp16 is nearly free; int8 and int4 (GPTQ, AWQ, GGUF) trade some accuracy for large memory savings and are how models run on a laptop.
  • Mixture of Experts (MoE) — only a subset of parameters activates per token, so a model can have huge total capacity with the inference cost of a much smaller one.

Hallucination: types and mitigations

A model samples from a distribution over plausible continuations. Nothing in that process consults a source of truth, so a confident falsehood is not a malfunction — it is the expected behaviour when the distribution is wrong. Knowing the type tells you the fix.

2.2  NumPy & Pandas

Core Deep dive →

NumPy — the array

An ndarray is a fixed-type, fixed-shape block of memory with fast operations over the whole block. Three concepts carry most of the value:

  • Shape and axis. arr.shape is a tuple; axis=0 runs down rows, axis=1 across columns. Nearly every NumPy bug is an axis confusion.
  • Broadcasting. Arrays of different shapes are stretched to match, right-aligned, where dimensions are equal or 1. This is why store / norms[:, None] normalises 100,000 vectors in one line.
  • Vectorisation. Replace loops with array expressions. Not just faster — the code is shorter and closer to the mathematics.
Views vs copies

Slicing an ndarray returns a view into the same memory, so writing to the slice mutates the original — unlike Java's Arrays.copyOfRange. Use .copy() when you mean a copy. Fancy indexing (arr[[0,3,7]]) always copies, which is a separate performance surprise in the other direction.

The workflow discipline Core

This is the part that transfers directly to LLM evaluation, and the part most people skip.

  • Split before you touch anything. Train / validation / test, typically 60 / 20 / 20. The test set is opened once, at the end.
  • Data leakage is the cardinal sin: fitting a scaler on all the data, or including a feature that encodes the answer. Symptom — excellent offline numbers, useless in production. Use Pipeline so preprocessing is fitted inside each fold.
  • Cross-validation types — k-fold (general), stratified k-fold (imbalanced classes; preserves ratios), time-series split (never train on the future), group k-fold (keep all rows of one customer in one fold).
  • Bias–variance. Underfitting is high bias — too simple, poor on train and test. Overfitting is high variance — memorises training data, poor on test. Fix underfitting with a richer model or better features; fix overfitting with more data, regularisation, or a simpler model.
  • Feature scaling types — StandardScaler (mean 0, sd 1; the default), MinMaxScaler (to [0,1]; needed by neural nets), RobustScaler (median and IQR; use when outliers are real). Distance-based models require scaling; tree models do not care.
  • Encoding types — one-hot for unordered categories, ordinal when order is genuine, target encoding for very high cardinality (and it leaks if done carelessly), embeddings when the category is text.
  • Class imbalance — class weights, resampling, SMOTE, and above all judging on PR-AUC rather than accuracy.

A neural network is a stack of layers, each computing y = f(Wx + b) — a matrix multiply, a bias, and a non-linear activation. Without the non-linearity, any stack of layers collapses into a single matrix and learns nothing a linear model could not.

3.1  Prompt Engineering

Basic Deep dive →

A prompt is not a magic incantation; it is the only interface you have to a program whose behaviour is a probability distribution. Treat prompts as source code: version them, review them, test them, and never edit them directly in production.

The anatomy of a request

  • System prompt — role, rules, tone, output contract. Stable across requests, which makes it the ideal candidate for prompt caching.
  • Context — retrieved documents, conversation history, tool results. Fenced with clear delimiters so the model can tell data from instruction.
  • User message — the actual request. Keep it last.
  • Assistant prefill — starting the model's reply for it ({") to force a format. Supported by some providers, and very effective.

Structured output Core

An enterprise service needs a typed object, not prose. Four mechanisms, in increasing order of reliability:

  1. Ask nicely — "respond in JSON". Works often, fails silently in production. Not acceptable on its own.
  2. JSON mode — the provider guarantees syntactically valid JSON, but not your schema.
  3. Schema-constrained / tool-based output — you supply a JSON Schema and the model must conform. This is what Spring AI's entity() and LangChain4j's AI Services use under the hood.
  4. Constrained decoding — the sampler is restricted at each step so invalid tokens are impossible. Guaranteed by construction; available with local inference and some APIs.

Whichever you use, still validate on receipt and retry with the validation error fed back into the conversation. That retry loop is a normal part of a robust client.

Prompt injection — your security background is an asset here

Any text the model reads can contain instructions: a retrieved document, a web page, an email, a filename. The model cannot reliably distinguish your instructions from data, so treat everything retrieved as untrusted input — exactly as you would with SQL or HTML. Delimit it clearly, state that content inside the delimiters is data and never instruction, and above all enforce authorisation outside the model: check permissions in your own code before a tool executes, never by asking the model to be careful. This is developed further in §5.6.

Operational discipline

  • Version prompts in the repository, with the model ID and parameters they were validated against.
  • Put the stable parts first. Prompt caching keys on prefixes, so system prompt and documents before user input can cut both cost and time-to-first-token substantially.
  • Budget tokens. Count input and output separately — output is typically several times more expensive per token.
  • Test prompts like code. A golden set of 30–50 cases in CI catches regressions that a manual spot-check never will.

3.4  The Model Context Protocol

  • Server — exposes capabilities. Your Spring Boot service can be an MCP server, publishing existing business operations to any MCP-capable model.

4.1  What RAG Is, and When to Use It

Basic Deep dive →

A model's knowledge is frozen at training time and contains nothing private. RAG fixes this without touching the model: retrieve relevant passages from your own corpus at query time, put them in the prompt, and instruct the model to answer only from them. Two pipelines, run at different times.

4.2  Embedding Models

Core Deep dive →

An embedding model maps text to a vector such that semantically similar text lands nearby. It is the foundation of the whole pipeline, and the choice constrains everything downstream — storage cost, recall, latency, and whether you can ever change your mind cheaply.

Types of embedding
TypeRepresentationStrengthExample
DenseOne fixed-length float vectorCaptures meaning; handles paraphrase and synonymstext-embedding-3, bge, e5, nomic-embed
SparseMostly-zero vector over the vocabularyExact term matching; interpretableBM25, SPLADE
Multi-vector (late interaction)One vector per tokenHighest quality; matches at the token levelColBERT, ColPali
MatryoshkaDense, but truncatableTake the first 256 of 1536 dims and it still works — tune cost against quality after the facttext-embedding-3, nomic-embed

A second distinction matters for architecture. A bi-encoder embeds query and document separately, so documents can be indexed in advance — fast, scalable, slightly less accurate. A cross-encoder feeds query and document through the model together, which is far more accurate but requires one model pass per candidate, so it cannot scan a corpus. The standard architecture uses both: a bi-encoder retrieves 50–100 candidates, then a cross-encoder re-ranks them to the final 5.

Choosing one

  • Check the MTEB leaderboard on Hugging Face, but filter to your language and task — the overall ranking is a poor proxy for your corpus.
  • Dimensions are a real cost. 100 million chunks at 1536 float32 dims is roughly 600 GB before the index. Matryoshka truncation or int8 quantisation cuts that by 4× or more for a small recall loss.
  • Respect the input limit. Most embedding models cap at 512 tokens; text beyond that is silently truncated, which is a common and invisible cause of poor retrieval.
  • Use the asymmetric prefixes if the model was trained with them (query: / passage: for E5-family models). Omitting them measurably degrades results.
  • Changing model means re-embedding everything. Vector spaces are not compatible across models — not even across versions. Store the model ID with each vector so a migration is possible.

4.3  Vector Index Types

Advanced Deep dive →

Comparing a query against every stored vector is exact but linear — fine at 10,000 vectors, hopeless at 100 million. Approximate Nearest Neighbour indexes trade a little recall for orders of magnitude of speed. Understanding the trade-off is what makes you the person who can size the system rather than guess at it.

Types of ANN index

Flat (brute force)Compare against everythingNoneO(n)Vectors only< ~100k vectors, or 100% recall required

HNSW, since you will tune it

Picture a skip list generalised to a graph. The top layer holds few nodes with long-range links; each layer down is denser. A search enters at the top, greedily walks toward the query, then drops a layer and repeats — coarse to fine. Search cost is roughly logarithmic in the number of vectors.

m
Links per node. Higher = better recall, more memory. Typical 16–64
ef_construction
Candidate breadth while building. Higher = better graph, slower build. Typical 100–200
ef_search
Candidate breadth at query time. The runtime recall/latency dial. Typical 40–400

Product quantisation is the other idea worth holding: split a 1536-dim vector into 96 sub-vectors of 16 dims, cluster each sub-space into 256 centroids, and store one byte per sub-vector. The vector shrinks from 6 KB to 96 bytes — roughly 64× compression — at the cost of approximate distances, which is why PQ results are usually re-scored against the full vectors at the end.

Filtering is where ANN indexes get hard

"Find similar documents where tenant_id = 42 and date > 2025-01-01" is not a vector operation. Post-filtering searches then discards, and can return fewer than k results — or none. Pre-filtering restricts the candidate set first, but naive pre-filtering breaks graph connectivity and destroys recall. Good vector databases implement filtered search natively; ask specifically how yours does it, and test recall with your real filters applied. Multi-tenant systems fail here constantly.

SELECT id, content, 1 - (embedding <=> :q) AS similarity
FROM   doc_chunk
WHERE  tenant_id = :tenant

ORDER  BY embedding <=> :q          -- ORDER BY distance ASC uses the index
LIMIT  50;                          -- over-fetch, then re-rank to 5

4.5  The Ingestion Pipeline & Chunking

Core Deep dive →

This is an ETL job. You have built dozens of them; the only unfamiliar stage is chunking, and it is the stage that most determines quality.

Parsing

Getting clean text out of real documents is the unglamorous majority of the work. PDFs are the worst offenders — multi-column layouts interleave, tables collapse into noise, scanned pages contain no text at all. Options: Apache Tika (JVM-native, handles a thousand formats, integrates naturally with your stack), PyMuPDF or pdfplumber (Python, good layout handling), Unstructured.io (layout-aware, element-typed output), Docling (strong on tables and structure), and vision-model parsing (send the page image to a multimodal model — expensive, and by far the best on complex layouts). For scans you need OCR: Tesseract free, cloud OCR better.

Preserve structure while you still have it. Convert to Markdown rather than plain text so headings, lists and tables survive. Capture the page number, section heading and source URI as metadata during parsing — you cannot recover them later, and you need them for citations.

Types of chunking strategy

Chunks must be small enough to be precise and self-contained, large enough to carry meaning. Two failure modes: too small and context is lost mid-thought; too large and the embedding averages several topics into a vector that matches nothing well.

Then measure — build the evaluation set in §4.7 before you start tuning, or you will be changing parameters on the basis of anecdote.

JavaSpring AI — the ingestion ETL, end to end
@Service
class IngestionService {

    private final VectorStore vectorStore;

    void ingest(Resource pdf, long tenantId) {

        // 1. PARSE -- Tika handles PDF, DOCX, HTML, PPTX and more
        var reader = new TikaDocumentReader(pdf);
        List<Document> documents = reader.get();

        // 2. CHUNK -- token-aware, respects sentence boundaries
        var splitter = TokenTextSplitter.builder()
                .withChunkSize(700)
                .withMinChunkSizeChars(350)
                .withKeepSeparator(true)
                .build();
        List<Document> chunks = splitter.apply(documents);

        // 3. ENRICH -- metadata is what makes filtering and citation possible
        chunks.forEach(c -> c.getMetadata().putAll(Map.of(
                "tenant_id",  tenantId,
                "source",     pdf.getFilename(),
                "ingested_at", Instant.now().toString()
        )));

        // 4. EMBED + STORE -- the VectorStore does both
        vectorStore.add(chunks);
    }

    // 5. RETRIEVE -- over-fetch, filter by tenant, drop weak matches
    List<Document> retrieve(String query, long tenantId) {
        return vectorStore.similaritySearch(
                SearchRequest.builder()
                        .query(query)
                        .topK(50)
                        .similarityThreshold(0.6)
                        .filterExpression("tenant_id == " + tenantId)
                        .build());
    }
}

4.6  Advanced Retrieval

Advanced Deep dive →

Naive RAG — embed the query, take the top 5, stuff them in the prompt — works in a demo and disappoints in production. The techniques below are what close that gap, and they are the difference between "we tried RAG" and "our RAG works".

Hybrid search

Dense vectors are strong on meaning and weak on exact tokens: product codes, error numbers, surnames, rare acronyms. Keyword search (BM25) is the reverse. Running both and fusing the results beats either alone on nearly every real corpus.

Reciprocal Rank Fusion RRF(d)  =  Σr ∈ retrievers 1k + rankr(d) With k ≈ 60. It fuses by rank rather than score, which is the point: BM25 scores and cosine similarities are not on a comparable scale, so any weighted sum of raw scores needs calibration. RRF needs none, and is the sane default.

Query transformation — the types

The user's question is often a poor search query. Rewriting it before retrieval is cheap and disproportionately effective.

Re-ranking and selection

Retrieve broadly, then narrow precisely. Over-fetch 50–100 candidates cheaply, then apply an expensive, accurate stage to pick the final 3–8.

  • Cross-encoder re-ranker — scores each (query, document) pair jointly. Cohere Rerank, bge-reranker, mxbai-rerank. Typically the single largest quality win available, for roughly 50–200 ms.
  • LLM-as-reranker — ask a model to score relevance. Flexible and slow; useful when relevance is domain-specific.
  • ColBERT late interaction — token-level matching, close to cross-encoder quality at much lower cost.
  • MMR (Maximal Marginal Relevance) — balances relevance against novelty so you do not return five near-identical chunks. Tune λ between pure relevance and pure diversity.
  • Context assembly — order matters. Models attend most reliably to the beginning and end of a long context (the "lost in the middle" effect), so put the strongest evidence at both ends, deduplicate, and label each chunk with its source so citations are checkable.

5.1  Tool & Function Calling

Core Deep dive →

The mechanism is simpler than the vocabulary suggests, and it is worth being precise because the misunderstanding is common.

  1. You send the model a request plus a list of tool definitions — name, description, JSON Schema for parameters.
  2. Instead of prose, the model may return a tool call: a name and a JSON argument object.
  3. Your code executes the function. The model never runs anything.
  4. You append the result to the conversation and call the model again.
  5. It either answers, or calls another tool. Loop until it answers or you hit a limit.
The mental model

The model is not invoking your method. It is proposing a call, in JSON, which your code may accept, modify, or refuse. Every guarantee — authentication, authorisation, validation, rate limiting, auditing — must live in your Java, because the model's cooperation is a probability, not a contract. That framing prevents most agent security incidents.

Designing tools that work

  • Descriptions are prompts. The description is how the model decides whether to call the tool. Write it for a competent new colleague: what it does, when to use it, when not to, what it returns. This is the highest-leverage text in an agent.
  • Few, well-named tools beat many overlapping ones. Past roughly 20 tools, accuracy falls; group them or route between tool sets.
  • Constrain the schema. Enums instead of free strings, required fields marked, formats declared. Every constraint is one fewer invalid call.
  • Return errors as data. A structured {"error": "SKU not found", "hint": "list_skus first"} lets the model recover; a thrown exception ends the run.
  • Make writes idempotent. Models retry. Require a client-supplied idempotency key on anything that mutates state.
  • Keep results small. Every result re-enters the context on the next turn. Paginate, summarise, truncate — a tool returning 50,000 tokens will wreck both cost and reasoning.
  • Gate destructive actions behind explicit human confirmation. Reads can be automatic; refunds, deletions and emails should not be.
JavaThe agent loop, written out explicitly
// Frameworks hide this loop. Write it once by hand and you will
// understand every agent framework you meet afterwards.
String runAgent(String userGoal, int maxSteps) {

    var messages = new ArrayList<Message>();
    messages.add(new SystemMessage(SYSTEM_PROMPT));
    messages.add(new UserMessage(userGoal));

    for (int step = 0; step < maxSteps; step++) {

        ChatResponse response = chatModel.call(
                new Prompt(messages, toolCallingOptions));

        var output = response.getResult().getOutput();
        messages.add(output);

        if (!output.hasToolCalls()) {
            return output.getText();               // done
        }

        for (ToolCall call : output.getToolCalls()) {
            // AUTHORISE FIRST -- against the real user, in Java.
            if (!policy.permits(currentUser(), call.name(), call.arguments())) {
                messages.add(ToolResponse.error(call, "Not permitted"));
                continue;
            }
            try {
                Object result = registry.execute(call);
                messages.add(ToolResponse.of(call, truncate(result, 4_000)));
            } catch (Exception e) {
                // Errors go back as data so the model can recover.
                messages.add(ToolResponse.error(call, e.getMessage()));
            }
        }
    }
    throw new AgentBudgetExceededException(maxSteps);   // always bound the loop
}

Drift
Output-length and refusal-rate shifts after any model update

Deployment practice mirrors what you already do: version prompts as code with the model and parameters they were validated against; run the golden set in CI on every prompt change; canary new prompts or models on a traffic slice and compare online metrics; keep the previous version one config change away; and pin model versions, because a silent provider upgrade will change your outputs. Add semantic caching — serving a cached answer for a semantically equivalent question — where repeated queries are common; it can remove a large fraction of spend.

Four habits that decide whether this works

  1. Build in public from week one. A GitHub repository per project, with a README explaining the trade-offs you chose. This is your actual CV.
  2. Measure before you tune. Every phase has an evaluation component for a reason — it is the habit that separates engineers from demo-builders.
  3. Do not skip Phase 1. It is the shortest phase and the one that makes every later decision cheaper to reason about.
  4. Lead with what you already have. You are not a beginner. Distributed systems, data modelling, observability and security are exactly what AI teams are short of — you are adding a layer, not starting over.
