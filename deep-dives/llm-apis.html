9.1

LLM APIs & Model Selection

Working with models as a commodity you buy. This page maps the provider landscape, gives a real framework for choosing a model (capability, cost, latency, context, licence), covers the API mechanics that matter in production — streaming, rate limits, retries, caching, fallback — and shows how to stay provider-agnostic so a price change never rewrites your app.

Section 01 BeginnerStart from zero

Assumed knowledge

How a model generates text and what tokens are (Topic 1.3). This page is about consuming models through APIs, which is how most production AI is built.

You will spend far more time calling models than training them. A model is, for most engineering purposes, a metered utility: text in, text out, billed per token. The skill is choosing the right one and calling it robustly — not building it.

The provider landscape
KindExamplesTrade-off

Open-weight modelsLlama, Mistral, Qwen, Gemma, DeepSeekSelf-hostable; you run the infrastructure (Topic 9.2)

The commodity mindset

Models are commoditising fast: capabilities converge, prices fall, and the best model for a task changes every few months. Build so that which model you use is a configuration value, not an architectural commitment. The teams that hard-wire one provider's SDK throughout their code pay for it at every price change and every new release. Abstract the model behind your own interface and switching becomes a config edit plus a re-run of your evals.

The words, in plain English
Context window
Max tokens per request (prompt + output). Bigger costs more and can be slower.
Input / output tokens
Billed separately; output is usually several times more expensive.
Rate limit
Requests or tokens per minute the provider allows you.
Streaming
Receiving the answer token by token as it is generated.
Prompt caching
The provider reuses computation for a stable prompt prefix — cheaper, faster.
Structured output
Forcing the reply into a schema you specify (Topic 3.1).

Section 02 IntermediateChoosing a model — a real framework

"Use the best model" is not a strategy. Choose per task, on five axes:

The five axes of model selection
AxisQuestionHow to decide
CapabilityCan it do the task well enough?Test on your eval set (Topic 4.7), not a public benchmark
CostWhat does it cost at your volume?Estimate tokens/request × requests/day × price
LatencyFast enough for the use case?Measure TTFT and total; output length dominates (Topic 1.3)
ContextDoes your input fit?Match to your longest realistic prompt
Licence / residencyAre you allowed to use it this way?Data-handling terms; open-model licences; region
Route, don't standardise

The highest-leverage cost decision is usually model routing: send easy requests to a small cheap model and only the hard ones to a frontier model. A classifier or a rules check picks the tier (Topic 8.2). This routinely cuts cost by more than any prompt tweak, because most requests do not need the biggest model. Do not pay frontier prices for "reformat this JSON."

PythonCost estimation and tier routing
PRICING = {  # $ per million tokens (in, out) -- always verify current rates
    "small":    (0.25, 1.25),
    "mid":      (3.00, 15.00),
    "frontier": (15.00, 75.00),
}

def cost(tier, in_tokens, out_tokens):
    pi, po = PRICING[tier]
    return in_tokens / 1e6 * pi + out_tokens / 1e6 * po

# Route by difficulty -- a cheap gate, big savings.
def choose_tier(request):
    if is_simple(request):          # classification, formatting, extraction
        return "small"
    if needs_deep_reasoning(request):
        return "frontier"           # or a reasoning model (Topic 9.4)
    return "mid"

# Daily cost projection before you ship, not after the invoice.
daily = sum(cost(choose_tier(r), 1500, 400) for r in sample) * (total / len(sample))
print(f"projected: ${daily:,.2f}/day")

Section 03 AdvancedThe API mechanics that matter in production

PythonA robust model call — the things demos skip
import time, random
from anthropic import Anthropic, APIStatusError, RateLimitError

client = Anthropic()

def call(messages, model="claude-opus-4-8", max_retries=5, **kw):
    for attempt in range(max_retries):
        try:
            return client.messages.create(
                model=model, messages=messages, max_tokens=1024, **kw)
        except RateLimitError as e:
            # Respect Retry-After; add JITTER so retries do not sync up
            # and re-trigger the limit in lockstep (Topic 5.4).
            wait = float(e.response.headers.get("retry-after", 2 ** attempt))
            time.sleep(wait + random.random())
        except APIStatusError as e:
            if e.status_code >= 500 and attempt < max_retries - 1:
                time.sleep(2 ** attempt + random.random())   # transient
            else:
                raise
    raise RuntimeError("exhausted retries")

# --- STREAMING: total time is unchanged, perceived time drops -----
with client.messages.stream(model=model, messages=messages,
                            max_tokens=1024) as stream:
    for text in stream.text_stream:
        yield text                  # tokens to the UI as they arrive

# --- PROMPT CACHING: mark a stable prefix as cacheable ------------
# Put long, unchanging content (system prompt, documents) FIRST and
# cache it; variable user input goes last. Big cost + TTFT win.
system = [{"type": "text", "text": LONG_SYSTEM_PROMPT,
           "cache_control": {"type": "ephemeral"}}]
Production concerns and the fix
ConcernFix
Rate limits (429)Backoff with jitter; respect Retry-After; request a quota increase
Transient 5xx / timeoutsRetry with backoff; set a sane timeout
Provider outageCircuit breaker → fall back to another provider or a cheaper model (Topic 5.4)
Cost spikesToken caps per request/user; budget alerts; semantic cache
Slow responsesCap max_tokens; stream; route long jobs async (Topic 5.4)
Non-determinismPin the model version; set a seed if offered; tolerant tests (Topic 1.2)

Section 04 AdvancedStaying provider-agnostic

The practical way to keep "which model" a config value: put a thin interface between your app and any provider. Several tools give you this for free.

PythonOne interface, many providers
# Option A: a router library that speaks every provider's API.
# LiteLLM exposes one OpenAI-style call for 100+ models.
from litellm import completion
completion(model="anthropic/claude-opus-4-8", messages=msgs)
completion(model="openai/gpt-...",            messages=msgs)   # same call
completion(model="together_ai/meta-llama/...", messages=msgs)  # open model

# Option B: your own tiny interface, swapped by config.
class LLM:
    def complete(self, messages, **kw) -> str: ...

# Option C (Java): Spring AI's ChatModel is already this abstraction
# -- swap the starter dependency, keep the code (Topic 3.2).

# Whatever the mechanism: when you switch model, RE-RUN YOUR EVALS
# (Topic 4.7). Prompts are tuned per model family; a swap can
# change output length, format adherence and tool-call reliability.
Abstraction removes the mechanical cost of switching, not the evaluation cost

A router makes changing providers a one-line edit — but the model still behaves differently. Prompts tuned for one family can regress on another; structured-output and tool-calling reliability vary. Treat every model change as a deployment: run your golden set, diff the results, canary it (Topic 5.5). The abstraction buys you cheap experiments, which is exactly what lets you take advantage of a better or cheaper model when it appears.

Section 05 ProfessionalOperating model APIs

Pin versions
Explicit dated model IDs
Secrets
Keys in a vault, never in code
Timeouts
Generous — models are slow
Budgets
Per request, user and tenant
Caching
Prompt cache + semantic cache
Fallback
A second provider on outage

The build-vs-buy question in one line: use a hosted API until data residency, steady high volume, or a fine-tuned model pushes you to self-host (Topic 9.2) — and even then, keep the same interface so parts of your traffic can stay on an API. Most systems are best served by APIs for the frontier work and self-hosted small models for the high-volume, latency-sensitive, or private paths. It is rarely all-or-nothing.

Section 06 ProfessionalExercises

Do these — roughly an evening
  1. Run the same task on a small, a mid and a frontier model. Compare quality (on your eval set), cost and latency. Decide which the task actually needs.
  2. Implement tier routing with a cheap classifier. Measure the cost saving vs always using the frontier model.
  3. Add retry-with-jitter and confirm it survives a simulated 429 storm without re-triggering the limit.
  4. Enable prompt caching on a long stable prefix. Measure the cost and TTFT difference over 100 calls.
  5. Wrap two providers behind one interface (or use LiteLLM). Swap between them with a config change and re-run your evals.
  6. Add a circuit breaker that falls back to a second provider on outage. Simulate an outage and confirm the fallback.
  7. Project daily cost for a real workload before building it. Compare to actuals after.
