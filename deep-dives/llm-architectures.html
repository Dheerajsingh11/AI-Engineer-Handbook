Modern LLM Architectures: MoE & Beyond

How today's frontier models are actually built. This page goes past the vanilla transformer to the ideas that power modern LLMs — mixture-of-experts for scaling, the tricks that make long context affordable, and the state-space challengers to attention — so you understand what "sparse", "128k context" and "Mamba" mean.

Section 01 BeginnerStart from zero

Assumed knowledge

LLM Mechanics (Topic 1.3) — the transformer, attention and tokens. This page assumes you know the standard architecture and shows how the frontier departs from it.

The transformer you learned in Topic 1.3 is the foundation, but no frontier model in 2026 is a plain, dense transformer. They have all adopted a handful of architectural ideas to get bigger, faster and longer-context without the cost exploding. This page covers the three that matter most: mixture-of-experts, long-context techniques, and the state-space model challengers.

The problem all of these solve

The transformer has two scaling pains. First, making it smarter means adding parameters, and in a dense model every parameter runs for every token — cost grows with size. Second, attention compares every token with every other token, so cost grows with the square of the context length — long documents become brutally expensive. Mixture-of-experts attacks the first; long-context tricks and state-space models attack the second. Understanding them is understanding why modern models can be simultaneously huge, fast and able to read a whole book.

The words, in plain English
Dense model
Every parameter is used for every token. The standard transformer.
Sparse / MoE
Only a few "expert" sub-networks activate per token. Big brain, small bill.
Context window
How many tokens the model can attend to at once (4k, 128k, 1M+).
Quadratic cost
Attention's cost grows with the square of the sequence length.
State-space model (SSM)
An attention alternative (e.g. Mamba) that scales linearly with length.

Section 02 IntermediateMixture-of-Experts

Mixture-of-experts (MoE) is how models get enormous parameter counts without enormous inference cost. It is the architecture behind many of the strongest open and closed models.

The idea: replace the single feed-forward block in each transformer layer with many parallel "expert" blocks plus a small router that, for each token, picks the best few experts (often 2 of 8, or 8 of 256). Only the chosen experts run. So a model can hold, say, 8× the parameters — more knowledge, more capacity — while each token still only pays for a couple of them. You get the capacity of a huge model at the compute of a much smaller one. The distinction people quote is total parameters (all the experts, the model's knowledge) versus active parameters (the ones that run per token, the cost).

MoE layer — route, then combine y = ∑i ∈ TopK(x) gi(x) · Experti(x) The router scores every expert for token x, keeps the top k (say 2), and combines their outputs weighted by the router's gate values gi. The other experts are never evaluated — that is where the saving comes from.
Dense vs mixture-of-experts
DenseMixture-of-experts
Params used per tokenAll of themA small fraction (the top-k experts)
Knowledge capacity= its sizeMuch larger than its per-token cost
Inference speedSlower per parameterFast for the capacity
Memory to loadIts sizeAll experts must fit — big VRAM footprint
TrainingStraightforwardTrickier — must balance expert load
The MoE catch

MoE saves compute, not memory. Every expert must be loaded into VRAM even though only a few run per token, so an MoE with 8× the parameters needs roughly 8× the memory to host — it is fast but heavy. The other subtlety is load balancing: if the router sends most tokens to a few favourite experts, the rest are dead weight, so training adds an auxiliary loss to spread the load. Modern MoEs refine the routing further — a top-k router (2-of-8 in Mixtral, 8-of-256 in DeepSeek) plus a few always-on shared experts that absorb common patterns while the routed experts specialise. This is why MoE is a frontier-lab and serious-infra technique — it powers Mixtral, DeepSeek, and (reportedly) GPT-4 — not something you casually run on a laptop.

Section 03 IntermediateMaking context long

Early transformers handled 512–2,048 tokens; modern ones handle 128k, a million, sometimes more. Getting there meant beating attention's quadratic cost and teaching the model where tokens sit in a long sequence.

The long-context toolkit
TechniqueWhat it does
Rotary embeddings (RoPE)Encode position by rotating vectors — extends gracefully to longer sequences
Position interpolationRescale positions to stretch a model trained short to run long
YaRN & NTK-aware scalingSmarter RoPE frequency scaling — extends a model's context far beyond its training length with little fine-tuning (how 128k–1M+ windows are actually reached)
FlashAttentionCompute exact attention without storing the huge matrix — faster, less memory
Sparse / sliding-window attentionEach token attends to a local window, not everything — near-linear cost
Grouped-query attention (GQA)Share key/value heads to shrink the KV cache (Topic 1.3)
Long context is not free recall

A 1M-token window does not mean the model uses all million tokens equally. Models show a "lost in the middle" effect — they attend best to the start and end of a long context and can miss facts buried in the middle. And every extra token still costs money and latency and enlarges the KV cache. So a big context window is a capability, not a strategy: for large corpora, retrieval (RAG, Topic 4.1) is usually still cheaper and more reliable than stuffing everything into the prompt. The two are complements — retrieve the right chunks, then let a long window reason over them.

Section 04 AdvancedState-space models & the challengers

Attention's quadratic cost has motivated a search for alternatives that scale linearly with sequence length. The most prominent is the state-space model family, of which Mamba is the best known.

Where a transformer re-examines the entire history for every new token, a state-space model carries a compressed running state forward through the sequence — conceptually closer to an RNN (Topic 12.2), but designed so it can still be trained in parallel and does not forget the way old RNNs did. The payoff is linear scaling with length and fast, constant-memory generation, which is attractive for very long sequences (genomics, audio, long documents). The catch: on mainstream language tasks, pure SSMs have not clearly beaten a well-tuned transformer, and their recall of specific earlier tokens can be weaker. The pragmatic result in 2026 is hybrids — models that interleave SSM layers with a few attention layers to get linear scaling and sharp recall. Jamba (a Mamba–Transformer–MoE hybrid) is the best-known production example, pairing SSM efficiency with attention's precision at long context.

Transformer (attention)State-space (Mamba)

Section 05 ProfessionalWhy this matters to you

You will rarely implement these, but you constantly choose between models described by them, and the vocabulary is decision-relevant. "It is a mixture-of-experts" tells you it is cheap to run for its capability but heavy to self-host. "128k context" tells you what fits — and that you should still not trust the middle of it, and should measure whether RAG is cheaper. "Grouped-query attention" tells you the KV cache is smaller, so it serves long conversations more efficiently. "A Mamba hybrid" signals a bet on very long sequences. Reading a model card (Topic 9.1) fluently — total vs active parameters, context length, attention variant — is what lets you predict a model's cost and behaviour before you spend a week integrating it.

The through-line

Every idea here is the same move: spend compute only where it pays. MoE spends parameters only on the experts a token needs. FlashAttention and sparse attention spend memory only where attention is informative. SSMs spend a fixed state instead of an ever-growing one. As an engineer, that is your instinct too — and it connects directly to compression (Topic 18.3) and efficiency engineering (Topic 19.3), where you make the same trade at the systems level.

Section 06 ProfessionalExercises

Do these — a mix of reading and building
  1. Read the model cards of a dense model and an MoE of similar quality. Compare total vs active parameters and the memory each needs.
  2. Run a "needle in a haystack" test on a long-context model: hide a fact at different depths and measure recall. See "lost in the middle" for yourself.
  3. For a real corpus, estimate the cost of a 128k-context prompt vs a RAG pipeline retrieving 8 chunks. Decide which you would ship.
  4. Implement a toy MoE layer: a few expert MLPs plus a top-2 router. Watch the load-balancing problem appear without an auxiliary loss.
  5. Read the Mamba abstract and one hybrid model's card. Articulate, in two sentences, when you would reach for each.
  6. Explain to a teammate why MoE saves compute but not memory. If you can, you understand Section 02.
