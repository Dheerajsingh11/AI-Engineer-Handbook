Testing AI Applications in Java

Testing software whose output is non-deterministic. This page shows how to unit-test AI code by mocking the model, how to write assertions that tolerate variation without becoming meaningless, how to run a golden set in JUnit and CI, and how Testcontainers and WireMock give you a full RAG integration test.

Section 01 BeginnerStart from zero

Assumed knowledge

JUnit 5, Mockito and Spring Boot testing. Evaluation concepts from Topics 4.7 and 5.5 — this page is their Java-testing implementation.

Your instinct is assertEquals(expected, actual). It does not work here, because the same input produces different output every time. That does not mean AI code is untestable — it means you test different things, at different layers, with different assertions.

The testing pyramid for an AI application
LayerTestsModel involved?Runs
UnitYour logic: parsing, routing, tool execution, retryNo — mockedEvery commit, fast
ContractOutput shape: valid JSON, required fields, rangesYes, but assert structureCI, moderate
EvaluationQuality: golden-set pass rate, faithfulnessYesCI on AI changes, slow
IntegrationThe whole pipeline against real infrastructureReal or stubbedCI, slow
The reframing that makes it tractable

Most of your code is not the model. It is parsing, validation, routing, tool execution, retry logic, memory management, authorisation. All of that is ordinary deterministic Java, and you test it exactly as you always have — by mocking the model out. Only the thin layer that genuinely depends on model output needs the special treatment, and even there you test properties, not exact strings.

Section 02 IntermediateUnit-test everything around the model

JavaMock the model; test your logic deterministically
@ExtendWith(MockitoExtension.class)
class TriageServiceTest {

    @Mock  ChatModel chatModel;
    @Mock  VectorStore vectorStore;
    TriageService service;

    @BeforeEach
    void setup() {
        service = new TriageService(ChatClient.create(chatModel), vectorStore);
    }

    @Test
    void parsesModelResponseIntoRecord() {
        // Give the mock a FIXED response. Now the test is deterministic
        // and checks YOUR binding logic, not the model's behaviour.
        when(chatModel.call(any(Prompt.class))).thenReturn(chatResponse("""
            {"category":"TECHNICAL","severityOneToFive":4,
             "summary":"Login failing for all users","requiresHumanReview":true}
            """));

        var result = service.triage("Nobody can log in");

        assertThat(result.category()).isEqualTo(Category.TECHNICAL);
        assertThat(result.severityOneToFive()).isEqualTo(4);
        assertThat(result.requiresHumanReview()).isTrue();
    }

    @Test
    void retriesOnMalformedJson() {
        // First response is broken, second is valid. Assert the repair
        // loop (Topic 3.1) recovers -- no real model needed.
        when(chatModel.call(any(Prompt.class)))
            .thenReturn(chatResponse("not json at all"))
            .thenReturn(chatResponse("""
                {"category":"BILLING","severityOneToFive":2,
                 "summary":"Refund query","requiresHumanReview":false}"""));

        var result = service.triage("How do I get a refund?");

        assertThat(result.category()).isEqualTo(Category.BILLING);
        verify(chatModel, times(2)).call(any(Prompt.class));   // it retried
    }

    @Test
    void appliesTenantFilterOnRetrieval() {
        // Security-relevant logic is deterministic and MUST be tested.
        service.triageWithContext("issue", 42L);
        var captor = ArgumentCaptor.forClass(SearchRequest.class);
        verify(vectorStore).similaritySearch(captor.capture());
        assertThat(captor.getValue().getFilterExpression())
                .asString().contains("tenant_id == 42");
    }
}

Section 03 IntermediateContract tests: assert shape, not content

Contract tests do call the real model, but they assert properties that must hold for any valid answer — not a specific string. They catch the failures that matter operationally without being flaky.

JavaProperty assertions that tolerate variation
@SpringBootTest
@EnabledIfEnvironmentVariable(named = "RUN_AI_TESTS", matches = "true")
class TriageContractTest {

    @Autowired TriageService service;

    @Test
    void outputAlwaysSatisfiesTheContract() {
        var result = service.triage("The checkout page returns a 500 error");

        // Structural guarantees -- true for every valid response.
        assertThat(result).isNotNull();
        assertThat(result.category()).isNotNull();
        assertThat(result.severityOneToFive()).isBetween(1, 5);
        assertThat(result.summary()).isNotBlank().hasSizeLessThan(200);
    }

    @Test
    void refusesWhenContextIsEmpty() {
        // A BEHAVIOURAL property: given no relevant context, the system
        // must decline rather than confabulate. Assert the property,
        // not the wording.
        var answer = service.answer("What is the capital of Atlantis?", emptyTenant);
        assertThat(answer.grounded()).isFalse();
        assertThat(answer.citations()).isEmpty();
    }

    @RepeatedTest(5)
    void isStableAcrossRuns() {
        // For a classification that SHOULD be stable, run several times
        // and require agreement -- catching prompts that are too
        // sensitive to sampling noise.
        var category = service.triage("URGENT: production database is down").category();
        assertThat(category).isEqualTo(Category.TECHNICAL);
    }
}
The two ways contract tests go wrong

Too strict — asserting exact strings. The test flakes on ordinary sampling variation, the team adds @Disabled, and you have no coverage. Too loose — asserting only "not null". The test passes while the output is useless.

The middle ground is to assert on invariants: valid schema, values in range, required behaviours (grounding, refusal, citation), and stability where stability is genuinely expected. Set temperature to 0 for these tests to reduce — though not eliminate — variation, and gate them behind an environment flag so they do not run on every local build and consume tokens.

Section 04 AdvancedGolden-set evaluation in CI

JavaThe golden set as a parameterised test, with statistics
@SpringBootTest
@EnabledIfEnvironmentVariable(named = "RUN_EVALS", matches = "true")
class RagEvaluationTest {

    @Autowired RagService rag;

    static List<GoldenCase> goldenSet() throws IOException {
        // Versioned with the code; grown from production failures (5.5).
        return MAPPER.readValue(
                new ClassPathResource("evals/rag-golden.jsonl").getInputStream(),
                new TypeReference<List<GoldenCase>>() {});
    }

    // RETRIEVAL: fix this first -- generation cannot recover a miss.
    @Test
    void retrievalRecallMeetsThreshold() throws IOException {
        var cases = goldenSet();
        double recallSum = cases.stream().mapToDouble(c -> {
            var ids = rag.retrieve(c.question(), 20).stream()
                         .map(Chunk::id).toList();
            return recallAt(ids, c.relevantChunkIds(), 20);
        }).sum();

        double recall = recallSum / cases.size();
        assertThat(recall)
                .as("recall@20 across %d cases", cases.size())
                .isGreaterThan(0.85);
    }

    // GENERATION: pass rate with a confidence interval, so a couple
    // of unlucky samples do not fail the build (Topic 5.5).
    @Test
    void answerQualityMeetsBaseline() throws IOException {
        var cases = goldenSet();
        long passed = cases.stream().filter(c -> {
            var answer = rag.answer(c.question(), c.tenantId());
            return judge.faithful(answer, c.groundTruth())
                && judge.relevant(answer, c.question());
        }).count();

        double rate = (double) passed / cases.size();
        double se = Math.sqrt(rate * (1 - rate) / cases.size());
        double lowerBound = rate - 1.96 * se;

        assertThat(lowerBound)
                .as("faithful+relevant pass rate %.3f (95%% lower bound %.3f)",
                    rate, lowerBound)
                .isGreaterThan(0.80);
    }

    // SECURITY cases live in the same suite (Topic 5.6).
    @ParameterizedTest
    @MethodSource("injectionCases")
    void resistsInjection(String attack) {
        var answer = rag.answer(attack, testTenant);
        assertThat(answer.text()).doesNotContain(SYSTEM_PROMPT_MARKER);
    }
}
YAMLWiring evals into the pipeline
# A separate CI stage: unit and contract tests gate every PR;
# the eval suite runs on changes to prompts, retrieval or models,
# and nightly. Keeping it separate stops slow, token-costing tests
# from blocking ordinary commits.
jobs:
  unit:
    steps:
      - run: ./mvnw test          # fast, no model, every PR

  evaluate:
    if: contains(github.event.head_commit.modified, 'prompts/')
        || github.event_name == 'schedule'
    env:
      RUN_EVALS: "true"
      ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
    steps:
      - run: ./mvnw test -Dtest=RagEvaluationTest
      - run: ./scripts/post-eval-report.sh    # comment results on the PR

Section 05 AdvancedIntegration tests with real infrastructure

Testcontainers gives you a real Postgres with pgvector; WireMock gives you a deterministic stand-in for the model API. Together they test the whole pipeline without flakiness and without spending tokens.

JavaFull RAG pipeline against real pgvector, stubbed model
@SpringBootTest
@Testcontainers
class RagPipelineIntegrationTest {

    @Container
    static PostgreSQLContainer<?> postgres =
        new PostgreSQLContainer<>("pgvector/pgvector:pg16")
            .withDatabaseName("rag");

    // WireMock stands in for the model API: deterministic responses,
    // zero tokens, and you can simulate rate limits and timeouts.
    static WireMockServer wireMock = new WireMockServer(options().dynamicPort());

    @DynamicPropertySource
    static void props(DynamicPropertyRegistry registry) {
        registry.add("spring.datasource.url", postgres::getJdbcUrl);
        registry.add("spring.ai.anthropic.base-url",
                     () -> "http://localhost:" + wireMock.port());
    }

    @Test
    void ingestRetrieveAnswerEndToEnd() {
        stubEmbeddings();
        stubChatResponse("The refund window is 30 days.");

        ingestionService.ingest(policyDocument(), TENANT, "policy-1");

        var answer = ragService.answer("How long do I have to get a refund?", TENANT);

        assertThat(answer.text()).contains("30 days");
        assertThat(answer.citations()).isNotEmpty();
    }

    @Test
    void enforcesTenantIsolationAtTheDatabase() {
        stubEmbeddings();
        ingestionService.ingest(secretDoc(), TENANT_A, "secret");

        var chunks = ragService.retrieve("secret information", TENANT_B);

        // A real database, a real query -- the isolation is genuinely
        // exercised, not mocked away.
        assertThat(chunks).isEmpty();
    }

    @Test
    void retriesOnRateLimitThenSucceeds() {
        // WireMock returns 429 twice, then 200 -- proving the resilience
        // layer (Topic 5.4) works against a real HTTP client.
        wireMock.stubFor(post("/v1/messages")
            .inScenario("rate-limit").whenScenarioStateIs(STARTED)
            .willReturn(aResponse().withStatus(429).withHeader("retry-after", "1"))
            .willSetStateTo("second"));
        // ... second attempt also 429, third succeeds ...

        var answer = ragService.answer("test", TENANT);
        assertThat(answer).isNotNull();
        wireMock.verify(3, postRequestedFor(urlEqualTo("/v1/messages")));
    }
}

Section 06 ProfessionalPerformance and load

What to benchmark, and what not to

Do not microbenchmark the model call — its latency is dominated by the provider and swamps anything JMH measures. Do benchmark your surrounding code: chunking throughput, embedding-batch assembly, vector-search latency against a loaded pgvector, RRF and re-ranking over realistic candidate sets, and context assembly. These are deterministic, CPU-bound, and genuinely yours to optimise.

For end-to-end load, use Gatling or k6 against a WireMock-stubbed model so you exercise your concurrency, connection pooling and backpressure (Topic 5.4) without a five-figure token bill. Test the real model separately, at low volume, to characterise latency distribution — then model that distribution in the load test.

Section 07 ProfessionalExercises

Do these — roughly a weekend
  1. Unit-test a service that parses model output, mocking ChatModel. Test the happy path and the malformed-JSON repair path with no real calls.
  2. Write a contract test that asserts schema validity and value ranges but never an exact string. Run it ten times and confirm it does not flake.
  3. Add a @RepeatedTest stability check for a classification that should be deterministic. Find a prompt where it fails and tighten it.
  4. Build a 30-case golden set as a JUnit resource and a parameterised test. Fail the build on a confidence-interval-adjusted threshold.
  5. Add injection cases to the same suite and confirm they fail if you weaken a guardrail.
  6. Write a Testcontainers integration test with real pgvector. Prove tenant isolation against an actual database query.
  7. Stub the model with WireMock and test that your retry logic handles 429-then-200 correctly.
  8. Split CI so unit tests gate every PR while evals run only on prompt changes and nightly. Have the eval job comment results on the PR.
