Memory & Context Engineering

Models are stateless; memory is your problem. This page implements every memory type from message windows to episodic recall, treats the context window as a resource to be managed rather than filled, and covers the compaction, offloading and sub-agent techniques that keep long-running agents coherent.

Section 01 BeginnerStart from zero

Assumed knowledge

How context windows work (Topic 1.3) and the agent loop (Topic 5.1).

A model has no memory between calls. None. Every request is processed as if it were the first thing the model has ever seen.

The illusion of a conversation exists because your application resends the entire history every time. Turn five of a chat sends turns one through four plus the new message. The model appears to remember; in fact you remembered on its behalf.

Two consequences that follow immediately
  • Cost grows quadratically with conversation length. Turn 1 sends 100 tokens, turn 20 sends 4,000. Across a 20-turn conversation you have paid for roughly 40,000 input tokens, not 4,000. Prompt caching mitigates this substantially, and only if your prefix is stable.
  • Conversations have a hard ceiling. Eventually the history exceeds the context window and the request fails outright. "Memory management" is really context budget management, and every technique below is a way of spending that budget better.
The words, in plain English
Short-term memory
The current conversation. Lives in the context window.
Long-term memory
Anything that survives across sessions. Lives in your database.
Working memory / scratchpad
Notes the agent keeps while solving one task.
Compaction
Summarising older turns to free context, keeping decisions verbatim.
Offloading
Writing a large result to storage and keeping only a reference in context.
Context engineering
Deciding what occupies the window at each step. The discipline this page is about.

JavaToken-aware summary-plus-buffer memory
public class SummaryBufferMemory implements ChatMemory {

    private final TokenCountEstimator tokens;
    private final ChatModel summariser;
    private final int maxTokens;
    private final int keepRecentTurns;
    private final MemoryStore store;

    @Override
    public List<Message> get(String conversationId) {
        var state = store.load(conversationId);
        var messages = new ArrayList<Message>();
        if (state.summary() != null) {
            messages.add(new SystemMessage(
                "Summary of earlier conversation:\n" + state.summary()));
        }
        messages.addAll(state.recent());
        return messages;
    }

    @Override
    public void add(String conversationId, Message message) {
        var state = store.load(conversationId);
        state.recent().add(message);

        if (countTokens(state) <= maxTokens) {
            store.save(conversationId, state);
            return;
        }

        // Over budget: fold the oldest turns into the summary.
        // Keep the most recent verbatim -- they carry the immediate
        // context the model needs to answer the next message.
        int cut = Math.max(0, state.recent().size() - keepRecentTurns);
        var toFold = new ArrayList<>(state.recent().subList(0, cut));
        state.recent().subList(0, cut).clear();

        state.setSummary(summariser.call(new Prompt("""
            Update the running summary with these new exchanges.

            PRESERVE VERBATIM: decisions made, commitments given,
            identifiers mentioned, unresolved questions, user preferences.
            COMPRESS: pleasantries, restatements, exploratory discussion.

            Existing summary:
            %s

            New exchanges:
            %s
            """.formatted(state.summary(), render(toFold)))).getResult()
              .getOutput().getText());

        store.save(conversationId, state);
    }
}
What summarisation quietly destroys

A naive summariser writes "the user asked about their order and we discussed shipping options" — and the order number is gone. So is the discount the agent promised, and the fact that the customer said they were travelling next week.

Instruct the summariser explicitly about what must survive verbatim: identifiers, numbers, decisions, commitments, open questions and stated preferences. Better still, extract those into structured fields before summarising, so they are stored as data rather than trusted to prose. Prose summaries lose exactly the details that later turns need.

Section 03 AdvancedLong-term memory

Long-term memory is RAG pointed at your own conversation history rather than at documents. The retrieval machinery from Phase 4 applies unchanged; what is new is deciding what is worth remembering.

JavaEpisodic and semantic memory
@Service
class LongTermMemory {

    private final VectorStore episodes;
    private final UserFactRepository facts;
    private final ChatClient extractor;

    // ---------- EPISODIC: what happened, searchable ---------------
    public void recordEpisode(String userId, Conversation conversation) {
        // Store a summary, not the transcript. A verbatim transcript
        // retrieves poorly (too much filler) and costs too much context.
        String summary = extractor.prompt()
                .user("Summarise what was discussed and decided:\n" + conversation)
                .call().content();

        episodes.add(List.of(new Document(summary, Map.of(
                "user_id", userId,
                "conversation_id", conversation.id(),
                "occurred_at", conversation.endedAt().toString()))));
    }

    public List<String> recallRelevant(String userId, String query, int k) {
        return episodes.similaritySearch(SearchRequest.builder()
                    .query(query).topK(k).similarityThreshold(0.7)
                    .filterExpression("user_id == '" + userId + "'")  // isolation
                    .build())
                .stream().map(Document::getText).toList();
    }

    // ---------- SEMANTIC: durable facts, structured --------------
    public void extractFacts(String userId, Conversation conversation) {
        FactExtraction extracted = extractor.prompt()
                .system("""
                    Extract durable facts about the user worth remembering
                    for future conversations: stated preferences, constraints,
                    role, recurring needs.

                    Do NOT extract: transient state, one-off requests,
                    anything the user asked you to forget, or sensitive
                    personal data not needed for service.
                    """)
                .user(conversation.toString())
                .call().entity(FactExtraction.class);

        for (Fact fact : extracted.facts()) {
            // UPSERT with conflict resolution. Without this, contradictory
            // facts accumulate ("prefers email" and "prefers phone") and
            // the model gets confused rather than informed.
            facts.upsert(userId, fact.key(), fact.value(),
                         fact.confidence(), Instant.now());
        }
    }

    public String buildProfile(String userId) {
        return facts.findByUserId(userId).stream()
                .filter(f -> f.confidence() > 0.7)
                .sorted(comparing(UserFact::updatedAt).reversed())
                .limit(20)                         // bound it: this is context
                .map(f -> "- " + f.key() + ": " + f.value())
                .collect(joining("\n"));
    }
}
Memory is personal data

Long-term memory means storing what users told you, indefinitely, in a form that influences future behaviour. That has consequences your legal team will care about: right to erasure means deleting facts and the vectors derived from them; users should be able to see and correct what has been remembered; and sensitive categories should not be extracted at all. Build the delete path, the inspect path and a category exclusion list from the start — retrofitting them into a vector store is unpleasant. This connects directly to §6.4.

Section 04 AdvancedContext engineering

The context window is a working set, not a container. Filling it is not the goal — the goal is that at every step it holds precisely what the model needs and nothing else.

The analogies are not decorative

Compaction is paging. Offloading is spilling to disk. Sub-agents are process isolation. Retrieval over history is indexing. These are the same problems as memory management in an operating system, and the same solutions apply — which means your instincts as a systems engineer transfer directly.

The four techniques
TechniqueMechanismUse when
CompactionSummarise older turns; keep decisions verbatimLong conversations approaching the limit
OffloadingWrite large results to storage; keep a referenceTool results are big and only occasionally needed
Sub-agentsDelegate to a fresh context; return only a summaryA subtask needs to read a great deal
Retrieval over historySearch past turns instead of replaying themVery long-running sessions
JavaOffloading, and a context budget you can enforce
// ---------- OFFLOADING ------------------------------------------
// A tool returning 200 rows costs context on EVERY subsequent turn.
// Write it out; hand back a handle and a preview.
@Tool(description = """
    Run an analytical query. Full results are written to a file;
    you receive a preview and a handle. Use read_result_page to
    read more if the preview is insufficient.
    """)
public QueryHandle runQuery(@ToolParam(description = "SQL") String sql) {
    var rows = warehouse.query(sql);
    var handle = artifacts.store(rows);          // S3, or a temp table

    return new QueryHandle(
            handle.id(),
            rows.size(),
            rows.stream().limit(5).toList(),     // preview only
            "Showing 5 of " + rows.size() + " rows. "
          + "Use read_result_page(handle, page) for more.");
}

// ---------- CONTEXT BUDGET --------------------------------------
public List<Message> assembleContext(AgentState state, int budget) {
    var messages = new ArrayList<Message>();
    int used = 0;

    // Fixed allocations, highest priority first. What does not fit
    // is dropped deliberately rather than truncated arbitrarily.
    used += add(messages, state.systemPrompt(),          budget);        // always
    used += add(messages, state.userProfile(),  (int)(budget * 0.05));   // 5%
    used += add(messages, state.goal(),                  budget);        // always
    used += add(messages, state.retrieved(),   (int)(budget * 0.35));    // 35%
    used += add(messages, state.recentTurns(), (int)(budget * 0.40));    // 40%
    used += add(messages, state.scratchpad(),  (int)(budget * 0.10));    // 10%

    // Reserve headroom for the answer itself. Running out mid-
    // generation is a common and avoidable production failure.
    if (used > budget - MIN_OUTPUT_TOKENS) {
        state.compact();
        return assembleContext(state, budget);
    }
    return messages;
}
Context rot

Long contexts degrade quality even when they fit. The "lost in the middle" effect means information in the centre is attended to less reliably; contradictory information from different turns confuses rather than informs; and stale tool results the model treats as current cause real errors.

A shorter, cleaner context often outperforms a longer, complete one. Actively prune: remove superseded tool results, drop retrieved chunks that turned out to be irrelevant, and delete resolved sub-tasks. This is the counterintuitive part — the instinct is to give the model everything, and it is usually wrong.

Section 06 ProfessionalExercises

Do these — roughly a weekend
  1. Instrument a 20-turn conversation and plot cumulative input tokens per turn. See the quadratic growth for yourself.
  2. Enable prompt caching and repeat. Measure the difference — then reorder the prompt so the volatile part is last and measure again.
  3. Implement message-window memory. Find a conversation where the window cuts mid-topic and the model loses the thread.
  4. Implement summary-plus-buffer. Mention an order number early, converse for 20 turns, then ask about it. Check whether the summariser preserved it.
  5. Add explicit "preserve verbatim" instructions and repeat. Measure how often key details survive.
  6. Build episodic memory over past conversations. Ask "what did we decide about X last week?" and check the retrieval.
  7. Implement offloading for a tool returning 500 rows. Compare total token consumption across a 10-step run with and without it.
  8. Implement the context budget with priority allocation. Force an overflow and confirm it compacts rather than failing.
  9. Implement full deletion for a user — facts, episodes and vectors — and write a test that proves nothing remains.
