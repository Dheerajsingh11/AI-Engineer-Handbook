MLOps Tooling

The tools that make ML reproducible. This page covers experiment tracking, model registries, pipelines and data/model versioning — MLflow, Weights & Biases, DVC and the rest — explains the MLOps lifecycle they support, and maps where classic MLOps overlaps with the LLMOps you already met and where it differs.

Section 01 BeginnerStart from zero

Assumed knowledge

The ML workflow (Topic 2.3), fine-tuning (Topic 3.5) and LLMOps (Topic 5.5). This page is the tooling that makes that work reproducible and operable.

Train a model in a notebook and you have a result nobody can reproduce: which data, which hyperparameters, which code version produced it? MLOps is the discipline — and this page is the tooling — that turns ad-hoc model building into an engineering process: tracked, versioned, reproducible, deployable.

The four jobs MLOps tooling does
JobAnswersTools
Experiment trackingWhat did I try, and how did each do?MLflow, Weights & Biases
Model registryWhich model is in production, and how was it made?MLflow Registry, W&B, SageMaker
Data / model versioningExactly which data and artefacts produced this?DVC, LakeFS, Git-LFS
Pipelines / orchestrationHow do I re-run the whole training flow reliably?Kubeflow, Airflow, Metaflow, ZenML
The core problem: reproducibility

Everything MLOps tooling does serves one goal — any model you have should be reproducible: you can say exactly which code, data, and configuration produced it, and re-create it. Without that, you cannot debug a regression, satisfy an auditor, or safely roll back. Experiment tracking records the "what and how well"; the registry records "what is live"; versioning pins the data and artefacts; pipelines make the whole thing repeatable. Reproducibility is not bureaucracy — it is the difference between engineering and guessing.

Section 02 IntermediateExperiment tracking

The most immediately useful tool. Instead of results scattered across notebook cells and memory, every run is logged: parameters, metrics, artefacts, code version — searchable and comparable.

PythonTracking a run with MLflow
import mlflow

mlflow.set_experiment("support-classifier")

with mlflow.start_run():
    # WHAT you tried
    mlflow.log_params({"model": "bge-small", "lr": 2e-4,
                       "epochs": 3, "chunk_size": 700})

    model = train(...)

    # HOW WELL it did (Topics 1.2, 4.7)
    mlflow.log_metrics({"f1": 0.87, "recall_at_5": 0.91,
                        "cost_usd": 4.20})

    # The ARTEFACT itself, versioned and retrievable
    mlflow.log_artifact("./adapter")
    mlflow.log_artifact("evals/golden.jsonl")   # pin the eval set too

# Now every run is comparable in the UI: sort by f1, see which
# hyperparameters produced it, reproduce the best. No more
# "which notebook had the good result?"

Section 03 AdvancedRegistry, versioning and pipelines

Tracking captures experiments; the rest of MLOps captures the lifecycle.

PythonA model registry with stages
from mlflow import MlflowClient
client = MlflowClient()

# Register a run's model, then promote it through stages -- the same
# canary/rollback discipline as prompts in LLMOps (Topic 5.5).
mv = mlflow.register_model("runs:/<run_id>/model", "support-classifier")
client.transition_model_version_stage(
    "support-classifier", mv.version, stage="Staging")
# ... after it passes evaluation in staging ...
client.transition_model_version_stage(
    "support-classifier", mv.version, stage="Production")

# The registry answers, at any moment: what is live, which version,
# from which run, from which data. That is your rollback path.
Data/model versioning and pipelines
NeedToolIdea
Version large data & models with gitDVCGit tracks pointers; data lives in object storage
Version a data lakeLakeFSGit-like branches/commits over your lake
Orchestrate the training flowKubeflow / Airflow / Metaflow / ZenMLA DAG of steps: data → train → eval → register
Feature reuse & consistencyFeast (feature store)Same features in training and serving
Data leakage hides in un-versioned data

A subtle reproducibility failure: your model looked great, you retrain a month later on "the same" data, and it is worse — because the data changed underneath you and nobody recorded which snapshot the good model used. Data versioning (DVC, LakeFS) pins the exact dataset to each model, which is also how you catch the leakage failures from Topic 2.3 after the fact. Version your data with the same seriousness as your code; "the data" is not a stable thing unless you make it one.

Section 04 ProfessionalMLOps vs LLMOps — overlap and difference

You met LLMOps in Topic 5.5. Classic MLOps and LLMOps share most of their DNA but diverge on a few axes worth being precise about.

Where they align and differ
Classic MLOpsLLMOps (Topic 5.5)
Core artefactA model you trainedOften a prompt + a model you call
Versioning targetModel weights, data, featuresPrompts, model versions, retrieval config
EvaluationMetrics vs a labelled test setGraded / statistical; LLM-as-judge (Topic 4.7)
Retraining triggerData drift, performance decayRarely retrain; iterate prompts / RAG
Cost modelTraining compute, then cheap inferencePer-token inference — ongoing (Topic 9.1)
SharedTracking, versioning, registries, pipelines, monitoring, CI/CD, reproducibility — all apply to both
Which do you need?

If your work is mostly calling models with prompts and RAG (the common enterprise case), LLMOps (Topic 5.5) is your day-to-day — prompt versioning, eval suites, tracing, cost monitoring — and you will touch classic MLOps tooling mainly when you fine-tune (Topic 3.5) or train a classifier (Topic 2.3), where experiment tracking and a registry become essential. Learn experiment tracking (it is an afternoon and immediately useful the first time you fine-tune anything), understand what a registry and data versioning give you, and reach for the heavier pipeline orchestrators only when you have a real recurring training flow to automate.

Section 05 ProfessionalExercises

Do these — roughly an evening
  1. Add MLflow tracking to a fine-tuning run (Topic 3.5). Log params, metrics and the adapter. Compare three runs in the UI.
  2. Register your best model and promote it through Staging → Production. Then roll back to the previous version.
  3. Version a dataset with DVC. Change the data, commit, and confirm you can restore the exact earlier snapshot a model used.
  4. Reproduce a model from a tracked run using only what you logged. If you cannot, note what was missing — that gap is the lesson.
  5. Sketch a training pipeline (data → train → eval → register) as a DAG. Implement it in ZenML or Airflow if you have time.
  6. Write a one-paragraph comparison of what you would version for a fine-tuned model vs a prompt-and-RAG system.
