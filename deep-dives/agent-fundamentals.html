Section 01 BeginnerStart from zero

Assumed knowledge

How a model generates text (Topic 1.3) and the basic idea of tool calling (Topic 5.1). This page is the doorway to the whole Agent Engineering module (Topics 8.2–8.10).

"Agent" is the most over-used word in AI. Strip the marketing and it means something precise and simple: an LLM in a loop, with tools and a goal, that decides its own next step. That is the whole definition. Everything else is detail.

The loop

Every agent, from a toy to a frontier research system, runs the same four-beat cycle:

  1. Perceive — read the current situation: the goal, the conversation, the result of the last action.
  2. Plan — the model decides what to do next. Answer directly, or call a tool.
  3. Act — your code executes the chosen tool. The model never acts itself; it proposes (Topic 5.1).
  4. Observe — feed the result back in, and loop — until the goal is met or a limit is hit.
The single distinction that matters

What makes something an agent rather than a workflow is who decides the control flow. In a workflow, you wrote the steps; the model fills in blanks at fixed points. In an agent, the model decides the steps at runtime — how many, in what order, when to stop.

That autonomy is powerful and expensive: it buys flexibility and costs predictability, testability and money. The entire discipline of agent engineering is spending that autonomy only where it earns its keep.

The words, in plain English
Agent
An LLM that runs in a loop, using tools to pursue a goal, choosing its own steps.
Tool
A function the agent can call to sense or affect the world (Topic 8.4 catalogues the types).
Trajectory
The full sequence of steps an agent took on one task. What you inspect to debug it.
Autonomy
How much the agent decides for itself vs how much you scripted.
Orchestration
How steps and sub-agents are coordinated (Topic 8.2).
Termination
The condition that ends the loop — goal met, step limit, budget exhausted.
Scaffolding
The code around the model: the loop, tools, memory, guardrails. Most of an agent's quality lives here, not in the model.

Section 02 BeginnerWhat is not an agent

Clearing this up early saves you from building the wrong thing.

The spectrum, least to most autonomous
ThingWho decides the stepsAgent?
A single prompt callYou (one step)No
A chatbotYou (reply to each message)No
A prompt chain / workflowYou (fixed sequence)No
RAG pipelineYou (retrieve → generate)No
Tool-calling in a fixed loop you wroteMostly youBorderline
Model chooses which tools, how many, when to stopThe modelYes
The honest test for "do I need an agent?"

Ask: can I write down the steps in advance? If yes, build a workflow — it will be cheaper, faster, testable and more reliable (Topic 5.2). Only when the steps genuinely cannot be known ahead of time — the task branches unpredictably on what it discovers — does an agent earn its cost. "It would be cool" and "we might need flexibility later" are not reasons. Most things labelled agents in production should have been workflows.

Section 03 IntermediateThe anatomy of an agent

An agent is not just a model. It is a model surrounded by scaffolding, and the scaffolding is where you spend your engineering effort. Six parts:

The six components, and where each is covered
ComponentRoleDeep dive
ModelThe reasoning engine that plans each stepTopic 1.3
ToolsHow it senses and acts on the worldTopic 8.4
The loop / orchestrationHow steps are sequenced and coordinatedTopic 8.2
MemoryWhat it remembers within and across tasksTopic 5.3
Hooks / guardrailsValidation, auth, logging around each actionTopic 8.6
SkillsPackaged, loadable capabilitiesTopic 8.5
The counterintuitive truth

The model matters less than the scaffolding. Two teams with the same model produce wildly different agents, because the difference is in tool design, context management, the loop, and the guardrails. This is good news: agent quality is an engineering problem you control, not a model capability you wait for. A well-scaffolded agent on a mid-tier model beats a naked prompt on the best model.

Section 04 AdvancedThe smallest real agent

Before any framework, the whole thing in plain Python. This is the backbone every later page in the module extends.

PythonAn agent in ~40 lines, no framework
import json
from anthropic import Anthropic

client = Anthropic()

# --- tools: name, description (a prompt!), and the real function --
def get_weather(city: str) -> str:
    return f'{{"city": "{city}", "temp_c": 18, "sky": "cloudy"}}'

TOOLS = [{
    "name": "get_weather",
    "description": "Current weather for a city. Use when asked about weather.",
    "input_schema": {"type": "object",
        "properties": {"city": {"type": "string"}}, "required": ["city"]},
}]
IMPL = {"get_weather": get_weather}

def run_agent(goal: str, max_steps: int = 6) -> str:
    messages = [{"role": "user", "content": goal}]

    for step in range(max_steps):                 # ALWAYS bound the loop
        response = client.messages.create(
            model="claude-opus-4-8", max_tokens=1024,
            tools=TOOLS, messages=messages)

        # PERCEIVE + PLAN happened inside the model. Record its turn.
        messages.append({"role": "assistant", "content": response.content})

        if response.stop_reason != "tool_use":
            # It answered -- terminate.
            return "".join(b.text for b in response.content if b.type == "text")

        # ACT: run every requested tool.
        results = []
        for block in response.content:
            if block.type == "tool_use":
                # AUTHORISE HERE in real code (Topic 5.6 / 8.6).
                output = IMPL[block.name](**block.input)
                results.append({"type": "tool_result",
                                "tool_use_id": block.id, "content": output})

        # OBSERVE: feed results back and loop.
        messages.append({"role": "user", "content": results})

    raise RuntimeError("step limit reached")       # termination guard

print(run_agent("Should I take an umbrella in Oslo today?"))
# The model calls get_weather("Oslo"), reads "cloudy", answers.

Read the four beats in that code: the model call is perceive + plan, the if tool_use branch is act, appending results is observe, and the for loop closes the cycle. Every framework in this module — LangGraph, CrewAI, the Anthropic and OpenAI agent SDKs — is a more ergonomic wrapper around exactly this. Write it once by hand and none of them will ever be mysterious.

Section 05 ProfessionalHow agents fail, and what to build in from the start

Failure modes — design against these on day one
FailureWhy it happensBuilt-in defence
Infinite loopNo progress, keeps tryingStep limit + loop detection (Topic 8.2)
Cost explosionLong trajectories, big tool resultsToken budget per run; bounded results (Topic 5.1)
Goal driftLoses the thread over many stepsRestate the goal each turn; verify output against it
Unsafe actionExecutes something destructiveHuman gate + authorisation hooks (Topics 8.6, 5.6)
Context exhaustionHistory outgrows the windowCompaction, offloading (Topic 5.3)
Silent wrong answerConfident but incorrectVerification tools, citations, eval (Topic 8.10)
The four limits every agent must have

Before an agent touches production, it needs hard ceilings on: steps (max loop iterations), tokens (total budget per run), time (wall-clock timeout), and cost (dollar cap). Hitting any of them should be an alert, not just a silent failure — it almost always signals an input class you did not anticipate. An agent without these limits is an unbounded liability, financially and operationally.

Section 07 ProfessionalExercises

Do these — roughly an evening
  1. Type in the 40-line agent. Add a second tool and watch the model choose between them.
  2. Give it a goal it cannot achieve with its tools. Watch it hit the step limit — confirm your termination guard fires.
  3. Print the full messages trajectory after a run. Identify each of the four beats in the transcript.
  4. Take three things you were going to build as "agents" and honestly classify each with the Section 02 test. How many are really workflows?
  5. Add a token counter and a hard budget. Trigger it deliberately and confirm the run stops.
  6. Remove the step limit and give it a looping task. Watch it run away — then put the limit back and appreciate why it exists.
