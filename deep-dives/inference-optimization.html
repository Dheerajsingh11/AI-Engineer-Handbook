Section 01 BeginnerStart from zero

Assumed knowledge

Serving & quantisation (Topic 6.1), the KV cache from LLM mechanics (Topic 1.3), and GPU memory (Topic 2.6). This page goes deeper on making generation fast and cheap.

Training a model happens once; serving it happens on every request, forever — so at scale, inference is where the cost and latency live (Topic 6.5). Squeezing more throughput from the same GPU is one of the highest-value skills in production AI, and it comes down to a handful of specific techniques that all target the same surprising bottleneck: memory, not maths.

The two phases, and the real bottleneck

Generation has two phases. Prefill processes the whole prompt at once — compute-heavy, parallel, fast. Decode generates one token at a time, each step reading the entire past — and here the GPU spends most of its time waiting for memory, not calculating. LLM inference is memory-bandwidth bound: the cores can multiply far faster than the weights and the KV cache can be fetched. Every technique on this page is really about moving less memory, or reusing it — because that, not raw FLOPS, is what limits how many users one GPU can serve.

The words, in plain English
KV cache
The stored attention keys/values for every token so far, so the model needn't recompute them.
Prefill / decode
Processing the prompt (parallel) vs generating tokens one by one (sequential).
PagedAttention
Managing the KV cache in small pages, like an operating system's virtual memory.
Continuous batching
Slotting new requests into the batch as others finish, instead of waiting.
Speculative decoding
A small model drafts several tokens; the big model verifies them in parallel.

Section 02 IntermediateThe KV cache is the constraint

To avoid recomputing attention over the whole history at every step, the model caches each token's keys and values — the KV cache. It makes generation fast, but it grows, and it eats VRAM alongside the weights.

KV cache size — why long context and big batches hurt bytes ≈ 2 × layers × heads × dhead × seq_len × batch × bytes/elem The KV cache grows linearly with sequence length and batch size — so a long context or many concurrent users can make it larger than the model weights themselves. It is the reason you run out of memory when serving long conversations, and the reason context length is a memory decision, not a free knob (Topic 18.4).

The first line of defence is architectural: Grouped-Query Attention (GQA) and Multi-Query Attention share key/value heads across query heads, shrinking the KV cache several-fold for almost no quality loss — which is why nearly every modern model uses it (Topic 18.4). You can also quantise the KV cache (store it in 8-bit) to halve it again. But the biggest wins come from managing the cache more cleverly, which is the next section.

Section 03 IntermediatePagedAttention & vLLM

The insight that changed LLM serving: the KV cache was being managed wastefully. Classic serving reserved one big contiguous block per request, sized for the longest possible output — so most of it sat empty. PagedAttention fixes this by borrowing an idea from operating systems.

Virtual memory for the KV cache

PagedAttention (the engine behind vLLM) stores the KV cache in small fixed-size pages instead of one contiguous block, and keeps a table mapping each request's tokens to pages — exactly how an OS manages RAM. Two big wins follow. Almost no waste: pages are allocated only as tokens are generated, so memory that used to sit reserved-but-empty is now free to serve more concurrent requests. Sharing: requests with a common prefix (the same system prompt, or one prompt sampled several ways) can share the same physical pages. Together with continuous batching — adding new requests to the running batch the instant a slot frees, rather than waiting for the whole batch to finish — this raised serving throughput by an order of magnitude, and made vLLM the default open serving engine.

Prefix & prompt caching

Sharing extends across requests, not just within a batch. Prefix caching keeps the computed KV cache for a common prefix (your long system prompt, or the retrieved context in a RAG app) so the next request that starts the same way skips re-processing it entirely — a large saving when every call shares a big fixed preamble. At the API level this appears as prompt caching (Topic 19.3): send the same prefix repeatedly and pay for it once. Both are the same idea — don't recompute what you already computed — applied to the most expensive shared part of the prompt.

Section 04 AdvancedFlashAttention & speculative decoding

Two more techniques attack the other costs: the attention computation itself, and the one-token-at-a-time nature of decoding.

Two heavy-hitters
TechniqueWhat it doesWin
FlashAttentionComputes exact attention without ever writing the huge N×N score matrix to memory — it fuses the steps and works in fast on-chip memoryFaster & far less memory → makes long context affordable (Topic 18.4)
Speculative decodingA small, fast “draft” model proposes several tokens; the big model checks them all in one parallel pass, keeping the ones it agrees with2–3× faster generation, identical output
Why speculative decoding is free speed

Decoding is slow because it is sequential — one forward pass per token, each bottlenecked on memory. Speculative decoding breaks the sequentiality: a cheap draft model guesses, say, the next 4 tokens, and the big model verifies all 4 in a single forward pass (verification is parallel, like prefill). Because the big model still has the final say on every token, the output is exactly what it would have produced alone — there is no quality trade-off, only speed, whenever the draft guesses right (which on easy stretches of text is often). It is one of the rare optimisations that is genuinely free.

Section 05 ProfessionalThe serving stack

What actually serves models in production

You rarely implement these; you choose and configure them — and the concepts on this page are what let you choose well. The recurring trade is throughput vs latency: bigger batches and more sharing serve more users per GPU (higher throughput) but can make each individual response wait slightly longer. For a high-traffic API, reach for vLLM/TGI with continuous batching, prefix caching on your shared prompts, GQA models, and speculative decoding where a good draft model exists; for a single-user local app, llama.cpp is plenty. The through-line, as everywhere in Phases 18–19: understand the memory bottleneck, then spend effort only where it buys real throughput — the same instinct as compression (18.3) and efficiency engineering (19.3), applied to the serving layer.

Section 06 ProfessionalExercises

Do these — feel the bottleneck
  1. Compute the KV-cache size for a model at 4k vs 128k context, batch 1 vs 32. See when it exceeds the weights.
  2. Serve a model with vLLM and with a naive loop; compare throughput (requests/sec) at increasing concurrency.
  3. Turn on prefix caching for a shared system prompt and measure the latency drop on the second request.
  4. Enable speculative decoding with a small draft model; measure tokens/sec and confirm the output is unchanged.
  5. Compare a GQA model vs a full-multi-head model of similar size for how many concurrent requests fit in your VRAM.
  6. Profile a decode step: confirm it is memory-bound, not compute-bound (Topic 2.6). That single fact explains this whole page.
