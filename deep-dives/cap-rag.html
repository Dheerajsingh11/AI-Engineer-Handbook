Step 01Dense + keyword = hybrid

Vector search (chapter 20.3) finds passages by meaning, but it can miss exact terms — an error code, a product name, an acronym. Keyword search (BM25) nails those but misses paraphrases. Hybrid retrieval runs both and combines them, and it beats either alone on almost every real corpus (Topic 4.6).

PythonTwo retrievers over the same chunks
from rank_bm25 import BM25Okapi

bm25 = BM25Okapi([c["text"].split() for c in records])   # keyword index

def retrieve(query, k=20):
    dense = search(query, k)                    # from Ch. 20.3 (vectors)
    kw_scores = bm25.get_scores(query.split())  # BM25 over all chunks
    kw = top_k(kw_scores, k)
    return fuse(dense, kw)                       # combine -- Step 02
BM25 — keyword relevance, scored score(q, d) = ∑t ∈ q IDF(t) · f(t,d) · (k₁+1)f(t,d) + k₁(1 − b + b · |d|/avgdl) f(t,d) is how often term t appears in chunk d; IDF(t) down-weights common words; the |d|/avgdl term penalises long chunks that match by sheer size. k₁ (≈1.5) tunes term-frequency saturation, b (≈0.75) tunes length normalisation. It is decades-old, fast, and still an excellent keyword ranker (Topic 4.6).

Step 02Fuse the two rankings

Dense scores (cosine, 0–1) and BM25 scores (unbounded) are not comparable, so we cannot just add them. Reciprocal Rank Fusion sidesteps this by combining ranks, not scores — simple and robust.

Reciprocal Rank Fusion (RRF) RRF(d) = ∑r ∈ retrievers 1k + rankr(d) Each retriever contributes 1/(k + rank), where rank is the document's position in that retriever's list and k (≈60) damps the tail. A chunk ranked highly by both retrievers rises to the top; the incomparable raw scores never enter the maths. Elegant and hard to beat.
PythonRRF in a few lines
def fuse(*rankings, k=60):
    scores = {}
    for ranking in rankings:                    # each is [(chunk_id, _), ...] in order
        for rank, (cid, _) in enumerate(ranking):
            scores[cid] = scores.get(cid, 0) + 1.0 / (k + rank)
    return sorted(scores.items(), key=lambda x: -x[1])

Step 03Re-rank the shortlist

Fusion gives a good top-20. A cross-encoder re-ranker then reads each candidate together with the query and scores true relevance far more accurately than the embedding could — too slow to run over the whole corpus, perfect over 20 candidates (Topic 4.6).

PythonPrecision at the top with a cross-encoder
from sentence_transformers import CrossEncoder
reranker = CrossEncoder("BAAI/bge-reranker-base")

def retrieve_rerank(query, k_final=5):
    candidates = retrieve(query, k=20)          # hybrid + fusion
    pairs = [(query, text_of(cid)) for cid, _ in candidates]
    rel = reranker.predict(pairs)               # joint query-doc scoring
    ranked = sorted(zip(candidates, rel), key=lambda x: -x[1])
    return [cid for (cid, _), _ in ranked[:k_final]]
Bi-encoder vs cross-encoder — the key distinction

The embedder in chapter 20.3 is a bi-encoder: it encodes the query and each document separately, so document vectors can be precomputed and searched fast — but query and document never “see” each other. A cross-encoder feeds query and document together through the model, so attention can compare them directly, giving much sharper relevance — at the cost of running the model once per pair, which is only affordable on a shortlist. The winning pattern is exactly this two-stage funnel: fast bi-encoder retrieves many, slow cross-encoder re-ranks a few (Topic 4.6). It mirrors the retrieve-then-rank shape of recommender systems (Topic 14.6).

Step 04Assemble the grounded prompt

Finally we build the prompt: the retrieved chunks as context, the question, and instructions to answer only from the context and to cite sources (Topic 3.1). This is what turns a language model into a grounded, honest assistant.

PythonContext + question + guardrail instructions
def build_prompt(query, chunk_ids):
    context = "\n\n".join(f"[{cid}] {text_of(cid)}" for cid in chunk_ids)
    return f"""Answer the question using ONLY the context below.
Cite the [chunk_id] for each claim. If the answer is not in the
context, say "I don't have that in the docs." Do not invent.

CONTEXT:
{{context}}

QUESTION: {{query}}
ANSWER:"""
Fix retrieval before you touch the model

The most common RAG mistake is blaming the LLM for bad answers when the real fault is retrieval — if the right chunk was never fetched, no model can answer correctly. So when Atlas gives a wrong answer, the first question is always “was the correct passage in the retrieved context?” If not, the fix is in this chapter (chunking, hybrid, re-ranking), not in the prompt or the model. Retrieval quality dominates RAG quality; the instruction to say “I don't have that” is what converts a retrieval miss into an honest non-answer instead of a hallucination (Topics 4.6, 4.7).
