13.2

Classic NLP Tasks

The classic language tasks, and how to choose your approach for each. This page surveys text classification, sentiment, named-entity extraction, translation, summarisation and question answering — and gives the decision that recurs in every one: classic model, fine-tuned model, or prompted LLM, driven by volume, cost and how much labelled data you have.

Section 01 BeginnerStart from zero

Assumed knowledge

NLP fundamentals (Topic 13.1), classical ML (Topic 2.3), and prompting (Topic 3.1). This page is about applying them to concrete language tasks.

Most language work reduces to a handful of recurring task types. Recognising which type you have — and knowing the three ways to tackle each — is more useful than any single technique. This page is a catalogue plus a decision framework.

The classic NLP tasks
TaskInput → outputExample
Text classificationText → a labelRoute a support ticket; detect spam
Sentiment analysisText → positive/negative/mixedAnalyse reviews
Named-entity extractionText → labelled spansPull names, dates, amounts from a contract
TranslationText → text in another languageEnglish → Spanish
SummarisationLong text → short textCondense a report
Question answeringQuestion (+context) → answerThe core of RAG (Phase 4)
The decision that recurs in every task

For each task you have three options, and the right one is an engineering trade-off, not a fashion:

  1. Classic ML — TF-IDF features + a classifier (Topic 2.3). Cheap, fast, deterministic, needs labelled data.
  2. Fine-tuned model — a small transformer fine-tuned on your data (Topic 3.5). Strong quality, moderate cost, needs some labelled data.
  3. Prompted LLM — describe the task to a large model (Topic 3.1). No training, flexible, most expensive per call.

The choice is driven by volume, cost tolerance, and how much labelled data you have — the same routing logic as Topic 9.1.

Section 02 IntermediateClassification & sentiment: three ways

PythonThe same task, three approaches
# --- 1. CLASSIC: TF-IDF + logistic regression (Topic 2.3) --------
# Cheap, instant, deterministic. Needs a few hundred+ labels.
from sklearn.pipeline import make_pipeline
from sklearn.feature_extraction.text import TfidfVectorizer
from sklearn.linear_model import LogisticRegression

clf = make_pipeline(TfidfVectorizer(), LogisticRegression())
clf.fit(train_texts, train_labels)
clf.predict(["My order never arrived"])          # -> "shipping"

# --- 2. FINE-TUNED transformer (Topics 3.5, 9.3) -----------------
# Best quality at high volume; needs labelled data + a training run.
from transformers import pipeline
classifier = pipeline("text-classification", model="./my-finetuned-model")

# --- 3. PROMPTED LLM (Topic 3.1) ---------------------------------
# Zero training, most flexible, most expensive per call.
llm(f"""Classify into shipping|billing|technical|other:\n{text}""")

# Rule of thumb:
#  - millions of calls, have labels    -> classic or fine-tuned
#  - few calls, no labels, need nuance -> prompted LLM
#  - somewhere between                 -> fine-tune a small model
Choosing an approach for classification
If you have…Use
Lots of labelled data + high volumeClassic ML or fine-tuned — cheapest at scale
Some labelled data + quality mattersFine-tune a small transformer
No labelled data or fuzzy categoriesPrompt an LLM (few-shot)
Categories that change oftenPrompt an LLM — no retraining

Section 03 IntermediateTranslation, summarisation, QA

These are generation tasks — text out, not a label — and here LLMs have decisively won over the classic sequence-to-sequence approaches.

Generation tasks now
TaskThen (pre-LLM)Now
TranslationDedicated seq2seq models per language pairOne LLM handles many languages; specialised models still win on some pairs
SummarisationExtractive (pick sentences) or seq2seqLLM, abstractive — genuinely rewrites
Question answeringRetrieve a span from a passageRAG: retrieve + generate (Phase 4)

Two flavours of summarisation worth knowing. Extractive summarisation picks the most important existing sentences — safe, never hallucinates, but stilted. Abstractive summarisation rewrites in new words — fluent, but can introduce errors or claims not in the source (a faithfulness problem, Topic 4.7). LLMs do abstractive summarisation, which is why you must evaluate their summaries for faithfulness, not just fluency. For high-stakes summarisation (medical, legal), the hallucination risk is real and the same grounding and evaluation discipline from Phase 4 applies.

Section 04 AdvancedExtraction: where classic tools still shine

Pulling structured data out of text — entities, relationships, fields — is one of the most common real tasks, and one where the choice genuinely matters.

Extraction approaches
ApproachStrengthWeakness
Rule / regexPerfect for structured patterns (emails, IDs)Brittle on natural language
Classic NER (spaCy)Fast, cheap, scalable (Topic 13.1)Fixed entity types; needs training for custom ones
Fine-tuned token classifierCustom entities, high accuracy at scaleNeeds labelled data
LLM with structured outputFlexible, handles nuance and new fields (Topic 3.1)Cost per call; validate the output
A hybrid that works well in practice

Real extraction pipelines often combine approaches: regex for the structured bits (dates, amounts, IDs — where rules are perfect and free), a fast NER model for common entities at scale, and an LLM with structured output only for the hard, ambiguous cases a cheaper method flags. This tiering — cheap deterministic methods first, the expensive flexible one only where needed — is the same cost-routing pattern that runs through this whole handbook (Topics 9.1, 9.4). It gets you LLM-quality on the difficult cases without paying LLM prices on the easy 90%.

Section 05 ProfessionalEvaluating language tasks

How to measure each task type
TaskMetric
Classification / sentimentPrecision, recall, F1 (Topic 1.2) — not accuracy on imbalanced data
NER / extractionF1 over spans; exact vs partial match
TranslationBLEU / COMET, plus human review
SummarisationROUGE + faithfulness (Topic 4.7); human review
Question answeringExact match / F1; for RAG, the Topic 4.7 suite
Reference-based metrics for generation are weak

BLEU and ROUGE compare generated text to a reference by word overlap — and penalise perfectly good outputs that use different words than the reference. A great summary phrased differently from the "gold" one scores poorly. They are useful as cheap, consistent signals for tracking regressions, but never as the final word on quality. For generation tasks, pair them with the LLM-as-judge and human review from Topic 4.7 — and always evaluate faithfulness, because fluent-but-wrong is the dangerous failure. As everywhere in this handbook: measure, but choose the metric that reflects what you actually care about.

Section 06 ProfessionalExercises

Do these — roughly a weekend
  1. Build a text classifier three ways (TF-IDF, fine-tuned, prompted LLM) on the same dataset. Compare accuracy, cost per 1,000, and latency.
  2. For a realistic volume and budget, decide which of the three you would actually ship, and justify it with the Section 02 table.
  3. Summarise the same document extractively and abstractively. Check the abstractive one for any claim not in the source (Topic 4.7).
  4. Build a tiered extraction pipeline: regex + NER + LLM-for-hard-cases. Measure how few calls reach the LLM.
  5. Evaluate a summariser with ROUGE, then have a human rate the same summaries. Note where the metric and the human disagree.
  6. Take three language tasks from your own work and assign each an approach using this page's framework.
