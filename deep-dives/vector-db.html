Vector Databases

Choosing and running the store. Section 01 BeginnerStart from zero

Assumed knowledge

Index types from Topic 4.3 — particularly HNSW parameters. SQL and general database operations.

A vector database stores embeddings and finds similar ones quickly. That is one job, and it is the job an ANN index does. So what does a database add beyond the index?

What separates a library from a database
CapabilityWhy you need it
Persistence and durabilityAn in-memory index disappears on restart
Insert, update, deleteDocuments change. Rebuilding a whole index nightly is not an update strategy
Metadata and filteringMulti-tenancy, permissions, freshness — all require predicates
TransactionsVector and its source row must not diverge
ConcurrencyMany readers while writers ingest
Backup and restoreRe-embedding 10M chunks after data loss costs real money
ObservabilitySlow-query logs, index statistics, connection metrics
Access controlRow-level security, roles, audit
The observation that should shape your decision

Look at that list again. Every row is something Postgres has done well for thirty years, and every row is something a young purpose-built vector database has had to build from scratch. The vector index is the only genuinely new capability.

That is the argument for pgvector: you add one extension and inherit all the rest, along with your team's existing operational knowledge, your backup tooling, your monitoring, and your ability to join vectors against business data in a single query.

The recommendation, and how to keep your options open

Start with pgvector. Your operational knowledge of Postgres is worth more than a marginal recall improvement, and one fewer system to run is a real and permanent saving.

Keep the option open by coding against Spring AI's VectorStore or LangChain4j's EmbeddingStore rather than raw SQL in your service layer. Moving to Qdrant later becomes a configuration change and a re-index, not a rewrite. Prove you need a specialist store — with a measurement, at your real scale, with your real filters — before adopting one.

Section 03 Advancedpgvector in production

SQLThe complete schema
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE doc_chunk (
    id           bigserial PRIMARY KEY,
    tenant_id    bigint       NOT NULL,
    document_id  text         NOT NULL,
    chunk_index  int          NOT NULL,
    content      text         NOT NULL,
    metadata     jsonb        NOT NULL DEFAULT '{}',

    -- Which model produced this vector. NOT optional: mixing vectors
    -- from two models silently corrupts retrieval (Topic 4.2).
    model_id     text         NOT NULL,
    embedding    vector(1536) NOT NULL,

    -- For hybrid search in 4.6. Generated, so it can never drift
    -- out of sync with the content.
    content_tsv  tsvector GENERATED ALWAYS AS
                     (to_tsvector('english', content)) STORED,

    created_at   timestamptz  NOT NULL DEFAULT now(),
    updated_at   timestamptz  NOT NULL DEFAULT now(),

    UNIQUE (tenant_id, document_id, chunk_index)
);

-- Vector index. The operator class MUST match the metric you query
-- with, or Postgres silently ignores the index and does a seq scan.
--   vector_cosine_ops  <=>   cosine distance
--   vector_l2_ops      <->   euclidean
--   vector_ip_ops      <#>   negative inner product
CREATE INDEX doc_chunk_embedding_hnsw
    ON doc_chunk USING hnsw (embedding vector_cosine_ops)
    WITH (m = 16, ef_construction = 128);

-- Supporting indexes for filters and full-text
CREATE INDEX doc_chunk_tenant     ON doc_chunk (tenant_id, document_id);
CREATE INDEX doc_chunk_metadata   ON doc_chunk USING gin (metadata);
CREATE INDEX doc_chunk_tsv        ON doc_chunk USING gin (content_tsv);

-- Defence in depth for multi-tenancy: even a bug that omits the
-- WHERE clause cannot cross tenants.
ALTER TABLE doc_chunk ENABLE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON doc_chunk
    USING (tenant_id = current_setting('app.tenant_id')::bigint);
SQLQuerying, and the traps
-- ef_search is a SESSION setting, and it is the recall dial.
SET hnsw.ef_search = 100;

-- CORRECT: ORDER BY the distance operator directly, ASC.
-- This is the only form the HNSW index can serve.
SELECT id, content, 1 - (embedding <=> :query) AS similarity
FROM   doc_chunk
WHERE  tenant_id = :tenant
  AND  model_id  = 'text-embedding-3-small'
ORDER  BY embedding <=> :query
LIMIT  50;

-- WRONG: the index cannot serve this. Sequential scan, no warning.
-- SELECT ... ORDER BY 1 - (embedding <=> :query) DESC LIMIT 50;

-- WRONG: a WHERE on the distance also defeats the index.
-- SELECT ... WHERE embedding <=> :query < 0.3 ORDER BY ...;
-- Instead: over-fetch with LIMIT, then filter in application code
-- or in an outer query.

-- Filter first, then rank, when the filter is highly selective:
WITH candidates AS (
    SELECT id, content, embedding
    FROM   doc_chunk
    WHERE  tenant_id = :tenant
      AND  metadata->>'status' = 'published'
      AND  updated_at > now() - interval '90 days'
)
SELECT id, content, 1 - (embedding <=> :query) AS similarity
FROM   candidates
ORDER  BY embedding <=> :query
LIMIT  50;

-- ALWAYS verify the plan. "Index Scan using doc_chunk_embedding_hnsw"
-- is what you want; "Seq Scan" means you are scanning the table.
EXPLAIN (ANALYZE, BUFFERS)
SELECT id FROM doc_chunk WHERE tenant_id = 42
ORDER BY embedding <=> :query LIMIT 10;
The silent sequential scan

pgvector will happily run your query without the index and return correct results, just slowly. Three ways to trigger it, none of which produce a warning: using an operator that does not match the index's operator class; ordering DESC by similarity instead of ASC by distance; or putting the distance expression in a WHERE clause.

On 10,000 rows in development this is imperceptible. On 10 million rows in production it is a 30-second query. Run EXPLAIN on your retrieval query as part of your test suite and assert that an index scan appears in the plan.

Section 04 AdvancedOperating it

SQLIndex builds, updates and maintenance
-- HNSW index builds are slow and memory-hungry. Give them room:
-- if the graph does not fit in maintenance_work_mem, the build
-- spills to disk and takes many times longer.
SET maintenance_work_mem = '8GB';
SET max_parallel_maintenance_workers = 7;

-- Build AFTER bulk loading, not before -- an order of magnitude faster.
-- CONCURRENTLY avoids taking a write lock on a live table.
CREATE INDEX CONCURRENTLY doc_chunk_embedding_hnsw
    ON doc_chunk USING hnsw (embedding vector_cosine_ops)
    WITH (m = 16, ef_construction = 128);

-- Re-ingestion MUST delete first. Without this, old and new chunks
-- coexist and stale content competes with fresh content in results.
BEGIN;
DELETE FROM doc_chunk WHERE tenant_id = :t AND document_id = :d;
INSERT INTO doc_chunk (tenant_id, document_id, chunk_index, content,
                       metadata, model_id, embedding)
SELECT :t, :d, i, c, m, :model, e FROM unnest(...) ;
COMMIT;

-- Deletes leave dead tuples in the HNSW graph. Autovacuum handles
-- normal churn, but a large deletion warrants an explicit pass.
VACUUM ANALYZE doc_chunk;

-- Watch index bloat over time:
SELECT relname,
       pg_size_pretty(pg_relation_size(oid))       AS index_size,
       pg_size_pretty(pg_total_relation_size(oid)) AS total
FROM   pg_class
WHERE  relname LIKE 'doc_chunk%';

Migrating to a new embedding model

You will do this — a better model appears, or you fine-tune your own. Never migrate in place; a partially re-embedded index returns nonsense for the mixed period.

  1. Add a column or a table for the new vectors, keeping the old ones live and serving traffic.
  2. Backfill in batches, writing to the new column. This may take hours or days; that is fine because nothing depends on it yet.
  3. Build the new index concurrently.
  4. Evaluate both on the golden set from §4.7. Compare recall@k, not intuition.
  5. Switch atomically — one configuration change, or a view swap in a transaction.
  6. Keep the old column for a rollback window, then drop it.
SQLThe migration pattern
ALTER TABLE doc_chunk ADD COLUMN embedding_v2 vector(1024);
ALTER TABLE doc_chunk ADD COLUMN model_id_v2  text;

-- Backfill in bounded batches so you never hold a long transaction.
UPDATE doc_chunk SET embedding_v2 = :new_vec, model_id_v2 = :new_model
WHERE  id IN (SELECT id FROM doc_chunk
              WHERE embedding_v2 IS NULL
              ORDER BY id LIMIT 1000);

CREATE INDEX CONCURRENTLY doc_chunk_embedding_v2_hnsw
    ON doc_chunk USING hnsw (embedding_v2 vector_cosine_ops)
    WITH (m = 16, ef_construction = 128);

-- Only after the golden set confirms the new model is better.
Operational checklist
ConcernPractice
SizingVectors should fit in RAM for good latency. n×d×4 bytes, plus the graph, plus Postgres overhead
Connection poolingHikariCP as usual; vector queries hold connections longer than OLTP, so size accordingly
BackupsStandard pg_dump or WAL archiving. Test a restore — re-embedding 10M chunks is expensive
Read replicasRetrieval is read-heavy; replicas scale it cleanly
PartitioningPartition by tenant when a few tenants dominate. Fixes the small-tenant recall cliff from §4.3
Monitoringp95 query time, index-scan ratio, dead tuple count, cache hit rate
Schema migrationsFlyway or Liquibase, as with any Postgres schema. Do not use initialize-schema: true in production

Section 05 ProfessionalWhen to leave Postgres

Signals that you have outgrown it
SignalWhat it meansConsider
Vectors no longer fit in RAMQueries hit disk; p95 degrades sharplyQuantisation first; then a store with native disk-based indexes
Filtered recall is poor for small tenantsPost-filtering with a selective predicateQdrant or Weaviate for native filtered search; or partition
Index build takes daysCorpus too large for single-node buildsMilvus for distributed builds
You need hybrid search and BM25 is weakPostgres full-text is decent, not best-in-classElasticsearch/OpenSearch, or a dedicated BM25 index
Sub-millisecond p99 requiredPostgres adds connection and planner overheadRedis or an in-process index
Beyond ~100M vectorsSingle-node limitsMilvus, Vespa, or sharding

Try these before migrating, in order — most teams that "outgrow pgvector" have not done them: reduce dimensions with Matryoshka truncation; quantise to int8 or binary with rescoring; add read replicas; partition by tenant; raise maintenance_work_mem and rebuild with better parameters; and confirm with EXPLAIN that you were actually using the index. Any one of these can buy an order of magnitude, and none requires a new system in your architecture diagram.

Section 06 ProfessionalExercises

Do these — roughly a weekend
  1. Stand up Postgres with pgvector in Docker and create the full schema from Section 03.
  2. Load 1M random vectors. Time the index build with maintenance_work_mem at 64 MB and at 4 GB. Note the difference.
  3. Run the correct query and confirm "Index Scan" in EXPLAIN. Then reverse the ORDER BY to DESC and watch it become a sequential scan with no warning.
  4. Write a test that asserts EXPLAIN output contains an index scan. Add it to CI.
  5. Enable row-level security. Write an integration test that ingests for two tenants and proves tenant A cannot retrieve tenant B's chunks — then delete the WHERE clause and confirm RLS still saves you.
  6. Measure p95 latency at hnsw.ef_search of 40, 100 and 400, alongside recall. Choose your operating point deliberately.
  7. Perform a full model migration on a copy: add column, backfill, index, evaluate, switch. Time each phase.
  8. Delete 30% of rows, measure query latency, then VACUUM ANALYZE and measure again.
