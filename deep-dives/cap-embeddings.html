Step 01Embed the chunks

Retrieval works by meaning, not keywords, and meaning is captured by an embedding: a vector where semantically similar texts land near each other (Topic 4.2). We run every chunk from chapter 20.2 through an embedding model once, offline.

PythonEmbed every chunk
from sentence_transformers import SentenceTransformer
import numpy as np

encoder = SentenceTransformer("BAAI/bge-small-en-v1.5")   # a strong small model

texts = [r["text"] for r in records]
emb = encoder.encode(texts, batch_size=64,
                     normalize_embeddings=True,            # unit length -- see Step 02
                     show_progress_bar=True)
emb = np.asarray(emb, dtype="float32")        # shape: (n_chunks, dim)
# Persist vectors alongside chunk_id so a hit maps back to its text.

Two choices matter. The model: a small, strong open embedder (bge, e5, gte) is usually the right default — cheap, private, good enough (Topic 4.2). And normalisation: scaling every vector to unit length, which — as the next step shows — turns the similarity computation into a plain dot product and makes the index simpler and faster.

Step 02The maths of similarity

“Which chunks are most relevant to the query?” becomes “which chunk vectors are closest to the query vector?” Closeness is measured by cosine similarity — the angle between two vectors, ignoring their length (Topic 1.1).

Cosine similarity, and why normalising simplifies it cos(q, d) = q · d‖q‖ ‖d‖ if ‖q‖ = ‖d‖ = 1  ⇒  cos(q, d) = q · d = ∑i qi di Cosine divides the dot product by both lengths, so it measures direction (meaning) not magnitude. If we normalise every vector to length 1 in Step 01, the denominator is 1 and similarity is just the dot product — a single fast multiply-accumulate the hardware loves (Topic 2.6). That is why we normalised.

Step 03Build the index (ANN)

Comparing the query against every chunk (a brute-force scan) is fine for thousands of chunks but not millions. An approximate nearest neighbour index trades a sliver of accuracy for a massive speed-up (Topic 4.3).

PythonAn HNSW index with FAISS
import faiss

dim = emb.shape[1]
index = faiss.IndexHNSWFlat(dim, 32)          # 32 = graph connectivity (M)
index.hnsw.efConstruction = 200               # build-time thoroughness
index.add(emb)                                # insert all chunk vectors

def search(query, k=20):
    q = encoder.encode([query], normalize_embeddings=True)
    index.hnsw.efSearch = 64                   # query-time thoroughness
    scores, ids = index.search(np.asarray(q, "float32"), k)
    return [(records[i]["chunk_id"], float(s)) for s, i in zip(scores[0], ids[0])]
How HNSW finds neighbours so fast

HNSW builds a multi-layer graph of the vectors: sparse long-range links at the top, dense local links at the bottom. A search enters at the top, greedily hops toward the query through the coarse layer, then descends into finer layers to refine — like zooming in on a map. It visits a few hundred vectors instead of millions, giving roughly logarithmic search time. The knobs trade accuracy for speed: M and efConstruction shape the graph at build time; efSearch sets how hard each query looks. That is the whole reason retrieval feels instant even over a huge corpus (Topic 4.3).

Step 04Where the vectors live

A FAISS index in memory is perfect for development. In production, a vector database adds persistence, metadata filtering, and updates as documents change (Topic 4.4).

The storage choice for Atlas
OptionWhen
FAISS (in-process)Dev, prototypes, read-only corpora
pgvector (Postgres)Atlas's choice — vectors beside the existing relational data, one system to run
Dedicated vector DBVery large scale, heavy filtering, managed ops
Why pgvector fits Atlas

The company already runs Postgres, and the documents have metadata (team, product, access level) we will filter on. pgvector stores the embeddings next to that metadata, so a query can say “nearest chunks where team = platform and access ≤ user_level” in one place — retrieval and authorisation together. For a backend engineer, one fewer system to operate is a real win, and it scales far enough for an internal tool. The lesson generalises: the best infrastructure choice is usually the one that fits the systems you already run (Topic 4.4).
