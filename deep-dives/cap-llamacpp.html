Step 01Merge, then convert to GGUF

Chapter 20.5 produced small LoRA adapters. To run efficiently we first merge them back into the base weights (folding B A into W₀), then convert to GGUF — the file format llama.cpp runs (Topic 19.4).

Python + shellAdapters → merged model → GGUF
# 1. Merge the LoRA adapters into the base model (Ch. 20.5).
from peft import PeftModel
merged = PeftModel.from_pretrained(base, "atlas-lora").merge_and_unload()
merged.save_pretrained("atlas-merged")

# 2. Convert the HF model to GGUF (llama.cpp's format).
$ python llama.cpp/convert_hf_to_gguf.py atlas-merged --outfile atlas-f16.gguf

# 3. Quantise to 4-bit -- a quarter of the size, minimal quality loss.
$ ./llama-quantize atlas-f16.gguf atlas-q4.gguf Q4_K_M

Merging matters for speed: an unmerged model computes W₀x + BAx as two operations every step, while a merged model computes a single Wx. For a stable, deployed model you merge once; you keep adapters separate only when you want to hot-swap different fine-tunes on one base.

Step 02The maths of quantisation

The Q4_K_M step stores each weight in roughly 4 bits instead of 16. The trick that keeps quality is block-wise scaling — quantise small groups of weights, each with its own scale (Topics 6.1, 18.3).

Block quantisation — per-group scale for a block of weights w:   scale = max|w|2b−1 − 1,   q = round(w / scale) dequantise at runtime:   w ≈ q × scale Each block (e.g. 32 weights) stores tiny integers q plus one scale. A per-block scale adapts to local magnitude, so outliers in one region do not wreck precision everywhere — far better than one global scale. At b=4 bits the model is ~4× smaller and faster, with quality loss usually too small to notice on-task. This is the memory win that lets Atlas run on ordinary hardware.

Step 03Serve it with llama.cpp

shell + PythonAn OpenAI-compatible local server
# llama.cpp ships a server exposing an OpenAI-style API on localhost.
$ ./llama-server -m atlas-q4.gguf --ctx-size 8192 --n-gpu-layers 999 --port 8080

# Atlas's code talks to it exactly like any chat API (Ch. 20.7, 20.8).
import openai
client = openai.OpenAI(base_url="http://localhost:8080/v1", api_key="local")
resp = client.chat.completions.create(
    model="atlas", messages=[{"role": "user", "content": prompt}],
    temperature=0.2, stream=True)               # low temp: factual, grounded
The KV cache — the other memory cost

Model weights are not the only thing in VRAM. As the model generates, it stores the attention keys and values for every token so far — the KV cache (Topic 1.3) — and it grows with context length × batch. That is why --ctx-size is a memory decision, not a free knob: an 8k context costs real VRAM on top of the weights, and a 128k context can cost more than the model itself (Topic 18.4). Grouped-query attention and cache quantisation shrink it, but the principle stands: budget the KV cache alongside the weights when sizing hardware (Topic 6.5).

Step 04Why local, for Atlas

Local inference vs a hosted API, for an internal tool
ConcernLocal (llama.cpp) wins because…
PrivacyInternal docs and queries never leave the network (Topic 6.4)
CostNo per-token bill; fixed hardware cost (Topics 6.5, 20.10)
ControlIt is our fine-tuned model, versioned and reproducible
LatencyNo network hop; predictable on our hardware
The trade we accepted

A local 8B model is not a frontier model — it is less capable in the abstract. But for Atlas's bounded job (answer support questions over our docs, in our voice), a fine-tuned, RAG-grounded 8B running privately on cheap hardware is the better product: private, affordable, fast, and ours. That is the recurring lesson of Phases 18–19 — the smallest model that clears the bar, on the cheapest hardware that fits, usually wins (Topics 18.3, 19.4). If a task later needs more, the hybrid pattern (Topic 19.4) escalates just those cases to a bigger model.
