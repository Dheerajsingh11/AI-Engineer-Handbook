19.3

Cost, Latency & Efficiency

Making AI fast enough and cheap enough to ship. This page covers the production discipline of controlling token cost and latency — the economics of a token, caching, model routing and cascades, batching and streaming — and how a thoughtful engineer cuts an AI bill by an order of magnitude without users noticing.

Section 01 BeginnerStart from zero

Assumed knowledge

How LLM APIs are priced and called (Topic 9.1), and serving basics (Topic 6.1). This page is about spending less and waiting less, once something works.

A prototype that ignores cost and latency can become a product that cannot afford to exist. LLM calls are metered by the token and measured in seconds, and at scale those two numbers decide whether your feature is viable. Efficiency engineering is the discipline of getting the same quality for a fraction of the cost and latency — and it is one of the highest-leverage skills in applied AI.

Why this is your edge

Anyone can call an LLM; far fewer can call it economically at scale. The naive version — biggest model, every request, whole context re-sent, no caching — can cost 10–100× what a well-engineered version costs for indistinguishable quality. That gap is pure engineering, and it is exactly where a systems background (yours) pays off: it is the same instinct as caching, batching and tiering that makes any backend affordable, applied to a new, expensive primitive. Teams that master it ship features that teams burning money on the naive path cannot.

The words, in plain English
Token
The unit LLMs bill by — roughly ¾ of a word. You pay for input and output tokens.
Latency
How long the user waits. Often dominated by output length.
TTFT
Time to first token — how long until something appears (streaming).
Caching
Reusing a previous result instead of paying to recompute it.
Routing / cascade
Sending easy requests to a cheap model, hard ones to an expensive model.

Section 02 IntermediateThe economics of a token

You cannot optimise what you do not understand. Two facts drive almost every decision: you pay for input and output tokens, and output tokens are both slower and often costlier than input.

Where the cost and latency actually go
DriverEffectLever
Long prompts / big contextMore input tokens every callTrim context; retrieve less, better (Topic 4.6)
Long outputsHigher cost and latency (generated one at a time)Ask for concise output; cap max tokens
Model sizeBigger = pricier & slower per tokenRoute to the smallest model that passes (Section 04)
Repeated contextRe-sending the same system prompt/docsPrompt caching (Section 03)
Redundant requestsPaying twice for the same answerSemantic caching (Section 03)

The output-length insight surprises people. Because a model generates output one token at a time, a 500-token answer is not just costlier than a 100-token answer — it is roughly five times slower to produce. So "be concise" is not only a quality instruction, it is a latency and cost instruction. Capping max_tokens, asking for structured or terse output, and not making the model restate the question are among the cheapest wins available. Input tokens, by contrast, are processed in parallel and are usually cheaper per token — which is why a long prompt hurts less than a long answer, and why prompt caching (next) is so effective.

Section 03 IntermediateCaching: the biggest win

Caching is almost always the highest-return optimisation, and there are two distinct kinds that stack.

Two kinds of caching
Prompt (prefix) cachingSemantic caching
CachesThe processing of a repeated prompt prefixThe final answer to a similar question
Triggered bySame system prompt / documents reused across callsA new query close to a past one (by embedding)
SavesInput cost & latency on the shared prefixThe entire call — no model run at all
Provided byThe model API (often automatic or a flag)You, with an embedding + vector lookup (Topic 4.2)
PythonSemantic cache: answer once, reuse for near-duplicates
# Many users ask the same thing in different words. Answer it once.
def answer(query, threshold=0.95):
    q_vec = embed(query)
    hit, score = cache.nearest(q_vec)          # vector similarity search
    if score >= threshold:
        return hit.answer                      # no LLM call at all -- free & instant
    ans = llm(query)                           # miss: pay once
    cache.add(q_vec, ans)
    return ans
# Tune the threshold: too low returns wrong cached answers,
# too high never hits. Validate against real queries (Topic 19.1).
The semantic-cache correctness risk

Semantic caching trades correctness for cost, and the threshold is the dial. Set it too loose and "how do I cancel my order?" returns the cached answer to "how do I cancel my account?" — a subtly wrong, confidently delivered answer. Set it too tight and you never get a hit. So a semantic cache needs the same evaluation discipline as the model itself (Topic 19.1): measure its hit rate and its error rate on real traffic, and be conservative wherever a wrong answer is costly. Prompt caching has no such risk — it is exact — which is why it is the safer first reach.

Section 04 AdvancedRouting, cascades & batching

Not every request needs your best model. Matching request difficulty to model cost is the other big lever.

The efficiency patterns
  1. RoutingClassify each request and send easy ones to a small model, hard ones to a large one.
  2. CascadeTry the cheap model first; escalate to the expensive one only if its answer fails a check.
  3. BatchingProcess many requests together to maximise GPU throughput (self-hosting).
  4. StreamingStream tokens so the user sees output immediately — latency felt, not just measured.
The cascade: cheap-first, escalate-on-doubt

The cascade is one of the most elegant cost patterns. Send the request to a small, cheap model first; check its answer with a fast, cheap validator (a confidence signal, a rule, or a lightweight judge from Topic 19.1); and only escalate to the big, expensive model for the fraction that fails. If the cheap model handles 70% of traffic acceptably, you have cut cost on 70% of requests while keeping quality on the hard 30% — often a 3–5× saving for negligible quality loss. It mirrors how a good support org works: front-line handles the routine, escalates the hard cases. The engineering is in the check — a good escalation trigger is what makes it safe.

Streaming changes the felt experience, not the cost

Streaming does not make generation cheaper or truly faster — the same tokens are produced — but it transforms perceived latency. A user watching words appear after 200ms feels a responsive product; the same user staring at a spinner for four silent seconds feels a broken one, even though the total time is identical. Time-to-first-token is the metric users actually feel. For any interactive AI feature, streaming is close to mandatory, and it is nearly free to add.

Section 05 ProfessionalPutting it together

A mature AI system layers these: route by difficulty, cache both prefixes and answers, keep prompts and outputs tight, stream to the user, and cascade to the big model only when needed — then measure cost-per-request and latency percentiles (p50, p95, p99) as first-class metrics next to quality (Topic 19.1). The discipline is to optimise without silently degrading quality: every efficiency change must be checked on the eval set, because the failure mode is a cheaper system that quietly gives worse answers. Do it well and the same product costs a fraction and feels faster; the order-of-magnitude gap between the naive and the engineered version is real, and closing it is squarely an engineer's job. This is also where model compression (Topic 18.3) and the architectural choices of Topic 18.4 pay off — efficiency runs from the silicon to the system.

Section 06 ProfessionalExercises

Do these — measure everything
  1. Instrument a feature to log tokens-in, tokens-out, cost and latency per request. Find where the money and the time actually go.
  2. Cut output length (concise instructions, capped max tokens) and measure the cost and latency drop against any quality change.
  3. Add a semantic cache. Measure hit rate and error rate on real queries, and tune the threshold with an eval set.
  4. Build a two-tier router: cheap model for easy requests, expensive for hard. Measure the blended cost and the quality.
  5. Implement a cascade with an escalation check. Report what fraction stays on the cheap model and the total saving.
  6. Add streaming to an interactive feature and measure time-to-first-token. Note how much better it feels at the same total latency.
