10.1

Cloud AI Platforms

The enterprise front door to AI. This page covers the three cloud AI platforms named in job postings — AWS Bedrock, Azure OpenAI / Azure AI, and Google Vertex AI — what they add over calling a model API directly (governance, data residency, managed RAG and infra), how they differ, and how to stay portable so the platform is a deployment choice, not a lock-in.

Section 01 BeginnerStart from zero

Assumed knowledge

Calling models via APIs (Topic 9.1) and RAG (Phase 4). Cloud platforms wrap those in enterprise infrastructure.

You can call a model with an API key and a URL (Topic 9.1). So why do enterprise job postings insist on AWS Bedrock, Azure OpenAI or Vertex AI? Because large organisations cannot just send data to a third-party API — they need it inside their cloud, under their governance, on their bill, with their compliance controls. The cloud platforms provide exactly that: models delivered through the same account, IAM, networking, logging and billing as the rest of their infrastructure.

What a cloud AI platform adds over a raw model API
AddsWhy enterprises need it
Data residency & isolationData stays in their region/VPC; not used for training
Unified IAM & authSame identity and access controls as everything else
Consolidated billingOne cloud invoice, not another vendor
Model choiceMany models (incl. open ones) behind one interface
Managed RAG & agentsKnowledge bases, vector stores, agent builders as services
Compliance & auditThe certifications and logging their auditors require
NetworkingPrivate connectivity — no public internet hop
The mental model

A cloud AI platform is a model API wrapped in the cloud's governance, security and infrastructure. The model call at the centre is the same one from Topic 9.1; the value is everything around it that lets a regulated enterprise actually use it. For your career, "which cloud" often follows your employer's existing cloud — a shop on AWS uses Bedrock, one on Azure uses Azure OpenAI. Knowing the shape of all three, and one deeply, is what postings ask for.

Your Spring AI knowledge transfers directly

Spring AI has starters for all three platforms — Bedrock, Azure OpenAI and Vertex AI. Your ChatClient, VectorStore and advisor code (Topic 3.2) stays the same; you change a dependency and some properties to move between a raw provider API and a cloud platform. That is a genuine advantage of the Java stack for enterprise work: the same application code runs against a hosted API in development and a governed cloud platform in production.

Section 03 AdvancedThe managed services, and when to use them

Each platform offers managed versions of things you learned to build by hand in this roadmap. The question is always: managed convenience, or your own control?

Managed service vs build-it-yourself
Managed serviceYou already know how to build…Use managed when
Knowledge Bases / RAG enginesRAG (Phase 4)Speed to ship; standard RAG; you want infra handled
Agent buildersAgents (Phase 08)Simple agents; tight platform integration
Vector storesVector DBs (Topic 4.4)You want it inside the platform
GuardrailsSecurity controls (Topic 5.6)As one layer — not your only defence
Model fine-tuningPEFT (Topic 3.5)You want managed training infra
Managed convenience trades away control — know what you are giving up

A managed RAG service is fast to stand up and hides the plumbing. But when its retrieval underperforms, you have far less control over chunking, hybrid search, re-ranking and evaluation than the Phase 4 techniques give you — and the same is true of managed agents versus the Phase 08 patterns. The right call is usually: use managed services to move fast, but understand the underlying techniques so you can drop to custom when quality demands it. Knowing how to build RAG yourself is what lets you judge whether the managed one is good enough. The knowledge in this roadmap is what makes you effective with these platforms, not obsolete beside them.

Section 04 ProfessionalAvoiding lock-in

Cloud platforms want you to build on their proprietary services. Some lock-in is worth it for the integration; some you should resist.

Portability strategy
Keep portablePlatform-specific is fine
Your prompts, evals and business logicIAM, networking, billing integration
The model interface (behind your own or Spring AI)Which region and account
Your RAG pipeline, if quality is criticalManaged RAG for low-stakes internal tools
Your data, in open formatsPlatform monitoring dashboards

A pragmatic default: use the cloud platform your organisation already runs on (that decision is usually made for you), call models through a thin interface so the model choice stays flexible, and build your own RAG and agent layers for anything quality-critical while using managed services for quick internal tools. That keeps the enterprise benefits — governance, residency, one bill — without surrendering the parts of the system where your Phase 4–8 skills produce a better result than the platform's defaults.

Section 05 ProfessionalExercises

Do these — on a free/low-cost tier
  1. Call a model through one cloud platform (Bedrock, Azure OpenAI, or Vertex). Note how auth differs from a raw API key.
  2. Do the same call through Spring AI by changing only the starter and config — confirm your code is unchanged (Topic 3.2).
  3. Stand up a managed RAG service (e.g. Bedrock Knowledge Base) over a few documents. Compare its answers to your own Phase 4 pipeline.
  4. Where the managed RAG underperforms, identify which Phase 4 lever (chunking, hybrid, re-rank) you would reach for — and note that you cannot.
  5. Set up private networking so a model call never touches the public internet.
  6. Compare the same model's price and latency across two platforms and a raw API.
  7. Write a one-page recommendation: which platform, and which parts to keep portable, for a hypothetical employer on a given cloud.
