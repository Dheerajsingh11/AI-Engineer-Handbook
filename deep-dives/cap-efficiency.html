Step 01Measure before optimising

You cannot cut what you have not measured. Atlas logs the token counts, cost and latency of every request (Topic 19.3), so optimisation targets the real hotspots instead of guesses.

PythonPer-request cost & latency accounting
@dataclass
class Usage:
    tokens_in: int; tokens_out: int; latency_ms: float
    @property
    def cost(self):                              # local model: cost = compute time
        return self.latency_ms * COST_PER_MS     # or per-token for an API

Step 02Caching — the biggest win

In an internal docs assistant, many people ask the same things. Semantic caching answers a repeat question — even reworded — without touching the model at all (Topic 19.3).

Expected cost with a cache E[cost] = (1 − h) · costfull + h · costcache h is the cache hit-rate. Since a cache hit costs almost nothing, a 40% hit-rate cuts cost and latency by roughly 40%. The reason it works: the query is embedded (Ch. 20.3) and matched against past questions by cosine similarity — the same geometry that powers retrieval, reused for caching.
PythonSemantic cache in front of the agent
def answer(query, threshold=0.95):
    qv = encoder.encode([query], normalize_embeddings=True)[0]
    hit, score = cache.nearest(qv)               # vector lookup (Ch. 20.3)
    if score >= threshold:
        return hit                               # no model call -- free & instant
    ans = agent(query)                           # miss: pay once (Ch. 20.7)
    cache.add(qv, ans)
    return ans
The threshold is a correctness dial

Set the similarity threshold too loose and “how do I rotate the signing key?” returns the cached answer for “how do I rotate the API key?” — a confident wrong answer. Too tight and you never get a hit. So the cache needs the same evaluation as the model (Ch. 20.9): measure hit-rate and error-rate on real traffic, and stay conservative where a wrong answer is costly. Prompt (prefix) caching — reusing the processed system prompt and retrieved context across calls — is exact and risk-free, so it is the safe first reach (Topic 19.3).

Step 03Cascade — cheap model first

Not every question needs the full model. A cascade tries Atlas's small fine-tuned model first and escalates only the hard cases — here, to a larger model for questions the small one is unsure about (Topic 19.3).

Blended cost of a cascade E[cost] = costsmall + (1 − p) · costlarge p = fraction the small model handles acceptably. Every request pays the (cheap) small model; only the (1−p) that escalate also pay the large one. If the small model handles 70% (p=0.7), you pay the large model on just 30% of traffic — a large saving for little quality loss. The art is the escalation check that decides when to trust the small answer.

Step 04Stacking the wins

The efficiency layers on Atlas, and what each buys
TechniqueSavesRisk
4-bit quantisation (Ch. 20.6)~4× memory, faster inferenceTiny quality loss
Prompt (prefix) cachingInput cost on the shared prompt/contextNone — exact
Semantic cachingWhole calls on repeat questionsThreshold-tuned
CascadeBig-model cost on easy queriesEscalation-check quality
Concise outputsOutput cost & latency directlyNone if prompt is careful
The order-of-magnitude gap is real

These stack multiplicatively. A quantised model, serving cached prefixes, answering 40% of queries from a semantic cache, cascading the rest, and emitting concise output can cost a fraction of the naive “biggest model, every request, full context, no cache” version — for quality a user cannot distinguish. Every layer is measured against the eval set (Ch. 20.9) so no saving silently degrades answers. This is squarely an engineer's job, and it is where a systems background pays off directly (Topics 19.3, 18.3).
