Section 01 BeginnerStart from zero

Assumed knowledge

NumPy (Topic 2.2), gradient descent (Topic 1.4), and ideally the from-scratch network in Topic 2.4. PyTorch will make far more sense if you have written backpropagation once by hand.

PyTorch is NumPy with three additions: arrays can live on a GPU, every operation records itself so gradients can be computed automatically, and there is a library of pre-built layers and optimisers. That is genuinely the whole pitch.

The words, in plain English
Tensor
PyTorch's array. Same as an ndarray, plus device and gradient tracking.
Device
Where the tensor lives: cpu, cuda (NVIDIA), mps (Apple Silicon). Two tensors must be on the same device to interact.
Autograd
The automatic differentiation engine — the production version of the Value class in Topic 1.4.
Module
A layer or a whole model. Holds parameters and defines forward.
Parameter
A tensor a Module registers as learnable. Optimisers update these.
Optimizer
The update rule: SGD, AdamW. Holds the parameters and applies gradients.
DataLoader
Batches, shuffles and loads data in parallel worker processes.
Checkpoint
Saved weights, usually via state_dict().

Section 02 IntermediateAutograd, concretely

PythonWhat .backward() actually does
import torch

x = torch.tensor([2.0], requires_grad=True)
w = torch.tensor([3.0], requires_grad=True)
b = torch.tensor([1.0], requires_grad=True)

y = w * x + b
z = y ** 2                      # z = (3*2+1)^2 = 49

z.backward()                    # walks the recorded graph backwards

print(w.grad)   # dz/dw = 2*(wx+b)*x = 2*7*2 = 28
print(x.grad)   # dz/dx = 2*(wx+b)*w = 2*7*3 = 42
print(b.grad)   # dz/db = 2*(wx+b)   = 14

# Gradients ACCUMULATE. Run backward twice without clearing
# and you get double. This is why every training loop calls
# optimizer.zero_grad() -- forgetting it is the single most
# common PyTorch bug, and it produces a model that trains badly
# rather than one that errors.

# Turn tracking off for inference: less memory, faster.
with torch.no_grad():
    prediction = w * x + b

# Detach a tensor from the graph (e.g. to log it or store it)
value = z.detach().cpu().item()
The three device and dtype errors you will hit
  • Expected all tensors to be on the same device — model on GPU, data on CPU. Move the batch: batch.to(device).
  • can't convert cuda:0 device type tensor to numpy — call .cpu() before .numpy().
  • expected scalar type Float but found Double — NumPy defaults to float64, PyTorch to float32. Convert with .float().

Section 03 AdvancedThe training loop, every line justified

PythonA training loop you could ship
import torch, torch.nn as nn
from torch.utils.data import DataLoader, TensorDataset

device = ("cuda" if torch.cuda.is_available()
          else "mps" if torch.backends.mps.is_available() else "cpu")

model = nn.Sequential(
    nn.Linear(784, 256), nn.ReLU(), nn.Dropout(0.2),
    nn.Linear(256, 128), nn.ReLU(), nn.Dropout(0.2),
    nn.Linear(128, 10),                 # NO softmax here -- see below
).to(device)

# CrossEntropyLoss applies log-softmax internally, in a numerically
# stable fused way. Adding your own softmax first applies it twice
# and quietly damages training. A very common mistake.
criterion = nn.CrossEntropyLoss(label_smoothing=0.1)

optimizer = torch.optim.AdamW(model.parameters(), lr=3e-4, weight_decay=0.01)
scheduler = torch.optim.lr_scheduler.OneCycleLR(
    optimizer, max_lr=3e-4, total_steps=EPOCHS * len(train_loader))

scaler = torch.amp.GradScaler(device)   # mixed precision

def train_epoch(model, loader):
    model.train()                       # enables dropout, batchnorm updates
    total, seen = 0.0, 0
    for X, y in loader:
        X, y = X.to(device, non_blocking=True), y.to(device, non_blocking=True)

        optimizer.zero_grad(set_to_none=True)   # 1. clear old gradients

        # 2. forward in bf16/fp16: ~2x faster, ~half the memory
        with torch.autocast(device_type=device, dtype=torch.bfloat16):
            logits = model(X)
            loss = criterion(logits, y)

        scaler.scale(loss).backward()           # 3. backward pass

        # 4. unscale BEFORE clipping, or the clip threshold is wrong
        scaler.unscale_(optimizer)
        torch.nn.utils.clip_grad_norm_(model.parameters(), max_norm=1.0)

        scaler.step(optimizer)                  # 5. update weights
        scaler.update()
        scheduler.step()                        # 6. adjust learning rate

        total += loss.item() * len(y); seen += len(y)
    return total / seen

@torch.no_grad()                                # no graph -> less memory, faster
def evaluate(model, loader):
    model.eval()                                # disables dropout
    loss_sum, correct, seen = 0.0, 0, 0
    for X, y in loader:
        X, y = X.to(device), y.to(device)
        logits = model(X)
        loss_sum += criterion(logits, y).item() * len(y)
        correct  += (logits.argmax(1) == y).sum().item()
        seen     += len(y)
    return loss_sum / seen, correct / seen

best, patience, wait = float("inf"), 5, 0
for epoch in range(EPOCHS):
    tr = train_epoch(model, train_loader)
    va, acc = evaluate(model, val_loader)
    print(f"epoch {epoch:3d}  train {tr:.4f}  val {va:.4f}  acc {acc:.4f}")

    if va < best - 1e-4:                        # 7. early stopping
        best, wait = va, 0
        torch.save({"model": model.state_dict(),
                    "optimizer": optimizer.state_dict(),
                    "epoch": epoch}, "best.pt")
    else:
        wait += 1
        if wait >= patience:
            print("early stop"); break
The two mode switches that cause silent bugs

model.train() and model.eval() do not train or evaluate anything — they set a flag. Dropout is active in train mode and disabled in eval; BatchNorm updates its running statistics in train mode and uses the stored ones in eval.

Forgetting model.eval() before validation gives you noisy, pessimistic numbers. Forgetting model.train() after validation means the rest of your training runs without dropout. Neither raises an error. Both are easy to catch if you always write them as the first line of each function, as above.

Section 04 AdvancedFine-tune an embedding model for your domain

This is the most immediately useful PyTorch task for a RAG engineer. A general embedding model does not know that in your company "P1" means a severity level rather than a product code. A few thousand labelled pairs can fix that, and it often beats every retrieval tweak in §4.6.

PythonContrastive fine-tuning with in-batch negatives
import torch, torch.nn as nn, torch.nn.functional as F
from transformers import AutoTokenizer, AutoModel

MODEL = "sentence-transformers/all-MiniLM-L6-v2"
tokenizer = AutoTokenizer.from_pretrained(MODEL)
encoder = AutoModel.from_pretrained(MODEL).to(device)

def mean_pool(output, attention_mask):
    """Average the token vectors, ignoring padding. Averaging over
    padding is a real bug that quietly degrades every embedding."""
    tokens = output.last_hidden_state
    mask = attention_mask.unsqueeze(-1).expand(tokens.size()).float()
    return (tokens * mask).sum(1) / mask.sum(1).clamp(min=1e-9)

def embed(texts, max_length=256):
    batch = tokenizer(texts, padding=True, truncation=True,
                      max_length=max_length, return_tensors="pt").to(device)
    out = encoder(**batch)
    return F.normalize(mean_pool(out, batch["attention_mask"]), dim=-1)

def info_nce(q_emb, d_emb, temperature=0.05):
    """Multiple-negatives ranking loss.

    Every other document in the batch acts as a negative for this
    query -- so a batch of 32 gives 31 free negatives per example
    with no extra labelling. This is why large batches matter
    disproportionately for embedding training."""
    sim = q_emb @ d_emb.T / temperature          # (B, B)
    labels = torch.arange(len(sim), device=sim.device)   # diagonal = correct
    # Symmetric: query->doc and doc->query
    return (F.cross_entropy(sim, labels) + F.cross_entropy(sim.T, labels)) / 2

# Training data: (question, the passage that answers it) pairs.
# Mine these from your support tickets, docs FAQs, or resolved
# issues. 2,000 real pairs beats 50,000 synthetic ones.
pairs = [("how do I reset my password",
          "To reset your password, visit Settings > Security ..."),
         ("what is the refund window",
          "Refunds are available within 30 days of purchase ...")]

optimizer = torch.optim.AdamW(encoder.parameters(), lr=2e-5)

encoder.train()
for epoch in range(3):
    for batch in batches(pairs, size=32):        # bigger batch = better
        queries, docs = zip(*batch)
        loss = info_nce(embed(list(queries)), embed(list(docs)))
        optimizer.zero_grad(set_to_none=True)
        loss.backward()
        torch.nn.utils.clip_grad_norm_(encoder.parameters(), 1.0)
        optimizer.step()
    print(f"epoch {epoch} loss {loss.item():.4f}")

encoder.save_pretrained("./domain-embeddings")
tokenizer.save_pretrained("./domain-embeddings")

# CRITICAL: this model produces a NEW vector space. Every stored
# embedding must be regenerated. Version your index alongside the
# model and never mix vectors from two models -- see Topic 1.1.
Measure before and after, on your own data

Fine-tuning an embedding model is one of the highest-return actions available in a RAG system — recall@5 improvements of 10–20 points on domain-specific corpora are common. It is also easy to make things worse with too few pairs or too high a learning rate. Build the golden set from §4.7 first, record baseline recall@k, then fine-tune, then re-measure. Without that sequence you are guessing.

PythonGradient accumulation and inference-time speed
# Effective batch of 64 with only 16 in memory at a time
ACCUM = 4
optimizer.zero_grad(set_to_none=True)
for i, (X, y) in enumerate(loader):
    with torch.autocast(device_type=device, dtype=torch.bfloat16):
        loss = criterion(model(X.to(device)), y.to(device)) / ACCUM
    loss.backward()                          # gradients accumulate
    if (i + 1) % ACCUM == 0:
        torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)
        optimizer.step()
        optimizer.zero_grad(set_to_none=True)

# --- inference ---------------------------------------------------
model.eval()
model = torch.compile(model)                 # 1.3-2x, PyTorch 2.x

# Export for serving from a JVM or any non-Python runtime:
dummy = torch.randn(1, 784, device=device)
torch.onnx.export(model, dummy, "model.onnx",
                  input_names=["input"], output_names=["logits"],
                  dynamic_axes={"input": {0: "batch"}})
# ONNX Runtime has a Java API -- so a model you fine-tune in Python
# can be served directly from your Spring Boot service.
Running models from Java

You do not have to keep a Python service in the request path. Three routes exist: export to ONNX and use ONNX Runtime's Java API; use Deep Java Library (DJL), which loads PyTorch models directly from Java; or serve locally with llama.cpp or Ollama behind an OpenAI-compatible HTTP endpoint that Spring AI already speaks. For an embedding model in a latency-sensitive RAG path, ONNX Runtime in-process is often the cleanest answer — no network hop, no second deployment.

Section 06 ProfessionalExercises

Do these — roughly a weekend
  1. Rewrite the NumPy XOR network from Topic 2.4 in PyTorch. Note how much less code it is, and that you understand every line of what was removed.
  2. Verify autograd against your hand-derived gradients from Topic 1.4. They should match exactly.
  3. Remove optimizer.zero_grad() and watch training degrade without any error. Then put it back.
  4. Train an MLP on MNIST to above 97%. Add dropout and weight decay and compare the train/validation gap.
  5. Deliberately omit model.eval() during validation. Measure how much the reported accuracy moves.
  6. Fine-tune all-MiniLM-L6-v2 on 500 question–passage pairs from your own domain. Measure recall@5 before and after on a held-out set.
  7. Export a model to ONNX and run inference from Java with ONNX Runtime. Compare latency against an HTTP call to a Python service.
  8. Halve your batch size and add gradient accumulation to compensate. Confirm the loss curve is nearly unchanged.
