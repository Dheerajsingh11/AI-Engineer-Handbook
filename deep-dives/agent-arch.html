Agentic Architecture

Most systems called agents should not be. This page draws the workflow/agent line precisely, implements all six workflow patterns and the autonomous loops in Java, explains when multi-agent genuinely helps and when it multiplies cost for nothing, and gives the failure taxonomy for debugging systems that decide their own path.

Section 01 BeginnerStart from zero

Assumed knowledge

Tool calling from Topic 5.1 — in particular the loop. This page is about what to put around that loop, and when not to have one at all.

"Agent" has become a marketing word covering everything from a prompt template to an autonomous system that modifies infrastructure. For engineering purposes there is one distinction that matters, and it is about who decides the control flow.

The distinction that determines everything else
WorkflowAgent
Control flowYou write it. LLM calls sit at fixed pointsThe model decides it at runtime
PathKnown before executionDiscovered during execution
CostPredictableVariable, unbounded without limits
TestingEach step independentlyOnly end-to-end, statistically
DebuggingStandard tracingRead the reasoning trace and infer
LatencyBoundedUnpredictable
Best forMost production tasksGenuinely open-ended tasks
The guidance worth taking seriously

Prefer the simplest thing that works. A single well-prompted call beats a workflow. A workflow beats an agent. Reach for an autonomous agent only when the sequence of steps genuinely cannot be known in advance — and be honest about that, because "we might need flexibility later" is not the same as needing it now.

Autonomy is a cost, not a feature. You pay in tokens, latency, testability and debuggability. Buy it only when it purchases something.

JavaChaining, routing and parallelisation
// ---------- 1. PROMPT CHAINING ----------------------------------
// Each step is small, testable, and can use a cheaper model.
// A gate between steps stops bad input propagating.
public Report generateReport(String rawData) {
    String outline = chat.prompt()
            .user("Produce a section outline for a report on:\n" + rawData)
            .call().content();

    if (!validator.isUsableOutline(outline)) {          // programmatic gate
        throw new WorkflowGateException("outline rejected");
    }

    String draft = chat.prompt()
            .user(u -> u.text("Write the report following this outline:\n{o}\n\nData:\n{d}")
                        .param("o", outline).param("d", rawData))
            .call().content();

    return chat.prompt()
            .user("Tighten this report. Remove repetition. Keep all facts:\n" + draft)
            .call().entity(Report.class);
}

// ---------- 2. ROUTING ------------------------------------------
// A cheap classifier sends work to a specialist. Each handler gets
// a focused prompt instead of one prompt trying to cover everything.
public String handle(String message) {
    Category category = cheapChat.prompt()
            .user("Classify this request:\n" + message)
            .call().entity(Category.class);

    return switch (category) {
        case BILLING   -> billingHandler.handle(message);
        case TECHNICAL -> technicalHandler.handle(message);   // larger model
        case SIMPLE_FAQ -> faqHandler.handle(message);        // no LLM at all
        case OTHER     -> escalate(message);
    };
}

// ---------- 3. PARALLELISATION: SECTIONING ----------------------
public ComplianceResult check(String document) {
    List<CompletableFuture<PolicyFinding>> futures = policies.stream()
            .map(policy -> CompletableFuture.supplyAsync(
                    () -> checkAgainst(document, policy), aiExecutor))
            .toList();

    // Ten sequential calls at 3s each = 30s. Concurrently = ~3s.
    var findings = futures.stream().map(CompletableFuture::join).toList();
    return ComplianceResult.of(findings);
}

// ---------- 4. PARALLELISATION: VOTING --------------------------
public RiskLevel assess(String transaction) {
    // Temperature > 0 so the samples actually differ.
    var votes = IntStream.range(0, 5).parallel()
            .mapToObj(i -> classify(transaction, 0.7))
            .collect(Collectors.groupingBy(r -> r, Collectors.counting()));

    var winner = votes.entrySet().stream()
            .max(Map.Entry.comparingByValue()).orElseThrow();

    // Disagreement is itself a signal -- escalate rather than guess.
    if (winner.getValue() < 4) {
        return RiskLevel.NEEDS_HUMAN_REVIEW;
    }
    return winner.getKey();
}
JavaOrchestrator-workers and evaluator-optimiser
// ---------- 5. ORCHESTRATOR-WORKERS -----------------------------
// The planner decides HOW MANY subtasks -- that is what makes this
// different from sectioning, where the list is fixed by you.
public Answer research(String question) {
    Plan plan = orchestrator.prompt()
            .user("Break this question into independent research subtasks:\n" + question)
            .call().entity(Plan.class);

    if (plan.subtasks().size() > MAX_SUBTASKS) {         // always bound it
        plan = plan.truncate(MAX_SUBTASKS);
    }

    var results = plan.subtasks().parallelStream()
            .map(t -> worker.execute(t))
            .toList();

    return synthesiser.prompt()
            .user(u -> u.text("Combine these findings to answer: {q}\n\n{r}")
                        .param("q", question).param("r", format(results)))
            .call().entity(Answer.class);
}

// ---------- 6. EVALUATOR-OPTIMISER ------------------------------
// Only works when quality is genuinely assessable. If the evaluator
// cannot tell good from bad, this burns tokens and changes nothing.
public String refine(String task, int maxRounds) {
    String candidate = generator.prompt().user(task).call().content();

    for (int round = 0; round < maxRounds; round++) {
        Critique critique = evaluator.prompt()
                .user(u -> u.text("""
                        Assess this against the requirements.
                        Score 1-10 and list specific, actionable issues.

                        Requirements: {task}
                        Candidate: {candidate}
                        """).param("task", task).param("candidate", candidate))
                .call().entity(Critique.class);

        if (critique.score() >= 8 || critique.issues().isEmpty()) {
            return candidate;                            // good enough
        }
        candidate = generator.prompt()
                .user(u -> u.text("Revise, addressing these issues:\n{i}\n\n{c}")
                            .param("i", format(critique.issues()))
                            .param("c", candidate))
                .call().content();
    }
    return candidate;
}

Section 03 AdvancedAutonomous agent loops

The four loop architectures
PatternMechanismStrengthWeakness
ReActThought → Action → Observation, repeatedSimple; adapts after every observationCan loop unproductively; no global plan
Plan-and-ExecutePlan the whole sequence, then run itFewer model calls; clear audit trailBrittle if the plan is wrong; cannot adapt mid-run
ReflexionCritique own attempt, retry with the lessonBetter outcomes on hard tasks2–3× the tokens
Tree searchExplore and score multiple branchesStrong on search and planning problemsVery expensive; rarely justified
JavaPlan-and-execute with replanning, and loop detection
public AgentResult planAndExecute(String goal, int maxSteps) {

    Plan plan = planner.prompt()
            .user("Create a numbered plan of tool-executable steps for:\n" + goal)
            .call().entity(Plan.class);

    var completed = new ArrayList<StepResult>();
    var recentCalls = new ArrayDeque<String>();

    for (int i = 0; i < maxSteps && !plan.isComplete(); i++) {
        Step step = plan.next();

        // LOOP DETECTION: the same call three times in a row means
        // the agent is stuck. Break out rather than burning the budget.
        String signature = step.tool() + "|" + step.arguments();
        recentCalls.addLast(signature);
        if (recentCalls.size() > 3) recentCalls.removeFirst();
        if (recentCalls.size() == 3 && Set.copyOf(recentCalls).size() == 1) {
            return AgentResult.stuck(goal, completed, "repeated identical call");
        }

        StepResult result = executor.execute(step);
        completed.add(result);

        // REPLAN on failure. A plan made before seeing the data is
        // often wrong; the ability to revise is what makes this work.
        if (result.failed()) {
            plan = planner.prompt()
                    .user(u -> u.text("""
                            Goal: {goal}
                            Completed: {done}
                            Step "{step}" failed: {error}
                            Produce a revised plan for the remaining work.
                            """)
                        .param("goal", goal).param("done", format(completed))
                        .param("step", step.description())
                        .param("error", result.error()))
                    .call().entity(Plan.class);
        } else {
            plan = plan.advance();
        }
    }
    return AgentResult.of(goal, completed, synthesise(goal, completed));
}

Section 04 AdvancedMulti-agent systems

Topologies, from most to least controllable
TopologyStructureCaution
SupervisorOne coordinator delegates to specialistsStart here if you need multiple agents at all
HierarchicalSupervisors of supervisorsDebugging cost grows sharply with depth
HandoffControl transfers with the conversationClean for support escalation; state must transfer too
BlackboardAgents read and write shared stateFamiliar — it is event-driven architecture (§5.4)
NetworkAny agent calls any otherEmergent behaviour; very hard to test or reason about
The questions to answer before adding a second agent

Most multi-agent designs would work better as one agent with more tools, or as a plain workflow. Each additional agent multiplies token cost, adds a failure mode, and makes the trace harder to read. Before adding one, answer:

  • Does it need a genuinely separate context window? Real reason — a research sub-agent can read 200k tokens and return a 500-token summary, keeping the parent's context clean.
  • Does it need different permissions? Real reason — a read-only analysis agent and a write-capable action agent is meaningful privilege separation.
  • Do the subtasks genuinely run in parallel? Real reason, and measurable.
  • "It seemed more modular"? Not a reason. Use methods.
JavaSupervisor with genuinely separated concerns
@Service
class SupervisorAgent {

    private final Map<String, SpecialistAgent> specialists;

    public Answer handle(String request, Principal principal) {

        Delegation delegation = supervisor.prompt()
                .system("""
                    You coordinate specialists. Choose ONE to handle the
                    request, and state precisely what you need from it.

                    research  - read-only. Searches documents and the web.
                    analysis  - read-only. Computes over structured data.
                    action    - can modify records. Requires approval.
                    """)
                .user(request)
                .call().entity(Delegation.class);

        var specialist = specialists.get(delegation.specialist());
        if (specialist == null) {
            return Answer.error("No such specialist.");
        }

        // PRIVILEGE SEPARATION is the real justification here.
        // The research agent physically cannot write, whatever any
        // injected instruction in a retrieved document may say.
        if (!authz.permits(principal, specialist.requiredScope())) {
            return Answer.error("Not permitted.");
        }

        // The specialist runs in its OWN context and returns a summary,
        // not a transcript. This is the context-isolation benefit.
        return specialist.execute(delegation.instruction(), principal);
    }
}

Section 05 ProfessionalHow agents fail, and how to see it

Failure taxonomy
FailureSymptomMitigation
Goal driftEnds up solving a different problemRestate the goal in each turn; check final output against it
Infinite loopSame action repeatedlyLoop detection (Section 03); step limits
Premature completionDeclares success without doing the workExplicit completion criteria; verification step
Context exhaustionDegrades after many stepsCompaction; offloading; sub-agents (§5.3)
Cascading errorsOne bad step poisons everything afterValidate between steps; replan on failure
Cost explosionOne run costs a hundred times the medianToken budget per run; alert on outliers
Silent wrong answerPlausible output, incorrectVerification tools; citations; human review on high stakes
Over-delegationSub-agents spawning sub-agentsBound recursion depth explicitly
What to trace

An agent run is a span tree, and it is the only way to debug something whose control flow you did not write. Capture per step: the model's stated reasoning, the tool called with arguments, the result size, the duration, tokens consumed, and cumulative cost. Then track four aggregates: steps per run (rising = the agent is struggling), cost per run p50 and p99 (the gap reveals runaway cases), completion rate, and human-intervention rate.

Set hard limits on all of it — max steps, max tokens, max wall time, max cost — and treat hitting a limit as an alert, not just a failure. It usually means a class of input you did not anticipate.

Choosing the architecture
If the task…Use
Is one well-defined transformationA single prompted call
Has known steps in a fixed orderPrompt chaining
Splits into distinct categoriesRouting
Has independent subtasks known in advanceParallelisation
Has a checkable quality barEvaluator–optimiser
Has subtasks discovered at runtimeOrchestrator–workers
Genuinely cannot be planned in advanceReAct agent, with hard limits
Needs separate permissions or context windowsSupervisor multi-agent

Section 06 ProfessionalExercises

Do these — roughly a weekend
  1. Take a task you were going to build as an agent. Implement it as a workflow instead. Compare cost, latency and testability honestly.
  2. Implement all six workflow patterns on small tasks. You will recognise them in every framework afterwards.
  3. Build routing with a small model as classifier and a large one for hard cases. Measure the cost saving over always using the large model.
  4. Implement voting with five samples. Find a case where the votes split and confirm your escalation path works.
  5. Build evaluator–optimiser. Then check whether the evaluator's scores correlate with human judgement — if not, the loop is theatre.
  6. Implement plan-and-execute with replanning. Make a tool fail deliberately and watch it recover.
  7. Add loop detection. Construct a scenario that loops and confirm you break out cleanly.
  8. Instrument a run as a span tree with per-step cost. Find the p99 run and work out what made it expensive.
