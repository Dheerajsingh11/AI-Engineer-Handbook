19.1

LLM Evaluation & Benchmarks

The discipline that separates engineers from demo-builders. This page covers how to measure whether an LLM system actually works — benchmarks, LLM-as-judge, human evaluation, and offline vs online testing — why "it looked good in the playground" is not evidence, and how to build an eval you can trust a decision on.

Section 01 BeginnerStart from zero

Assumed knowledge

Prompting (Topic 3.1) and a system worth measuring. This page is the general evaluation discipline; RAG evaluation (Topic 4.7) and agent evaluation (Topic 8.10) are the task-specific specialisations of it.

You cannot improve what you cannot measure, and with LLMs this is unusually hard: the output is open-ended text, "correct" is often a matter of degree, and the same prompt can give different answers. LLM evaluation is the set of methods for turning "does this system work?" into a number you can track, compare and defend.

Why this is the skill that gets you hired

Everyone can wire up an LLM and get a plausible-looking answer. Far fewer can say how often it is right, where it fails, and whether yesterday's prompt change helped or hurt. That gap — between a demo and a measured system — is the whole difference between a hobby project and production engineering, and it is exactly what interviewers and hiring managers screen for (Topic 17.4). Evaluation is not the boring part after the building; on a serious AI project it is the building.

The words, in plain English
Eval set
A fixed collection of test cases with known-good answers or criteria.
Benchmark
A standard public eval set used to compare models (MMLU, HumanEval…).
LLM-as-judge
Using a strong model to score another model's outputs.
Offline eval
Testing against a fixed dataset before shipping.
Online eval
Measuring real user outcomes in production (A/B tests, feedback).
Regression
A change that quietly makes something that worked stop working.

Section 02 IntermediateBenchmarks & their limits

Public benchmarks are how the field compares models. They are useful for orientation and dangerous if over-trusted.

Benchmarks you will see quoted
BenchmarkMeasures
MMLUBroad knowledge across 57 subjects (multiple choice)
GPQAHard, graduate-level science reasoning
HumanEval / SWE-benchCode generation; real GitHub issue fixing
MATH / GSM8KMathematical reasoning
MT-Bench / Chatbot ArenaConversation quality; human preference at scale
Why benchmarks lie to you

Three reasons to distrust a leaderboard. Contamination: a benchmark on the public web may be in the model's training data, so a high score can mean memorisation, not skill. Mismatch: MMLU tells you nothing about how the model handles your customers' insurance queries. Saturation & gaming: once everyone optimises for a benchmark, it stops discriminating and models get tuned to it. Benchmarks are a rough first filter for picking candidate models — the real decision needs your own eval on your own task. Your task is your benchmark.

Section 03 IntermediateBuilding your own eval

The eval that matters is the one built from your task. It does not need to be big to be transformative — even 50–100 good cases change how you work.

  1. Collect real cases. Pull actual inputs from logs or users, including the weird ones. Cover the range of what production will see.
  2. Define "good". For each case, write the expected answer or explicit criteria. This forces you to say what you actually want — usually the hardest, most clarifying step.
  3. Choose a scoring method. Exact match, or a rubric, or an LLM judge (Section 04) — matched to how open-ended the task is.
  4. Run & record a baseline. Score the current system. Now you have a number.
  5. Change one thing, re-run. New prompt, new model, new retrieval — and see the number move instead of guessing.
  6. Guard against regressions. Keep the eval in CI so an "improvement" that breaks ten old cases is caught before it ships.
The unit test analogy

For a Java engineer this is the most natural framing: an eval set is a test suite for a non-deterministic system. You would never refactor a payments service with no tests and ship on vibes; an LLM prompt is no different. The difference is that assertions are fuzzy (a rubric or a judge, not assertEquals) and you track a pass rate rather than green/red. But the discipline — write cases, run on every change, block regressions — is identical, and it is what turns prompt-tweaking from guesswork into engineering.

Section 04 AdvancedLLM-as-judge & human eval

When outputs are open-ended, you cannot match strings. The two scalable answers are a model judge and human raters — each with a role.

PythonAn LLM judge with a rubric
# Judge with EXPLICIT criteria and a scale. Vague prompts give vague scores.
judge_prompt = """You are grading a support answer. Score 1-5 on:
- Correctness: are the facts right per the reference?
- Completeness: does it fully answer the question?
- Grounding: is every claim supported by the provided context?

Question: {q}
Reference: {ref}
Answer to grade: {ans}

Return JSON: {{"correctness": n, "completeness": n, "grounding": n,
"reason": "..."}}"""

# Validate the judge against ~50 human-scored examples before trusting it.
# Bias to watch: judges favour longer, more confident answers.
Which scoring method, when
MethodGood forWatch out for
Exact / rulesClosed answers, extraction, classificationToo rigid for open text
LLM-as-judgeOpen-ended quality, scale, cheap iterationLength/position bias; must be validated
Human evalGround truth, nuance, the gold standardSlow, costly — use for calibration
A/B test (online)Real outcomes: resolution rate, clicksNeeds traffic; slower signal
Validate the judge, then let it scale

An LLM judge is only trustworthy once you have checked it against humans: have people score ~50 examples, compare the judge's scores, and confirm they agree well enough. Then the judge scales the humans' judgement across thousands of cases cheaply. Known biases to correct for: judges tend to prefer longer and more confident answers, and to favour whichever response comes first in a pairwise comparison — so randomise order and control for length. Used this way, judge + periodic human calibration + online A/B on the metric that matters is the full evaluation stack.

Section 05 ProfessionalOffline to online

Offline evals tell you whether to ship a change; online evals tell you whether it worked. The professional loop connects them: iterate fast against an offline eval set, ship the winner behind an A/B test, measure the real outcome (resolution rate, task success, thumbs-up, escalation rate), and feed the failures back into the offline set so it keeps getting harder and more representative (Topic 18.1). Beware the classic trap — a change that improves your offline number and hurts the real metric, which means your eval set has drifted from reality. Watch cost and latency as first-class metrics too (Topic 19.3): a "better" answer that doubles cost or latency may be a worse product. The eval set is a living asset, not a one-off; the teams that win are the ones whose evaluation compounds.

Section 06 ProfessionalExercises

Do these — the highest-leverage habit in the handbook
  1. Build a 50-case eval set for a real task from actual inputs. Writing the "expected answer" column is the exercise.
  2. Score your current system to get a baseline number. Change the prompt, re-run, and watch it move.
  3. Write an LLM judge with an explicit rubric. Grade the same outputs yourself and measure how well the judge agrees.
  4. Demonstrate judge bias: feed it a short correct answer and a long waffly one. See which it prefers.
  5. Put your eval in CI. Make a "clever" prompt change that improves new cases but breaks old ones, and catch the regression.
  6. Design an online A/B test for the same feature: what real metric would prove it works? Contrast it with the offline score.
