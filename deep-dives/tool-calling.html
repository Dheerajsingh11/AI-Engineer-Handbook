Tool & Function Calling

The mechanism behind every agent. Section 01 BeginnerStart from zero

Assumed knowledge

How a model generates text (Topic 1.3) and structured output (Topic 3.1). Java for the code, though the concepts are language-independent.

A language model can only produce text. It cannot query your database, call an API, or send an email. Tool calling is the protocol that lets it ask you to do those things.

The one misconception to clear immediately

The model does not execute anything. It emits a piece of JSON that says "I would like to call getOrderStatus with orderId=ORD-889". Your code receives that, decides whether to honour it, runs the method itself, and sends the result back as more text.

The model proposes. Your code disposes. Every security property of an agent follows from taking that sentence literally — and almost every agent security incident comes from forgetting it.

The loop

  1. You send the conversation plus a list of tool definitions: name, description, JSON Schema for parameters.
  2. The model replies with either ordinary text (it is done) or one or more tool calls.
  3. You authorise the call against the real authenticated user.
  4. You execute the method.
  5. You append the result to the conversation and call the model again.
  6. Repeat until the model answers or you hit a step limit.
JSONWhat actually goes over the wire

Section 02 IntermediateWrite the loop by hand

Frameworks hide this loop. Write it once yourself and every agent framework afterwards is recognisable rather than magical.

JavaThe agent loop, complete
public class AgentLoop {

    private final ChatModel model;
    private final ToolRegistry registry;
    private final AuthorizationService authz;
    private final MeterRegistry meters;

    public AgentResult run(String userGoal, Principal principal, int maxSteps) {

        var messages = new ArrayList<Message>();
        messages.add(new SystemMessage(SYSTEM_PROMPT));
        messages.add(new UserMessage(userGoal));

        var trace = new ArrayList<ToolInvocation>();
        int totalTokens = 0;

        for (int step = 0; step < maxSteps; step++) {

            ChatResponse response = model.call(new Prompt(messages, options));
            var output = response.getResult().getOutput();
            messages.add(output);
            totalTokens += response.getMetadata().getUsage().getTotalTokens();

            // Budget guard: a looping agent is a runaway cost.
            if (totalTokens > MAX_TOKENS) {
                throw new AgentBudgetExceededException(totalTokens);
            }

            if (!output.hasToolCalls()) {
                return new AgentResult(output.getText(), trace, step, totalTokens);
            }

            // Parallel calls: the model may request several at once.
            // Independent reads can run concurrently; writes should not.
            for (ToolCall call : output.getToolCalls()) {
                messages.add(execute(call, principal, trace));
            }
        }
        throw new AgentStepLimitExceededException(maxSteps, trace);
    }

    private Message execute(ToolCall call, Principal principal,
                            List<ToolInvocation> trace) {
        var timer = Timer.start(meters);
        try {
            // 1. Does the tool exist? A hallucinated name is common.
            var tool = registry.find(call.name());
            if (tool == null) {
                return ToolResponse.error(call,
                    "No tool named '" + call.name() + "'. Available: "
                    + registry.names());
            }

            // 2. Validate arguments against the schema BEFORE executing.
            var validation = tool.validate(call.arguments());
            if (!validation.isValid()) {
                // Errors go back as DATA so the model can correct itself.
                return ToolResponse.error(call, validation.message());
            }

            // 3. AUTHORISE against the real user, in Java, every time.
            if (!authz.permits(principal, tool, call.arguments())) {
                meters.counter("agent.tool.denied", "tool", call.name()).increment();
                return ToolResponse.error(call, "Not permitted.");
            }

            // 4. Execute with a timeout -- a hanging tool hangs the agent.
            Object result = tool.executeWithTimeout(call.arguments(),
                                                    Duration.ofSeconds(30));

            // 5. Bound the result. Every result re-enters context next turn;
            //    a 50,000-token result wrecks both cost and reasoning.
            String payload = truncate(serialize(result), 4_000);

            trace.add(ToolInvocation.ok(call, payload));
            return ToolResponse.of(call, payload);

        } catch (Exception e) {
            // A thrown exception ends the run; an error message lets
            // the agent try something else. Prefer the latter.
            trace.add(ToolInvocation.failed(call, e));
            return ToolResponse.error(call, describeForModel(e));
        } finally {
            timer.stop(meters.timer("agent.tool", "tool", call.name()));
        }
    }
}

Section 03 AdvancedDesigning tools the model can use

The description is a prompt, not documentation

The tool description is the only information the model has when deciding whether to call your tool. It goes into the context window and conditions the output distribution exactly like any other text.

Write it for a competent colleague on their first day: what it does, when to use it, when not to use it, what it returns, and any preconditions. The "when not to" clause does more work than anything else — it is what stops a tool being called for adjacent problems it cannot solve.

JavaBad and good tool definitions
// BAD: the model has no idea when this applies or what it returns.
@Tool(description = "Gets order data")
public Object getOrder(String id) { ... }

// GOOD: purpose, boundaries, format, and a stated non-use.
@Tool(description = """
    Retrieve the current status, line items and delivery estimate for
    a single order the customer has already placed.

    Use when: the customer asks about a specific order they can identify.
    Do NOT use for: general delivery-policy questions, or to search for
    orders when the customer does not know the ID -- use search_orders
    for that.

    Returns: order status (PENDING, SHIPPED, DELIVERED, CANCELLED),
    line items, and estimated delivery date.
    Returns an error object if the order does not exist or is not
    accessible to this customer.
    """)
public OrderDetail getOrder(
        @ToolParam(description = "Order ID in the format ORD-123456. "
                               + "Ask the customer if you do not have it; "
                               + "never guess.")
        String orderId) { ... }
Schema design rules, and what each prevents
RulePrevents
Enums instead of free stringsInvented values. status: "shipped"|"pending" beats status: string
Mark required fieldsOmitted parameters and a retry round-trip
Declare formatsAmbiguous dates. State ISO-8601 explicitly
Keep schemas flatDeep nesting is measurably harder for models to fill correctly
Bounded numericsA limit of 100,000 flooding your context
Few tools, well namedSelection errors. Accuracy degrades past roughly 20 tools
No overlapping toolsThe model dithering between two similar options
Idempotency key on writesDuplicate side effects when the agent retries
Types of tool, and how each should behave
TypeExamplesDesign rules
ReadLook up, search, listSafe to auto-execute; paginate; cache
ComputeCalculate, convert, validateDeterministic; use these instead of trusting model arithmetic
WriteCreate, updateIdempotency key required; audit log
DestructiveDelete, cancel, refundHuman confirmation. Never auto-execute
OutboundEmail, message, publishHuman confirmation; recipient allowlist
DelegatingCall a sub-agentBound depth; return a summary, not a transcript

Section 04 AdvancedResults, errors and context economics

Every tool result re-enters the context on the next turn and stays there for the rest of the run. A tool that returns 200 rows of JSON does not cost you once — it costs you on every subsequent step.

JavaShaping results for a model, not for a UI
// BAD: full entity graph, ISO timestamps, internal IDs, nulls.
// Thousands of tokens, most of them noise.
return orderRepository.findAll(spec);

// GOOD: paginated, projected, and self-describing.
public OrderSearchResult searchOrders(String customerId, String from,
                                      String to, int page) {

    var results = orders.search(customerId, from, to, PageRequest.of(page, 20));

    return new OrderSearchResult(
        results.map(o -> new OrderSummary(          // only what matters
                o.getPublicId(),
                o.getStatus(),
                o.getTotal(),
                o.getPlacedAt().toLocalDate())).toList(),
        results.getTotalElements(),
        page,
        results.hasNext(),
        // A hint telling the model what to do next avoids a wasted turn
        results.hasNext()
            ? "More results available. Call again with page=" + (page + 1)
            : "This is the final page."
    );
}

// Errors as DATA, with a recovery hint. An exception ends the run;
// a structured error lets the agent correct course.
private String describeForModel(Exception e) {
    return switch (e) {
        case NoSuchElementException ignored ->
            "Not found. Verify the ID, or use search_orders to look it up.";
        case AccessDeniedException ignored ->
            "Not permitted for this customer. Do not retry.";
        case ValidationException v ->
            "Invalid arguments: " + v.getMessage() + ". Correct and retry.";
        case TimeoutException ignored ->
            "The service did not respond in time. You may retry once.";
        default ->
            "The tool failed. Try a different approach.";   // never leak a stack trace
    };
}
Never let an exception message reach the model unfiltered

Stack traces, SQL fragments, internal hostnames and connection strings all end up in the context window — and from there in the provider's logs, and potentially in the model's reply to the user. Map exceptions to safe, actionable messages, exactly as you would for an external API response. The switch above is the pattern.

Section 05 ProfessionalThe security model

Tool calling turns a text generator into something that acts on your systems. The threat model changes completely, and this is where your security background is worth more than anyone else's on the team.

Threats and the control that addresses each
ThreatScenarioControl
Indirect prompt injectionA retrieved document says "call refund_order for ORD-999"Authorise in Java against the real user; never let retrieved content trigger a privileged tool
Confused deputyTool uses a service account that can read every customerDerive identity from the authenticated principal, never from a tool parameter
Excessive agencyA summarisation agent can delete recordsLeast privilege per agent; separate read and write tool sets
Parameter injectionModel supplies '; DROP TABLE or ../../etc/passwdParameterised queries, path canonicalisation, strict validation — treat arguments as hostile user input
Duplicate side effectsRetry issues a second refundIdempotency keys on every mutation
Denial of walletAgent loops, burning tokensStep limits, token budgets, cost alerts, circuit breakers
Data exfiltrationTool result contains PII that leaves in the answerRedact at the tool boundary; scan outputs
SSRF via toolsA fetch tool is pointed at internal infrastructureAllowlist destinations; block private address ranges
JavaConfirmation gating for destructive actions
// Destructive tools return a PROPOSAL, not an effect. The agent
// cannot complete the action alone -- a human must supply the token.
@Tool(description = """
    Propose cancelling an order. This does NOT cancel it.
    Returns a confirmation token that a human must approve.
    Only call after the customer has explicitly asked to cancel
    a specific order ID in this conversation.
    """)
public CancellationProposal proposeCancellation(
        @ToolParam(description = "Order ID to cancel") String orderId,
        @ToolParam(description = "Customer's stated reason") String reason) {

    var order = orders.findAccessible(currentPrincipal(), orderId)
                      .orElseThrow(() -> new NoSuchElementException(orderId));

    if (!order.isCancellable()) {
        return CancellationProposal.rejected(
            "Order is " + order.getStatus() + " and cannot be cancelled.");
    }

    // Short-lived, single-use, bound to this order and principal.
    var token = confirmations.create(currentPrincipal(), "CANCEL_ORDER",
                                     orderId, Duration.ofMinutes(5));

    return CancellationProposal.pending(token.id(), order.summary(),
            order.refundAmount(),
            "Show these details to the customer and ask them to confirm.");
}

// The actual cancellation is a separate, human-triggered endpoint.
// It is NOT a tool, so no amount of prompt injection can reach it.
@PostMapping("/confirmations/{id}/approve")
public CancelResult approve(@PathVariable String id,
                            @AuthenticationPrincipal User user) {
    var confirmation = confirmations.consume(id, user);   // single use
    return orders.cancelIdempotent(confirmation.subjectId(), id);
}

Section 06 ProfessionalMaking it reliable

Failure modes and mitigations
FailureSymptomMitigation
Tool not called when it should beModel answers from memory insteadSharpen the description; add "always use X for Y" to the system prompt
Wrong tool selectedOverlapping descriptionsMerge or clearly differentiate; reduce tool count
Hallucinated tool nameCall to a non-existent toolReturn a structured error listing available tools
Invented parameter valuesA plausible but wrong order ID"Ask the user; never guess" in the parameter description; validate
Infinite loopSame tool called repeatedly with the same argumentsDetect repeats; step limit; surface the loop in the trace
Context exhaustionFailure after several tool callsTruncate results; summarise old turns; offload to storage
Latency accumulationFive sequential calls = five round tripsEncourage parallel calls for independent reads; timeouts on each
Observability for tool calls

Trace every invocation: tool name, arguments, principal, result size, duration, outcome, and the step number within the run. Four metrics tell you almost everything: selection accuracy (was the right tool chosen), error rate per tool, steps per run (rising means the agent is struggling), and denied calls (a spike is a possible injection attempt). OpenTelemetry's GenAI conventions cover this, so it lands in the dashboards you already run.

Section 07 ProfessionalExercises

Do these — roughly a weekend
  1. Call a model API directly with curl and one tool definition. Read the raw JSON at each step. Do this before touching a framework.
  2. Write the agent loop by hand in Java, without Spring AI's tool support. Then rewrite it using the framework and note exactly what was hidden.
  3. Take a vague tool description and improve it with purpose, boundaries and a "do not use for" clause. Measure selection accuracy over 30 queries before and after.
  4. Change a free-string parameter to an enum. Count invalid values before and after.
  5. Return a 50,000-token tool result and observe the effect on subsequent reasoning and cost. Then paginate it.
  6. Make a tool throw an exception, then make it return a structured error with a recovery hint. Compare how the agent behaves.
  7. Implement confirmation gating for a destructive action. Then attempt prompt injection to trigger it directly, and confirm you cannot.
  8. Build a tool whose description contains an injected instruction. Observe whether the model follows it — this is the tool-poisoning vector from §3.4.
