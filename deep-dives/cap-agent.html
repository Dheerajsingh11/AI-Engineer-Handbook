Step 01Why an agent, not a pipeline

A fixed pipeline — always retrieve, then answer — is fine until a query does not need retrieval (“summarise our last conversation”) or needs a different tool (“what's the status of ticket 412?”). An agent lets the model decide which action to take each turn (Topic 5.2, 8.1).

Step 02The reason–act loop

Atlas uses the ReAct pattern: the model alternates between reasoning about what to do and acting by calling a tool, observing the result, and repeating until it can answer (Topic 8.7).

TextReAct — the loop, in the abstract
loop:
    Thought   : the model reasons about the query and what it still needs
    Action    : it emits a tool call, e.g. retrieve("rotate signing key")
    Observation: the tool result is fed back into the context
until the model chooses Action = final_answer(...)   --> then return it
PythonThe agent loop, concretely
TOOLS = {"retrieve": retrieve_rerank, "lookup_ticket": lookup_ticket}

def agent(query, max_steps=5):
    messages = [{"role": "system", "content": SYSTEM_PROMPT},
                {"role": "user", "content": query}]
    for _ in range(max_steps):
        step = llm(messages, tools=TOOL_SCHEMAS)      # model picks a tool
        if step.tool == "final_answer":
            return step.args["answer"]                # done
        result = TOOLS[step.tool](**step.args)        # execute it
        messages += [step.as_assistant(),
                     {"role": "tool", "content": str(result)}]  # observe
    return "I couldn't complete that in time."        # step budget guard

Step 03Reliable tool calls

For the loop to work, the model's tool call must be machine-valid every time — the right tool name and correctly-typed arguments. This is exactly the structured-generation problem (Topic 5.7).

PythonTyped tool schemas force valid calls
from pydantic import BaseModel

class Retrieve(BaseModel):     query: str
class LookupTicket(BaseModel): ticket_id: int          # must be an int
class FinalAnswer(BaseModel):  answer: str; sources: list[str]

# The schema is passed to the model; constrained decoding guarantees
# the emitted call parses and types check -- no "mostly valid" (Ch. 5.7).
TOOL_SCHEMAS = [Retrieve, LookupTicket, FinalAnswer]
Tool taxonomy — what Atlas's tools represent

Atlas's three tools cover the two fundamental kinds (Topic 8.4). retrieve and lookup_ticket are read tools — they fetch information and are safe to call freely. A write tool (say close_ticket) would change the world and demands more care: confirmation, permissions, an audit trail (Topic 20.11). Atlas deliberately ships only read tools first — the safe half — and would gate any write behind a human approval step. Knowing which side of that line a tool sits on is the core of safe agent design.

Step 04Memory & orchestration

Real conversations have history, and real agents need structure beyond a for loop. A state graph (LangGraph-style) makes the flow explicit and lets memory, retries and branching live in one place (Topics 5.3, 7.1, 8.2).

PythonThe agent as an explicit state graph
from langgraph.graph import StateGraph

g = StateGraph(AtlasState)          # state: messages, memory, step count
g.add_node("reason", call_model)
g.add_node("act", run_tool)
g.add_conditional_edges("reason",
    lambda s: "end" if s.done else "act")   # final_answer -> end
g.add_edge("act", "reason")                 # observe -> reason again
atlas = g.compile(checkpointer=memory)      # memory persists turns (Ch. 5.3)
Agents fail in specific ways — design for them

Give an agent tools and a loop and three failures appear. Loops: it calls the same tool forever — cap the steps (the budget above). Runaway cost: each step is an LLM call, so a chatty agent is expensive — the efficiency levers of chapter 20.10 apply. Unsafe actions: a write tool acting on a hallucinated argument — gate writes behind confirmation (Topic 20.11). The professional agent is not the one with the most tools; it is the one with the tightest guardrails around them (Topic 8.10). Atlas keeps the loop short, the tools read-only, and every step observable.
