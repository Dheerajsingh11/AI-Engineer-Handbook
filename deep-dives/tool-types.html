Types of Tools in AI

The full taxonomy of what an agent can be given. This page catalogues every kind of tool — function, retrieval, code-execution, computer-use, web, memory, sub-agent, human-in-the-loop, MCP — with what each is for, how to design it, its failure modes and its blast radius, so you can assemble an agent's capabilities deliberately rather than bolting on whatever is handy.

Section 01 BeginnerStart from zero

Assumed knowledge

Tool calling mechanics (Topic 5.1) and the agent loop (Topic 8.1). This page is the catalogue; 8.1 is the machine that uses it.

An agent is only as capable as its tools. "Give it tools" sounds simple, but tools are not all one thing — they differ in what they touch, how much can go wrong, and how you must design and guard them. Treating them as one undifferentiated bag is how agents become unsafe and unreliable.

The most useful first cut is by what a tool does to the world:

The two axes that decide everything about a tool
Reads onlyChanges something
Inside your systemQuery a DB, search docs — safe to auto-runUpdate a record — needs idempotency + audit
Outside your systemWeb search, fetch a URL — watch for injectionSend email, make payment — human gate
The rule this axis gives you

Reads can be automatic; writes need controls; outbound and destructive actions need a human. Before adding any tool to an agent, place it in that 2×2 grid — it tells you immediately how much guarding it needs (Topics 8.6, 5.6). An agent whose tools are all in the top-left is low-risk; one tool in the bottom-right changes the entire security posture.

Section 03 IntermediateDesigning each type well

Function / API tools — the workhorse

The default and most common. The description is a prompt (Topic 5.1); the schema is your validation boundary. Return errors as data with a recovery hint. Make writes idempotent.

PythonA well-designed function tool
@tool
def create_ticket(title: str, severity: int, team: str) -> dict:
    """Create a support ticket. Use ONLY after the user has confirmed
    the details. Returns the ticket ID, or an error object.
    - severity: 1 (trivial) to 5 (outage)
    - team: one of engineering | billing | account
    """
    if severity not in range(1, 6):
        return {"error": "severity must be 1-5"}      # error as data
    if team not in {"engineering", "billing", "account"}:
        return {"error": f"unknown team '{team}'"}
    # idempotency key so a retry does not double-create (Topic 5.1)
    return tickets.create_idempotent(title, severity, team,
                                     key=hash((title, severity, team)))

Code-execution tools — the most powerful and most dangerous

Letting the model write and run code makes it dramatically more capable — and hands it arbitrary execution. The non-negotiable is the sandbox.

Sandboxing is mandatory, not optional

Generated code must run in an isolated environment with: no access to your network or secrets, a read-only or scratch-only filesystem, CPU/memory/time limits, and no ability to reach production. Use a container, a microVM (gVisor, Firecracker), or a hosted sandbox (E2B, Modal, the provider's own code-execution tool). Never exec() model output in your application process. A single unsandboxed code tool turns prompt injection (Topic 5.6) into remote code execution on your infrastructure.

Retrieval tools

A RAG query engine (Topic 7.2) exposed as a tool. The agent decides when to search rather than searching every turn — which is more efficient and lets it combine retrieval with other actions. Enforce tenant filters inside the tool, never trust the agent to scope them.

Web and browsing tools

Search and URL-fetch open the widest attack surface: everything the tool returns is untrusted and may contain injected instructions (Topic 5.6). Allowlist destinations, block private IP ranges (SSRF), strip active content, and treat every returned page as data, never instruction.

Sub-agent tools

A tool whose implementation is another agent. The value is context isolation (Topic 5.3): a research sub-agent can read 200k tokens and return a 500-token summary, keeping the parent's context clean. The danger is unbounded recursion and cost — cap delegation depth explicitly.

Human-in-the-loop tools

Model a human decision as a tool the agent can call: "ask the user to approve." It pauses the run (Topic 7.1's interrupt), surfaces the request, and resumes with the answer. This is the clean way to gate everything in the bottom-right of the Section 01 grid.

Section 04 AdvancedChoosing an agent's tool set

Which tools to give an agent is a design decision with real consequences. Two principles:

  1. Least privilege. Give the minimum set the task needs. A summarisation agent needs retrieval, not delete_records. Every tool you add widens the blast radius if the agent is compromised or confused (Topic 5.6).
  2. Few, well-differentiated tools. Past roughly 15–20 tools, selection accuracy drops — the model dithers or picks wrong. Group related tools, or route between tool sets by task, rather than exposing everything at once.
Tool-set design by agent type
AgentAppropriate toolsShould NOT have
Research / Q&ARetrieval, web search, memory-readAny write or destructive tool
Data analysisSandboxed code, retrievalNetwork access, production DB writes
Customer supportRead customer data, create ticket, human-gate for refundsDirect refund/cancel without a human
Ops automationScoped API tools, human-gate for destructive opsUnrestricted shell
Tools are how you separate privilege

The cleanest security architecture for multi-capability systems is to split by agent, each with a different tool set and permission scope (Topic 8.9): a read-only research agent that physically cannot write, and a separate action agent behind a human gate. Since the tool set defines what an agent can do, curating it is your primary access-control lever — more reliable than any instruction in the prompt, because an injected instruction cannot conjure a tool that was never registered.

Section 05 AdvancedHow tools are defined, across the stack

Every framework expresses the same thing — name, description, JSON-schema parameters, implementation — differently. Recognising the pattern makes them all readable.

Python / JavaThe same tool, four ways
# Raw API (any provider) -- the ground truth (Topic 5.1)
{"name": "get_weather", "description": "...",
 "input_schema": {"type": "object", "properties": {...}}}

# LangChain / LangGraph -- decorator, docstring is the description
@tool
def get_weather(city: str) -> str:
    """Current weather for a city."""
    ...

# LlamaIndex -- FunctionTool wrapper
from llama_index.core.tools import FunctionTool
weather_tool = FunctionTool.from_defaults(fn=get_weather)

# Spring AI (Java) -- annotation, for your existing stack (Topic 3.2)
// @Tool(description = "Current weather for a city")
// public Weather getWeather(@ToolParam String city) { ... }

# MCP -- the same shape, exposed over a protocol so ANY host can
# use it (Topic 3.4). One definition, many consumers.
The unifying insight

Whatever the framework, a tool is always the same four things: a name, a description written for the model, a typed parameter schema, and an implementation your code controls. MCP (Topic 3.4) simply standardises the transport so one tool definition works across every host. Learn the shape once and every framework's tool API is just syntax.

Section 06 ProfessionalExercises

Do these — roughly an evening
  1. Take an agent you are designing and place every one of its tools in the Section 01 2×2 grid. Note which need a human gate.
  2. Build one tool of each of the first four types (function, retrieval, code, web). Give them all to one agent and observe how it chooses.
  3. Set up a real sandbox (a container or E2B) for a code-execution tool. Then try to make the code escape it — confirm it cannot reach your network.
  4. Build a web-fetch tool, then feed the agent a page containing an injected instruction. Watch what happens, then add an egress allowlist (Topic 5.6).
  5. Give an agent 25 tools and measure selection accuracy. Then group them to 8 and measure again.
  6. Implement a human-in-the-loop tool that pauses for approval before a destructive action.
  7. Design two agents for the same system split by privilege (read-only vs action). Prove the read-only one has no write tool registered.
