14.6

Recommender Systems

The systems that decide what you see next. This page covers how recommenders work — collaborative filtering, content-based, and the hybrid two-stage retrieve-then-rank architecture that runs at scale — why it is fundamentally a vector-similarity problem you already understand, and the pitfalls (cold start, feedback loops, filter bubbles) that define the field.

Section 01 BeginnerStart from zero

Assumed knowledge

Vectors and similarity (Topic 1.1), and vector search (Topic 4.3). Recommenders are, at heart, similarity search — which you already know.

Every "recommended for you," "customers also bought," and personalised feed is a recommender system. They drive a huge share of engagement and revenue online, and — conveniently for you — they rest on exactly the vector-similarity machinery you learned for RAG.

The two classic approaches
ApproachIdea"You might like…"
Collaborative filteringPeople similar to you liked this…because users like you bought it
Content-basedThings similar to what you liked…because it resembles items you enjoyed
HybridCombine both…most real systems do this
The insight that connects it to what you know

Recommenders learn embeddings (Topic 1.1): a vector for each user and each item, placed so that a user's vector is close to the vectors of items they will like. Recommending is then nearest-neighbour search in that space — find the items closest to the user — which is exactly the vector search from Topic 4.3. The whole field is: learn good user and item vectors, then do similarity search. If you understand RAG retrieval, you already understand the core of recommendation.

The words, in plain English
Collaborative filtering
Recommending based on the behaviour of similar users.
Content-based
Recommending items similar to ones a user liked.
Interaction
A signal: a click, purchase, rating, watch.
Embedding

Cold start
The problem of recommending to a brand-new user or item.
Candidate generation
Narrowing millions of items to a few hundred to rank.

Section 02 IntermediateCollaborative filtering, concretely

The classic method is matrix factorisation: you have a giant, mostly-empty matrix of users × items (who interacted with what), and you factor it into a user-embedding matrix and an item-embedding matrix whose product reconstructs the interactions.

Matrix factorisation predicted_rating(u, i)  =  useru · itemi Each user and item gets a vector; their dot product (Topic 1.1) predicts how much the user will like the item. Training finds vectors that reproduce the known interactions — and then the dot product predicts the unknown ones. This is the same dot-product-as-affinity idea as everywhere else in this handbook.

The magic is generalisation. The learned vectors capture latent taste dimensions nobody labelled — a user vector might implicitly encode "likes indie films," an item vector "is an indie film," and their dot product is high. Deep-learning recommenders (two-tower models, neural collaborative filtering) learn richer embeddings the same way, often incorporating item content and context. But the shape is constant: learn user and item vectors, score by similarity.

Section 03 AdvancedThe two-stage architecture at scale

You cannot score millions of items for every user on every page load. Real recommenders use a two-stage design — and if it sounds familiar, it is exactly the retrieve-then-rerank pattern from RAG (Topic 4.6).

  1. Candidate generation (retrieval). Cheaply narrow millions of items to a few hundred plausible ones — using vector similarity (ANN search, Topic 4.3) between the user vector and item vectors. Fast, approximate.
  2. Ranking. Apply an expensive, accurate model to score just those few hundred candidates precisely, using rich features (recency, context, price, diversity), and return the top few.
You have seen this pattern three times now

Retrieve broadly and cheaply, then rank narrowly and expensively. It is the recommender architecture here, the RAG retrieve-then-rerank pattern (Topic 4.6), and the ANN-then-exact-rescore pattern in vector indexes (Topic 4.3). The same shape solves the same problem everywhere: you cannot afford the accurate method on everything, so use a cheap filter first. Recognising this recurring structure is worth more than memorising any single system — it is a transferable design instinct, and it means your RAG skills transfer directly to building recommenders.

Section 04 ProfessionalThe hard problems

What makes recommendation hard
ProblemWhat it isMitigation
Cold startNo data on a new user or itemContent-based fallback; ask preferences; popularity
SparsityMost users interact with few itemsMatrix factorisation; side features
Popularity biasPopular items get over-recommendedDiversity re-ranking; de-bias
Feedback loopsRecommendations shape future dataExploration; off-policy correction
Filter bubblesUsers only see more of the sameDeliberate diversity & serendipity
The feedback loop is the subtle, serious one

A recommender's outputs become its future training data: it recommends X, users click X (because it was shown), the model learns "users like X," and recommends X even more. The system trains on data it created, amplifying its own biases and narrowing what users ever see (filter bubbles). This is both a quality problem (the model's world shrinks) and an ethical one (echo chambers, homogenisation). Mitigations involve deliberate exploration — sometimes showing items the model is unsure about, the explore-exploit trade-off from Topic 14.4 — and correcting for the bias that the logged data was itself shaped by past recommendations. Being aware that your system shapes the data it learns from is essential to building recommenders responsibly.

Evaluation is its own discipline

Offline metrics (precision@k, recall@k, NDCG — the same ranking metrics as RAG, Topic 4.7) only approximate what matters, because they are computed on data biased by past recommendations. The real test is online A/B testing against business metrics: engagement, retention, revenue. As with LLM evaluation (Topic 5.5), offline metrics catch regressions cheaply and online experiments measure reality. Never ship a recommender on offline numbers alone.

Section 05 ProfessionalExercises

Do these — roughly a weekend
  1. Build a matrix-factorisation recommender on the MovieLens dataset. Inspect the learned item vectors — do similar films cluster?
  2. Recommend by nearest-neighbour search on user/item vectors. Confirm it is the same operation as Topic 4.3.
  3. Build a content-based recommender using item embeddings (Topic 4.2). Compare against collaborative filtering.
  4. Implement the two-stage retrieve-then-rank architecture. Note its identity with RAG's pattern (Topic 4.6).
  5. Simulate cold start: recommend to a brand-new user and show collaborative filtering fails; add a content-based fallback.
  6. Add diversity re-ranking (MMR, Topic 4.6) and show it reduces popularity bias.
