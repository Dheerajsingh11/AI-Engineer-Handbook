17.1

Conversational AI & Chatbots

Designing systems people talk to. This page covers building good conversational AI — the architecture beneath a chatbot, managing multi-turn state, when to answer versus act versus hand off to a human, the design choices that separate a helpful assistant from a frustrating one, and how everything from earlier phases composes into a product.

Section 01 BeginnerStart from zero

Assumed knowledge

Prompting (Topic 3.1), RAG (Phase 4), agents (Phase 8) and memory (Topic 5.3). Conversational AI composes all of them into a product.

Chatbots and assistants are the most visible form of AI, and building a genuinely good one is harder than it looks. A demo that answers one question is easy; a system that holds a coherent multi-turn conversation, knows your data, takes actions safely, and hands off gracefully when it cannot help — that is real engineering, and it composes almost everything from earlier phases.

Conversational AI is composition, not a new technique

There is no separate "chatbot algorithm." A good conversational system is your earlier skills assembled: prompting for the persona and rules (Topic 3.1), RAG so it knows your facts (Phase 4), tools and agents so it can act (Phase 8), memory so it holds the thread (Topic 5.3), guardrails so it stays safe (Topics 5.6, 8.6), and evaluation so you know it works (Topics 4.7, 8.10). This page is about the design decisions that turn those components into something people actually find helpful rather than frustrating.

Section 02 IntermediateManaging the conversation

The thing that makes conversation hard is state — a conversation is not independent questions, it is a thread where each turn depends on what came before.

The follow-up problem

Users speak in context. "How much does it cost?" — how much does what cost? Depends entirely on the previous turns. A RAG system that embeds "How much does it cost?" and searches will retrieve nothing useful, because the query is meaningless alone. The fix (Topic 4.6): before retrieval, rewrite the follow-up into a standalone question using the conversation history — "How much does the premium plan cost?". This single step, easy to forget, is the difference between a chatbot that follows a conversation and one that treats every message as if it were the first. It is the most common gap in naive conversational RAG.

Knowing when to say "I don't know" and hand off

The mark of a good assistant is not answering everything — it is knowing its limits and handing off gracefully. A support bot that confidently invents a wrong answer (Topic 1.3) is worse than one that says "I can't resolve this — let me connect you to a person" with a summary of the conversation. Design the escape hatches deliberately: detect low-confidence or out-of-scope situations, decline honestly rather than confabulate, and make human handoff smooth (transfer the context, don't make the user repeat themselves). Users forgive a bot that knows its limits; they abandon one that wastes their time with confident nonsense. This humility is a design choice you must build in, because the model's default is to always produce an answer.

Evaluate conversations, not turns

A subtle but important shift: a conversational system must be evaluated at the conversation level, not the single-message level. A bot can give a great answer to each isolated message yet fail the overall task — losing track, contradicting itself, never resolving the user's actual need. Build eval cases that are whole conversations with a success criterion for the outcome (was the issue resolved? did it escalate appropriately?), and measure process too: turns to resolution, escalation rate, cost per conversation (Topic 8.10). This is the same trajectory-vs-outcome thinking as agent evaluation, applied to dialogue. Single-turn evals will pass a bot that frustrates every real user.

Section 05 ProfessionalExercises

Do these — roughly a weekend
  1. Build a RAG chatbot, then add follow-up handling (query rewriting, Topic 4.6). Test with context-dependent follow-ups and confirm it now follows the thread.
  2. Add memory (Topic 5.3) and hold a 15-turn conversation. Confirm it stays coherent and cost stays bounded.
  3. Add a tool so the assistant can act, and a human-handoff path for what it cannot do. Make handoff transfer the context.
  4. Design the "I don't know" behaviour: detect low confidence or out-of-scope and decline honestly instead of confabulating.
  5. Build a conversation-level eval set (whole dialogues with outcome criteria) and measure resolution rate and turns-to-resolution.
  6. Add streaming and measure the perceived-latency improvement.
