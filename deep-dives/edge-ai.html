19.4

Edge & On-Device AI

Running AI where the data is, not in the cloud. This page covers on-device and edge AI — models on phones, browsers, sensors and embedded hardware — why you would give up the big cloud model for a small local one, the runtimes that make it possible, and the privacy, latency and cost benefits that are driving it.

Section 01 BeginnerStart from zero

Assumed knowledge

Model compression (Topic 18.3) and running open models (Topic 9.2). Edge AI is where compression stops being optional and becomes the whole game.

Most AI runs in a data centre: your app sends data to a server, a big model answers, the answer comes back. Edge and on-device AI flips that — the model runs on the device itself: your phone, your laptop, a browser tab, a camera, a car, a sensor. No round trip to the cloud, and often no internet needed at all.

Why give up the big cloud model?

Four reasons, and any one can be decisive. Privacy: the data never leaves the device — enormous for health, personal or regulated data (Topic 6.4). Latency: no network round trip, so responses are instant and consistent. Cost: no per-call API bill — the user's hardware does the work. Offline: it works with no connection, on a plane or in a factory. The trade you make is capability — an on-device model is far smaller than a frontier one — so edge AI is the art of getting a good-enough model small and fast enough to live on the device.

The words, in plain English
Edge
Computation near the data source — the device, not a central server.
On-device
Running directly on a phone, laptop or browser.
SLM
Small Language Model — a compact LLM (often 1–8B) built to run locally.
Runtime
The engine that executes a model efficiently on given hardware.
NPU
Neural Processing Unit — a chip in modern phones/laptops built for AI maths.
GGUF / ONNX
Portable model file formats made for efficient local inference.

Section 02 IntermediateHow a model gets onto a device

You cannot drop a 70B cloud model onto a phone. Getting to the edge is a pipeline of the compression techniques from Topic 18.3, plus a runtime tuned for the hardware.

  1. Pick or make a small model. Start from an SLM, or distil a big model down to a small student (Topic 18.3).
  2. Quantise it. Drop to 4-bit (or lower) so the weights fit in the device's limited memory — the single biggest enabler.
  3. Convert to a portable format. Export to GGUF, ONNX, Core ML or TensorFlow Lite — formats built for on-device inference.
  4. Run on a device-tuned runtime. Use an engine that exploits the device's CPU, GPU or NPU (Section 03).
  5. Measure on the real device. Speed, memory, battery and heat — edge constraints a server never has.

The enabling shift of the last few years is twofold: small models got good (a modern 3–8B model does things that needed a giant model a couple of years ago) and consumer hardware got AI silicon (phones and laptops now ship NPUs). Together they moved on-device AI from "toy demo" to "real feature". A quantised small model on an NPU can transcribe speech, answer questions, classify images or draft text locally, fast enough to feel native.

The browser is now an inference target

One of the more striking recent developments: with WebGPU, a model can run entirely inside a web page — libraries like transformers.js and WebLLM download a quantised model and execute it on the user's GPU, with no server call and no data leaving the browser. For a web engineer this is a genuinely new capability: private, zero-marginal-cost inference that ships as part of your front end. It will not run a frontier model, but for classification, embeddings, speech or a small chat model, "the model runs in the tab" is now a real architecture — and a compelling privacy story.

Section 04 AdvancedEdge vs cloud — and hybrids

Edge is not a replacement for the cloud; it is a different point on a trade-off curve, and the best systems often use both.

The trade-off, honestly
On-device / edgeCloud
CapabilitySmall model — limitedFrontier model — strong
PrivacyData never leaves the deviceData sent to a server
LatencyInstant, no networkNetwork round trip
CostFree per call (user's hardware)Per-token API bill
OfflineWorks with no connectionNeeds connectivity
UpdatesMust ship a new model to devicesUpdate centrally, instantly
The hybrid pattern

The most powerful designs are hybrid: do the fast, private, common work on-device and escalate to the cloud only when needed — conceptually the same cascade as Topic 19.3, but split across the network. A phone keyboard predicts words locally and calls the cloud for a hard rewrite. A voice assistant wakes and transcribes on-device (private, instant) and sends only the transcript up for a complex answer. A camera runs detection locally and uploads only flagged frames. This keeps the latency, privacy and cost benefits of edge for the bulk of work while preserving the cloud's capability for the hard fraction. Deciding what runs where is the core design question of edge AI.

Section 05 ProfessionalThe edge constraints

Shipping to the edge means engineering against limits a server never imposes. Memory: a phone has a few gigabytes shared with everything else, so model size is a hard wall — quantisation is mandatory, not optional. Battery & heat: sustained inference drains and heats the device; you budget compute the way you budget bytes. Fragmentation: thousands of device/chip combinations, each with different capabilities — you target a floor and detect capability at runtime. Updates: the model is on the device, so improving it means shipping an update through an app store, not a server deploy — slower, and you must support old versions in the wild. And measurement moves on-device: the numbers that matter (tokens/sec, memory peak, battery per query) can only be trusted when measured on the real hardware, not a laptop. None of this is a reason to avoid edge — it is simply the discipline that makes it work, and it is squarely systems engineering.

Section 06 ProfessionalExercises

Do these — run a model where it shouldn't fit
  1. Run a quantised small LLM locally with llama.cpp (GGUF). Measure tokens/sec and memory, and compare answers to a cloud model.
  2. Run a model in the browser with transformers.js or WebLLM. Confirm no network call happens after the model loads.
  3. Take one model to two quantisation levels (int8, int4). Measure the size, speed and quality trade on your own device.
  4. Design a hybrid feature: decide exactly what runs on-device and what escalates to the cloud, and why (Section 04).
  5. Convert a small model to ONNX or Core ML / TFLite and run it. Note what the conversion and the runtime change about performance.
  6. Profile battery and heat during sustained on-device inference on a phone. Feel the constraint a server never has.
