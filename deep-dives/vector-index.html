Section 01 BeginnerStart from zero

Assumed knowledge

Cosine similarity from Topic 1.1, particularly the section on high-dimensional strangeness. k-means from Topic 2.3 is used directly in Section 03.

You have a million document vectors and a query vector. Finding the closest matches is conceptually trivial: compare the query against all one million and keep the best ten. This is exact or brute-force search, and it is correct.

It is also linear. A million comparisons is fine. A hundred million, thousands of times per second, is not. So you trade a little correctness for a lot of speed, and that trade is what an Approximate Nearest Neighbour index is.

Why approximate is the right answer, not a compromise

Recall from Topic 1.1 that in 1536 dimensions the nearest neighbour is already about 84% as far away as the farthest. Distances have largely collapsed, so the difference between the "true" tenth-best result and the eleventh is often smaller than the noise in your embedding model.

Insisting on mathematically exact results buys you very little real quality and costs a full scan. Accepting 95–99% recall for a hundredfold speedup is not cutting corners — it is recognising what the numbers actually mean.

The words, in plain English
Recall
What fraction of the true nearest neighbours the index actually returned. The quality measure for an index.
QPS
Queries per second. The throughput measure.
Build time
How long it takes to construct the index. Matters for large or frequently rebuilt corpora.
Graph index
Stores vectors as nodes connected by edges; searching means walking the graph toward the query.
Partition index
Divides vectors into groups; searching means picking a few groups and scanning only those.
Quantisation
Storing vectors in fewer bits, approximately.
Rescoring
Re-computing exact distances for a small candidate set at the end, to undo quantisation error.

Section 03 AdvancedHNSW, built from the skip list

HNSW is the default in pgvector, Qdrant, Weaviate, Milvus, Elasticsearch and FAISS. Understanding it is what lets you tune it rather than accept defaults.

Step 1: the idea it generalises

A skip list speeds up search in a sorted linked list by adding express lanes. The bottom layer holds every element. The layer above holds roughly half, with longer hops. The next holds a quarter. Searching means starting at the top, moving right until you would overshoot, dropping a layer, and repeating — O(log n) instead of O(n).

HNSW is that idea in many dimensions. Instead of a sorted line you have a graph; instead of "move right" you have "move to whichever neighbour is closer to the query".

  1. Assign each vector a maximum layer drawn from an exponentially decaying distribution. Most vectors live only at layer 0; a few reach layer 1; very few reach higher. This produces the express-lane structure automatically.
  2. Connect each node to its m nearest neighbours within each layer it occupies. Higher layers are sparse, so their edges span long distances.
  3. Search greedily from the top. Enter at the single top node, repeatedly move to the neighbour closest to the query until no neighbour improves, then drop to the layer below and continue from there.
  4. At layer 0, search with a beam. Keep a candidate set of size ef_search rather than following a single path — this is what makes recall tunable at query time.
PythonHNSW from scratch — simplified but functionally real
import numpy as np, heapq, math

class HNSW:
    def __init__(self, m=16, ef_construction=100, ml=None, seed=0):
        self.m = m                                # neighbours per node per layer
        self.m0 = m * 2                           # layer 0 gets double: it holds everything
        self.ef_construction = ef_construction
        # 1/ln(m) is the level multiplier that yields ~log_m(n) layers
        self.ml = ml or 1.0 / math.log(m)
        self.rng = np.random.default_rng(seed)
        self.vectors, self.layers, self.entry = [], [], None

    def _random_level(self):
        # Exponential decay: P(level >= l) = exp(-l/ml).
        # Most nodes get 0; a handful get high levels and become highways.
        return int(-math.log(self.rng.random()) * self.ml)

    def _distance(self, a, b):
        return float(np.linalg.norm(self.vectors[a] - b))

    def _search_layer(self, query, entry_points, ef, layer):
        """Beam search within one layer. Returns the ef closest found."""
        visited = set(entry_points)
        # candidates: min-heap by distance (explore closest first)
        candidates = [(self._distance(p, query), p) for p in entry_points]
        heapq.heapify(candidates)
        # results: max-heap by distance (evict the worst)
        results = [(-d, p) for d, p in candidates]
        heapq.heapify(results)

        while candidates:
            dist, node = heapq.heappop(candidates)
            # If the closest unexplored candidate is worse than our worst
            # kept result, no further exploration can help. Stop.
            if results and dist > -results[0][0]:
                break
            for neighbour in self.layers[layer].get(node, []):
                if neighbour in visited:
                    continue
                visited.add(neighbour)
                d = self._distance(neighbour, query)
                if len(results) < ef or d < -results[0][0]:
                    heapq.heappush(candidates, (d, neighbour))
                    heapq.heappush(results, (-d, neighbour))
                    if len(results) > ef:
                        heapq.heappop(results)      # drop the worst
        return [p for _, p in results]

    def add(self, vector):
        idx = len(self.vectors)
        self.vectors.append(np.asarray(vector, dtype=np.float32))
        level = self._random_level()

        while len(self.layers) <= level:
            self.layers.append({})

        if self.entry is None:
            self.entry = idx
            for l in range(level + 1):
                self.layers[l][idx] = []
            return idx

        # Descend the layers above `level` with a greedy single-path search
        entry_points = [self.entry]
        for l in range(len(self.layers) - 1, level, -1):
            entry_points = self._search_layer(vector, entry_points, 1, l)

        # Insert with proper beam search on layers at and below `level`
        for l in range(min(level, len(self.layers) - 1), -1, -1):
            found = self._search_layer(vector, entry_points, self.ef_construction, l)
            max_conn = self.m0 if l == 0 else self.m
            neighbours = sorted(found, key=lambda p: self._distance(p, vector))[:max_conn]
            self.layers[l][idx] = list(neighbours)

            # Bidirectional edges, pruned to keep degree bounded
            for n in neighbours:
                self.layers[l].setdefault(n, []).append(idx)
                if len(self.layers[l][n]) > max_conn:
                    nv = self.vectors[n]
                    self.layers[l][n] = sorted(
                        self.layers[l][n],
                        key=lambda p: float(np.linalg.norm(self.vectors[p] - nv))
                    )[:max_conn]
            entry_points = found

        if level >= len(self.layers) - 1:
            self.entry = idx                      # new highest node becomes entry
        return idx

    def search(self, query, k=10, ef_search=50):
        query = np.asarray(query, dtype=np.float32)
        entry_points = [self.entry]
        for l in range(len(self.layers) - 1, 0, -1):
            entry_points = self._search_layer(query, entry_points, 1, l)
        found = self._search_layer(query, entry_points, max(ef_search, k), 0)
        return sorted(found, key=lambda p: self._distance(p, query))[:k]

data = rng.normal(size=(5000, 64)).astype(np.float32)
data /= np.linalg.norm(data, axis=1, keepdims=True)

    index.add(v)

query = data[7]

    got = set(index.search(query, k=10, ef_search=ef))
    print(f"ef_search={ef:4d}  recall@10 = {len(got & exact) / 10:.2f}")

# ef_search=  20  recall@10 = 0.90
# ef_search=  50  recall@10 = 1.00

m
Edges per node. Higher = better recall, more memory. 16–64
ef_construction
Beam width while building. Higher = better graph, slower build. 100–200
ef_search
The runtime dial. Higher = better recall, slower query. 40–400
The one parameter to actually tune

m and ef_construction are baked in at build time — changing them means rebuilding the whole index. ef_search is per query, so you can tune it live, set it per endpoint, or raise it for high-value queries and lower it under load. Plot recall against ef_search on your own data once, pick the knee, and set it explicitly rather than inheriting a default.

Section 04 AdvancedProduct quantisation from scratch

HNSW is fast but memory-hungry: it stores full vectors plus a graph. At a billion vectors that is impractical. Product quantisation compresses each vector by roughly 32–64×.

  1. Split each d-dimensional vector into M sub-vectors. A 1536-dim vector into 96 sub-vectors of 16 dimensions each.
  2. Cluster each sub-space independently with k-means, using 256 centroids — because 256 fits in exactly one byte.
  3. Encode each sub-vector as the id of its nearest centroid. The vector becomes 96 bytes instead of 6,144.
  4. Search using a lookup table: precompute the distance from the query's sub-vector to all 256 centroids in each sub-space, then a full distance is 96 table lookups and adds — no multiplication at all.
PythonProduct quantisation, implemented
import numpy as np
from sklearn.cluster import KMeans

class ProductQuantizer:
    def __init__(self, n_subvectors=8, n_centroids=256, seed=0):
        self.M = n_subvectors
        self.K = n_centroids                       # 256 -> one byte per code
        self.seed = seed
        self.codebooks = None

    def fit(self, X):
        n, d = X.shape
        assert d % self.M == 0, "dimension must divide evenly"
        self.sub_dim = d // self.M
        self.codebooks = np.zeros((self.M, self.K, self.sub_dim), dtype=np.float32)

        for m in range(self.M):
            sub = X[:, m * self.sub_dim:(m + 1) * self.sub_dim]
            km = KMeans(self.K, n_init=4, random_state=self.seed).fit(sub)
            self.codebooks[m] = km.cluster_centers_
        return self

    def encode(self, X):
        codes = np.zeros((len(X), self.M), dtype=np.uint8)
        for m in range(self.M):
            sub = X[:, m * self.sub_dim:(m + 1) * self.sub_dim]
            d2 = ((sub[:, None, :] - self.codebooks[m][None]) ** 2).sum(-1)
            codes[:, m] = d2.argmin(1)
        return codes

    def search(self, query, codes, k=10):
        # ASYMMETRIC distance computation: the query stays in full
        # precision, only the database is quantised. More accurate
        # than quantising both, and costs nothing extra.
        tables = np.zeros((self.M, self.K), dtype=np.float32)
        for m in range(self.M):
            q_sub = query[m * self.sub_dim:(m + 1) * self.sub_dim]
            tables[m] = ((self.codebooks[m] - q_sub) ** 2).sum(-1)

        # Distance for every stored vector: M lookups and adds. No multiplies.
        distances = tables[np.arange(self.M), codes].sum(axis=1)
        return np.argsort(distances)[:k]


rng = np.random.default_rng(0)
X = rng.normal(size=(20_000, 128)).astype(np.float32)
X /= np.linalg.norm(X, axis=1, keepdims=True)

pq = ProductQuantizer(n_subvectors=16).fit(X)
codes = pq.encode(X)

original = X.nbytes / 1e6
compressed = codes.nbytes / 1e6
print(f"{original:.1f} MB -> {compressed:.1f} MB  ({original/compressed:.0f}x)")
# 10.2 MB -> 0.3 MB  (32x)

q = X[5]
approx = set(pq.search(q, codes, k=10).tolist())
exact  = set(np.argsort(-(X @ q))[:10].tolist())
print(f"recall@10 = {len(approx & exact) / 10:.2f}")     # ~0.7

Section 05 ProfessionalFiltered search — where indexes get hard

"Find similar documents where tenant_id = 42 and status = published and updated_at > 2025-01-01". This is the query every real system needs, and it is genuinely difficult, because the ANN structure was built without knowledge of your filter.

Three strategies, three failure modes
StrategyHowFails when
Post-filterSearch the index, then discard non-matching resultsThe filter is selective. Search top-100, 3 match, you asked for 10. Returns too few, or nothing
Pre-filterRestrict to matching ids, then search among themNaive implementation breaks graph connectivity — the walk cannot reach relevant regions and recall collapses silently
Filtered searchThe index applies the predicate during traversalRequires index support. Qdrant, Weaviate and Milvus do this well; check what yours actually does
The multi-tenant recall cliff

You test with one tenant holding most of the data: recall is excellent. You go live; tenant 4,000 has 200 documents out of 50 million. Their queries traverse a graph built mostly of other tenants' vectors, and post-filtering discards nearly everything. Recall for small tenants collapses while your aggregate metrics look fine, because they are dominated by large tenants.

Mitigations: use a store with native filtered search and verify it; consider a separate index or partition per large tenant; over-fetch aggressively (topK of 200+) when filters are selective; and — the important one — measure recall per tenant size bucket, not in aggregate. This failure is invisible to an average.

Section 06 ProfessionalCapacity planning

Memory for an HNSW index vectors  =  n × d × bytes_per_component graph  ≈  n × m × 2 × 4 bytes   (bidirectional 4-byte ids) For 10M vectors at 1536 dims, float32, m=16: vectors = 61.4 GB, graph ≈ 1.3 GB. The graph is not the problem — the vectors are. That is why quantisation and Matryoshka truncation matter far more than graph tuning.

  2. Set m=4 and rebuild. Watch recall drop even at high ef_search — a poorly connected graph cannot be rescued at query time.

  8. Benchmark pgvector HNSW against exact search on 1M vectors. Record QPS and recall at three ef_search values.
