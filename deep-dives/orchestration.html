Orchestration Patterns

How steps and agents are coordinated. This page lays out the orchestration spectrum from a fixed chain to a free-for-all network, implements the core patterns — sequential, routing, parallel, orchestrator-workers, graph — and gives the decision rule for how much control to hand the model versus keep in your code.

Section 01 BeginnerStart from zero

Assumed knowledge

The agent loop (Topic 8.1) and workflow patterns (Topic 5.2). This page is the coordination layer — how you arrange the loop and connect multiple steps or agents.

Orchestration is a plain word for a plain question: once you have models, tools and steps, who decides what runs when? That is the whole topic. Get it right and your system is predictable and debuggable; get it wrong and it is an expensive black box.

Orchestration lives on a spectrum, defined by how much control you keep versus how much you hand to the model:

The orchestration spectrum
ApproachControl flow decided byPredictable?
Fixed chainYou, entirelyFully
RouterYou, with one model-chosen branchMostly
Graph (state machine)You define nodes; model picks edges at branch pointsInspectable
Orchestrator–workersA planner model decides the subtasksPartly
Autonomous agentThe model, at runtimeLeast
Agent networkMultiple models, freelyEmergent
The governing principle

Keep control in your code until you have a concrete reason to hand it to the model. Every step of autonomy you give up buys flexibility and costs predictability, testability and money. Good orchestration is not "maximise agency" — it is choosing the least autonomous shape that still solves the problem.

The words, in plain English
Chain
A fixed sequence of steps, each feeding the next.
Router
A step that classifies the input and dispatches to one of several handlers.
Fan-out / fan-in
Split into parallel branches, then merge the results.
Orchestrator
A coordinator that decides and delegates subtasks (often itself a model).
Worker
A component that executes one delegated subtask.
Graph
Nodes (steps) connected by edges (transitions); the modern way to make control flow explicit.

Section 02 IntermediateThe core patterns, implemented

Five shapes cover almost everything. They compose — real systems nest them.

PythonSequential, routing, parallel
import asyncio

# --- 1. SEQUENTIAL CHAIN: fixed order, each step's output feeds on -
def summarise_pipeline(doc):
    outline = llm(f"Outline the key points of:\n{doc}")
    draft   = llm(f"Write a summary from this outline:\n{outline}")
    return  llm(f"Tighten this, keep all facts:\n{draft}")

# --- 2. ROUTING: classify, then dispatch to a specialist ----------
def route(message):
    category = llm(f"Classify as billing|technical|sales:\n{message}").strip()
    return {
        "billing":   handle_billing,
        "technical": handle_technical,       # maybe a bigger model / more tools
        "sales":     handle_sales,
    }.get(category, handle_general)(message)

# --- 3. PARALLEL FAN-OUT / FAN-IN: independent subtasks at once ----
async def check_compliance(doc, policies):
    # Ten sequential calls at 3s each = 30s; concurrently = ~3s.
    findings = await asyncio.gather(*[
        check_against(doc, p) for p in policies])
    return merge(findings)                   # fan-in: combine results
PythonOrchestrator-workers: the model decides the subtasks
# The difference from parallel fan-out: here the PLANNER decides how
# many subtasks and what they are -- not known when you wrote the code.
def research(question):
    plan = llm_json(f"""Break this into independent research subtasks.
        Return JSON: {{"subtasks": [...]}}\n\nQuestion: {question}""")

    subtasks = plan["subtasks"][:MAX_SUBTASKS]   # ALWAYS bound it
    results = [worker(task) for task in subtasks]  # or run in parallel

    return llm(f"""Synthesise these findings to answer the question.
        Question: {question}\nFindings: {results}""")

Section 03 IntermediateGraphs: the modern default

For anything with loops, branches, human checkpoints or resumability, the winning shape is an explicit state graph (Topic 7.1): nodes are steps, edges are transitions, a shared state flows through. It makes the control flow data you can see rather than behaviour hidden in a loop.

Why graphs beat both extremes

A fixed chain is predictable but rigid. A fully autonomous agent is flexible but opaque. A graph is the sweet spot: you define the possible states and transitions, and the model only chooses among them at explicit branch points. You keep structural control; the model provides adaptivity exactly where you allow it. Every hard agent problem — loops, drift, debugging, human approval — becomes a property of a graph you can inspect and test node by node.

PythonAn orchestration graph with a router and a loop
from langgraph.graph import StateGraph, START, END

graph = StateGraph(State)
graph.add_node("classify", classify_node)
graph.add_node("retrieve", retrieve_node)
graph.add_node("agent",    agent_node)
graph.add_node("respond",  respond_node)

graph.add_edge(START, "classify")

# ROUTING as a conditional edge -- the model's classification
# decides which path, but only among paths you defined.
graph.add_conditional_edges("classify", pick_path, {
    "needs_docs": "retrieve",
    "needs_tools": "agent",
    "simple": "respond",
})
graph.add_edge("retrieve", "respond")

# A LOOP: the agent node cycles until it stops calling tools.
graph.add_conditional_edges("agent", still_working,
                            {"continue": "agent", "done": "respond"})
graph.add_edge("respond", END)

app = graph.compile(checkpointer=checkpointer)   # resumable, inspectable

Section 04 AdvancedOrchestrating multiple agents

When one agent is not enough, the same spectrum applies to agents as to steps. The topologies, most to least controllable:

Multi-agent orchestration topologies
TopologyStructureControl
SupervisorOne coordinator delegates to specialistsHigh — start here
HierarchicalSupervisors of supervisorsMedium; debugging cost grows
HandoffControl passes with the conversationMedium; clean for escalation
BlackboardAgents share a common state storeMedium — it is event-driven (Topic 5.4)
NetworkAny agent calls any otherLow — emergent, hard to test
Do not reach for multi-agent too early

Most multi-agent designs would work better as one agent with more tools, or as a graph. Each extra agent multiplies cost, adds a failure mode, and makes the trajectory harder to read. Justify each agent by a concrete need — a separate context window, a different permission scope, or measured parallelism — not by "it felt more modular." This is developed fully in Topic 8.9.

Section 05 ProfessionalChoosing the shape

A decision procedure you can apply to any task:

  1. Can you write the steps down in advance? Yes → sequential chain or router. Stop here if you can — it is the cheapest and most reliable.
  2. Are there independent subtasks? Yes → parallelise them.
  3. Are there loops, branches, or human checkpoints? Yes → model it as a graph.
  4. Is the number of subtasks unknown until runtime? Yes → orchestrator–workers, bounded.
  5. Do subtasks need separate context or permissions? Yes → multiple agents, supervisor topology.
  6. Otherwise → a single agent loop with the right tools.
The same spectrum in your Java stack

These patterns are framework-agnostic. In LangGraph they are nodes and edges; in Spring AI they are Advisor chains and method calls; in plain code they are functions and conditionals. The shape is what matters, not the tool — and the shape is a design decision you make before writing any framework code. Sketch the graph on paper first; the implementation is mechanical once the shape is right.

Section 06 ProfessionalExercises

Do these — roughly an evening
  1. Implement all five core patterns from Section 02 on small tasks. You will recognise them in every framework afterwards.
  2. Build a router that sends three input categories to three handlers using different models. Measure the cost saving vs one big model for all.
  3. Convert a sequential chain into a parallel fan-out where steps are independent. Measure the latency drop.
  4. Build the orchestration graph from Section 03 with a router and a loop. Add loop detection.
  5. Build an orchestrator–workers researcher. Deliberately let the planner over-produce subtasks and confirm your bound caps it.
  6. Take a task and apply the Section 05 decision procedure end to end. Justify the shape you land on in one sentence.
