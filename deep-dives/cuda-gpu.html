CUDA & GPU Computing for AI

Why AI runs on GPUs, and what is actually happening when it does. This page covers GPU computing for AI from the ground up — why a graphics chip trains neural networks, the CUDA execution and memory model, tensor cores and mixed precision, how PyTorch quietly drives all of it, and the profiling and out-of-memory skills you will need.

Section 01 BeginnerStart from zero

Assumed knowledge

Neural network basics (Topic 2.4) and PyTorch (Topic 2.5). You have called .to("cuda"); this page explains what that actually does.

Almost all modern AI runs on GPUs — graphics processors originally built to draw video-game pixels. Understanding why, and how to use them well, is the difference between an engineer who waits hours for training and one who does not, and between a model that fits on the hardware and one that crashes with "out of memory."

Why a graphics chip trains neural networks

A CPU has a few very fast cores optimised for doing one complicated thing after another. A GPU has thousands of simpler cores optimised for doing the same simple thing to a lot of data at once. Neural networks are, underneath, enormous piles of matrix multiplications (Topic 1.1) — millions of identical multiply-and-add operations with no dependency between them. That is the perfect job for thousands of parallel cores. The GPU did not get repurposed for AI by accident; AI's core operation happens to be exactly what a GPU was already built to do. This is why a training run can be 10–100× faster on a GPU than a CPU.

The words, in plain English
GPU
Graphics Processing Unit — a chip with thousands of parallel cores.
CUDA
NVIDIA's platform for running general (non-graphics) code on its GPUs.
Kernel
A small function that runs on the GPU, across many data elements at once.
VRAM
The GPU's own memory. The model and its data must fit in it.
Tensor core
Specialised hardware that does small matrix multiplies extremely fast.
Mixed precision
Using 16-bit numbers where possible for speed, 32-bit where accuracy matters.

Section 02 IntermediateThe CUDA execution model

CUDA lets you run your own code across the GPU's cores. The programming model is a hierarchy: you launch a kernel, which runs as a grid of blocks, each block a group of threads, and every thread does the same operation on its own slice of data.

The parallel hierarchy
LevelWhat it is
ThreadOne worker doing the kernel on one element
Warp32 threads that execute in lockstep — the real unit of scheduling
BlockA group of threads that can share fast memory and cooperate
GridAll the blocks launched for one kernel
CUDA CA kernel: every thread adds one element
// Each thread computes ONE output element. Thousands run at once.
__global__ void add(float* a, float* b, float* c, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;  // this thread's index
    if (i < n) c[i] = a[i] + b[i];                   // the actual work
}
// Launch: enough blocks of 256 threads to cover n elements.
add<<<(n + 255) / 256, 256>>>(a, b, c, n);

You will rarely write raw CUDA — but seeing it demystifies the whole stack. That blockIdx * blockDim + threadIdx pattern is how each of thousands of threads figures out which piece of data is "mine." When PyTorch runs a + b on a GPU tensor, it launches a kernel exactly like this one under the hood. Understanding the model tells you why GPUs love big, uniform, independent workloads and hate small, branchy, sequential ones — and that intuition guides every performance decision you make.

Section 03 IntermediateMemory: the real bottleneck

Here is the counter-intuitive truth of GPU performance: most AI code is limited by memory, not by maths. The cores can multiply far faster than data can be fetched, so moving data efficiently is usually what determines speed.

The GPU memory hierarchy (fast & small → slow & large)
MemorySpeedRole
RegistersFastestPer-thread scratch
Shared memoryVery fastShared within a block — the key optimisation lever
Global (VRAM)Slow(er)The big pool — where your tensors live
Host (CPU) RAMSlowest linkAcross the PCIe bus — avoid moving data back and forth
The two memory traps

CPU↔GPU transfers: moving tensors across the PCIe bus is slow. Calling .cpu() or .item() inside a training loop, or printing a GPU tensor every step, silently kills performance — keep data on the GPU and sync rarely. Running out of VRAM: the entire model, its gradients, the optimiser state, and the activations for the current batch must all fit in VRAM at once. This is why "CUDA out of memory" is the most common training error, and why the fixes are always the same set of levers (Section 05). VRAM, not compute, is usually the wall you hit first.

Section 04 AdvancedTensor cores & mixed precision

Modern GPUs have tensor cores — dedicated units that do a small matrix multiply-and-accumulate in one step, far faster than the general cores. They only reach full speed at lower precision, which is why mixed precision became standard.

The number formats you will meet
FormatBitsUse
fp3232Full precision — the safe default, the slowest
fp1616Fast on tensor cores; narrow range — can overflow
bf1616Same range as fp32, less precision — the modern training default
fp8 / int8 / int48–4Inference & quantisation (Topics 6.1, 18.3)
Why bf16 quietly won

Mixed-precision training does the heavy matrix multiplies in 16-bit (fast, on tensor cores) while keeping a 32-bit copy of the weights for the accumulation that needs accuracy — roughly 2× faster and half the memory for a negligible quality cost. The subtlety is which 16-bit. fp16 has high precision but a narrow numeric range, so gradients can overflow to infinity — it needs "loss scaling" to survive. bf16 keeps fp32's wide range at the cost of some precision, so it just works, no scaling needed. That robustness is why bf16 became the default format for training modern models. In PyTorch this is one context manager (torch.autocast) — but knowing what it does is what lets you debug it when a loss suddenly becomes NaN.

Section 05 ProfessionalPyTorch, profiling & OOM

In practice PyTorch is your interface to all of this: it dispatches kernels, manages VRAM, and drives the tensor cores. Your job is to feed it well and to fix it when it runs out of memory.

PythonMixed precision, and the OOM toolkit
scaler = torch.cuda.amp.GradScaler()             # for fp16; bf16 needs none
for x, y in loader:
    x, y = x.cuda(non_blocking=True), y.cuda(non_blocking=True)
    with torch.autocast("cuda", dtype=torch.bfloat16):   # tensor cores
        loss = model(x, y)
    scaler.scale(loss).backward()
    scaler.step(opt); scaler.update(); opt.zero_grad()

# When VRAM runs out, these are the levers, in order:
#  1. smaller batch size        3. gradient checkpointing (Topic 9.6)
#  2. mixed precision (above)   4. a smaller / quantised model (Topic 18.3)
torch.cuda.memory_summary()                      # see where VRAM went
The mental model to keep

You do not need to write kernels to be effective — you need the instincts this page builds. Keep work on the GPU and batch it large and uniform. Minimise host↔device transfers and avoid syncing every step. Use mixed precision (bf16) by default. Watch VRAM as your primary constraint and know the four levers to reclaim it. And when you profile (with the PyTorch profiler or nvidia-smi), ask first "am I compute-bound or memory-bound?" — the answer points to the fix. This is the same systems intuition you already have, applied to a massively parallel machine; scaling it across many GPUs is the next page (Topic 9.6).

Section 06 ProfessionalExercises

Do these — feel the hardware
  1. Time the same matrix multiply on CPU and GPU across growing sizes. Find where the GPU starts winning, and by how much.
  2. Deliberately cause "CUDA out of memory," then fix it with each of the four levers in turn. Watch VRAM with nvidia-smi.
  3. Turn on torch.autocast with bf16. Measure the speed and memory change, and confirm the accuracy holds.
  4. Put a .item() call inside a hot training loop, then remove it. Measure how much the CPU↔GPU sync cost you.
  5. Profile a training step with the PyTorch profiler. Decide whether it is compute-bound or memory-bound.
  6. Write (or read) a tiny CUDA/Triton kernel for vector add. Map the thread-indexing back to Section 02.
