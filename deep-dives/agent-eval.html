Agent Evaluation & Observability

How you know an agent works, and catch it when it stops. Agents are harder to evaluate than single calls because you must judge a whole trajectory, not one answer. This page covers outcome vs process metrics, trajectory evaluation, LLM-as-judge for agent runs, tracing, and building the regression suite that keeps a non-deterministic system trustworthy.

Section 01 BeginnerStart from zero

Assumed knowledge

Evaluation basics (Topics 1.2, 4.7) and LLMOps (Topic 5.5). This page applies them to the harder case: a whole agent trajectory rather than a single response.

Evaluating a single model call is hard (Topic 4.7). Evaluating an agent is harder, because an agent produces a trajectory — a sequence of decisions, tool calls and observations — and it can reach a good answer by a terrible path, or a bad answer by a reasonable one. You have to judge both the destination and the journey.

Two questions, not one

Outcome: did the agent achieve the goal? Process: did it get there sensibly — the right tools, no wasted steps, no unsafe actions, acceptable cost? A good agent needs both. An agent that produces correct answers by calling every tool five times and burning ten dollars a run is not production-ready, and outcome-only evaluation will call it a success. You must measure the trajectory, not just the final message.

The words, in plain English
Trajectory
The full sequence of steps an agent took on one task.
Outcome metric
Did it achieve the goal? Task success rate.
Process metric
How well it worked: steps, cost, tool accuracy, safety.
Trajectory eval
Judging the sequence of steps, not just the answer.
Trace
The recorded, inspectable trajectory — what you debug from.
Regression suite
A fixed set of tasks run on every change to catch degradation.

Outcome-only evaluation hides the problems that bankrupt you

A suite that checks only "was the final answer right?" will happily pass an agent that loops, over-uses expensive tools, attempts unauthorised actions that happened to be blocked, and costs ten times what it should. Every one of those is invisible to an outcome metric and lethal in production. Always report cost-per-task and steps-per-task alongside success rate, and alert on the p99 — the runaway trajectories, not the median, are what generate the surprise invoice and the incident.

Section 03 AdvancedTrajectory evaluation

Judging a sequence needs different tools than judging an answer. Three approaches, cheapest first.

Ways to evaluate a trajectory
MethodHowGood for
Rule assertionsDeterministic checks on the traceSafety, budget, required tools — free and never flaky
Reference trajectoryCompare against a known-good sequence of tool callsTasks with a canonical path
LLM-as-judgeA model scores the trajectory against a rubric"Was this a sensible way to solve it?"
PythonTrajectory assertions — run these first, they are free
def evaluate_trajectory(trace, case):
    checks = {
        # OUTCOME
        "succeeded":       case.verify_outcome(trace.final_answer),
        # PROCESS -- deterministic, instant, never flaky (Topic 5.5)
        "used_required_tool": "check_order" in trace.tools_called,
        "no_forbidden_tool":  "delete_all" not in trace.tools_called,
        "within_step_budget": trace.n_steps <= 10,
        "within_cost_budget": trace.cost_usd <= 0.10,
        "no_auth_violations":  trace.denied_calls == [],
        "no_loops":            not trace.has_repeated_calls(3),
        "all_args_valid":      all(c.args_valid for c in trace.tool_calls),
    }
    return checks

# Reserve the expensive LLM judge for the subjective question only.
JUDGE = """Given the task and the agent's steps, rate 1-5:
was this an efficient, sensible way to solve it? Penalise wasted
steps, wrong tools, and unnecessary cost. Explain briefly.

Task: {task}
Trajectory: {steps}"""

Order by cost, as with all eval (Topic 5.5). Deterministic assertions — safety, budget, required/forbidden tools, loop detection — are free, instant and never flaky; run them on every case. Save the LLM judge for the one genuinely subjective question ("was this sensible?"). A suite that leads with the judge is slow, expensive and eventually distrusted.

Section 04 AdvancedTracing: you cannot evaluate what you cannot see

Evaluation depends on a recorded trajectory. Instrument the agent so every run is a complete, inspectable trace — this is the same span-tree from Topic 5.5, applied to agent steps.

PythonWhat an agent trace must capture
@dataclass
class AgentTrace:
    run_id: str
    task: str
    steps: list          # each: model reasoning, tool call, args, result, tokens, ms
    final_answer: str
    tools_called: list
    denied_calls: list   # attempted-but-blocked actions -- a key safety signal
    n_steps: int
    total_tokens: int
    cost_usd: float
    duration_ms: int
    outcome: str         # done | step_limit | budget | error

# you populate this. Tracing is not an add-on; it is the same

Tracing pays off twice

The trace you build for evaluation is the same trace you need for production debugging. When a user reports a bad agent run, you pull its trace and see exactly which step went wrong — the reasoning, the tool call, the result. Use OpenTelemetry's GenAI conventions (Topic 5.5) so agent traces sit in the same dashboards as the rest of your system, and carry business identifiers (user, tenant, session) as attributes so you can find a specific run when a complaint arrives. Tag each span with the tool, sub-agent and session so cost and latency attribute down to the individual tool and user — not just the run — and pick a tracer built for hierarchical agent graphs (Langfuse, Arize Phoenix via OpenInference, or LangSmith) so the User → Orchestrator → Tool → Observation tree stays legible.

Section 05 ProfessionalThe regression suite and the production loop

The same discipline as Topics 4.7 and 5.5, sized for agents.

  1. Build a task set. 30–100 real tasks with a way to verify each outcome and the process constraints (budget, allowed tools, safety). Include failure cases: unanswerable tasks, injection attempts, tasks that should trigger a human gate.
  2. Run it in CI on every change to prompts, tools or the model. Fail the build on a success-rate regression — using a confidence interval, since agents are non-deterministic (Topic 5.5).
  3. Track process, not just outcome. Fail also on cost-per-task or steps-per-task regressions, and on any new safety violation.
  4. Compare pairwise. "Is this version better than the last on these tasks" is more reliable than an absolute score.
  5. Grow from production. Every real failure — a runaway run, a wrong action, a complaint — becomes a new eval case. The suite converges on the failures that actually happen.
Automated red-teaming in CI

Regression on normal tasks is only half of it — also run a synthetic attack suite in CI: injection payloads, jailbreaks, and unsafe-tool provocations (Topic 8.11), executed on every change to a prompt or tool so a well-meaning edit can't quietly re-open a security hole. Libraries like DeepEval, Promptfoo and Giskard package attack datasets and metrics to make this a pipeline step rather than a manual audit — the same “fail the build on a regression” discipline, applied to safety.

Non-determinism is not an excuse to skip evaluation

"Agents are non-deterministic, so we can't test them" is the reasoning that ships unmonitored agents. The answer is statistical, not binary: run each task several times, report success rate with a confidence interval, and treat differences inside the interval as noise (Topic 5.5). Deterministic process checks — budget, forbidden tools, auth violations — are not subject to this at all; they must pass every single run. An agent you cannot evaluate is an agent you cannot safely deploy.

Section 06 ProfessionalExercises

Do these — roughly a weekend
  1. Instrument an agent to emit a full AgentTrace. Confirm you can reconstruct any run from it.
  2. Build a 20-task suite with outcome verifiers and process constraints. Include one injection task and one that should trigger a human gate.
  3. Write the deterministic trajectory assertions from Section 03. Run them on every task — they should never flake.
  4. Add an LLM judge for trajectory efficiency. Calibrate it against your own judgement on 20 traces and report the agreement rate.
  5. Run each task five times and report success rate with a confidence interval. Change a prompt and detect whether the difference is real or noise.
  6. Wire the suite into CI so a success-rate or cost-per-task regression fails the build.
  7. Find your p99 most expensive trajectory. Work out from its trace what made it run away, and add a guard.
