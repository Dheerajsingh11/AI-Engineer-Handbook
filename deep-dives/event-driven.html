Section 01 BeginnerStart from zero

Assumed knowledge

Kafka or any message broker, and Spring Boot. No new AI concepts are introduced — this page is about applying what you already know.

Most AI tutorials show a synchronous request: user asks, service calls model, service returns answer. That works for a chat box and fails for almost everything else, because of four properties of model calls.

Why AI workloads want a queue
PropertyTypical valueConsequence
Latency1–60 seconds; minutes for agentsHolding an HTTP thread is wasteful and fragile
ReliabilityRate limits, overload, timeouts are routineNeeds retries with backoff, not a 500 to the user
CostPer token, and it adds up fastBatching and deduplication have real financial value
DeterminismNone — same input, different outputRetries can produce different results; idempotency matters
The reframing that makes this straightforward

An LLM provider is a slow, flaky, expensive, non-deterministic third-party API. You have integrated dozens of those. Every pattern you already reach for — async request/reply, retry with jitter, circuit breakers, dead-letter queues, idempotency keys, the outbox pattern, bulkheads, backpressure — applies unchanged.

There is very little new engineering here. That is the point of this page, and it is why a backend engineer moving into AI is more valuable than the job title suggests.

Section 03 AdvancedAn event-driven ingestion pipeline

The ingestion pipeline from §4.5 is embarrassingly parallel, latency-tolerant and failure-prone. It is the natural first thing to make event-driven.

JavaStaged consumers, with batching where it pays
@Component
class DocumentParsedConsumer {

    private final KafkaTemplate<String, ChunkEvent> kafka;

    @KafkaListener(topics = "documents.uploaded", groupId = "parser",
                   concurrency = "4")
    public void parse(DocumentUploadedEvent event, Acknowledgment ack) {
        try {
            // Claim check: the message carries a reference, not the bytes.
            var resource = objectStore.get(event.storageKey());
            var text = parser.extract(resource);

            if (text.strip().length() < 100) {
                // Probably a scan. Route to OCR instead of silently
                // indexing an empty document (Topic 4.5).
                kafka.send("documents.needs-ocr", event.documentId(), event);
                ack.acknowledge();
                return;
            }

            int index = 0;
            for (String chunk : chunker.split(text)) {
                kafka.send("chunks.parsed", event.documentId(),
                        new ChunkEvent(event.documentId(), index++, chunk,
                                       event.tenantId(), event.contentHash()));
            }
            ack.acknowledge();

        } catch (UnparseableDocumentException e) {
            // Permanent failure: do not retry, send straight to DLQ.
            kafka.send("documents.dlq", event.documentId(), event);
            ack.acknowledge();
        }
    }
}

@Component
class EmbeddingConsumer {

    private final EmbeddingModel embeddings;
    private final VectorStore vectorStore;

    // BATCHING IS THE POINT. One call with 64 texts costs a fraction
    // of 64 calls, and avoids per-request rate limits entirely.
    @KafkaListener(topics = "chunks.parsed", groupId = "embedder",
                   batch = "true", containerFactory = "batchFactory")
    public void embed(List<ChunkEvent> batch, Acknowledgment ack) {

        // Deduplicate within the batch -- re-ingestion often replays
        // identical chunks, and embedding them twice is pure waste.
        var unique = batch.stream()
                .collect(toMap(ChunkEvent::contentHash, identity(), (a, b) -> a))
                .values().stream().toList();

        var texts = unique.stream().map(ChunkEvent::text).toList();
        var vectors = embeddings.embed(texts);      // ONE provider call

        var documents = IntStream.range(0, unique.size())
                .mapToObj(i -> toDocument(unique.get(i), vectors.get(i)))
                .toList();

        vectorStore.add(documents);
        ack.acknowledge();
    }
}
YAMLConsumer configuration that matters for AI workloads
spring:
  kafka:
    consumer:
      max-poll-records: 64             # matches the embedding batch size
      enable-auto-commit: false        # manual ack: never lose work
      properties:
        # A batch of 64 embeddings can take a while. Too low and the
        # broker evicts the consumer mid-batch, and the whole batch
        # is reprocessed -- paying for the same embeddings twice.
        max.poll.interval.ms: 600000   # 10 minutes
        session.timeout.ms: 45000
    listener:
      ack-mode: manual
      concurrency: 4

resilience4j:
  ratelimiter:
    instances:
      embedding-api:
        limit-for-period: 100          # stay under the provider's ceiling
        limit-refresh-period: 1s
  circuitbreaker:
    instances:
      llm-provider:
        failure-rate-threshold: 50
        wait-duration-in-open-state: 30s
        sliding-window-size: 20
The rebalance loop that costs real money

Default max.poll.interval.ms is five minutes. An embedding batch that occasionally takes six minutes causes the broker to consider the consumer dead, trigger a rebalance, and hand the batch to another consumer — which also takes six minutes, and so on. You get a rebalance storm, no forward progress, and a provider bill for the same work repeated indefinitely.

Raise the poll interval to comfortably exceed your worst-case batch time, keep batches bounded, and alert on rebalance frequency. This failure is expensive precisely because the system looks busy rather than broken.

Section 04 AdvancedLong-running agents as workflows

An agent that runs for two minutes across eight tool calls should not live inside an HTTP request. Model it as a durable workflow with persisted state, so a pod restart does not lose the run.

JavaAsync job with SSE result delivery
@RestController
class AgentJobController {

    @PostMapping("/agent/jobs")
    ResponseEntity<JobAccepted> submit(@RequestBody AgentRequest request,
                                      @AuthenticationPrincipal User user) {

        // Idempotency: the same client key returns the same job rather
        // than starting a second expensive run.
        var job = jobs.createOrGet(request.idempotencyKey(), user.getId(), request);

        if (job.isNew()) {
            kafka.send("agent.jobs", job.id(),
                       new AgentJobEvent(job.id(), user.getId(), request));
        }
        return ResponseEntity.accepted()
                .body(new JobAccepted(job.id(), "/agent/jobs/" + job.id() + "/stream"));
    }

    // The client subscribes and receives progress as it happens.
    @GetMapping(value = "/agent/jobs/{id}/stream",
                produces = MediaType.TEXT_EVENT_STREAM_VALUE)
    Flux<ServerSentEvent<AgentProgress>> stream(@PathVariable String id,
                                               @AuthenticationPrincipal User user) {
        jobs.assertOwnedBy(id, user.getId());       // authorise the stream too
        return progressBroker.subscribe(id)
                .map(p -> ServerSentEvent.builder(p).event(p.type()).build())
                .timeout(Duration.ofMinutes(15))
                .doOnCancel(() -> progressBroker.unsubscribe(id));
    }
}

@Component
class AgentJobConsumer {

    @KafkaListener(topics = "agent.jobs", groupId = "agent-workers",
                   concurrency = "8")
    public void run(AgentJobEvent event, Acknowledgment ack) {

        var state = jobs.load(event.jobId());
        if (state.isTerminal()) {                   // already done: replay-safe
            ack.acknowledge();
            return;
        }

        try {
            agentLoop.run(event.request(), state, progress -> {
                // Persist each step BEFORE publishing. If the pod dies
                // mid-run, a replay resumes rather than restarting --
                // which matters when each step costs money.
                jobs.appendStep(event.jobId(), progress);
                progressBroker.publish(event.jobId(), progress);
            });
            jobs.complete(event.jobId());

        } catch (AgentBudgetExceededException e) {
            jobs.fail(event.jobId(), "budget exceeded");   // do NOT retry
        } catch (TransientProviderException e) {
            throw e;                                // let Kafka retry with backoff
        } finally {
            ack.acknowledge();
        }
    }
}
Retry semantics need thought here

Not every failure should be retried, and getting this wrong is expensive in a way ordinary services are not.

  • Retry: 429, 5xx, timeouts, connection resets — transient provider problems.
  • Do not retry: budget exceeded, step limit, content policy refusal, malformed input, authorisation denied. These will fail identically and each attempt costs money.
  • Retry carefully: a partially completed agent run. Resume from persisted state rather than restarting, or you pay twice and may repeat side effects.

Encode this as an exception hierarchy so the classification is structural rather than a set of instanceof checks scattered through consumers.

Section 05 ProfessionalCost control as an architectural concern

In a conventional service, a runaway consumer wastes CPU you have already paid for. Here it produces an invoice. That changes what belongs in the architecture.

JavaSemantic caching and budget enforcement
@Service
class SemanticCache {

    private final VectorStore cache;
    private final EmbeddingModel embeddings;

    // Exact-match caching helps little -- users phrase things
    // differently every time. Semantic caching answers "has anyone
    // asked something equivalent?" and can remove a large share of
    // spend on repetitive workloads such as support desks.
    public Optional<String> lookup(String question, long tenantId) {
        var hits = cache.similaritySearch(SearchRequest.builder()
                .query(question)
                .topK(1)
                .similarityThreshold(0.97)      // high: near-paraphrase only
                .filterExpression("tenant_id == " + tenantId)
                .build());

        return hits.stream().findFirst()
                .filter(this::notStale)
                .map(d -> d.getMetadata().get("answer").toString());
    }
}

@Component
class BudgetGuard {

    @Scheduled(fixedRate = 60_000)
    public void enforce() {
        for (var tenant : tenants.active()) {
            var spend = costs.spendToday(tenant.id());

            if (spend > tenant.dailyLimit()) {
                // Pause consumption rather than failing requests: work
                // queues up and resumes rather than being lost.
                consumers.pause("agent.jobs", tenant.id());
                alerts.notify(tenant, "daily AI budget reached");
            } else if (spend > tenant.dailyLimit() * 0.8) {
                // Degrade before denying: route to a cheaper model.
                routing.downgrade(tenant.id());
                alerts.warn(tenant, "80% of daily AI budget used");
            }
        }
    }
}

Section 06 ProfessionalTracing across the pipeline

Propagate trace context through the broker

The whole value of tracing here is answering "this answer was wrong — what produced it?". That requires one trace spanning upload, parse, chunk, embed, store, retrieve and generate, across four consumers and two days.

Spring Kafka propagates W3C trace context in message headers automatically when Micrometer Tracing is on the classpath. Add the GenAI attributes — model, tokens in/out, cost, cached — and your AI pipeline appears in the same Grafana or Jaeger view as everything else. Carry a document_id and tenant_id as baggage so you can filter a trace search by business identity rather than by span id.

Section 07 ProfessionalExercises

Do these — roughly a weekend
  1. Build the four-stage ingestion pipeline in Kafka. Feed 1,000 documents through it and measure throughput per stage.
  2. Compare embedding one chunk per message against batches of 64. Record the cost and wall-clock difference.
  3. Set max.poll.interval.ms deliberately too low and reproduce the rebalance storm. Watch the same work being paid for repeatedly.
  4. Add retry with exponential backoff and jitter. Then remove the jitter and observe synchronised retries re-triggering the rate limit.
  5. Implement the async agent job with SSE progress. Kill the worker mid-run and confirm it resumes from persisted state rather than restarting.
  6. Build an exception hierarchy separating retryable from permanent failures. Verify permanent failures reach the DLQ without retrying.
  7. Implement semantic caching at 0.97 similarity. Measure the hit rate on real traffic, then try 0.90 and inspect the false matches.
  8. Wire distributed tracing end to end and view one document's full journey as a single trace.
