Hooks, Middleware & Interceptors

The interception layer around every agent action. This page explains pre-hooks and post-hooks — the middleware that runs before and after each tool call and model step — why they are where real control lives (auth, validation, guardrails, caching, cost, logging), builds a hook system, and covers the lifecycle events worth intercepting.

Section 01 BeginnerStart from zero

Assumed knowledge

The agent loop (Topic 8.1) and robust tool execution (Topic 8.3). If you know Servlet filters, Spring interceptors, Express middleware or React effects, you already know this pattern — this is the same idea around agent actions.

An agent takes actions in a loop. A hook is code that runs around those actions — before one (a pre-hook) or after one (a post-hook). Hooks are the seam where you insert everything that must happen on every action but does not belong inside the action itself: authorisation, validation, guardrails, caching, cost tracking, logging, redaction.

Why hooks matter more than they sound

The prompt is guidance the model can ignore. Hooks are enforcement your code guarantees. "Never delete production data" in a system prompt is a hope; a pre-hook that blocks any delete tool call against a production resource is a rule. When you read that the real security controls for agents live "in the code, not the prompt" (Topics 5.6, 8.3), the code they mean is largely hooks. This is the layer that makes an agent trustworthy.

The words, in plain English
Hook
Code that runs at a defined point in the agent's lifecycle.
Pre-hook
Runs before an action. Can inspect it, modify it, or block it.
Post-hook
Runs after an action. Can inspect or transform the result.
Middleware
The general name for this interception pattern; hooks are middleware for agents.
Short-circuit
A pre-hook stopping an action from running at all (e.g. denying it).
Lifecycle event
A named point where hooks can fire — before a tool, after a tool, on each model step, and so on.

Section 03 IntermediateBuild a hook system

A hook system is a registry of functions that fire at named lifecycle points, and the agent loop calling them at the right moments. A pre-hook can return a decision that short-circuits the action.

PythonA minimal but real hook system
from dataclasses import dataclass
from enum import Enum

class Decision(Enum):
    ALLOW = "allow"
    DENY = "deny"          # block the action, return a message to the model
    MODIFY = "modify"      # run it, but with changed arguments
    ASK = "ask"            # pause for human approval (Topic 8.4)

@dataclass
class HookResult:
    decision: Decision = Decision.ALLOW
    reason: str = ""
    new_args: dict | None = None

class Hooks:
    def __init__(self):
        self.pre_tool, self.post_tool, self.on_step = [], [], []
    def pre(self, fn):  self.pre_tool.append(fn);  return fn
    def post(self, fn): self.post_tool.append(fn); return fn

hooks = Hooks()

# --- PRE-HOOKS: run before every tool call ------------------------
@hooks.pre
def authorise(ctx):
    if not authz.permits(ctx.principal, ctx.tool, ctx.args):
        return HookResult(Decision.DENY, "not permitted")   # short-circuit
    return HookResult()

@hooks.pre
def gate_destructive(ctx):
    if ctx.tool.is_destructive:
        return HookResult(Decision.ASK, f"Approve {ctx.tool.name}?")
    return HookResult()

@hooks.pre
def budget_guard(ctx):
    if costs.spent(ctx.run_id) > ctx.budget:
        return HookResult(Decision.DENY, "run budget exceeded")
    return HookResult()

# --- POST-HOOKS: run after every tool call ------------------------
@hooks.post
def redact_pii(ctx, result):
    return pii.redact(result)             # scrub before it re-enters context

@hooks.post
def record(ctx, result):
    tracer.log(ctx.tool.name, ctx.args, size=len(str(result)))
    return result
PythonThe loop calling the hooks
def execute_with_hooks(call, ctx):
    # --- PRE: run all pre-hooks; first non-ALLOW wins -------------
    args = call.arguments
    for hook in hooks.pre_tool:
        r = hook(ctx.with_args(args))
        if r.decision is Decision.DENY:
            return tool_error(call, r.reason)          # action never runs
        if r.decision is Decision.ASK:
            if not human_approves(r.reason):           # pause for a person
                return tool_error(call, "rejected by human")
        if r.decision is Decision.MODIFY:
            args = r.new_args                          # e.g. force a tenant filter

    result = ctx.tool.run(args)                        # THE ACTION

    # --- POST: transform the result through every post-hook -------
    for hook in hooks.post_tool:
        result = hook(ctx, result)
    return tool_result(call, result)
You have built this before

This is Servlet Filter, Spring HandlerInterceptor, and Spring AI's Advisor chain (Topic 3.2), applied to agent actions instead of HTTP requests. The preHandle/postHandle split is exactly pre-hook/post-hook, and a filter that stops the chain is a DENY. If you have written request middleware, you are not learning a new concept — you are pointing a familiar one at a new target.

Section 04 AdvancedThe lifecycle events worth intercepting

Tool calls are the most important interception point, but a full agent lifecycle has several, and real frameworks expose them.

Agent lifecycle hooks
EventFiresTypical use
on_run_startBefore the loop beginsBudget setup, run-level tracing, load memory
pre_toolBefore each tool callAuth, validation, human gate, cache lookup
post_toolAfter each tool callRedaction, cache store, usage accounting
pre_model / post_modelAround each model callPrompt redaction, token accounting, guardrail check on output
on_messageEach new message addedContent moderation, logging
on_run_endAfter the loop finishesPersist memory, final trace, cost report
on_errorOn any failureFallback, alerting, safe cleanup
Hooks are cross-cutting concerns, kept out of the agent logic

The reason to use hooks rather than sprinkling checks through your loop is the same reason you use middleware anywhere: separation of concerns. Auth, logging, cost and redaction are cross-cutting — they apply to every action regardless of what it does. Putting them in hooks keeps the agent's actual logic clean, makes each concern testable in isolation, and lets you add or remove a policy (say, a new PII rule) in one place without touching the agent. It is the same argument as aspect-oriented programming, and it is right for the same reasons.

Two failure modes of hooks themselves

A slow hook slows every action. Hooks run on the hot path of every step — a synchronous network call in a pre-hook multiplies your latency by the number of tool calls. Keep them fast, or make them async.

A crashing hook can take down the agent. A post-hook that throws on an unexpected result shape halts a run that would otherwise have succeeded. Make hooks defensive and fail-open where they are advisory (logging) and fail-closed only where they are security controls (auth). Decide that per hook, deliberately.

Section 06 ProfessionalExercises

Do these — roughly an evening
  1. Build the hook system from Section 03 and wire it into your agent loop from Topic 8.3.
  2. Write an authorisation pre-hook that DENYs an unpermitted tool. Confirm the action never runs and the model gets a clean message.
  3. Write a destructive-action gate that ASKs for human approval. Approve one call and reject another.
  4. Write a MODIFY pre-hook that injects a tenant filter into every retrieval call — enforcing isolation regardless of what the model requested.
  5. Write a PII-redaction post-hook and confirm sensitive data never re-enters the context.
  6. Add a budget pre-hook and a caching pre/post pair. Measure the cost reduction on a repetitive workload.
  7. Make a post-hook throw and observe it breaking a run. Then make it fail-open and confirm the run survives.
