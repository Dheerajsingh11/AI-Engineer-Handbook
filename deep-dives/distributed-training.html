Distributed & Large-Scale Training

Training models too big for one GPU. This page covers distributed training — splitting a model and its data across many GPUs — the three kinds of parallelism, how FSDP and ZeRO shard the memory, the communication cost that decides whether it scales, and the practical levers that let you train large models without a supercomputer.

Section 01 BeginnerStart from zero

Assumed knowledge

GPU computing and VRAM (Topic 2.6), the training loop (Topic 2.5), and hardware sizing (Topic 6.5). This page is what happens when one GPU is not enough.

Modern models do not fit on one GPU — sometimes the model itself is too big for a single card's memory, sometimes it fits but training would take months. Distributed training is the set of techniques for spreading the work across many GPUs (and many machines) so that large models can be trained at all, and trained in reasonable time.

Two different problems, often confused

Distribution solves two distinct pains, and knowing which you have decides the technique. "Training is too slow" — the model fits on one GPU, you just want it faster — is solved by data parallelism: copy the model to many GPUs, split the batch among them. "The model does not fit" — even one copy exceeds a single GPU's VRAM — is solved by sharding the model itself across GPUs (model/tensor/pipeline parallelism, or FSDP/ZeRO). Most real setups combine them. Everything on this page is one of these two moves, or a blend.

The words, in plain English
Data parallelism
Every GPU has the whole model, each processes a different slice of the batch.
Model parallelism
The model itself is split across GPUs because it is too big for one.
Sharding
Splitting the weights/gradients/optimiser state across GPUs so no one holds all of it.
All-reduce
The step where GPUs combine their gradients so all stay in sync.
FSDP / ZeRO
Techniques that shard the memory to train big models on modest hardware.

PythonData parallelism — the everyday case
# PyTorch DDP: one process per GPU, each with a full model copy.
# Each GPU does forward+backward on ITS slice of the batch, then
# all-reduce averages the gradients so every copy stays identical.
import torch.distributed as dist
from torch.nn.parallel import DistributedDataParallel as DDP

dist.init_process_group("nccl")          # GPU-to-GPU comms backend
model = DDP(model.to(local_rank), device_ids=[local_rank])

for x, y in sampler_split(loader):        # each rank sees different data
    loss = model(x, y)
    loss.backward()                       # DDP all-reduces grads here
    opt.step(); opt.zero_grad()
# Effective batch size = per-GPU batch x number of GPUs.

Section 03 IntermediateSharding memory: FSDP & ZeRO

Plain data parallelism has a hidden waste: every GPU stores a full copy of the weights, the gradients, and the optimiser state — the last of which is often the biggest. Sharding removes that redundancy.

The insight behind ZeRO (and PyTorch's FSDP): if you have 8 GPUs, you do not need 8 identical copies of the optimiser state — you need one copy, split into 8 pieces, one per GPU. Each GPU holds only its shard of the weights, gradients and optimiser state, and gathers the full weights for a layer only briefly when it needs them, then releases them. The effect is dramatic: memory per GPU drops roughly in proportion to the number of GPUs, so a model that would need one impossible 640 GB card can train across eight 80 GB cards. The cost is more communication — the pieces must be gathered and scattered constantly — which is the trade the next section is about.

What ZeRO shards, in stages
StageShardsMemory saved
ZeRO-1Optimiser stateLarge (optimiser state is often the biggest)
ZeRO-2+ gradientsMore
ZeRO-3 / FSDP+ weightsMost — near-linear in GPU count

Section 04 AdvancedCommunication is the bottleneck

Distribution is never free: every technique trades compute savings for communication cost. Whether it scales comes down to how much the GPUs must talk, and how fast the links between them are.

Why the interconnect decides everything

The moment work is split, GPUs must synchronise — averaging gradients (all-reduce), gathering sharded weights, passing activations down a pipeline. That traffic runs over the links between GPUs, and those links are wildly unequal: GPUs inside one machine talk over fast NVLink; GPUs in different machines talk over comparatively slow network. So the same algorithm can scale beautifully on one node and stall across a cluster. This is why the practical art is keeping communication local and overlapping it with computation — and why tensor parallelism (chatty, needs NVLink) is kept within a machine while data/pipeline parallelism (less chatty) spans machines. If you ever see "we added GPUs and it barely got faster," the interconnect is almost always the reason.

Diminishing returns & the levers before you scale out

Doubling GPUs rarely doubles speed — communication overhead means real scaling is sub-linear, and past a point adding GPUs adds cost faster than throughput. So before reaching for more hardware, exhaust the single-GPU levers: gradient accumulation (simulate a big batch by summing several small ones — more effective batch, no extra memory), gradient checkpointing (recompute activations in the backward pass instead of storing them — trade compute for memory), mixed precision (bf16, Topic 2.6), and parameter-efficient fine-tuning (LoRA/QLoRA, Topic 3.5), which sidesteps most of the memory problem entirely for fine-tuning. Distribute when you must, not by default.

Section 05 ProfessionalIn practice

You will almost never wire this up by hand — frameworks (PyTorch FSDP, DeepSpeed, Hugging Face Accelerate) implement the hard parts, and you configure them. But the concepts are what let you configure them correctly: choose data parallelism when the model fits and you want speed; reach for FSDP/ZeRO when it does not; keep tensor parallelism inside a node; and lean on accumulation, checkpointing and LoRA before scaling out. For the vast majority of applied work — including fine-tuning your own model (Topic 3.5) — a single GPU with QLoRA, or a handful of GPUs with FSDP, is enough; thousand-GPU training is a frontier-lab concern. The value of this page is knowing which regime you are in, and choosing the cheapest technique that fits — the same judgement that runs through all of Phases 18–19.

Section 06 ProfessionalExercises

Do these — scale a training run
  1. Train a model with PyTorch DDP on 2 GPUs (or 2 processes). Confirm the effective batch size and measure the speedup vs one.
  2. Add gradient accumulation to reach a large effective batch on one GPU. Compare it to true multi-GPU on the same batch.
  3. Turn on gradient checkpointing. Measure the memory saved and the extra compute time — feel the trade.
  4. Fine-tune a model too big for your GPU using FSDP or DeepSpeed ZeRO-3. Watch per-GPU memory drop as you add shards.
  5. Compare full fine-tuning vs QLoRA (Topic 3.5) for memory. Understand why LoRA often removes the need to distribute at all.
  6. Profile a multi-GPU run and find the communication time. Identify whether the interconnect is your bottleneck (Section 04).
