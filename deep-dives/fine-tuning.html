Section 01 BeginnerStart from zero

Assumed knowledge

Gradient descent (Topic 1.4), matrix rank (Topic 1.1), and the PyTorch training loop (Topic 2.5). This is the most mathematically demanding page in Phase 3.

Fine-tuning means continuing to train an already-trained model on your own data, so it adapts to your task. The concept is simple. The judgement about whether to do it is where most of the value lies.

Read this before you fine-tune anything

RAG teaches a model facts. Fine-tuning teaches it behaviour.

If the complaint is "it doesn't know our products", that is retrieval — and fine-tuning is a poor way to inject facts, because the model will still confuse them, cannot cite them, and needs retraining whenever they change. If the complaint is "it won't reliably produce our XML format", or "it doesn't sound like us", or "it can't handle our domain's terminology" — that is behaviour, and fine-tuning may genuinely be the answer.

Most fine-tuning projects are attempts to solve a retrieval problem with training. They cost weeks and produce a model that is worse at everything else.

When fine-tuning genuinely wins

  • Consistent structured output at very high volume, where a smaller fine-tuned model replaces a large prompted one at a fraction of the cost.
  • Domain language — medical, legal, or an internal jargon the base model misreads.
  • Latency and cost — distilling a large model's behaviour into a small one you host yourself.
  • Classification at scale where a fine-tuned small model beats a prompted large one on both accuracy and price.
  • Embedding models for retrieval — the highest-return fine-tune available to a RAG engineer, covered in Topic 2.5.

Section 02 IntermediateLoRA, derived

Full fine-tuning updates every parameter. For a 7B model in fp16 that means 14 GB of weights, 14 GB of gradients and roughly 56 GB of Adam optimiser state — over 84 GB before activations. Beyond a single GPU, and that is the small model.

LoRA starts from an empirical observation: the change a fine-tune makes to a weight matrix has very low intrinsic rank. The update is not arbitrary; it lies in a small subspace. If that is true, you do not need to store the full update.

From the low-rank hypothesis to the parameter saving
  1. Fine-tuning computes W′ = W + ΔW, where W is d×k. The trained model is the base plus an update.
  2. Hypothesis: rank(ΔW) = r ≪ min(d,k). The update lies in a low-dimensional subspace — measured empirically, and it holds well.
  3. Any rank-r matrix factorises: ΔW = BA with B being d×r and A being r×k. Standard result. This is the whole trick.
  4. Freeze W. Train only A and B: h = Wx + BAx. Parameter count falls from dk to r(d+k).
  5. For d=k=4096 and r=8: 16,777,216 → 65,536 parameters. A 256× reduction, per matrix. And no optimiser state for the frozen 99.6%.  ■
The LoRA forward pass h  =  Wx  +  αr BAx A is initialised from a Gaussian, B to zeros — so BA = 0 at step one and the model starts as an exact copy of the base. Training then departs from it smoothly rather than from a random perturbation. The α/r scaling means changing r does not force you to retune the learning rate; a common convention is α = 2r.
Three properties that make LoRA operationally excellent
  • Adapters are tiny. A LoRA for a 7B model is 10–200 MB, versus 14 GB. You can version them in a registry and ship them like config.
  • They are composable and hot-swappable. One base model in GPU memory can serve many adapters — per tenant, per task — swapped per request. Full fine-tunes would need a separate model each.
  • They can be merged. W + BA can be folded into the base weights for deployment, giving zero added inference latency. You choose: merged for speed, unmerged for flexibility.
PythonLoRA implemented from scratch
import torch, torch.nn as nn, math

class LoRALinear(nn.Module):
    """Wrap a frozen Linear layer with a trainable low-rank update."""

    def __init__(self, base: nn.Linear, r=8, alpha=16, dropout=0.05):
        super().__init__()
        self.base = base
        for p in self.base.parameters():
            p.requires_grad = False               # freeze the original

        self.r = r
        self.scaling = alpha / r
        self.dropout = nn.Dropout(dropout)

        # A: random init. B: ZEROS -- so BA = 0 initially and the
        # wrapped layer is numerically identical to the base at step 0.
        self.A = nn.Parameter(torch.empty(r, base.in_features))
        self.B = nn.Parameter(torch.zeros(base.out_features, r))
        nn.init.kaiming_uniform_(self.A, a=math.sqrt(5))

    def forward(self, x):
        return self.base(x) + self.dropout(x) @ self.A.T @ self.B.T * self.scaling

    @torch.no_grad()
    def merge(self):
        """Fold the adapter into the base weights: zero inference cost."""
        self.base.weight += (self.B @ self.A) * self.scaling
        return self.base


def apply_lora(model, target_names=("q_proj", "v_proj"), r=8, alpha=16):
    """Attach LoRA to the attention projections. Targeting q and v
    is the original paper's recommendation and remains a strong
    default; adding k, o and the MLP projections helps on harder
    tasks at proportionally more cost."""
    for name, module in list(model.named_modules()):
        for child_name, child in list(module.named_children()):
            if isinstance(child, nn.Linear) and child_name in target_names:
                setattr(module, child_name, LoRALinear(child, r, alpha))
    return model

QLoRA, and why it changed who can fine-tune

QLoRA quantises the frozen base model to 4 bits — using a data type called NF4 designed for normally-distributed weights — while keeping the LoRA adapters in bf16. Gradients flow through the quantised weights to the adapters without ever needing a full-precision copy of the base.

The arithmetic: a 70B model in fp16 needs 140 GB; in 4-bit it needs about 35 GB. Add adapters, activations and optimiser state for 0.5% of parameters and it fits on a single 48 GB GPU. Fine-tuning a frontier-class open model went from a cluster job to something you can rent for a few dollars an hour.

Section 04 AdvancedThe data is the whole job

Practitioners consistently report the same thing: fine-tuning outcomes are dominated by data quality, and the hyperparameters barely matter by comparison. A thousand carefully curated examples routinely beat fifty thousand scraped ones.

PythonPreparing a dataset properly
import json, hashlib
from collections import Counter

def load_and_clean(path):
    seen, rows = set(), []
    for line in open(path, encoding="utf-8"):
        row = json.loads(line)

        # 1. DEDUPLICATE. Duplicates across the train/eval split are
        #    leakage, and they make your eval numbers meaningless.
        key = hashlib.sha256(
            (row["messages"][-2]["content"] + row["messages"][-1]["content"])
            .encode()).hexdigest()
        if key in seen:
            continue
        seen.add(key)

        # 2. Drop degenerate examples
        answer = row["messages"][-1]["content"].strip()
        if len(answer) < 10 or len(answer) > 8000:
            continue

        rows.append(row)
    return rows

def audit(rows):
    """Look at the distribution before training, not after."""
    lengths = [len(json.dumps(r)) for r in rows]
    lengths.sort()
    print(f"n = {len(rows)}")
    print(f"length p50={lengths[len(lengths)//2]} p95={lengths[int(len(lengths)*.95)]}")

    # 3. Class balance. If 80% of your examples are one category,
    #    the model learns to always predict that category.
    labels = Counter(r.get("label", "unlabelled") for r in rows)
    for label, count in labels.most_common():
        print(f"  {label:24s} {count:6d}  {count/len(rows):6.1%}")

# 4. SPLIT BY A NATURAL GROUPING, not randomly. If ten examples
#    come from one document, a random split puts some in train and
#    some in eval, and your eval score is inflated by memorisation.
def split_by_group(rows, group_key="document_id", eval_fraction=0.1):
    groups = sorted({r[group_key] for r in rows})
    cutoff = int(len(groups) * (1 - eval_fraction))
    train_groups = set(groups[:cutoff])
    train = [r for r in rows if r[group_key] in train_groups]
    evaluation = [r for r in rows if r[group_key] not in train_groups]
    return train, evaluation

Section 05 AdvancedA complete fine-tuning run

PythonQLoRA with PEFT and TRL, end to end
import torch
from transformers import (AutoModelForCausalLM, AutoTokenizer,
                          BitsAndBytesConfig)
from peft import LoraConfig, get_peft_model, prepare_model_for_kbit_training
from trl import SFTTrainer, SFTConfig
from datasets import load_dataset

BASE = "meta-llama/Llama-3.1-8B-Instruct"

# --- 1. Load the base model in 4-bit ------------------------------
bnb = BitsAndBytesConfig(
    load_in_4bit=True,
    bnb_4bit_quant_type="nf4",              # NF4: designed for normal weights
    bnb_4bit_compute_dtype=torch.bfloat16,  # compute in bf16, store in 4-bit
    bnb_4bit_use_double_quant=True,         # quantise the quantisation constants
)

model = AutoModelForCausalLM.from_pretrained(
    BASE, quantization_config=bnb, device_map="auto",
    attn_implementation="flash_attention_2")
model = prepare_model_for_kbit_training(model, use_gradient_checkpointing=True)

tokenizer = AutoTokenizer.from_pretrained(BASE)
tokenizer.pad_token = tokenizer.eos_token
tokenizer.padding_side = "right"            # left padding breaks training

# --- 2. Attach LoRA adapters --------------------------------------
peft_config = LoraConfig(
    r=16,
    lora_alpha=32,                          # alpha = 2r, a common convention
    lora_dropout=0.05,
    bias="none",
    task_type="CAUSAL_LM",
    # Targeting all projections beats q,v alone on harder tasks.
    target_modules=["q_proj", "k_proj", "v_proj", "o_proj",
                    "gate_proj", "up_proj", "down_proj"],
)
model = get_peft_model(model, peft_config)
model.print_trainable_parameters()
# trainable: 41,943,040 || all: 8,072,204,288 || trainable%: 0.5196

# --- 3. Data ------------------------------------------------------
dataset = load_dataset("json", data_files={"train": "train.jsonl",
                                           "eval":  "eval.jsonl"})

# --- 4. Train -----------------------------------------------------
trainer = SFTTrainer(
    model=model,
    train_dataset=dataset["train"],
    eval_dataset=dataset["eval"],
    processing_class=tokenizer,
    args=SFTConfig(
        output_dir="./out",
        num_train_epochs=3,                 # more than 3 usually overfits
        per_device_train_batch_size=4,
        gradient_accumulation_steps=4,      # effective batch = 16
        learning_rate=2e-4,                 # LoRA wants ~10x a full fine-tune
        lr_scheduler_type="cosine",
        warmup_ratio=0.03,
        max_grad_norm=1.0,
        bf16=True,
        gradient_checkpointing=True,
        logging_steps=10,
        eval_strategy="steps", eval_steps=100,
        save_strategy="steps", save_steps=100,
        load_best_model_at_end=True,        # keep the best, not the last
        metric_for_best_model="eval_loss",
        max_length=2048,
        packing=True,                       # pack short examples: less padding waste
    ),
)
trainer.train()
trainer.save_model("./adapter")             # ~80 MB, not 16 GB

# --- 5. Serve -----------------------------------------------------

Section 06 ProfessionalHow fine-tuning goes wrong

Failure modes and their fixes
FailureSymptomFix
Catastrophic forgettingGreat at your task, noticeably worse at everything elseLower learning rate, fewer epochs, lower rank, mix in general instruction data
OverfittingTrain loss falls, eval loss risesMore data, fewer epochs, early stopping, more dropout
Format driftOutput no longer matches the chat templateUse the tokeniser's own chat template; never hand-roll it
Loss on the promptModel learns to generate questions, not answersMask prompt tokens so loss is computed only on completions
Leakage across splitExcellent eval, poor in productionDeduplicate; split by document or customer, not randomly
Padding side wrongNonsense output after trainingpadding_side="right" for training, "left" for batched generation
Safety regressionThe fine-tune eroded refusal behaviourInclude safety examples; re-run a red-team suite before shipping
No baselineNobody can say whether it helpedMeasure the prompted baseline first. Non-negotiable
The evaluation that makes this defensible

Run three evaluations, not one. (1) Your task — did it improve, and by more than the confidence interval? (2) General capability — run a standard benchmark before and after to quantify forgetting. (3) Safety — a red-team suite, because fine-tuning demonstrably erodes alignment even when your data contains nothing harmful.

A fine-tune that gains 8 points on your task and loses 15 on general reasoning is a regression that a single-metric evaluation will report as a success. This is the most common way fine-tuning projects mislead their own teams.

Fitting this into a Java estate

Serve the fine-tuned model with vLLM behind an OpenAI-compatible HTTP endpoint. Spring AI already speaks that protocol, so your Java service changes one property and points at your own model instead of a provider. vLLM supports multi-LoRA, so a single deployment can serve per-tenant adapters selected by request. This keeps all the Python confined to a model-serving container that your platform team can operate like any other service — no Python in your application code path.

Section 08 ProfessionalExercises

Do these — roughly a weekend, plus GPU rental
  1. Compute the parameter counts by hand for r = 4, 8, 16, 64 on a 4096×4096 matrix. Plot trainable parameters against rank.
  2. Implement LoRALinear and verify that with B=0 the wrapped layer produces bit-identical output to the base.
  3. Implement merge() and confirm the merged layer matches the unmerged forward pass to floating-point tolerance.
  4. Fine-tune a small model (1–3B) with QLoRA on a formatting task using 500 examples. Free Colab is enough.
  5. Measure the prompted baseline first. Then measure the fine-tune. Report the difference with a confidence interval.
  6. Run a general benchmark before and after. Quantify the forgetting. Decide honestly whether the trade was worth it.
  7. Deliberately train for 10 epochs on 100 examples. Watch eval loss diverge from train loss — overfitting, seen directly.
  8. Serve your adapter with vLLM and call it from Spring AI by changing only configuration.
