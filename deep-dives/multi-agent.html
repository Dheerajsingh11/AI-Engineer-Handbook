Multi-Agent Systems & Frameworks

When one agent is not enough — and the honest test for whether that is ever true. This page covers the multi-agent topologies, the frameworks (LangGraph, CrewAI, AutoGen, OpenAI Agents SDK), how agents communicate and hand off, and the disciplined case for privilege separation and context isolation as the real reasons to split an agent in two.

Section 01 BeginnerStart from zero

Assumed knowledge

Building agents (Topic 8.3), orchestration (Topic 8.2) and tool types (Topic 8.4). Multi-agent is orchestration applied to whole agents.

A multi-agent system is several agents working together on a task. It is the most over-reached-for pattern in the field, so this page leads with the skepticism: most systems labelled multi-agent should be one agent with more tools, or a workflow. But there are two genuine reasons to split, and when they apply, multi-agent is the right answer.

The only two good reasons to use multiple agents
  1. Context isolation. A sub-task needs to read a huge amount — 200k tokens of documents, a long web crawl — and you want it to return a small summary without polluting the main agent's context (Topic 5.3). A separate agent with its own window does this cleanly.
  2. Privilege separation. Different parts of the task need different permissions. A read-only research agent that physically cannot write, and a separate action agent behind a human gate, is meaningful security (Topics 5.6, 8.4) — not achievable within one agent.

Measured parallelism is a third, weaker reason. "It felt more modular" is not a reason — use functions.

The words, in plain English
Supervisor
A coordinating agent that delegates to specialist agents.
Handoff
Passing control (and the conversation) from one agent to another.
Specialist / worker
An agent focused on one kind of subtask.
Blackboard
A shared state store agents read from and write to.
Topology
The shape of how agents connect — who can talk to whom.

PythonThe supervisor pattern — the one to reach for first
def supervisor(request, principal):
    # The coordinator chooses ONE specialist and states what it needs.
    plan = llm_json(f"""Choose a specialist for this request and say
        precisely what to ask it. Return {{"agent": ..., "task": ...}}.
        Specialists:
          research - read-only; searches documents and the web
          analysis - read-only; computes over structured data
          action   - can modify records; REQUIRES a human gate
        Request: {request}""")

    specialist = SPECIALISTS[plan["agent"]]

    # PRIVILEGE SEPARATION is the real payoff: the research agent has
    # no write tool registered, so no instruction can make it write.
    if not authz.permits(principal, specialist.scope):
        return "Not permitted."

    # CONTEXT ISOLATION: the specialist runs in its OWN window and
    # returns a summary, not its full transcript.
    return specialist.run(plan["task"], principal)

Section 03 AdvancedHow agents talk to each other

The channel between agents determines how coupled and how debuggable the system is.

Inter-agent communication
MechanismHowTrade-off
Direct callOne agent invokes another as a tool (Topic 8.4)Simple, synchronous; tight coupling
Shared stateAgents read/write a common store (blackboard)Decoupled; needs conflict handling
Message passingAgents exchange messages via a queue (Topic 5.4)Scalable, async; more infrastructure
HandoffControl + context transfer to another agentClean ownership; state-transfer bugs
What goes wrong at scale
  • Cost multiplies. Each agent is a full loop with its own token spend. A five-agent system can cost 5–10× a single well-toolled agent for the same task.
  • Errors compound. A mistake by one agent becomes the input to the next. Without validation at handoffs, one bad step poisons the whole chain.
  • Traceability collapses. "Which agent decided that, and why?" is hard across a network. Trace the whole system as one linked trajectory (Topic 8.10), not per-agent.
  • Coordination overhead. Agents spend tokens talking about the work instead of doing it. Keep the number of agents small and the topology shallow.

PythonThe same idea in CrewAI — roles and tasks
from crewai import Agent, Task, Crew, Process

researcher = Agent(role="Researcher",
    goal="Find accurate facts from the knowledge base",
    tools=[retrieval_tool],            # read-only -- privilege separation
    llm=llm)
writer = Agent(role="Writer",
    goal="Turn findings into a clear brief",
    tools=[], llm=llm)

crew = Crew(
    agents=[researcher, writer],
    tasks=[Task(description="Research {topic}", agent=researcher),
           Task(description="Write a brief from the research", agent=writer)],
    process=Process.sequential,        # or hierarchical with a manager
)
result = crew.kickoff(inputs={"topic": "our 2025 refund policy"})

# Note this specific crew is really a two-step WORKFLOW (Topic 5.2).
# The role framing is pleasant, but ask honestly whether the
# multi-agent overhead is buying you anything a chain would not.
The discipline that keeps multi-agent sane

Before splitting into agents, write down which of the two good reasons (Section 01) applies to each agent. If an agent has neither a distinct context need nor a distinct permission scope, fold it back into its caller as a tool or a function. Systems that grow to a dozen agents almost always contain several that should never have been agents — and each one is paying full token cost to exist. Start with one agent; add a second only when you can name the reason.

Section 05 ProfessionalExercises

Do these — roughly a weekend
  1. Take a "multi-agent" idea and honestly test each agent against the Section 01 two-reasons rule. Collapse the ones that fail.
  2. Build a supervisor with two specialists (one read-only, one action-capable). Prove the read-only one has no write tool.
  3. Build the same task as (a) one agent with all tools and (b) a supervisor with specialists. Compare cost, latency and quality.
  4. Implement a research sub-agent that reads a large corpus and returns only a summary. Confirm the parent's context stays small.
  5. Add validation at a handoff so a bad output from one agent is caught before it reaches the next.
  6. Trace a full multi-agent run as one linked trajectory. Answer "which agent decided X?" from the trace.
