Section 01 BeginnerStart from zero

Assumed knowledge

Core Python (Topic 2.1) and the idea of tool calling (Topic 5.1). If you have used Spring AI or LangChain4j, you already know most of the concepts — this is the Python dialect.

LangChain is the most widely used — and most argued-about — framework in AI engineering. It appears in a large share of job descriptions, so you need to be fluent in it. You also need to know which parts to use and which to ignore, because it grew fast and carries history.

Think of the ecosystem as three layers:

The one thing to internalise

Modern LangChain is two ideas: LCEL (compose model + prompt + parser with the | operator into a runnable pipeline) and LangGraph (when the flow has state, branches or loops, model it as a graph of nodes). Everything you read from before ~2024 uses the old chain/agent classes — recognise them so you can avoid copying them.

The words, in plain English
Runnable
Anything with an .invoke() method. Models, prompts, parsers, whole pipelines — all runnables, all composable.
LCEL
LangChain Expression Language: chaining runnables with |, like a Unix pipe.
Node
One step in a LangGraph — a Python function that reads state and returns an update.
Edge
A connection between nodes. Conditional edges are how the graph branches.
State
A shared dictionary passed between nodes, accumulating as the graph runs.
Checkpointer
Persists graph state so a run can pause, resume, or survive a restart.
Reducer
A rule for how a node's output merges into state (replace, append, etc.).

Section 02 IntermediateLCEL: composition with a pipe

LCEL is genuinely elegant. A prompt, a model, and a parser are each a runnable; the | operator wires the output of one into the next. You get streaming, batching, and async for free on the whole pipeline.

PythonLCEL from first principles
from langchain_anthropic import ChatAnthropic
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser
from pydantic import BaseModel, Field

model = ChatAnthropic(model="claude-opus-4-8", temperature=0)

prompt = ChatPromptTemplate.from_messages([
    ("system", "You are a concise assistant. Answer in one sentence."),
    ("user", "{question}"),
])

# The pipe composes three runnables into one. Read left to right:
# fill the prompt -> call the model -> extract the string.
chain = prompt | model | StrOutputParser()

chain.invoke({"question": "What is HNSW?"})        # -> "HNSW is a graph index ..."
chain.batch([{"question": q} for q in questions])  # parallel, free
for chunk in chain.stream({"question": "Explain RAG"}):
    print(chunk, end="")                           # streaming, free

# --- structured output: bind a schema to the model ----------------
class Triage(BaseModel):
    category: str = Field(description="billing | technical | account")
    severity: int = Field(ge=1, le=5)

structured = prompt | model.with_structured_output(Triage)
result = structured.invoke({"question": "Site is down for everyone"})
print(result.severity)                             # 5, as a typed object

# --- parallel branches and passthrough ---------------------------
from langchain_core.runnables import RunnableParallel, RunnablePassthrough
combo = RunnableParallel(
    answer=prompt | model | StrOutputParser(),
    original=RunnablePassthrough(),                # keep the input alongside
)
Java bridge

LCEL's prompt | model | parser is the same idea as Spring AI's ChatClient.prompt().user(...).call().entity(...) fluent chain, and with_structured_output(Triage) is .entity(Triage.class). The concepts transfer one-to-one; only the syntax differs. If you know the Java stack, you are not learning orchestration from scratch here — you are re-spelling it.

Section 03 IntermediateWhy agents became graphs

The old AgentExecutor hid the control loop inside a black box. When an agent misbehaved — looped, skipped a step, lost state — you could not see or change the flow. LangGraph's insight: an agent is a state machine, so make the states and transitions explicit.

A LangGraph program is three things:

  1. A state schema — a typed dictionary that flows through the graph and accumulates.
  2. Nodes — functions that read state and return a partial update. A node might call the model, run a tool, or transform data.
  3. Edges — how control moves. Normal edges are fixed; conditional edges branch based on state, which is how the agent loops "keep calling tools until done".
Why this matters

Because the graph is explicit, you can inspect it, test each node in isolation, pause and resume it, add human-in-the-loop checkpoints, and stream its progress. Every hard agent problem from Topic 5.2 — loops, goal drift, debugging — becomes tractable when the control flow is data you can see rather than behaviour hidden in a library.

Section 04 AdvancedBuild a tool-using agent as a graph

PythonThe ReAct loop as an explicit LangGraph
from typing import Annotated, TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages
from langgraph.checkpoint.memory import MemorySaver
from langchain_core.messages import HumanMessage, ToolMessage
from langchain_core.tools import tool
from langchain_anthropic import ChatAnthropic

# 1. STATE. `add_messages` is a reducer: node outputs are APPENDED
#    to the list, not replaced. That is how the conversation grows.
class State(TypedDict):
    messages: Annotated[list, add_messages]

# 2. TOOLS. A decorated function; its docstring is the description
#    the model reads (Topic 5.1 -- descriptions are prompts).
@tool
def check_stock(sku: str) -> str:
    """Return current stock for a product SKU, format SKU-1234."""
    return f'{{"sku": "{sku}", "available": 12}}'

tools = [check_stock]
model = ChatAnthropic(model="claude-opus-4-8").bind_tools(tools)
tools_by_name = {t.name: t for t in tools}

# 3. NODES.
def call_model(state: State):
    return {"messages": [model.invoke(state["messages"])]}

def run_tools(state: State):
    # AUTHORISE HERE in real code, against the real user (Topic 5.6).
    last = state["messages"][-1]
    results = []
    for call in last.tool_calls:
        output = tools_by_name[call["name"]].invoke(call["args"])
        results.append(ToolMessage(content=str(output), tool_call_id=call["id"]))
    return {"messages": results}

# 4. THE CONDITIONAL EDGE -- the whole agent loop in one function.
def should_continue(state: State):
    return "tools" if state["messages"][-1].tool_calls else END

# 5. ASSEMBLE THE GRAPH.
graph = StateGraph(State)
graph.add_node("model", call_model)
graph.add_node("tools", run_tools)
graph.add_edge(START, "model")
graph.add_conditional_edges("model", should_continue, {"tools": "tools", END: END})
graph.add_edge("tools", "model")          # after tools, back to the model

# A checkpointer makes the graph resumable and gives it memory
# per thread_id -- this is short-term memory (Topic 5.3) for free.
app = graph.compile(checkpointer=MemorySaver())

config = {"configurable": {"thread_id": "user-42"}}
for event in app.stream(
        {"messages": [HumanMessage("Is SKU-4471 in stock?")]}, config):
    print(event)          # watch each node fire, in order

That graph is the ReAct agent from Topic 5.2, but every state and transition is visible and testable. Add a node and an edge and you have plan-execute; add a conditional edge to a "human_review" node and you have human-in-the-loop; swap MemorySaver for a Postgres checkpointer and the agent survives restarts. The prebuilt create_react_agent helper collapses all of this into one call once you understand what it is doing.

Section 05 AdvancedThe patterns you will actually build

PythonHuman-in-the-loop with interrupt
from langgraph.types import interrupt, Command

def approval_gate(state: State):
    # Pauses the graph and surfaces this to your application.
    # The run persists (checkpointer) until a human responds --
    # the clean way to gate destructive tools (Topic 5.1).
    decision = interrupt({"action": state["pending_action"],
                          "question": "Approve this action?"})
    if decision != "approve":
        return {"messages": [("system", "Action rejected by human.")]}
    return {"approved": True}

# Later, resume the paused run with the human's answer:
app.invoke(Command(resume="approve"), config={"configurable": {"thread_id": "user-42"}})

Two things that bite teams

Version churn. LangChain reorganised its packages (langchain → langchain-core + provider packages like langchain-anthropic) and deprecated the original agent classes. Tutorials rot fast — pin versions, and check that any example you copy imports from the new packages and uses LangGraph, not initialize_agent.

Over-abstraction. LangChain can hide so much that a five-line task becomes a debugging session through library internals. When an abstraction fights you, drop to the model API directly — you already know how it works from Topic 5.1. The framework is a convenience, not a requirement.

Section 07 ProfessionalExercises

Do these — roughly a weekend
  1. Build a three-runnable LCEL chain (prompt | model | parser). Then add with_structured_output and get a typed Pydantic result.
  2. Build the tool-using agent graph from Section 04. Add a second tool and watch the model choose between them.
  3. Add a checkpointer and hold a multi-turn conversation using one thread_id. Confirm the graph remembers earlier turns.
  4. Add a human-in-the-loop interrupt() before a "delete" tool. Approve one call and reject another.
  5. Add a conditional router node that sends billing vs technical questions to different subgraphs.
  6. Take a tutorial that uses initialize_agent and rewrite it in LangGraph. Note what the old abstraction was hiding.
  7. Trace a run in LangSmith (or Langfuse) and inspect every node, prompt and tool call.
