Planning & Reasoning for Agents

How an agent decides well. This page covers the reasoning strategies that make an agent effective rather than merely busy — ReAct, plan-and-execute, reflection, self-consistency, tree search — with when each is worth its cost, and the honest limits of LLM planning you must design around.

Section 01 BeginnerStart from zero

Assumed knowledge

The agent loop (Topic 8.1) and chain-of-thought prompting (Topic 3.1). This page is about the plan beat of perceive-plan-act-observe — how the model chooses its next move.

An agent that acts without thinking flails: it calls the wrong tools, repeats itself, declares success too early. The quality of an agent is largely the quality of its planning — how it decides what to do next, and how it recovers when a step fails.

The good news from Topic 3.1: reasoning is compute. A model given room to think before it commits produces better plans, because each intermediate step conditions the next. Planning strategies are structured ways of spending that thinking.

The words, in plain English
Planning
Deciding the sequence of actions to reach a goal.
Reasoning
Thinking through a problem before answering — the model's internal working.
ReAct
Reason + Act: interleave a thought and an action each step.
Reflection
The agent critiques its own work and revises.
Self-consistency
Sample several attempts and take the majority.
Decomposition
Breaking a hard goal into simpler sub-goals.

ReAct vs Plan-and-Execute — the core trade-off

ReAct decides one step at a time, re-planning after every observation. It adapts beautifully to surprises but has no global view and can wander. Plan-and-Execute commits to a full plan up front, then executes — fewer model calls, a clear audit trail, but brittle if the plan was wrong. The strong hybrid: plan first, execute, and re-plan when a step fails. That keeps the global structure of a plan with the adaptivity of ReAct.

PythonPlan-and-execute with re-planning
def plan_and_execute(goal, max_steps=10):
    plan = llm_json(f"Create a numbered plan of tool-executable "
                    f"steps for:\n{goal}")["steps"]
    done = []

    for _ in range(max_steps):
        if not plan:
            break
        step = plan.pop(0)
        result = execute(step)
        done.append((step, result))

        if result.failed:
            # RE-PLAN from where we are. A plan made before seeing the
            # data is often wrong; the ability to revise is the point.
            plan = llm_json(f"""Goal: {goal}
                Completed: {done}
                Step failed: {step} -> {result.error}
                Produce a revised plan for the remaining work.""")["steps"]

    return synthesise(goal, done)

Section 03 AdvancedReflection and self-consistency

Two ways to trade tokens for quality when correctness matters more than latency.

PythonReflection: generate, critique, revise
def reflect(task, max_rounds=3):
    answer = llm(f"Complete this task:\n{task}")

    for _ in range(max_rounds):
        critique = llm_json(f"""Assess this against the requirements.
            Score 1-10 and list specific, actionable problems.
            Task: {task}
            Answer: {answer}""")
        if critique["score"] >= 8 or not critique["problems"]:
            return answer                          # good enough; stop
        answer = llm(f"""Revise, addressing these problems:
            {critique['problems']}\n\n{answer}""")
    return answer
Reflection only works if the critique is real

Self-critique helps only when the model can actually tell good from bad on this task. On tasks where it cannot judge quality — often the same tasks it cannot do — reflection burns tokens and changes nothing, or worse, "revises" a correct answer into a wrong one. Reflection shines when there is an external signal: test results, a compiler, a validator, a retrieval check. Prefer grounding the critique in something objective over asking the model to grade itself.

Self-consistency is simpler and robust for problems with a single answer: sample n times at temperature > 0 and take the majority. It works because independent reasoning paths tend to agree on the right answer and scatter on wrong ones — the correct answer is the mode. Cost is linear in n; reserve it for high-stakes decisions.

Section 04 ProfessionalThe honest limits of LLM planning

Design around these rather than pretending they are solved.

Where LLM planning is weak, and the mitigation
LimitSymptomMitigation
Long-horizon planningLoses coherence over many stepsDecompose; checkpoint sub-goals; keep the goal in context
No true backtrackingCommits to a bad path, cannot cleanly undoRe-planning on failure; explicit state you can reset
OverconfidenceDeclares success without verifyingVerification tools; a "did I meet the goal?" check
Arithmetic / precise logicPlausible but wrong calculationsGive it a calculator/code tool (Topic 8.4)
Unstated assumptionsPlans around facts it inventedForce it to gather information (retrieval) before planning
Stated reasoning ≠ real reasoningThe plan it writes is not why it actedDo not treat the chain-of-thought as an audit record
Reasoning models change the calculus

A newer class of reasoning models (o1/o3-style, DeepSeek-R1) does extended internal thinking before answering, and is markedly better at multi-step planning and self-correction — you get much of the benefit of reflection and tree-search built into a single call. They cost more per call and add latency, so the trade is: use a reasoning model for the hard planning step, a cheaper model for routine tool-execution steps. This is covered in its own right in the LLM module (Reasoning Models & Test-Time Compute), and it is increasingly how capable agents are built — a strong planner directing cheap executors.

The most reliable single improvement to an agent's planning is usually not a cleverer strategy — it is giving it the right tools and the right information. An agent that can retrieve the facts it needs and verify its own work with a real check will out-plan a cleverer agent working blind. Spend your effort on tools and grounding (Topics 8.4, 4.6) before elaborate planning schemes.

Section 05 ProfessionalExercises

Do these — roughly an evening
  1. Implement plan-and-execute with re-planning. Make a step fail deliberately and watch it recover.
  2. Add reflection to a writing task with clear criteria. Measure quality vs a single-shot attempt — and find a task where reflection does not help.
  3. Implement self-consistency on an arithmetic-word-problem set. Plot accuracy against n.
  4. Ground a reflection loop in an external check (unit tests or a validator) instead of self-critique. Compare reliability.
  5. Give a planning agent a calculator tool and re-run a task it previously failed on arithmetic. Confirm the tool fixes it.
  6. Run the same hard planning task with a reasoning model vs a standard model. Compare quality, latency and cost.
