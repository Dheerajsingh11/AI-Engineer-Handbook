10.2

Containerised Deployment

Getting an AI application into production. This page covers packaging an AI service — a FastAPI app, containerised with Docker, deployed on Kubernetes — and the concerns AI adds on top of ordinary web deployment: long requests, streaming, GPU scheduling, autoscaling on the right signal, and cost as a first-class operational metric.

Section 01 BeginnerStart from zero

Assumed knowledge

Basic web services and, ideally, containers. Serving mechanics (Topic 6.1) and event-driven patterns (Topic 5.4) are the AI-specific background.

An AI feature is not done until it is a running service someone can call. For a lot of it, this is ordinary web deployment — an HTTP API in a container, orchestrated by Kubernetes. What AI adds is a handful of twists: requests take seconds not milliseconds, responses stream, some workloads need GPUs, and cost is per-request rather than fixed. This page is the standard deployment stack plus those twists.

Python or Java here?

For the application service, use what your team knows — Spring Boot is a perfectly good AI API host, and you already know how to deploy it. FastAPI is the Python default and worth knowing because so much AI code and so many examples assume it. The deployment concerns below (containers, K8s, streaming, autoscaling, cost) are identical for both. Where Python is genuinely required is the model-serving tier (Topic 6.1) — keep that as a separate service and your application layer stays on whatever stack you prefer.

Section 02 BeginnerA container-ready AI service

PythonA FastAPI service with streaming and health
from fastapi import FastAPI
from fastapi.responses import StreamingResponse
from pydantic import BaseModel

app = FastAPI()

class Query(BaseModel):
    question: str

@app.get("/health")                 # K8s liveness/readiness probe target
def health():
    return {"status": "ok"}

@app.post("/ask")
async def ask(q: Query):
    return {"answer": await run_rag(q.question)}

@app.post("/stream")                # streaming: perceived latency (Topic 1.3)
async def stream(q: Query):
    async def gen():
        async for token in stream_rag(q.question):
            yield token
    return StreamingResponse(gen(), media_type="text/event-stream")
DockerfilePackaging it reproducibly
FROM python:3.12-slim
WORKDIR /app

# Install deps first so this layer caches across code changes.
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY . .
# uvicorn workers; keep 1 worker per GPU if this holds a local model.
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]

# Pin versions in requirements.txt. Do NOT bake API keys into the
# image -- inject them as env/secrets at runtime.

Section 03 IntermediateKubernetes, with the AI twists

YAMLDeployment with the settings AI needs
apiVersion: apps/v1
kind: Deployment
metadata: {name: rag-service}
spec:
  replicas: 3
  template:
    spec:
      containers:
      - name: rag
        image: registry/rag-service:1.4.0     # pinned tag, never :latest
        ports: [{containerPort: 8000}]
        env:
        - name: ANTHROPIC_API_KEY
          valueFrom: {secretKeyRef: {name: ai-secrets, key: anthropic}}
        readinessProbe: {httpGet: {path: /health, port: 8000}}
        livenessProbe:  {httpGet: {path: /health, port: 8000}}
        resources:
          requests: {cpu: "500m", memory: "1Gi"}
          limits:   {cpu: "2",    memory: "2Gi"}
          # For a GPU workload (self-hosted model, Topic 6.1):
          # limits: {nvidia.com/gpu: 1}
      terminationGracePeriodSeconds: 120   # let in-flight LLM calls finish
What AI changes about ordinary deployment
ConcernOrdinary webAI service
Request durationMillisecondsSeconds to minutes — long timeouts, graceful shutdown
ResponseOne payloadOften streamed (SSE)
ComputeCPUSometimes GPU — node pools, scheduling, taints
Autoscale signalCPU %Queue depth / concurrency, not CPU (Topic 5.4)
CostRoughly fixed per instancePer request — a first-class metric
Cold startSecondsMinutes for a GPU model — keep a warm floor
Do not autoscale AI services on CPU

A model-calling service spends most of each request waiting on the model, using little CPU. Scale it on CPU and it will look idle while requests pile up and time out. Scale on the signal that reflects real load: in-flight request concurrency or queue depth (Topic 5.4). For a self-hosted model tier, scale on GPU utilisation and KV-cache pressure (Topic 6.1). Getting the autoscaling signal wrong is the most common way AI deployments fall over under load while the dashboards say everything is fine.

Section 04 AdvancedTiering the deployment

A robust AI system is usually not one service but a few, each scaled on its own terms.

Typical tiers
TierRunsScales onHardware
API / applicationYour FastAPI or Spring Boot serviceRequest concurrencyCPU
Async workersIngestion, long agent jobs (Topic 5.4)Queue depthCPU
Model servingSelf-hosted models via vLLM (Topic 6.1)GPU util, KV cacheGPU
Vector storepgvector / Qdrant (Topic 4.4)Query load; often managedMemory-heavy

Why separate them: they have completely different scaling and hardware needs. The API tier is cheap CPU that scales with users; the GPU model tier is expensive and scales slowly; async workers absorb bursts. Bundling them into one deployment means scaling the expensive GPU tier every time user traffic rises, which is wasteful, and it couples failure domains. Keep them as separate deployments talking over HTTP or a queue — the same reasoning as any microservice split, sharpened by the cost of GPUs.

Most of this you already do

Containers, Kubernetes, health probes, secrets, canary rollouts, autoscaling, observability — this is standard cloud-native operations, and if you have deployed a Spring Boot service you have done nearly all of it. The genuinely new parts are small and specific: scale on concurrency not CPU, allow long timeouts and graceful drain, treat cost as an SLO, and add a GPU tier only if you self-host models. Your existing platform skills are most of what makes AI deployment work — which is exactly why a backend engineer moving into AI is valuable here.

Section 06 ProfessionalExercises

Do these — roughly a weekend
  1. Build the FastAPI service with health and streaming endpoints. Containerise it with the Dockerfile shown.
  2. Deploy it to a local Kubernetes (kind/minikube) with readiness/liveness probes and secret injection.
  3. Add a Horizontal Pod Autoscaler on request concurrency (a custom metric), not CPU. Load-test and watch it scale correctly.
  4. Deliberately configure the HPA on CPU instead and reproduce the "looks idle while overloaded" failure.
  5. Set a long termination grace period and confirm in-flight LLM calls complete during a rolling update.
  6. Split into two deployments (API tier + async worker consuming a queue, Topic 5.4). Scale each independently.
  7. Add OTel tracing and a Grafana panel for p95 latency, cost per request and error rate.
