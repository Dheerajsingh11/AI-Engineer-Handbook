Step 01The API surface

Atlas needs to be callable — by a chat UI, a Slack bot, another service. A thin FastAPI layer turns the agent into an HTTP endpoint, which is exactly the kind of service a backend engineer builds every day (Topics 6.1, 10.2).

PythonThe agent behind an endpoint
from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()

class Ask(BaseModel):
    query: str
    user_id: str                                # for auth + rate limiting (Ch. 20.11)

@app.post("/ask")
async def ask(req: Ask):
    answer = await run_in_threadpool(agent, req.query)   # the Ch. 20.7 agent
    return {"answer": answer}

Step 02Stream the tokens

A grounded answer can take several seconds to generate. Making the user stare at a spinner for all of it feels broken; streaming the tokens as they are produced feels instant — even though the total time is identical (Topic 19.3).

Why streaming wins — time-to-first-token felt latency ≈ TTFT,   not   total time = TTFT + Nout · tper-token The model generates one token at a time, so a 400-token answer takes 400 × the per-token time. Without streaming the user waits for all of it; with streaming they see the first words after just the time-to-first-token, then read at generation speed. Same total, radically different experience — which is why streaming is near-mandatory for interactive AI.
PythonServer-sent events stream the answer
from fastapi.responses import StreamingResponse

@app.post("/ask/stream")
async def ask_stream(req: Ask):
    async def gen():
        async for token in agent_stream(req.query):   # yields tokens
            yield f"data: {token}\n\n"                 # SSE frame
    return StreamingResponse(gen(), media_type="text/event-stream")

Step 03Batch for throughput

When many users ask at once, feeding requests to the model one by one wastes the GPU. Batching processes several together, exploiting exactly the parallelism GPUs are built for (Topics 2.6, 6.1).

The economics: a GPU running one request uses a fraction of its cores; running a batch of sixteen uses far more of them for barely more time — so throughput (requests per second) rises sharply while cost per request falls. Serving engines like the llama.cpp server (Ch. 20.6) or vLLM do continuous batching — slotting new requests into the batch as others finish, rather than waiting for a full batch. For Atlas you rarely implement this yourself; you configure it, and understanding it is what lets you tune the concurrency for your hardware. The trade is latency vs throughput: bigger batches serve more users but make each wait slightly longer.

This is a service, and you know how to build services

Strip away the model and Atlas's serving layer is an ordinary backend: an API with auth, rate limiting, caching, logging, health checks, timeouts, and graceful degradation. That is home turf for a backend engineer, and it is precisely the half of AI engineering that people who only know how to call an LLM tend to get wrong (Topic 17.4). The AI-specific parts — streaming, batching, token-cost logging — bolt onto solid service fundamentals. Event-driven patterns (Topic 5.4) fit naturally too: long jobs can go on a queue, results delivered by webhook. The serving layer is where your existing expertise is worth the most.
