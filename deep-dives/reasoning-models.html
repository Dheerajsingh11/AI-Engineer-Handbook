Reasoning Models & Test-Time Compute

Models that think before they answer. This page explains what reasoning models are, how test-time compute trades tokens for correctness, why they changed how hard problems are solved, when they are worth their cost and latency, and how to use them well — including as the planner directing cheaper executor models.

Section 01 BeginnerStart from zero

Assumed knowledge

How models generate tokens (Topic 1.3) and chain-of-thought prompting (Topic 3.1). Reasoning models push the chain-of-thought idea into the model itself.

A standard model answers immediately — it produces the response token by token with no separate "thinking." A reasoning model does something different: before it gives you an answer, it generates a long internal chain of thought, working through the problem, checking itself, exploring approaches. Only then does it produce the final response. The examples are OpenAI's o-series, DeepSeek-R1, and the "extended thinking" modes of frontier models.

The core idea: test-time compute

There are two ways to make a model better at a hard problem: make the model bigger (train-time compute), or let it think longer at the moment you ask (test-time compute). Reasoning models exploit the second. Spending more tokens thinking before answering measurably improves accuracy on hard reasoning — maths, logic, multi-step planning, coding. It is the chain-of-thought effect from Topic 3.1, made a native, trained-in behaviour and scaled up dramatically.

The words, in plain English
Reasoning model
A model trained to think at length internally before answering.
Test-time compute
Computation spent when you ask (inference), as opposed to during training.
Reasoning tokens
The internal thinking tokens — you pay for them, and often do not see them.
Reasoning effort
A dial (low/medium/high) trading more thinking for better answers.
Extended thinking
A mode on a general model that turns on long internal reasoning.

Section 02 IntermediateHow they are made, and why they work

Reasoning models are typically trained with reinforcement learning on problems that have checkable answers — maths, code, logic. The model generates a long reasoning trace, and it is rewarded when the trace leads to a correct final answer. Over training, it learns reasoning strategies that pay off: breaking problems down, trying an approach, noticing a mistake, backtracking, verifying.

Why this beats prompting for chain-of-thought. Asking a normal model to "think step by step" (Topic 3.1) helps, but the model was never specifically trained to reason well — it imitates reasoning it saw in text. A reasoning model was optimised, with a reward signal, to produce reasoning that actually reaches correct answers. The difference shows most on genuinely hard problems: the reasoning model will spot and correct its own errors mid-thought, where a prompted model often confidently continues down a wrong path.

Standard model vs reasoning model
Standard modelReasoning model

LatencyLowHigher — thinking takes time
CostLowerHigher — you pay for reasoning tokens
Self-correctionWeakStrong — catches its own errors

Section 03 AdvancedUsing them well

PythonPrompting a reasoning model — less is more
# Give it the problem and the goal. DON'T tell it how to think --
# it has its own trained reasoning process, and step-by-step
# instructions can interfere with it.

# GOOD: state the problem and the answer format.
prompt = """A logistics network has the following constraints: [...].
Find the minimum-cost routing. Show the final plan as a table."""

# LESS GOOD for a reasoning model: "Think step by step. First do X,
# then Y..." -- you are overriding a better internal process.

# The 'reasoning effort' dial trades thinking for cost/latency.
response = client.responses.create(
    model="a-reasoning-model",
    reasoning={"effort": "high"},      # low | medium | high
    input=prompt)

# You are billed for reasoning tokens even when they are hidden.
print(response.usage.reasoning_tokens)
When to reach for a reasoning model
Use one for…Don't bother for…
Complex maths, logic, proofsSimple classification or extraction
Multi-step planning (Topic 8.7)Formatting, summarising, rewriting
Hard debugging / code generationChit-chat, retrieval-grounded Q&A
Analysis with many interacting constraintsAnything latency-critical
Tasks where being right matters more than speedHigh-volume, cost-sensitive work
Do not use a reasoning model for everything

Reasoning models are slower and more expensive per call, and on easy tasks they are overkill — they burn reasoning tokens deliberating over a question a small model answers instantly and correctly. Using one as your default is a common and costly mistake. Match the model to the task: reasoning model for the genuinely hard step, a fast cheap model for everything routine. This is the model-routing principle from Topic 9.1, and it matters even more here because the cost gap is larger.

Section 04 ProfessionalReasoning models in agents

The most effective pattern in modern agent design uses a reasoning model where it counts and cheaper models elsewhere.

Planner-executor with a reasoning planner

An agent (Topic 8.1) makes many model calls: some are hard planning decisions, most are routine tool executions. Use a reasoning model as the planner — it decides the strategy, decomposes the problem, and recovers from failures far better (Topic 8.7) — and a fast, cheap model for the executor steps. You get the reasoning quality where it changes the outcome, and pay routine prices for routine work. This split gives much of the benefit of expensive techniques like reflection and tree search (Topic 8.7) with a single strong planning call, and it is increasingly how capable agents are built.

Cost/quality patterns
PatternReasoning model for…Cheap model for…
Planner-executorThe plan / hard decisionsTool execution, formatting
EscalationRequests a router flags as hardEverything else (Topic 9.1)
Verify-then-trustChecking a critical answerProducing the draft

A note on the trajectory. Reasoning models are an active frontier — capabilities, pricing and controls change quickly, and some models now blend "think when needed" into a single general model rather than offering a separate reasoning model. The principle is stable and worth internalising even as products shift: you can trade inference-time compute for correctness on hard problems, and the engineering skill is deciding when that trade is worth it.

Section 05 ProfessionalExercises

Do these — roughly an evening
  1. Take a hard multi-step problem a standard model gets wrong. Run it on a reasoning model and compare.
  2. Run the same easy task (e.g. sentiment) on a reasoning model and a small model. Compare cost, latency and quality — feel the overkill.
  3. Sweep the reasoning-effort dial (low/medium/high) on a hard problem. Plot accuracy against cost.
  4. Try prompting a reasoning model with heavy "think step by step, first do X" instructions vs just stating the problem. Compare.
  5. Build a router that sends only hard requests to a reasoning model. Measure the cost saving vs using it for everything.
  6. Build a planner-executor agent: reasoning model plans, cheap model executes. Compare quality and cost against a single-model agent.
