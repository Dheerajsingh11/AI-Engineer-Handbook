18.1

Data Engineering for AI

The unglamorous work that decides whether any AI project succeeds. This page covers the data lifecycle behind a model — collection, cleaning, labelling and annotation, versioning and pipelines — why data quality beats model choice almost every time, and the practices that keep a dataset trustworthy as it grows.

Section 01 BeginnerStart from zero

Assumed knowledge

Pandas (Topic 2.2) and a sense of what a model consumes. This page is about the data before feature engineering (Topic 14.1) ever begins.

Every model, classical or frontier, is a function of its data. You can swap architectures all week, but if the data is wrong, incomplete, mislabelled or leaking, the model will be wrong in exactly the same ways. Data engineering for AI is the discipline of getting the right data, in the right shape, with the right labels, reliably and repeatably — and it is where most real projects spend most of their time.

The 80% rule

Practitioners repeat a rough figure: roughly 80% of the effort on a real AI project is data work — collecting it, cleaning it, labelling it, fixing it — and only the remaining fraction is modelling. The famous phrase is "data-centric AI": hold the model fixed and improve the data, and you often gain more than any architecture change would give you. The models are increasingly commoditised; the data, and the pipeline that keeps it clean, is the durable advantage.

The words, in plain English
Dataset
The collection of examples a model learns or is evaluated on.
Label / annotation
The correct answer attached to an example, usually by a human.
Ground truth
The labels you treat as correct — the standard everything is measured against.
Data pipeline
The automated flow that takes raw data to model-ready data.
Data versioning
Tracking exactly which data produced which model, like Git for datasets.
Drift
The world changing so that yesterday's data no longer matches today's.

Section 02 IntermediateThe data lifecycle

Data for AI moves through a repeatable set of stages. Naming them makes the work visible — and shows where quality is won or lost.

From raw signal to model-ready data
StageWhat happensThe failure to avoid
CollectionGather from sources: logs, databases, APIs, scraping, sensors, user inputSampling bias — the data does not represent production
CleaningFix types, dedupe, handle missing/corrupt rows, normalise formatsSilent corruption that survives into training
LabellingAttach ground-truth answers (Section 03)Inconsistent labels — the ceiling on model accuracy
ValidationSchema checks, range checks, distribution checksBad data reaching the model unnoticed
VersioningSnapshot the exact dataset used for each model (Section 04)Not being able to reproduce a result
MonitoringWatch for drift once in production (Topic 14.7, 5.5)A model quietly decaying as the world moves

For LLM applications, the lifecycle looks a little different but the principle is identical. You are less often training on labelled rows and more often curating: the documents that feed a RAG index (Topic 4.5), the prompt–response pairs for fine-tuning (Topic 3.5), the evaluation sets that tell you whether anything works (Topic 19.1). Each of those is a dataset with a lifecycle — and each rewards the same collect→clean→validate→version discipline.

Section 03 IntermediateLabelling & annotation

Supervised learning needs labels, and the quality of those labels is a hard ceiling on the quality of the model. If humans disagree on the answer 15% of the time, no model trained on those labels can reliably do better than 85%.

How labels get made
ApproachWhat it isTrade-off
In-house expertsYour own domain specialists labelHigh quality, low volume, expensive
CrowdsourcingMany non-experts (e.g. via a platform) labelHigh volume, needs quality control
Programmatic / weak supervisionRules and heuristics generate noisy labels at scaleCheap and fast, noisier — e.g. Snorkel
Model-assistedA model pre-labels; humans correctFast, but risks anchoring humans to model errors
LLM-as-labellerA strong LLM labels the data (Topic 18.2)Very cheap and scalable, needs auditing
Measure your labels before you trust them

The single most valuable habit in annotation is measuring inter-annotator agreement — have several people label the same examples and compute how often they agree (Cohen's or Fleiss' kappa). Low agreement is not a people problem to paper over; it is telling you the task itself is ambiguous, and no amount of modelling will fix an ambiguous target. The fix is a clearer labelling guideline, adjudication of disagreements, and sometimes redefining the task. Good ground truth is engineered, not assumed.

Section 04 AdvancedPipelines, versioning & validation

A one-off cleaned CSV is not data engineering. The goal is a reproducible pipeline: raw data in, model-ready data out, the same way every time, with a record of exactly what produced each model.

PythonA validated, versioned data step
import pandas as pd
# Data validation: assert the shape you expect, fail loudly if not.
# (pandera / Great Expectations do this declaratively at scale.)
def validate(df: pd.DataFrame) -> pd.DataFrame:
    assert df["age"].between(0, 120).all(),      "age out of range"
    assert df["label"].isin({0, 1}).all(),       "unexpected label value"
    assert df["user_id"].notna().all(),          "missing user_id"
    assert not df.duplicated("event_id").any(),  "duplicate events"
    return df

The reproducibility trap

If you cannot say exactly which data produced a given model, you cannot debug it, reproduce it, or safely improve it. "We retrained on the latest data" is not a version. The discipline — snapshot the dataset, hash it, tie the hash to the model artefact and the code commit — is what separates an experiment from an engineering practice. It is the data equivalent of a Git commit, and skipping it is the most common reason a good result cannot be recovered three months later.

Section 05 ProfessionalIn production: drift & feedback

Data engineering does not stop at launch. The world changes, and a model trained on last quarter's data slowly stops matching this quarter's reality — data drift (the inputs shift) and concept drift (the input→output relationship shifts).

The professional response is a feedback loop: log production inputs and outcomes, monitor input distributions against the training distribution (Topic 14.7), flag when they diverge, and feed corrected real-world examples back into the dataset for the next retrain. The best AI products are the ones whose data pipeline turns usage into better training data — a data flywheel. Beware the failure mode: if you train on the model's own outputs uncritically, errors compound. Keep humans in the loop on the feedback data (Topic 19.2), and treat production data collection as consciously as you treated the first dataset.

Section 06 ProfessionalExercises

Do these — roughly a weekend
  1. Take a messy public dataset. Write a cleaning pipeline with explicit validation assertions that fail loudly on bad rows.
  2. Label 100 examples yourself, twice, a day apart. Measure your own self-agreement — feel how ambiguous "obvious" labels are.
  3. Have two people label the same 100 examples. Compute inter-annotator agreement (kappa) and adjudicate the disagreements.
  4. Put a dataset under DVC. Change it, commit, and roll back — prove you can reproduce an exact version.
  5. Add a schema check with Great Expectations or pandera and wire it into a pipeline so bad data cannot pass silently.
  6. Simulate drift: train on one time slice, evaluate on a later one, and quantify the decay. This is why monitoring exists.
