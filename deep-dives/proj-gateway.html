Project 1 — The LLM Gateway

A reverse proxy that every other project calls instead of hitting a provider directly: streaming passthrough, model routing, two kinds of caching, per-team budgets and cost attribution, retries and failover. Roughly 80 % of it is backend engineering you already know — which is exactly why it is the first project.

Build order · two weeks
  1. Stage 1Streaming passthroughA façade over the SDK that streams tokens and counts them.
  2. Stage 2Routing & cachingCheap/default/hard tiers; prompt cache and semantic cache.
  3. Stage 3GovernanceKeys, rate limits, budgets, cost attribution.
  4. Stage 4ResilienceRetries, circuit breaker, failover, tracing.
Why this one first

“Design an LLM gateway for forty teams” is one of the three most common AI system-design prompts, and this project is that question with running code behind it. It also converts your existing backend skill into AI credibility in two weeks, before you have learned anything about models — which makes it the fastest possible route to a portfolio you can talk about.

One design decision matters more than the rest: define a Provider interface first and write every backend against it. Failover, testing and the “migrate to a self-hosted model” question in Project 4 all become trivial if this boundary exists, and all become a rewrite if it does not.

Pythonapp/providers/base.py
from dataclasses import dataclass
from typing import AsyncIterator, Protocol

@dataclass
class Usage:
    input_tokens: int = 0
    output_tokens: int = 0
    cache_read_tokens: int = 0        # billed at roughly 0.1x
    cache_write_tokens: int = 0       # billed at roughly 1.25x

@dataclass
class Chunk:
    text: str = ""
    usage: Usage | None = None        # set only on the final chunk

class Provider(Protocol):
    name: str
    async def stream(self, *, model: str, system: str,
                     messages: list[dict], max_tokens: int) -> AsyncIterator[Chunk]:
        ...

Step 03Streaming passthrough

This is the deceptively hard part and the reason to do it first. You must stream tokens to the client as they arrive and still capture the final usage numbers, and handle the client hanging up mid-stream without leaking the upstream connection.

Pythonapp/providers/anthropic_.py
import anthropic
from .base import Provider, Chunk, Usage

class AnthropicProvider:
    name = "anthropic"

    def __init__(self) -> None:
        # Zero-arg constructor resolves credentials from the environment.
        # max_retries=0: we own retry policy at the gateway layer, so the
        # SDK retrying underneath would double-count and hide failures.
        self.client = anthropic.AsyncAnthropic(max_retries=0)

    async def stream(self, *, model, system, messages, max_tokens=4096):
        async with self.client.messages.stream(
            model=model,
            max_tokens=max_tokens,
            # Cache the stable system prefix. Prefix match: one byte of drift
            # anywhere before this point invalidates everything after it.
            system=[{"type": "text", "text": system,
                     "cache_control": {"type": "ephemeral"}}],
            messages=messages,
        ) as stream:
            async for text in stream.text_stream:
                yield Chunk(text=text)

            # The accumulated message carries the authoritative usage totals.
            final = await stream.get_final_message()
            u = final.usage
            yield Chunk(usage=Usage(
                input_tokens=u.input_tokens,
                output_tokens=u.output_tokens,
                # These two fields are the whole cost story. Log them or you
                # will never notice the day your cache hit rate goes to zero.
                cache_read_tokens=getattr(u, "cache_read_input_tokens", 0) or 0,
                cache_write_tokens=getattr(u, "cache_creation_input_tokens", 0) or 0,
            ))
Pythonapp/main.py — the SSE endpoint
import json
from fastapi import FastAPI, Request, HTTPException
from fastapi.responses import StreamingResponse

app = FastAPI()

@app.post("/v1/chat")
async def chat(req: ChatRequest, request: Request, team = Depends(auth)):
    if not await limits.allow(team, estimated_tokens=req.estimate()):
        raise HTTPException(429, "rate limit or budget exceeded")

    model = router.choose(req)
    provider = providers.primary()

    async def events():
        usage = Usage()
        try:
            async for chunk in provider.stream(model=model, system=req.system,
                                               messages=req.messages,
                                               max_tokens=req.max_tokens):
                # Client gone? Stop pulling from upstream immediately --
                # otherwise you keep paying for tokens nobody will read.
                if await request.is_disconnected():
                    break
                if chunk.usage:
                    usage = chunk.usage
                else:
                    yield f"data: {json.dumps({'delta': chunk.text})}\n\n"
        finally:
            # finally, not after the loop: a disconnect or an upstream error
            # must still be billed and recorded. Partial generations cost money.
            await ledger.record(team=team, model=model, usage=usage)
        yield "data: [DONE]\n\n"

    return StreamingResponse(events(), media_type="text/event-stream")
The three bugs everyone writes here
  1. Recording usage outside a finally. Disconnects and upstream errors then vanish from your cost data, and your reported spend drifts below the invoice.
  2. Not checking is_disconnected(). A user who closes the tab keeps generating tokens you pay for.
  3. Buffering. A proxy, a compression middleware or a reverse proxy in front will happily buffer your SSE into one response. Test through the whole chain, not just against uvicorn.

Step 04Model routing

Route on the shape of the work, not on a regex over the prompt. Three tiers is the right starting point, and the cost spread between them is what makes routing worth building at all.

Published list prices, per million tokens — the spread is the whole argument for routing
TierModelInputOutputSend it
Cheapclaude-haiku-4-5$1.00$5.00Classification, extraction, routing decisions, short rewrites.
Defaultclaude-sonnet-5$2.00$10.00High-volume production work; most RAG answering.
Hardclaude-opus-5$5.00$25.00Multi-step reasoning, agent loops, anything correctness-critical.
Pythonapp/router.py
CHEAP, DEFAULT, HARD = "claude-haiku-4-5", "claude-sonnet-5", "claude-opus-5"

def choose(req) -> str:
    # 1. An explicit caller request always wins -- teams need an override.
    if req.model:
        return req.model

    # 2. Declared task type beats any inference we could do.
    if req.task in {"classify", "extract", "route", "summarize_short"}:
        return CHEAP
    if req.task in {"agent", "plan", "code"}:
        return HARD

    # 3. Fall back to a cheap signal. Long inputs are usually synthesis;
    # tool definitions mean an agent loop, which needs the strong model.
    if req.tools or req.estimated_input_tokens > 20_000:
        return HARD
    return DEFAULT
The upgrade that makes this interview-grade

Replace rule 3 with a learned router: send a sample of traffic to both the cheap and the strong model, score both answers with the eval harness from Project 5, and label which requests the cheap model handled acceptably. Now you can state a real trade-off — “routing 60 % of traffic to the small model cost 1.8 points of quality and saved 55 % of spend” — which is precisely the sentence that wins a design round. Before building a cascade, though, measure the simpler option first: the stronger model at a lower effort setting often beats a weaker model outright, and one model means one cache namespace.

Step 05The two caches

These are different mechanisms solving different problems, and conflating them is a common interview stumble. Implement both, and be able to say in one sentence when each applies.

Two caches, two jobs
Prompt cache (provider-side)Semantic cache (yours)
Matches onAn exact prefix of the request, byte for byteMeaning of the whole request, via embedding similarity
SavesRe-processing a long stable prefix — reads bill around 0.1×The entire call, including all output tokens
Use forLong system prompts, tool definitions, a fixed documentRepeated or near-duplicate user questions
RiskSilent invalidation from one changed byteReturning a subtly wrong answer for a similar-but-different question
Pythonapp/cache/prompt.py — ordering is the whole technique
# Render order is tools -> system -> messages, and caching is a PREFIX match.
# So: everything stable goes first, everything volatile goes last.

def build_request(system_text, tools, history, question):
    return dict(
        # Sort tools by name. An unordered dict iteration reorders them
        # between processes and silently destroys the cache hit rate.
        tools=sorted(tools, key=lambda t: t["name"]),
        system=[{"type": "text", "text": system_text,
                 "cache_control": {"type": "ephemeral"}}],
        # The volatile part -- the actual question -- comes after the
        # breakpoint, so it never invalidates the cached prefix.
        messages=[*history, {"role": "user", "content": question}],
    )

# Verification, not faith: if this stays 0 across repeated calls with the
# same prefix, something is invalidating it. Alert on it in production.
def cache_hit_rate(usage):
    total = usage.cache_read_tokens + usage.input_tokens
    return usage.cache_read_tokens / total if total else 0.0
Silent cache invalidators — audit for these

A timestamp or a request ID in the system prompt. json.dumps() over an unsorted dict. A tool list built from a set. A per-user greeting placed before the cached block instead of after. Every one of them produces a cache hit rate of exactly zero while the code looks correct — and each is a genuine war story to bring to an interview.

Pythonapp/cache/semantic.py
import numpy as np

class SemanticCache:
    """Return a stored answer when a new question means the same thing.
    The threshold is a product decision, not a technical one: too low and
    you confidently answer a question nobody asked."""

    def __init__(self, redis, embedder, threshold: float = 0.95, ttl: int = 3600):
        self.redis, self.embed = redis, embedder
        self.threshold, self.ttl = threshold, ttl

    async def get(self, namespace: str, question: str) -> str | None:
        # Namespace by tenant AND by prompt version. Without the prompt
        # version, deploying a new prompt keeps serving answers generated
        # by the old one -- an genuinely nasty bug to track down.
        q = self.embed(question)
        q = q / (np.linalg.norm(q) + 1e-10)

        best, best_score = None, -1.0
        for key, vec, answer in await self._candidates(namespace):
            score = float(np.dot(q, vec))
            if score > best_score:
                best, best_score = answer, score

        return best if best_score >= self.threshold else None

For a portfolio project, scanning candidates within a namespace is fine and honest. The upgrade — and the right answer when asked “how does this scale?” — is to store cache entries in the same vector index you build in Project 2 and do an approximate nearest-neighbour lookup instead.

Step 06Budgets, limits, attribution

The AI-specific twist on familiar backend work: providers limit you on two dimensions at once — requests per minute and tokens per minute — and you cannot know the output token count until after you have paid for it.

Pythonapp/limits.py
class Limiter:
    """Two buckets per team, because providers enforce two limits.
    Reserve on the estimate, reconcile on the actual."""

    async def allow(self, team: str, estimated_tokens: int) -> bool:
        return (await self.rpm[team].take(1)
                and await self.tpm[team].take(estimated_tokens))

    async def reconcile(self, team: str, estimated: int, actual: int) -> None:
        # Output length is unknown up front, so we reserve an estimate and
        # settle afterwards. Refund an over-estimate; let an under-estimate
        # push the bucket negative so the next caller waits it off.
        await self.tpm[team].adjust(estimated - actual)


# Estimating before the call: count_tokens is exact for input, and the
# output estimate is a policy choice -- max_tokens is the safe ceiling.
async def estimate(client, model, system, messages, max_tokens) -> int:
    counted = await client.messages.count_tokens(
        model=model, system=system, messages=messages)
    return counted.input_tokens + max_tokens
SQLThe usage ledger — one row per request, and the source of every cost answer
CREATE TABLE usage (
  id              bigserial PRIMARY KEY,
  ts              timestamptz NOT NULL DEFAULT now(),
  team            text        NOT NULL,
  route           text        NOT NULL,   -- which product feature
  model           text        NOT NULL,
  input_tokens    int         NOT NULL,
  output_tokens   int         NOT NULL,
  cache_read      int         NOT NULL,   -- the two columns that explain
  cache_write     int         NOT NULL,   -- every cost regression
  latency_ms      int         NOT NULL,
  ttft_ms         int,                    -- time to first token
  status          text        NOT NULL,   -- ok | error | disconnected
  cost_usd        numeric(12,6) NOT NULL
);

CREATE INDEX ON usage (team, ts DESC);
CREATE INDEX ON usage (route, ts DESC);

-- The query you will actually run, and the one that answers
-- "why did costs go up 6x last month" in about four seconds.
SELECT route, model,
       sum(cost_usd)                                   AS spend,
       sum(cache_read)::float
         / NULLIF(sum(cache_read + input_tokens), 0)   AS cache_hit_rate,
       count(*)                                        AS calls
FROM usage
WHERE ts > now() - interval '7 days'
GROUP BY route, model
ORDER BY spend DESC;
Cost is computed at write time, not read time

Store cost_usd on the row using the price that applied when the call happened. Prices change and models get added; recomputing historical spend from a current price table produces numbers that quietly disagree with the invoice. This is ordinary financial-data discipline, and stating it in an interview signals that you have run something with a budget attached.

Step 07Retries, breakers, failover

Pythonapp/resilience.py
import asyncio, random, anthropic

RETRYABLE = (anthropic.RateLimitError, anthropic.APIConnectionError,
             anthropic.APITimeoutError)

async def with_retry(fn, *, attempts=4, base=0.5, cap=20.0):
    for i in range(attempts):
        try:
            return await fn()
        except anthropic.RateLimitError as e:
            # Honour the server's own guidance before falling back to backoff.
            wait = float(e.response.headers.get("retry-after", 0)) or None
        except RETRYABLE:
            wait = None
        except anthropic.APIStatusError as e:
            if e.status_code < 500:
                raise                       # 400s are our bug -- retrying just burns budget
            wait = None

        if i == attempts - 1:
            raise
        # Full jitter. Without the random term, every client that failed
        # together retries together and you rebuild the thundering herd.
        await asyncio.sleep(wait or random.uniform(0, min(cap, base * 2 ** i)))

Wrap that in a circuit breaker per provider — after N consecutive failures, stop calling for a cool-off window and fail fast or route to the secondary. Then implement failover across the Provider interface, and note the honest caveat in your write-up: failing over changes model behaviour. Prompts tuned for one model can degrade on another, which is why Project 5 runs the eval suite against every provider you are willing to fail over to.

Streaming and degradation

  • A failure before the first token can be retried transparently. A failure mid-stream cannot — the user has already seen partial output. Decide the policy explicitly (restart with a marker, or fail forward) and say which you chose and why.
  • When the primary is down and the secondary is saturated, degrade rather than error: serve from the semantic cache with a staleness marker, or queue and return a job ID.

Exercises — do these before calling it done
  1. Put datetime.now() into the system prompt. Watch the cache hit rate go to zero. Remove it. Write both numbers in FINDINGS.md — this is a real interview answer.
  2. Kill Redis while streaming. The gateway should degrade, not 500.
  3. Drive the semantic-cache threshold from 0.99 down to 0.85 and hand-grade fifty hits at each setting. Plot false-hit rate against hit rate; pick a threshold and justify it.
  4. Load-test with 200 concurrent streams. Find where it falls over and say why.
  5. Add a second provider behind the same interface and fail over mid-stream. Document what the user sees.
