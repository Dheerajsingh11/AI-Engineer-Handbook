Section 01 BeginnerStart from zero

Assumed knowledge

The naive RAG loop from Topic 4.1, and bi-encoder versus cross-encoder from Topic 4.2. This page assumes you have a working baseline to improve.

Naive RAG — embed the query, take the top 5, stuff them in the prompt — works in a demo and disappoints in production. Understanding why tells you exactly what to add.

The ordering that matters

Add these in order of return: hybrid search, then re-ranking, then query transformation, then everything else. The first two together typically account for most of the gap between a naive pipeline and a good one, and neither requires touching your chunking or your embedding model.

And measure recall@20 before optimising ranking. If the right chunk is not in the candidate set, no re-ranker can find it.

BM25, and where its formula comes from

BM25 scores a document by summing a contribution per query term. Three ideas, each correcting a flaw in the naive version.

BM25 score(q,d)  =  Σt∈q IDF(t) · f(t,d) · (k1+1)f(t,d) + k1(1 − b + b · |d|/avgdl) Three corrections at work. IDF down-weights terms appearing in many documents — "the" carries no information. Saturation via k1: the tenth occurrence of a word means far less than the second, so the contribution flattens rather than growing linearly. Length normalisation via b: a long document contains more of everything, so raw counts must be discounted by length. Defaults k1=1.5, b=0.75 are near-universal.
PythonBM25 from scratch
import math, re
from collections import Counter

class BM25:
    def __init__(self, documents, k1=1.5, b=0.75):
        self.k1, self.b = k1, b
        self.docs = [self.tokenize(d) for d in documents]
        self.doc_len = [len(d) for d in self.docs]
        self.avgdl = sum(self.doc_len) / len(self.docs)
        self.N = len(self.docs)

        # Document frequency: in how many documents does each term appear?
        self.df = Counter()
        for doc in self.docs:
            self.df.update(set(doc))

        # Precompute IDF. The +0.5 terms are smoothing; the +1 inside
        # the log keeps IDF non-negative for very common terms.
        self.idf = {t: math.log(1 + (self.N - n + 0.5) / (n + 0.5))
                    for t, n in self.df.items()}

        self.tf = [Counter(doc) for doc in self.docs]

    @staticmethod
    def tokenize(text):
        return re.findall(r"[a-z0-9]+", text.lower())

    def score(self, query, index):
        tf, length = self.tf[index], self.doc_len[index]
        total = 0.0
        for term in self.tokenize(query):
            f = tf.get(term, 0)
            if f == 0:
                continue
            numerator = f * (self.k1 + 1)
            denominator = f + self.k1 * (1 - self.b + self.b * length / self.avgdl)
            total += self.idf.get(term, 0.0) * numerator / denominator
        return total

    def search(self, query, k=50):
        scores = [(self.score(query, i), i) for i in range(self.N)]
        scores.sort(reverse=True)
        return [(i, s) for s, i in scores[:k] if s > 0]

Fusing the two result lists

Why you cannot just add the scores

BM25 scores are unbounded and corpus-dependent — they might range 0–15 on one corpus and 0–40 on another. Cosine similarities live in [−1,1]. Adding them, or even weighting them, means calibrating two incomparable scales, and that calibration breaks whenever the corpus or the embedding model changes.

Reciprocal Rank Fusion sidesteps this entirely by discarding the scores and fusing on rank. It has no calibration to maintain, and it is remarkably hard to beat.

Reciprocal Rank Fusion RRF(d)  =  Σr 1k + rankr(d) Sum over every retriever r that returned the document. The constant k (conventionally 60) damps the influence of the very top ranks, so a document ranked 1st by one retriever and 30th by another does not automatically beat one ranked 3rd by both — agreement across retrievers is rewarded.
PythonRRF, and hybrid search assembled
def reciprocal_rank_fusion(result_lists, k=60, weights=None):
    """result_lists: list of ranked id lists, best first."""
    weights = weights or [1.0] * len(result_lists)
    scores = {}
    for weight, results in zip(weights, result_lists):
        for rank, doc_id in enumerate(results, start=1):
            scores[doc_id] = scores.get(doc_id, 0.0) + weight / (k + rank)
    return sorted(scores.items(), key=lambda kv: -kv[1])

def hybrid_search(query, dense_index, bm25, embed_fn, k=50):
    q = embed_fn([query])[0]
    q = q / np.linalg.norm(q)
    dense_ids = np.argsort(-(dense_index["vectors"] @ q))[:k].tolist()
    sparse_ids = [i for i, _ in bm25.search(query, k=k)]

    # Weight dense slightly higher for natural-language corpora;
    # raise the sparse weight for code, identifiers and part numbers.
    return reciprocal_rank_fusion([dense_ids, sparse_ids], weights=[1.0, 0.7])
SQLHybrid search in a single pgvector query
WITH dense AS (
    SELECT id, ROW_NUMBER() OVER (ORDER BY embedding <=> :query_vec) AS rank
    FROM   doc_chunk
    WHERE  tenant_id = :tenant
    ORDER  BY embedding <=> :query_vec
    LIMIT  50
),
sparse AS (
    SELECT id, ROW_NUMBER() OVER (
               ORDER BY ts_rank_cd(content_tsv, plainto_tsquery('english', :q)) DESC
           ) AS rank
    FROM   doc_chunk
    WHERE  tenant_id = :tenant
      AND  content_tsv @@ plainto_tsquery('english', :q)
    ORDER  BY ts_rank_cd(content_tsv, plainto_tsquery('english', :q)) DESC
    LIMIT  50
)
SELECT c.id, c.content,
       COALESCE(1.0 / (60 + d.rank), 0) + COALESCE(0.7 / (60 + s.rank), 0) AS rrf
FROM   doc_chunk c
LEFT   JOIN dense  d ON d.id = c.id
LEFT   JOIN sparse s ON s.id = c.id
WHERE  d.id IS NOT NULL OR s.id IS NOT NULL
ORDER  BY rrf DESC
LIMIT  20;

Section 03 AdvancedRe-ranking — the biggest single win

Retrieval is a recall problem; ranking is a precision problem. Solve them with different tools: cast a wide net cheaply, then apply an expensive accurate model to the small candidate set.

PythonCross-encoder re-ranking
from sentence_transformers import CrossEncoder

reranker = CrossEncoder("BAAI/bge-reranker-v2-m3", max_length=512)

def retrieve_and_rerank(query, dense_index, bm25, embed_fn,
                        candidates=100, final_k=5, min_score=0.3):
    # 1. WIDE: cheap retrieval, optimised for recall not precision
    fused = hybrid_search(query, dense_index, bm25, embed_fn, k=candidates)
    candidate_ids = [doc_id for doc_id, _ in fused[:candidates]]
    texts = [dense_index["chunks"][i] for i in candidate_ids]

    # 2. NARROW: the cross-encoder reads query and document TOGETHER,
    #    so attention can match terms across them directly. Far more
    #    accurate, and only feasible on ~100 items.
    scores = reranker.predict([(query, t) for t in texts])

    ranked = sorted(zip(candidate_ids, scores), key=lambda x: -x[1])
    # 3. A real relevance threshold. Now that scores are calibrated,
    #    this actually means something -- unlike a cosine cutoff.
    return [(i, float(s)) for i, s in ranked[:final_k] if s >= min_score]

Diversity: Maximal Marginal Relevance

Pure relevance ranking can return five chunks that all say the same thing, wasting context on redundancy. MMR trades a little relevance for coverage.

MMR MMR  =  argmaxd∈R\S [ λ · sim(d,q) − (1−λ) · maxs∈S sim(d,s) ] Pick the document that is most relevant to the query while being least similar to what you have already selected. λ=1 is pure relevance; λ=0 is pure diversity; 0.5–0.7 is the useful range. Note this is the same deflation idea as PCA in Topic 1.1 — take the best, discount everything like it, repeat.
PythonMMR
def mmr(query_vec, doc_vecs, candidate_ids, k=5, lam=0.6):
    selected, remaining = [], list(range(len(candidate_ids)))
    relevance = doc_vecs @ query_vec

    while len(selected) < k and remaining:
        if not selected:
            best = max(remaining, key=lambda i: relevance[i])
        else:
            chosen = doc_vecs[selected]
            best = max(remaining, key=lambda i:
                       lam * relevance[i]
                       - (1 - lam) * float((chosen @ doc_vecs[i]).max()))
        selected.append(best)
        remaining.remove(best)
    return [candidate_ids[i] for i in selected]

The user's question is often a poor search query. Rewriting it before retrieval is cheap and disproportionately effective.

PythonThe transformations that earn their cost
def compress_history(chat_fn, history, question):
    """Turn a follow-up into a standalone query. Do this FIRST --
    every other technique operates on the compressed query."""
    return chat_fn(f"""Given the conversation, rewrite the final question
so it is fully self-contained. Output the question only.

{format_history(history)}
Final question: {question}""")

def multi_query(chat_fn, query, n=4):
    raw = chat_fn(f"""Generate {n} different phrasings of this search query,
using varied vocabulary. One per line, no numbering.

Query: {query}""")
    return [query] + [line.strip() for line in raw.split("\n") if line.strip()]

def hyde(chat_fn, query):
    """Embed a hypothetical answer instead of the question.
    Answers and documents share vocabulary and structure; questions
    and documents do not. Often a large win on short queries."""
    return chat_fn(f"Write a short factual passage that would answer "
                   f"this question. Invented details are fine.\n\n{query}")

def route(chat_fn, query):
    """The transformation with the highest return, because it
    prevents a whole class of confidently wrong answers."""
    choice = chat_fn(f"""Classify this query. Answer with one word.

VECTOR   - conceptual/explanatory, answered by document text
SQL      - counts, sums, aggregates, "how many", "total", date ranges
LOOKUP   - a specific record by identifier
GENERAL  - needs no retrieval

Query: {query}""").strip().upper()
    return choice if choice in {"VECTOR","SQL","LOOKUP","GENERAL"} else "VECTOR"

def retrieve(query, history, chat_fn, ...):
    query = compress_history(chat_fn, history, query) if history else query
    destination = route(chat_fn, query)
    if destination == "SQL":
        return text_to_sql(query)         # vector search CANNOT count
    if destination == "GENERAL":
        return []
    variants = multi_query(chat_fn, query)
    lists = [dense_search(v) for v in variants]
    fused = reciprocal_rank_fusion(lists)
    return rerank(query, fused[:100])[:5]

Section 05 ProfessionalContext assembly

You have five excellent chunks. How you arrange them still changes the answer.

  1. Order for position. Models attend most reliably to the beginning and end of a long context. Put the strongest evidence first and second-strongest last, weakest in the middle — the opposite of a naive relevance ordering.
  2. Deduplicate. Near-identical chunks from different documents waste budget. Drop any chunk above ~0.95 cosine similarity to one already selected.
  3. Label every chunk with its source, page and date, so citations are checkable and the model can reason about recency.
  4. Delimit clearly and state that the content is data, never instruction. This is a security control as well as a quality one.
  5. Budget explicitly. Count tokens; truncate at chunk boundaries, never mid-chunk.
  6. Put stable content first so prompt caching applies.
PythonAssembling the context
def assemble_context(chunks, max_tokens=8000, count_tokens=len):
    # 1. Deduplicate near-identical content
    kept = []
    for c in chunks:
        if not any(cosine(c["vec"], k["vec"]) > 0.95 for k in kept):
            kept.append(c)

    # 2. Budget
    budgeted, total = [], 0
    for c in kept:
        n = count_tokens(c["text"])
        if total + n > max_tokens:
            break                          # stop at a boundary, never mid-chunk
        budgeted.append(c); total += n

    # 3. Reorder: strongest at the edges, weakest in the middle
    ordered, left, right = [], 0, len(budgeted) - 1
    for i, c in enumerate(budgeted):
        (ordered.insert(0, c) if i % 2 else ordered.append(c))

    # 4. Label and delimit
    return "\n\n---\n\n".join(
        f"[source: {c['source']} | page: {c.get('page','?')} "
        f"| updated: {c.get('updated','?')}]\n{c['text']}"
        for c in ordered)

Latency budget for the production default

Query transformation 200–600 ms · hybrid retrieval 20–80 ms · cross-encoder rerank 50–200 ms · generation 1–5 s. Retrieval is a small fraction of the total — generation dominates. That means you can afford re-ranking almost always, and you should be sceptical of optimising retrieval latency before you have optimised output length. Run query transformation and the first retrieval concurrently where the transformation is optional, and stream the answer so time-to-first-token is what the user experiences.

Section 07 ProfessionalExercises

Do these — roughly a weekend
  1. Implement BM25 from scratch and verify against rank_bm25. Then find a query where BM25 beats dense retrieval, and one where the reverse holds.
  2. Implement RRF. Measure recall@20 for dense alone, BM25 alone, and fused. Record the improvement.
  3. Add a cross-encoder re-ranker over the top 100. Measure recall@5 before and after. This is usually the largest single number you will record in Phase 4.
  4. Try weighted score fusion instead of RRF. Tune the weights on one corpus, then apply them to a different corpus and watch the calibration fail.
  5. Implement MMR and sweep λ from 0 to 1. Inspect the returned sets at each end to see relevance and diversity trade off.
  6. Implement HyDE and measure its effect on short queries specifically versus long ones.
  7. Implement routing with four destinations. Log the routing decision for 100 real queries and check it by hand.
  8. Place the correct chunk at position 1, 5 and 10 in a long context and measure answer accuracy at each. Reproduce "lost in the middle" on your own stack.
