9.2

Open Models & Running Locally

The open-weight ecosystem, and how to run a model on your own machine. This page explains what "open" actually means (and its licence traps), surveys the model families, and walks the tools — Ollama, llama.cpp, LM Studio, vLLM, Hugging Face — that take you from "download a model" to "call it from your app."

Section 01 BeginnerStart from zero

Assumed knowledge

Quantisation and the serving basics (Topic 6.1), and calling models via APIs (Topic 9.1). This page is the open-source, run-it-yourself counterpart to those.

Closed APIs (Topic 9.1) are one half of the world. The other half is open-weight models — models whose parameters you can download and run yourself. This is what people mean by "run your own local AI." You asked about OpenLLaMA; that was an early (2023) open reproduction of LLaMA, now superseded — the living ecosystem is Llama, Mistral, Qwen, Gemma and DeepSeek.

Why run models yourself
  • Privacy / residency — data never leaves your machine or VPC.
  • Cost at volume — steady high-throughput workloads can be cheaper on your own hardware.
  • Control — no rate limits, no surprise deprecations, pin a version forever.
  • Offline — runs with no internet, on a laptop.
  • Customisation — fine-tune it (Topic 3.5) and host the result.

The cost is that you run the infrastructure — hardware, serving, updates — and frontier closed models are still ahead of open ones on the hardest tasks.

The words, in plain English
Open-weight
The trained parameters are downloadable. You can run and often fine-tune it.
Open-source
Stricter: weights and training code and data are open. Rarer than "open-weight."
Base vs instruct
Base = raw next-token model; Instruct/Chat = tuned to follow instructions. Use Instruct.
GGUF
The quantised file format llama.cpp uses to run models on CPUs and laptops.
Parameters (7B, 70B)
Model size. Bigger = more capable and more memory (Topic 6.1).
Hugging Face Hub
Where open models are published and downloaded (Topic 9.3).

"Open" does not always mean "free to do anything"

Licences vary and matter commercially. Some open-weight models carry custom licences with restrictions (acceptable-use clauses, or extra terms above a user threshold); others are truly permissive (Apache 2.0, MIT). "Open weights" is not automatically "OK for my commercial product." Read the licence before building on a model — check the model card on Hugging Face — and prefer a clearly permissive licence for anything you ship. This is a real legal gate, not a formality.

Shell / PythonFrom download to your app in minutes
# --- OLLAMA: the fastest path to a running local model ------------
ollama pull llama3.1:8b          # download (quantised by default)
ollama run  llama3.1:8b          # chat in the terminal

# It serves an OpenAI-COMPATIBLE API on localhost:11434 -- so your
# existing code points at it with one config change (Topics 9.1, 3.2).
from openai import OpenAI
client = OpenAI(base_url="http://localhost:11434/v1", api_key="ollama")
client.chat.completions.create(
    model="llama3.1:8b",
    messages=[{"role": "user", "content": "Explain HNSW in one sentence."}])

# --- vLLM: the same OpenAI API, but built for throughput ----------
# python -m vllm.entrypoints.openai.api_server \
#   --model meta-llama/Llama-3.1-8B-Instruct --quantization awq
# Point Spring AI / LangChain / your code at its endpoint. Done.
The OpenAI-compatible endpoint is the bridge

Ollama, vLLM, LM Studio and the hosting APIs (Together, Fireworks, Groq) all expose an OpenAI-compatible HTTP interface. That is the single most useful fact for a backend engineer: your application code — Spring AI, LangChain, or a raw HTTP client — does not care whether the model behind that endpoint is a hosted GPT or a Llama running on your own GPU. Swapping between "call a frontier API" and "run it myself" becomes a base-URL change. Design to that interface and you keep both options open permanently.

Section 04 AdvancedWhat can you actually run?

The binding constraint is memory, and the arithmetic is from Topic 6.1: params × bytes-per-param, plus the KV cache. Quantisation is what makes a big model fit small hardware.

Rough fit — model size vs hardware (4-bit quantised)
Model4-bit sizeRuns on
1–3B~1–2 GBAny laptop, even CPU-only
7–8B~4–5 GBA laptop with 16 GB RAM; a modest GPU
13–14B~8 GBA 12–16 GB GPU
30–34B~20 GBA 24 GB GPU
70B~40 GBA 48 GB GPU, or two smaller ones

The pragmatic sweet spot for most local use is a 7–14B instruct model, 4-bit quantised. It runs on accessible hardware, responds fast, and is genuinely useful for classification, extraction, summarisation, RAG generation and drafting — the high-volume tasks where you least want to pay per token. Reserve frontier APIs (Topic 9.1) for the hardest reasoning. This split — small open models for the bulk, frontier APIs for the peak — is how cost-efficient systems are built.

Section 05 ProfessionalOpen vs closed — the honest comparison

Choosing between them, per workload
Open, self-hostedClosed API
Top-end capabilityClose, behind on hardest tasksFrontier
Data privacyTotal — never leaves youGoverned by contract
Cost at high volumeCan be much cheaperPer token adds up
Cost at low volumeGPU sits idle — wastefulPay only for use
Ops burdenYours (serving, scaling, updates)None
LatencyNo network hop; you control itNetwork + provider queue
CustomisationFull — fine-tune freelyLimited to what the API offers
Self-hosting is not automatically cheaper

A GPU costs the same whether it serves one request or a thousand. At low volume, a self-hosted model is more expensive than an API, because you pay for idle hardware. Self-hosting wins on cost only at steady high throughput where the GPU stays busy — or when privacy/residency makes an API a non-starter regardless of cost. Run the numbers for your actual volume before assuming "local = free." The serving-cost arithmetic is in Topic 6.1.

Section 06 ProfessionalExercises

Do these — roughly an evening
  1. Install Ollama and run a 7–8B instruct model locally. Chat with it offline — confirm no network is used.
  2. Call your local model from code via its OpenAI-compatible endpoint. Change only the base URL from a hosted API.
  3. Run the same prompt on a 3B, an 8B and a 14B local model. Note where quality plateaus for your task.
  4. Compare a local 8B model against a frontier API on ten of your real tasks. Decide which tasks the local model handles well enough.
  5. Check the licence of three open models you might use commercially. Note which are truly permissive.
  6. Compute the break-even volume where self-hosting an 8B model beats an API, using Topic 6.1's cost model.
  7. Serve a model with vLLM and point Spring AI (or LangChain) at it with one config change.
