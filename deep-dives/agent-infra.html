Agent Infrastructure: Gateways & Durable Execution

The plumbing that makes agents survive production. This page covers the two infrastructure layers a real agent needs beyond a request/response API — an AI gateway (unified access, fallback, budgets) in front of the models, and a durable execution engine (Temporal-style) underneath the agent loop for retries, replay and long-running state.

Section 01 BeginnerStart from zero

Assumed knowledge

Building agents (Topics 8.1–8.3), event-driven AI (Topic 5.4), and cost/efficiency (Topic 19.3). This page is the production infrastructure around an agent.

A single LLM call fits the request/response model your web stack already knows. An agent run does not: it is a dozen steps, it calls several tools, it hits errors and retries, it may run for seconds, minutes, or hours, and it talks to multiple model providers. Two pieces of infrastructure make that reliable — a gateway in front of the models, and a durable execution engine underneath the agent loop.

Why an agent breaks ordinary request/response infra

Standard serving assumes: one call, quick, stateless, one provider. An agent violates all four — many calls, slow, stateful (the plan and history matter), across providers. A network blip 12 steps in shouldn't lose 12 steps of work. A provider outage shouldn't kill the request. A run that needs a human approval shouldn't hold an HTTP connection open for an hour. The two layers on this page exist precisely to handle those realities — and without them, agents that work in a demo fall over in production.

The words, in plain English
AI gateway
A proxy all model calls pass through — one API, with fallback, limits and logging.
Fallback / failover
If one provider is down or slow, automatically try another.
Durable execution
An engine that runs your workflow so it survives crashes and resumes exactly where it left off.
Checkpointing
Saving the agent's state so it can be resumed, replayed, or paused for a human.
Human-in-the-loop (HITL)
Pausing for a person to approve an action, without blocking a live connection.

Section 02 IntermediateThe AI gateway

Instead of your code calling OpenAI, Anthropic and a self-hosted model directly, it calls one endpoint — the gateway — which routes onward. Centralising every model call in one place buys a lot.

What an AI gateway gives you
CapabilityWhy it matters for agents
Unified API across providersSwap models/providers without touching agent code
Cross-provider fallbackFailover from one provider to another on outage, rate limit or latency spike — the agent keeps running
Rate limits & budget capsPer-tenant, per-agent spend and request ceilings — one runaway loop can't bankrupt you
Load balancingSpread traffic across self-hosted and managed endpoints
Central logging & cost attributionEvery call logged and tagged in one place (feeds Topic 8.10)
The tools, and the one-line reason to use them

LiteLLM Proxy (open source), Portkey, and Cloudflare AI Gateway are the common choices — they present an OpenAI-compatible endpoint and add fallback, budgets, caching and observability as configuration. The reason to adopt one early is the same reason you put a gateway in front of any set of downstream services: one place to enforce policy. Rate limits, budget caps, provider failover, key management, and logging all live in the gateway instead of being re-implemented in every agent. Two capabilities from earlier phases plug in here too: semantic caching to short-circuit repeated sub-queries, and model cascading / routing — send trivial classification and tool-selection steps to a small fast model (Llama-3 8B, Haiku), reserve the frontier model for hard planning. Both are covered in depth in Topic 19.3; the gateway is simply where you apply them across every agent at once.

Section 03 IntermediateDurable execution

The harder problem: an agent loop is a long, stateful workflow, and long stateful workflows fail halfway. Durable execution engines solve exactly this, and they predate AI — they run mission-critical business workflows (payments, provisioning) reliably.

Run the agent as a durable workflow

A durable execution engine (Temporal, Inngest, Cadence) runs your workflow so that its state is persisted at every step. If the process crashes, the machine dies, or a provider times out, the engine resumes from the last completed step — not from the beginning. It gives you, for free: automatic retries with backoff on any failing step (a flaky tool call just retries), deterministic replay (re-run the workflow's history to reproduce and debug exactly what happened — “time-travel debugging”), and durability across time (a workflow can sleep for an hour, or a week, waiting on something, without holding any resources open). For an agent that runs 15 steps and might hit an error at step 12, this is the difference between losing all the work and retrying just step 12.

Ordinary loop vs durable execution
Plain agent loopDurable engine
Crash mid-runLose everything, start overResume from the last step
Flaky tool callYou hand-code retriesAutomatic retry + backoff
Long wait / human approvalHold an HTTP connection openSuspend and resume later — no open connection
Debugging a bad runRe-read logs, guessReplay the exact history

Section 04 AdvancedState, checkpointing & human-in-the-loop

Underneath durable execution is a simple idea you can also apply directly: persist the agent's state (its messages, plan, and step counter) after every step, in Redis or Postgres, so the run is recoverable and pausable.

This is what a checkpointer does in a graph-based agent (LangGraph, Topic 7.1): each node's output is saved, so the graph can be stopped and resumed at any node. Two big capabilities fall out. Human-in-the-loop approvals: when the agent reaches a sensitive action, checkpoint the state, return control to the user, and resume from that exact checkpoint when they approve — hours later, with no connection held open (this pairs with the human-approval gate on mutating tools from Topic 8.11). Time-travel debugging: because every state is stored, you can rewind to any step, change an input, and replay forward to see what would have happened. Persisted state turns an agent from a fragile in-memory loop into a resumable, auditable, inspectable workflow — which is what production demands.

Section 05 ProfessionalThe production agent stack

Put together, a production agent has four layers, each covered in this handbook. The gateway in front (this page) — unified access, fallback, budgets, caching/routing (19.3). Durable execution + persisted state underneath (this page) — retries, replay, HITL. Observability around it (Topic 8.10) — distributed tracing of every step, trajectory evaluation, cost attribution. And security/guardrails wrapping it (Topics 8.11, 16.6) — injection defence, least privilege, sandboxed execution. The honest caveat: you do not need all of this on day one. A simple in-process loop is right for a prototype; reach for the gateway when you have multiple providers or tenants to govern, and for durable execution when runs are long, valuable, or must survive failure and human approval. The skill is recognising which layer a given agent actually needs — and this is squarely distributed-systems engineering, the half of AI that people from a backend background already own (Topic 17.4).

Section 06 ProfessionalExercises

Do these — make an agent survive production
  1. Put a gateway (LiteLLM Proxy) in front of two providers. Add a fallback so that killing the primary transparently fails over to the secondary.
  2. Set a per-tenant budget cap in the gateway. Run an agent past it and confirm it is stopped, not silently overspending.
  3. Add semantic caching at the gateway for repeated sub-queries; measure the call reduction (Topic 19.3).
  4. Wrap an agent loop in Temporal (or Inngest). Kill the worker mid-run and watch it resume from the last step, not the start.
  5. Add a checkpointer (LangGraph + Redis/Postgres). Pause at a sensitive action for human approval; resume from the checkpoint an hour later.
  6. Reproduce a bad run by replaying its saved history. Change one tool result and replay forward — time-travel debugging.
